### C-1 — The train flow is not connected to the API. No model can be trained through the product.

`engine/pipeline.py` implements the whole train flow (`Pipeline.run_train`, line 1486; `_TrainFlow`,
lines 502–950). **Nothing calls it.** Its only occurrence outside `engine/pipeline.py` and `tests/`
is its own definition.

`api/routes/runs.py:228` still dispatches training to the Milestone-2 placeholder:

```
build_m2_job(...)                       # mode=train  → the M2 stub
else build_score_job(...)               # mode=score  → the real Pipeline.run_score
```

`build_m2_job` (line 509) replays ingest and validate onto the status document and then fails on
purpose (line 540, `STAGE_NOT_IMPLEMENTED`). Its docstring still reads *"M3 replaces this one
function."* M3 did not. Score was wired; train was left behind — that asymmetry is the whole bug.

Verified live at `9aaf25d` (2,500 valid rows built from the shipped template, 43 % positives):

```
POST /uploads → 201
POST /runs {mode:train} → 202  r_20260922_fd56e100
GET  /runs/{id} → state=failed
     error: STAGE_NOT_IMPLEMENTED | "Preparing features is not built yet."  stage=prepare
     stages: ingest=done, validate=done, prepare=failed,
             split/train/evaluate/explain/register=pending
```

The failure closes a loop the user cannot escape:

1. Training always fails at `prepare`, so no model is ever produced.
2. `GET /models?use_case=targeted-advertisement` is therefore permanently `{"versions":[]}`.
3. `POST /runs {mode:score}` returns `409 CHAMPION_NOT_FOUND` — *"Train a model and approve it"* —
   advice that cannot be followed, because training is the thing that does not work.

Six of the eight pipeline stages are unreachable from the API. The Phase 1 acceptance test
(template → fill → upload → defaults → Run → scored file) **cannot be completed**; it fails ~8 s in,
at step 5 of 6. That is the timing for this week's replay.

**Why 2,672 green tests did not catch it.** The integration test bypasses the API:
`tests/integration/test_train_flow.py:110` calls `Pipeline(...).run_train(ctx)` directly. And
`tests/integration/test_api_runs.py:460`,
`test_m2_job_runs_two_stages_then_fails_honestly_at_prepare`, **asserts the broken behaviour**:

```python
assert detail.run.error.code == "STAGE_NOT_IMPLEMENTED"
assert detail.run.error.stage.value == "prepare"
assert by_key["prepare"].state is RunState.FAILED
```

So the suite does not merely miss the gap — it pins it in place. Whoever wires `run_train` into
`api/routes/runs.py` will see that test go red; it must be replaced, not satisfied. Flagging it
here so it is not "fixed" by reverting the wiring.

`.github/workflows/ci.yml` runs `make setup`, `make lint`, `make test` and nothing that exercises
the HTTP train path end to end, which is why CI is green on a product that cannot train.

**This blocks all three phase branches.** Phase 2, 3a and 4a each assume a working train flow

## 3. Bugs (reproduced at `9aaf25d`)

**B-1 — An Excel file renamed to `.csv` is accepted as a valid upload.** *Business impact: high;
"Save as CSV" is the most common non-technical user error.*

Steps: save any `.xlsx` as `Report.csv` (rename only, no conversion) → `POST /uploads`.
Expected: a 415/422 saying the file is an Excel workbook and must be exported as CSV.
Actual: **HTTP 201**. The Setup screen then offers one column literally named
`PK\x03\x04\x14` and preview rows of mojibake:

```json
"column_count":1, "encoding":"latin-1",
"columns":[{"name":"PK\u0003\u0004\u0014", "null_rate":0.75, ...}],
"preview_rows":[["\u001bd\u001fN¿!ôÆ\f\u0010\u0012\t´ò?\u0014Ø\u000fPK\u0003\u0004\u0014"]]
```

Cause: `engine/stages/ingest.py:115` ends its fallback chain with `latin-1`, which by construction
never fails to decode, so any binary file parses as text. Pushing on to validation, the user is
told *"Choose the column that identifies each customer"* and *"This file has 4 rows"* — nothing
says the file is not a CSV. `.xlsx`/`.ods` start with the magic `PK\x03\x04` and legacy `.xls`
with `\xd0\xcf\x11\xe0`; both are two-byte-cheap to detect before the encoding chain runs.

**B-2 — `min_rows` is enforced against uploaded rows, not trainable rows, and rows with no outcome
are dropped silently.** *Data-quality guard can be bypassed without the user knowing.*

Steps: upload 1,200 rows where 800 have an empty `converted_30d`, and run.
Expected: blocked, or at minimum a warning that 800 rows will be discarded.
Actual: **no error and no warning at any severity.** The run proceeds and trains on 400 rows —
below the configured `min_rows` floor of 1,000.

```
rows=1200 nulls=800 trainable= 400 -> errors=NONE  warnings: none about the target
rows=2000 nulls=800 trainable=1200 -> errors=NONE  warnings: none about the target
```

`min_positive` *is* computed on non-null rows (`TARGET_TOO_FEW_POSITIVES` fires correctly), so the
two guards disagree about which population they police. There is no `TARGET_NULLS` check code at
all, while `PK_NULLS` exists for the primary key — that asymmetry looks like an oversight rather
than a decision. The drop itself is deliberate (`DEC-046`, `prepare_rows`); its invisibility is
the bug. The user sees "1,200 rows" on the Data page and gets a model fitted on a third of them.

**B-3 — Choosing the same column as primary key and target is not detected.** *Confusing error.*

Steps: pick `converted_30d` as both key and target → run.
Expected: "The primary key and the target must be different columns."
Actual: `PK_NOT_UNIQUE` — *"This file has 600.0 rows per customer on average. The model needs one
row per customer."* The file has exactly one row per customer; the sentence is false and points
the user at their data instead of at the dropdown they mis-set. No `PK_IS_TARGET` check exists.

**B-4 — A `Yes`/`yes`/`YES` target is rejected as non-binary with no hint that case is the cause.**
*Common in spreadsheet exports.*

Steps: target column containing `Yes`, `yes`, `YES`, `no` → run.
Actual: `TARGET_NOT_BINARY` — *"'converted_30d' has 4 different values. A yes/no model needs
exactly two."* The user sees two values; the engine counts four.

`resolve_positive_label` (`engine/stages/validate.py:625`) already normalises with
`.strip().lower()`, but the `len(counts) != 2` gate rejects the column before that code is reached,
so the case-insensitivity is unreachable on exactly the input it was written for
(`resolve_positive_label` returns `(None, 0, 0)`). Either fold case before counting, or name the
cause in the message.

# A-4 — Merge simulation (protocol §8), and a correction to A-1

**Correction first.** In A-1 and in my `docs/CROSS_BRANCH_REQUESTS.md` entry I wrote that the
divergence in `engine/contracts.py` "is additive on the branch … so merging the branch into `main`
should not break `main`'s Phase 2 work." **That was a prediction from reading the diff, not a
measurement, and it is wrong.** I have now run the simulation §8 asks for. The merge does not
complete.

`git merge branchref` onto `main` (`04c76da`), in a scratch clone:

| File | Conflict hunks |
|---|---|

| `api/routes/runs.py` | 3 |
| `docs/API.md` | 3 |

`make test` on the merged tree could not be run: the merge leaves conflict markers and never
reaches a commit. Resolving them needs the A-2 ruling, and resolution is build work, not mine.

**The conflicts are semantic, not textual.** The two sides chose different *types* for the same
shared field. Protocol §2.1 item 1 specifies:

> `primary_key: str | list[str]` on `RunRequest`, `RunConfig`, `RunManifest`

- Branch: `PrimaryKey = str | list[str]` (`engine/config.py:63`) — **matches the protocol.**
- `main`: `primary_key: str | tuple[str, ...]` — **does not.**

So `main`'s contracts-first commit diverged from the protocol's own specification on the headline
field of the task, and it collides in three separate hunks of `engine/contracts.py`. `tuple` and
`list` are not interchangeable here: they differ in JSON serialisation and in every `isinstance`
and type check downstream, and `sole_key()`, the whole composite-key narrowing path and
`FeatureSchema` are all typed against the branch's alias.

**This strengthens A-1 rather than changing its recommendation.** The reconciliation is not the
clean fast-forward I implied — it is a real merge needing a decision per hunk, and one of those
decisions (`list` vs `tuple`) the protocol has already made. It is still far cheaper now, with 17
hunks and no phase branch cut, than after three branches have built on two incompatible surfaces.

**Revised recommendation:** resolve in the protocol's favour (`str | list[str]`, i.e. the branch's
`PrimaryKey`), since §2.1 is the written specification and `main` departed from it; then merge;
then cut the phase branches. A-2 still gates `specs.py`, which is 2 of the 17 hunks.

**On the process.** I asserted merge safety in a cross-branch entry other agents were meant to act
on, from a diff read rather than the simulation my own routine specifies. The entry has been
corrected in place. Filing a prediction as a finding is the error; §8 exists precisely so that
this claim is measured.
