# Runbook

Day-two operations for a deployment that is already serving. `docs/AWS_DEPLOYMENT.md` is the other
half: it is read once per account, to get a deployment up. This one is read under time pressure, so
it is organised by symptom and every entry says what to look at before it says what to do
(DEC-398).

Assumptions throughout: one customer, one AWS account, `ap-south-1`, `ENV` is the deployment name
(`dev` or `prod`), and the commands run from the repository root with credentials for that account.

```bash
export ENV=dev
export AWS_REGION=ap-south-1
export SERVICE_URL=$(aws cloudformation describe-stacks --stack-name "marketing-ai-$ENV-compute" \
  --query "Stacks[0].Outputs[?OutputKey=='ServiceUrl'].OutputValue" --output text)
```

---

## 1. Is it up

```bash
curl -fsS "$SERVICE_URL/healthz"                     # {"status":"ok","version":"..."}
aws ecs describe-services --cluster "marketing-ai-$ENV" --services "marketing-ai-$ENV-api" \
  --query 'services[0].{desired:desiredCount,running:runningCount,pending:pendingCount}'
aws logs tail "/marketing-ai/$ENV/api" --since 15m
```

`/healthz` returns the status and the version and deliberately nothing else. A task that answers it
is a task the load balancer will send traffic to; one that does not is replaced.

---

## 2. An alarm fired

The alarm topic is the `AlarmTopicArn` output of the observability stack. The alarms themselves are
rendered from `infra/observability/alarms.json`, which is generated by `python -m scripts.gen_dashboard`
rather than typed into a CDK file — a threshold typed into code is a number that looks measured
because it is in code (DEC-374).

| Alarm | First look | Usual cause |
|---|---|---|
| No healthy targets | `aws ecs describe-tasks` `stoppedReason`, then the API log group | A bad image digest, a failed migration, or a settings refusal (§5) |
| `StageDurationSeconds` | The run's `run_manifest.json`, then the job's CloudWatch logs | A larger file than the deployment has seen before |
| `RunsFailed` | `GET /runs`, then the failing run's `status.json` (there is no state filter on the list route; read the records) | A validation refusal, which is a `409` and not an incident |
| `JobCostUsd` | The run manifest's `cost_estimate` and `compute` | An instance type changed, or a job ran much longer than usual |
| Budget threshold | Cost Explorer, grouped by service | See `docs/AWS_DEPLOYMENT.md` §6 |

Several alarm thresholds are left unset on purpose, because nothing in this repository has measured
a stage against real data and an invented threshold would read like a measurement. The placeholder
names are listed in `infra/observability/alarms.json`; fill them from this deployment's own history,
not from another deployment's.

## 3. A run is stuck, failed, or has to be stopped

```bash
curl -s "$SERVICE_URL/runs/$RUN_ID"            | python -m json.tool   # run.json + status.json
curl -s "$SERVICE_URL/runs/$RUN_ID/artefacts/run_manifest.json" | python -m json.tool
curl -sX POST "$SERVICE_URL/runs/$RUN_ID/cancel"
```

Cancellation is cooperative and is observed **between stages**, not inside one (DEC-017). A run that
is inside a long training stage will stop at the next checkpoint, not immediately. A run that has
not started is cancelled outright.

`run_manifest.json` is written for every outcome, including a failure, so a failed run still has a
record with its recipe, its dataset fingerprint and whatever metrics it reached.

For a run executed as a SageMaker job:

```bash
aws sagemaker list-training-jobs --name-contains "marketing-ai" --max-results 20 \
  --sort-by CreationTime --sort-order Descending \
  --query 'TrainingJobSummaries[].[TrainingJobName,TrainingJobStatus]' --output table
aws sagemaker describe-training-job --training-job-name "$JOB" \
  --query '{status:TrainingJobStatus,reason:FailureReason,billable:BillableTimeInSeconds}'
aws sagemaker stop-training-job --training-job-name "$JOB"
aws logs tail "/marketing-ai/$ENV/jobs" --since 1h --filter-pattern "$RUN_ID"
```

The role may describe and stop a job whose name starts with `marketing-ai-`, and holds no `List*`
action at all — `list-training-jobs` above is run with your own credentials, not the task's.

**Nothing in a log quotes a data value.** `log_failure` names an exception's class and not its
message, and `RedactingFormatter` withholds every exception message while still rendering the
traceback's frames. If a failure cannot be diagnosed from a log line, that is the control working;
reproduce it against a synthetic file instead of loosening the formatter.

## 4. The run list is missing runs

The run index exists so that a list page does not read every run in the bucket, and it is written
best-effort *after* `run.json`. A database that was down when a run finished costs that run its row
and nothing else (DEC-342). The run documents in S3 are the authoritative thing.

```bash
.venv/bin/python -m scripts.reconcile_runs --dry-run   # the same scan, writing nothing
.venv/bin/python -m scripts.reconcile_runs
```

It walks `runs/*/run.json`, upserts a row for each and drops rows whose document is gone. It is
idempotent, so running it when nothing is wrong is harmless. It is also a full listing of the runs
prefix, which is exactly the expensive operation the index removes from the request path — so it is
a command somebody runs, never a thing that happens on its own.

Exit codes: `0` fine, `2` there is no index table to rebuild (a deployment shaped differently), `3`
the scan finished but some documents could not be read or some rows could not be written.

## 5. The service will not start

Work through these in order; each one is a different failure with the same symptom.

1. **A settings refusal.** The task exits immediately with a message naming a field.
   `SETTINGS_UNKNOWN` is a `MARKETING_AI_*` variable that names no field, `SETTINGS_INCOMPLETE` is a
   backend selected without what it needs, `SETTINGS_INVALID` is a value that does not parse — or
   `cors_origins` containing `*` on a prod deployment. The message names the field and never the
   value. `docs/AWS_DEPLOYMENT.md` §3.2 is the field table.
2. **A missing parameter.** `aws ssm get-parameters-by-path --path "/marketing-ai/$ENV/"
   --query 'Parameters[].Name' --output text`. Parameters are read with `Recursive=False`, so one
   written a level deeper is stored, looks right, and is never read.
3. **The database.** `.venv/bin/python -m scripts.aws_bootstrap --env "$ENV" --no-migrate` probes
   every permission with one real call each and prints a `fix:` line naming the IAM action.
4. **The image.** `aws ecs describe-task-definition --task-definition "marketing-ai-$ENV-api"
   --query 'taskDefinition.containerDefinitions[0].image'` must be a digest, not a tag.
5. **The network.** No log lines at all usually means the task could not start its log driver: see
   `docs/AWS_DEPLOYMENT.md` §10.2.

## 6. Deploying a fix

```bash
make aws-deploy ENV=$ENV        # build, push by digest, cdk deploy --all
make aws-bootstrap ENV=$ENV     # migrations, then probe every permission
```

To roll back, deploy the previous digest explicitly rather than rebuilding: ECR tags are immutable
and a rollback window of untagged images is kept.

```bash
cd infra && PATH="$PWD/../.venv-infra/bin:$PATH" npx --yes aws-cdk@2.1142.0 deploy --all \
  -c env_name=$ENV -c image_digest="<registry>/marketing-ai@sha256:<previous>" \
  --require-approval broadening
```

An in-flight run is not resumed when its task is replaced. Before a deployment, let running jobs
finish or cancel them.

## 7. Schema changes

```bash
MARKETING_AI_DATABASE_URL="postgresql://...?sslmode=require" make migrate
.venv/bin/alembic current
.venv/bin/alembic history --verbose | head -20
```

Additive first, destructive later: add a column, deploy the image that uses it, drop the old column
in a separate migration after every task is running the new image. ECS replaces tasks one at a time,
so a window in which both images are live is the normal case.

## 8. Credential rotation

The credential secret `marketing-ai/<env>/db` is rotated by the AWS single-user rotation function.
The application document `marketing-ai/<env>/app` holds a `database_url` **composed at deploy time**,
and the rotation function knows nothing about it (DEC-376). After a rotation, redeploy the database
stack to recompose it:

```bash
cd infra && PATH="$PWD/../.venv-infra/bin:$PATH" npx --yes aws-cdk@2.1142.0 deploy \
  "marketing-ai-$ENV-database" -c env_name=$ENV
```

Then restart the service so the tasks re-read the document:

```bash
aws ecs update-service --cluster "marketing-ai-$ENV" --service "marketing-ai-$ENV-api" \
  --force-new-deployment
```

The real repair is for `engine/settings.py` to read the RDS credential document directly and build
the URL itself; until then the rotation interval is deliberately long.

## 9. Restoring the database

RDS automated backups are on, with `db_backup_retention_days` of retention. A restore creates a
**new instance**; it never overwrites the running one.

```bash
aws rds describe-db-instances --db-instance-identifier "marketing-ai-$ENV" \
  --query 'DBInstances[0].{earliest:EarliestRestorableTime,latest:LatestRestorableTime}'
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier "marketing-ai-$ENV" \
  --target-db-instance-identifier "marketing-ai-$ENV-restore" \
  --restore-time 2026-10-14T09:00:00Z --no-publicly-accessible
```

The restored instance comes up with a default parameter group, so `rds.force_ssl` is **not** set on
it until the deployment's parameter group is applied. Point the deployment at it by updating
`marketing-ai/<env>/app`, or by restoring into the original identifier after renaming the old one.

The artefacts are a separate question. S3 object versioning protects against an overwrite or a
delete of an object; it is not a copy of the bucket anywhere else. To recover an overwritten
artefact:

```bash
aws s3api list-object-versions --bucket "$BUCKET" --prefix "runs/$RUN_ID/" \
  --query 'Versions[].{Key:Key,Id:VersionId,When:LastModified}' --output table
aws s3api get-object --bucket "$BUCKET" --key "runs/$RUN_ID/run.json" \
  --version-id "$VERSION" ./run.json
```

## 10. Scaling

| Pressure | Knob | Effect |
|---|---|---|
| API latency or CPU | `api_min_tasks`, `api_max_tasks`, `api_cpu`, `api_memory` | The service already scales on CPU; the range is the knob. `api_cpu`/`api_memory` pairs are refused at synth time if Fargate does not allow the combination |
| Runs queueing | `sagemaker_max_concurrent_jobs` (`-c max_concurrent_jobs`) | How many jobs may run before a run waits for compute |
| A job that is too slow or too large | `sagemaker_train_instance_type`, `sagemaker_processing_instance_type` | No default exists on purpose: an instance type is a cost decision. Change it, then measure the next run's `compute` and `cost_estimate` |
| Database | `db_instance_class`, `db_storage_gb`, `db_multi_az` | An instance-class change restarts the database; do it in a window |

Measure before and after from the run manifests of comparable runs. Do not write a new number into
any document without saying where it was measured (plan §13.3).

## 11. Refreshing the price table

`configs/aws_prices.yaml` holds AWS **list prices** with the offer version and publication date they
were read at. They go stale when AWS changes them, and a stale rate makes every `estimated_usd`
quietly wrong while `basis` still names the old offer version.

```bash
make prices          # rewrites configs/aws_prices.yaml; review the diff
```

It is deliberately not part of `make lint` or `make check-generated`: its input is a third party's
rate card, and a price change at AWS must not turn a green build red. An instance type missing from
the table produces a null `estimated_usd`, never a zero and never a guess (DEC-333).

| When | What |
|---|---|

| Weekly | The alarm topic has subscribers, and somebody reads them |
| Weekly | `scripts/reconcile_runs.py --dry-run` reports nothing to do |

| Monthly | `make prices`, and review the diff |

## 13. What this deployment cannot do

Worth knowing before an incident rather than during one. The full list is
`docs/AWS_DEPLOYMENT.md` §9.2.

- There is **no authentication**. Anyone who can reach the load balancer can run, approve and
  download. `approved_by` is a caller-supplied claim and not an identity (DEC-055).
- There is **no per-tenant isolation** inside a deployment; the boundary is the AWS account.
- `governance.retention_days` is recorded and **not enforced**. A deletion request is a manual
  sequence today (`docs/AWS_DEPLOYMENT.md` §8.3).
- Phase 2 (clients, datasets, DuckDB) and Phase 3a (Bedrock, LLM usage) are **not in this
  repository**. The `bedrock_*` settings are inert.
