# Decisions

The architecture decision log. `plan.md` is normative and the reference prototype fills its silences;
**every other choice is an entry here**, in the order it was made. Each entry states its **Context**
(what the plan and the prototype do and do not say), the **Decision** taken, and its **Consequences**.

Milestone 1 opens the log with DEC-001 … DEC-030 from the design, DEC-031 … DEC-035 from its integration and
DEC-036 … DEC-040 from its review. Later milestones append; entries are never rewritten
in place — a decision that is reversed gets a new entry that names the one it supersedes (plan §13.2).

---

- **DEC-001 — `engine.yaml` has a non-merged `catalog` and a merged `defaults` block.** *Context:* plan §5 wants every default in `engine.yaml`, but engine constants (AutoGluon key map, presets, labels, markers) are not per-use-case settings. *Decision:* two top-level blocks; only `defaults` is merged into use cases; `catalog` is read-only engine data whose dict keys are enums. *Consequences:* one file to read; a use-case YAML cannot invent or remap a model family, a metric or a label.
- **DEC-002 — Merge semantics: deep for mappings, replace for lists, `null` clears; `extra="forbid"` everywhere.** *Context:* plan §5 says "merges" without defining list behaviour. *Decision:* §4.5 rules 1–5; unknown keys fail after the merge with the offending path. *Consequences:* `candidates: [LightGBM]` means exactly one candidate; no "unset" syntax is needed; documented in `docs/API.md`.
- **DEC-003 — Seven use cases, six files: industry entries carry `status: available | planned` plus `name`/`description` for planned ones.** *Context:* plan §1.2 lists seven, §3 lists six YAMLs; the overview must show the Onboarding stage and its card. *Decision:* §3.7 loader rules; planned entries have no config and expose `problem_type`/`entity`/`target` as `null`; `GET /use-cases/{planned}` is `404 USE_CASE_PLANNED`. *Consequences:* the overview matches the prototype without a fabricated config; promoting a use case is one word plus one file.
- **DEC-004 — Per-use-case defaults equal `defaultAdv()`; the only value change is `min_positive` 200.** *Context:* prototype `minpos: 500`, plan §4.1 says 200; other prototype pages hint at per-use-case values (consent filter for win-back, focal loss / "watch" drift for fault prediction) that `defaultAdv()` does not set. *Decision:* the plan wins for `min_positive`; every other advanced-setting default is `defaultAdv()`'s for all six use cases (no per-use-case `recently_contacted_days`, `control_group_fraction`, `retraining`, `imbalance`, `consent_column`, `reasons_per_row`). Allowed per-use-case differences are listed in §3's preamble. *Consequences:* `test_prototype_parity.py` pins 36 values for all six configs; win-back's "marketing opt-in only" outcome comes from the default `suppress_opted_out`.
- **DEC-005 — Fractions in config, `scale: 100` in the schema, config units on the wire.** *Context:* prototype stores 15/15/10; plan §5 stores 0.15/0.15/0.10. *Decision:* config and overrides are fractions; the schema field carries `scale: 100` and min/max/step in config units; the UI multiplies for display and divides on submit; the server never guesses units (a submitted `15` fails the range check). *Consequences:* one representation in every artefact; no ambiguous `0.5 = 50 % or 0.5 %` coercion.
- **DEC-006 — `evaluation.threshold` is `{mode, value}`; `fixed` is enforced by rejection, not mutation.** *Context:* the prototype's "Manual (below)" has no number. *Decision:* §2.2; `THRESHOLD_FIXED_NOT_HALF`; `value` always present (default 0.50); revealed by `visible_when`. *Consequences:* one extra stage-5 field; frozen models stay frozen.
- **DEC-007 — KPI formulas are a three-form mini-grammar, parsed at load, never evaluated in M1.** *Context:* plan §5 shows one formula and no grammar. *Decision:* `count_rows()`, `count_where_band_in([...])`, `sum_where_band_in("col", [...])`; band/column names validated against the config. *Consequences:* no `eval`; a new KPI shape is a deliberate engine change.
- **DEC-008 — `actions.bands` is canonical; `hi`/`md` are generated views; three bands everywhere.** *Context:* prototype keeps two numbers and, on two Output pages, shows illustrative four-band pill sets (`Critical` for fault prediction, `Very low` for payment propensity) that `defaultAdv()` never configures. *Decision:* §2.1; every shipped use case has `High 0.80 / Medium 0.50 / Low 0.00`; the schema emits one field per non-floor band, so a client restores the prototype's fourth band with one YAML line (e.g. `{name: Critical, min_score: 0.90, action: "Schedule visit"}` above `High`) and gets a third field with no UI change. *Consequences:* settings match the prototype's advanced settings exactly; Output-page pills read High/Medium/Low for those two use cases.
- **DEC-009 — Model families and metrics are restricted to the engine's six families and seven metrics; per-use-case lists are the prototype's lists intersected with them, in prototype order.** *Context:* prototype offers `Linear Learner`, `LSTM (sequence)`, `Isolation Forest (anomaly)`, `Uplift forest`, `Uplift (Qini)` and "Focal loss"; plan §6.3 fixes six families, §5 seven metrics, §1.3 defers uplift. *Decision:* `Linear Learner` is covered by `LogisticRegression`; LSTM, Isolation Forest, Uplift forest and Qini are dropped; fault prediction's intersection would be two families, so `LightGBM` is added (the engine's default gradient-boosting family; CatBoost is not added, keeping the deviation minimal) → `[XGBoost, LightGBM, RandomForest]`; win-back → `[LightGBM, XGBoost, LogisticRegression]` and metrics `[roc_auc, recall, f1]`; fault prediction keeps `imbalance: auto` (AutoGluon Tabular has no focal loss). *Consequences:* two use cases show fewer options than the prototype mock; sequence/anomaly/uplift models are a Phase 3 conversation.
- **DEC-010 — Family and metric labels live in the catalog; config stores ids.** *Context:* the prototype shows `Random Forest`, `Logistic Regression`, `ROC-AUC`; the plan stores `RandomForest`, `roc_auc`. *Decision:* `catalog.model_families[*].label`, `catalog.metrics[*].label`, `CHOICE_LABELS` for every UI enum; `AutoML (recommended)` is `catalog.automl_choice` with sentinel value `__automl__`. *Consequences:* no display string is ever a wire value or a config value.
- **DEC-011 — `NeuralNet` is the optional `nn` extra (torch), absent from every default list, greyed in the schema, rejected at config validation when torch is missing.** *Context:* ENV_FACTS — torch is not installed and pulls multiple GB. *Decision:* `nn = ["torch>=2.10,<2.14"]`; `catalog.model_families.NeuralNet.requires: [torch]`; `check_dependencies()` raises `MODEL_FAMILY_UNAVAILABLE` ("The Neural network model needs the optional 'nn' extra. Run `make setup EXTRAS=nn`, or deselect it.") for YAML and override selections alike; the schema shows the choice `enabled: false` with that help. *Consequences:* `make setup` stays fast; nobody discovers the missing dependency mid-training.
- **DEC-012 — Hybrid use cases are predictive in Phase 1 and carry no generative keys.** *Context:* `rca` and `win-back-campaign` are hybrid; plan §1.3 defers LLM work. *Decision:* `ai_type: hybrid` loads, validates, trains the tabular model and shows the eight stages; no `generative:` block exists in M1; `rca` keeps `complaint_text` in its template with `features.text_columns: ignore`. *Consequences:* Phase 3 adds an optional block, never changes an existing one.
- **DEC-013 — `mypy --strict` covers `engine/`, `api/` and `scripts/` globally; the only override is `ignore_missing_imports` for autogluon/shap/sklearn/imblearn.** *Context:* plan §13.6 requires strict on `engine/`; ENV_FACTS shows the rest passes; `strict` is not a valid per-module option. *Consequences:* one flag, no per-module strictness games; tests are outside `files`.
- **DEC-014 — Generated files (`templates/*.csv`, `templates/*_README.md`, `docs/API.md`) are committed and drift-checked.** *Context:* the plan says generate, not whether to commit. *Decision:* commit; `make lint` and `test_generated_files.py` run `--check`. *Consequences:* reviewable diffs; regeneration is mandatory before commit.
- **DEC-015 — `run_config.json` is `ResolvedConfig` with `overrides_applied`, per-leaf `sources` and `warnings`.** *Context:* plan §5 requires the merged result; the Model page shows the training setup. *Consequences:* the UI can mark user-changed values; a run is reproducible from one file.
- **DEC-016 — Storage keys are opaque posix strings validated by one gate; writes are atomic; `local_path()` is the only escape hatch.** *Context:* plan §2.1 principle 3 and the Phase 4 S3 swap. *Consequences:* `S3Storage` later materialises into a temp dir and nothing else changes.
- **DEC-017 — Job cancellation is cooperative.** *Context:* plan §8 has `POST /runs/{id}/cancel`; Python threads cannot be killed. *Decision:* a `CancelToken` per job; stages poll between steps; a pending job is cancelled outright. *Consequences:* cancel is near-instant between stages and bounded by AutoGluon's `time_limit` during training.
- **DEC-018 — `hatchling` is unpinned; `requirements-freeze.txt` is committed for the pin test.** *Context:* pins must come from the resolver, whose output has no build backend and lives outside the repo. *Consequences:* no invented pin; the pin test has input on a clean checkout.
- **DEC-019 — Per-use-case `metric_choices` and `candidate_pool` preserve the prototype's per-use-case order; `candidates` is the ticked subset.** *Context:* prototype `SETUP` orders metrics and models differently per use case; the plan is silent on ordering. *Decision:* both lists are validated as subsets of the catalog (metrics filtered by problem type) and `candidates ⊆ candidate_pool`. *Consequences:* the "Optimise for" select and the algorithm grid match the prototype; the engine default lists cover targeted-advertisement, payment-propensity and rca's pool without restating.
- **DEC-020 — `status.json` keeps the plan's 8/7 engine stages; each carries the prototype's Running-screen `group_label`.** *Context:* plan §6/§9 render every stage; the prototype shows five/four rows. *Decision:* `GROUP_LABELS` in `engine/pipeline.py`; the UI renders one row per distinct `group_label`; engine `title`s never reach the screen; the API's `running_rows` is derived from the same constants. *Consequences:* engine honesty and UI fidelity coexist; one source of truth.
- **DEC-021 — Two stage modules beyond plan §3's tree: `engine/stages/register.py` and `engine/stages/export.py`.** *Context:* plan §6.1/§6.2 list `register` and `export` stages but §3's tree has no module for them; `split` fits in `prepare.py` as the tree says. *Consequences:* every stage id has a home (`STAGE_MODULE_MAP`); no logic in M1.
- **DEC-022 — Setup copy lives in a mergeable `ui` block; page titles are per use case.** *Context:* mode labels/help, target label, dataset/columns hints, run-button text and the Data/Model/Output H1s are per-use-case (or per-ai-type) prototype copy. *Decision:* `defaults.ui` with `{entity}` substitution; use cases override `ui.pages`; the generative case overrides labels in its own file later. *Consequences:* copy changes are config changes; `ui` is immutable per run.
- **DEC-023 — Column-name references are not config-load errors.** *Context:* `split.time_column`, `consent_column`, `fairness_column`, `opt_out_column` name columns of a file the engine has not seen; plan §4.2 lets the user pick the time column and §6.3 makes `TIME_COLUMN_MISSING`/`CONSENT_COLUMN_MISSING` validate-stage errors. *Decision:* `time_based` with `time_column: null` loads and adds a `ResolvedConfig.warnings` entry; template cross-checks apply only when the template is non-empty and the name is set. *Consequences:* the UI can switch split type before picking a column and gets the plan's 409 later, not a 422 now.
- **DEC-024 — `GET /healthz`, `GET /use-cases/{id}/template_README.md`, and open CORS in Phase 1.** *Context:* plan §8 lists neither route; the UI is opened as a local file with no auth. *Consequences:* two extra routes in `docs/API.md`; CORS must be tightened before Phase 4 (noted in `docs/AWS_DEPLOYMENT.md`).
- **DEC-025 — Template columns carry a `role`.** *Context:* the README's "Required" section and the target/time/consent cross-checks need to know what each column is. *Decision:* `primary_key | time | feature | target | consent | contact` with the validators of §3. *Consequences:* templates and configs cannot disagree about the key or target.
- **DEC-026 — `""` means "not selected" only in the UI; optional column paths coerce `""` → `null` in overrides.** *Context:* prototype uses `""`; config uses `null`. *Consequences:* `str | None` semantics stay honest; the UI needs no change.
- **DEC-027 — One state vocabulary `pending | running | done | failed | cancelled (| skipped)` for runs, stages and jobs.** *Context:* plan §6 defines it for stages. *Consequences:* `RunState` in `engine.contracts` is the only state enum; `skipped` is stage-only.
- **DEC-028 — Registry semantics: `approve` promotes `pending_approval → champion`; `promote` is the manual override; demotion happens in the same transaction; `should_promote` is a pure function in `engine/registry.py`, not a Protocol method.** *Context:* plan §6.3/§8. *Consequences:* Phase 4 registries store facts only; the policy is tested without a database in M1.
- **DEC-029 — Override shapes and paths: nested or dotted, `OVERRIDABLE_PATHS` = schema paths + `EXTRA_OVERRIDABLE_PATHS`, `IMMUTABLE_PATHS`, index patches as the one exception to "lists replace".** *Context:* plan §8 shows nested overrides; the UI holds dotted schema paths; the bands need element addressing. *Consequences:* "advanced settings are exactly the fields of this schema" is enforced in both directions.
- **DEC-030 — New validation code `SUPPRESSION_COLUMN_MISSING` (warning).** *Context:* plan §13.4 requires every user-facing message to be in the validation table; suppression columns may be absent from a scoring file. *Consequences:* the table gains one row, documented in `docs/DATA_CONTRACT.md` when M2 writes it.
- **DEC-031 — `VALIDATION_CODES` has 19 entries: plan §6.3's 18 codes plus `SUPPRESSION_COLUMN_MISSING`.** *Context:* the M1 design counts "19 plan codes plus one"; plan §6.3's table has exactly 18 rows (`PK_MISSING` … `CONSENT_COLUMN_MISSING`) and no other code appears anywhere in the plan. *Decision:* the plan wins; `engine.contracts.VALIDATION_CODES` holds the 18 transcribed codes plus DEC-030's, and `tests/unit/test_contracts.py` pins the literal table and the count. *Consequences:* a nineteenth plan code, should M2 find one, is added to the contract, the test and the plan's table together; `ValidationCheck` rejects any code outside the set.
- **DEC-032 — `404 TEMPLATE_EMPTY` is raised as a FastAPI `HTTPException` carrying the same `{"detail": {"code", "message", "path"}}` body, not as a `ConfigError`.** *Context:* the design fixes the `ConfigError` codes that map to 404 to exactly `USE_CASE_NOT_FOUND | USE_CASE_PLANNED | INDUSTRY_NOT_FOUND` (every other code is 422) and, in the same section, requires `404 TEMPLATE_EMPTY` for a use case that declares no template columns; such a use case is not an invalid document, so 422 would be wrong. *Decision:* `api/routes/use_cases.py` raises `HTTPException(404, detail={code, message, path})`; the app's 404 code set stays verbatim. *Consequences:* clients see one error shape for every 4xx; the code is API-only and never enters `engine/`.
- **DEC-033 — The template download routes answer `HEAD`, registered explicitly and kept out of the OpenAPI schema.** *Context:* FastAPI's `APIRoute` does not add `HEAD` to a `GET` route (Starlette's plain `Route` does); the M1 verification checklist probes `template.csv` with `curl -I`, and download clients probe the headers before fetching the body. *Decision:* a stacked `@router.head(..., include_in_schema=False)` on the same handler for `template.csv` and `template_README.md`, so the headers are the `GET` headers by construction and the server drops the body; the endpoint table in `docs/API.md` documents resources only (`HEAD`/`OPTIONS` rows are never rendered). *Consequences:* `curl -I` returns `200` with `content-type`, `content-disposition`, `cache-control` and the exact `content-length`; the other routes stay `GET`-only until a client needs more.
- **DEC-034 — In `engine/contracts.py` a bare `X | None` field is required-but-nullable; only a field written `= None` is optional.** *Context:* the design's code blocks write `= None` where a default is intended and a bare `X | None` elsewhere (41 fields such as `SplitReport.time_column`, `EvaluationReport.calibration` and `RunError.stage`); the prototype shows "—" for a value that does not exist and plan §2.1 forbids fabricated values. *Decision:* producing stages state every nullable value explicitly (`stage=None` when a failure is not tied to a stage) instead of relying on a silent default; `RunRecord`, which the design gives as a prose table, keeps sensible defaults. *Consequences:* a stage that forgets a value fails at validation time, not on the screen; the Required column of `docs/API.md` shows the convention; M2+ stage code constructs artefacts with explicit nulls.
- **DEC-035 — Registry edge cases the plan and the design leave open.** *Context:* plan §6.3 fixes the champion rule and DEC-028 the transitions; neither says what a `0.0` champion score, a repeated `archive`, or SQLite's dropped timezone should do. *Decision:* `should_promote` treats a champion `test_score` of exactly `0.0` as beaten by any strictly better candidate (and by an equal one only when the rule is `0 %`) instead of dividing by zero; `archive` is idempotent and accepts a version in any status; rows are stored in UTC and `tzinfo` is re-attached on read so `ModelVersion`'s aware datetimes round-trip; a `UNIQUE(use_case_id, version)` clash surfaces as the driver's `IntegrityError` because stages call `next_version()`. *Consequences:* no policy hides in a database; a friendly code for a version clash is added only when an API needs one.
- **DEC-036 — `model_search.time_limit_minutes` accepts 1 … 240 in steps of 1.** *Context:* the prototype's widget is `num("limit","Time limit (min)",5,5,240)` (minimum 5, step 5) and the design's §2 table copied it; plan §10 requires the integration train flow to run "with `time_limit_minutes: 1` and `strategy: fast`", and a schema that rejects 1 cannot run the plan's own test. The plan wins over the prototype. *Decision:* `ge=1` on the field; `min: 1` and `step: 1` on the schema field (a step of 5 from a minimum of 1 would make the default 30 an off-step value in a browser number input). The default stays 30 and the ceiling 240. *Consequences:* `tests/unit/test_advanced_settings_schema.py` pins `(1, 240, 1)`; the UI spinner is finer than the mock's; a one-minute limit is only useful for smoke runs, which is exactly what the plan uses it for.
- **DEC-037 — The `LEAKAGE_SUSPECTED` name patterns are the plan's four, split into two catalog keys.** *Context:* plan §6.3 lists `*_date` after target, `churn*`, `converted*`, `outcome*`; the M1 design shipped `^(churn|converted|outcome|label|target)|_after$`, which adds `label`, `target` and `_after`, drops `*_date`, and still claimed to be the plan's list. *Decision:* `catalog.column_name_patterns.leakage` is exactly `^(churn|converted|outcome)`, checked on every column. The fourth pattern needs a column's position as well as its name, so it has its own key, `leakage_after_target: "_date$"`, read as "a `*_date` column placed after the target column in the header": features describe the entity as of the snapshot (plan §4.2), so a date recorded after the outcome is the answer in disguise. M2's validate stage applies the first pattern to every column and the second only to the columns that follow the target. `label`, `target` and `_after` are not added; a deployment that wants them edits the catalog regex. *Consequences:* the catalog says what the plan says and nothing more; this reading of "after target" is recorded here, and a data-driven refinement (date values later than the snapshot) would be a new entry.
- **DEC-038 — A `UseCaseConfig` carries the catalog it was validated against, exposed as `config.catalog`.** *Context:* `load_use_case(id, root)`, `load_industry(root)`, `resolve_config(root=…)` and `create_app(config_root=…)` all take a configuration root, but the cross-file rule `METRIC_NOT_FOR_PROBLEM`, `check_dependencies`, the `trainable_in_phase_1`/`marker` properties, the advanced-settings labels and the time-like column pattern read `get_catalog()` with no root, so an explicit root was validated and labelled against the default (or `$MARKETING_AI_CONFIG_DIR`) `engine.yaml`, and a missing default root broke loading from a valid explicit one; the design (§4.4) only foresaw the environment variable. *Decision:* the loaders validate with `context={"catalog": get_catalog(root)}`; `UseCaseConfig` keeps that catalog in a private attribute and every catalog-dependent helper reads `config.catalog`. A document validated without a root (a `UseCaseConfig(...)` literal, or `run_config.json` read back) gets the default root's catalog, as before. *Consequences:* `_validate_use_case(document, catalog=…)` is keyword-only and nothing outside `engine/config.py` changes its calls; two configs are equal only when their fields and their catalog agree; `tests/unit/test_config_loading.py` and `tests/integration/test_api_config.py` point the loaders and the app at a fixture root whose catalog differs from the checkout's and assert that it governs.
- **DEC-039 — A `problem_type` override re-derives `model_search.metric_choices` and `metric` from the catalog; `ResolvedConfig.sources` gains `"derived"`.** *Context:* plan §6.3 (`TARGET_NOT_BINARY`: "Offer switch to regression if numeric") and §9 (detected problem type with override) need the switch to work, and the prototype promises "Metrics and models will switch to regression defaults"; but a use case's `metric_choices` are written for its own problem type and are not overridable, so `{"problem_type": "regression"}` was rejected for every shipped use case whatever else the run sent. *Decision:* in `resolve_config`, when the merged document's `problem_type` has catalog metrics and the use case's `metric_choices` do not all fit it, `metric_choices` becomes `catalog.metrics_for(problem_type)` in catalog order and `metric` its first entry unless the run set `model_search.metric` itself (an explicit metric that does not fit is still `METRIC_NOT_IN_CHOICES`); the touched leaves are `"derived"` in `sources`, `overrides_applied` stays what the run sent, and a warning states the switch. Model families are untouched: every supported family handles both problem types. A YAML that pairs a problem type with the wrong metrics is still a `METRIC_NOT_FOR_PROBLEM` load error; only runs switch. *Consequences:* `run_config.json` records what the engine chose and why; the UI can show derived values apart from user-changed ones; `forecasting` and `clustering` have no catalog metrics and are left alone.
- **DEC-040 — `humanise_count` and `humanise_bytes` round like the prototype's JavaScript and extend it one unit upwards.** *Context:* the prototype's `fmtSize` shows KB with one decimal (`toFixed(1)`) and `fmtN` uses `Math.round`; JavaScript rounds a half up on the exact binary value where Python's `round` and `format` round it to even; M1 rendered whole kilobytes and `2500 → "2K"`. Neither prototype helper has a branch above MB/M, so a 2 GB upload (plan §4.1's ceiling) would read `2048.0 MB`. *Decision:* KB, MB and M use `Decimal(value).quantize(0.1, ROUND_HALF_UP)` on the exact float and K rounds the same way to an integer, so `1536 → "1.5 KB"`, an exact `1.25 MB → "1.3 MB"` and `2500 → "3K"`, as in the browser; the GB and B branches stay as the one deliberate extension; a negative value is formatted by magnitude and signed. *Consequences:* `tests/unit/test_utils.py` pins the JavaScript results, exact-half cases included; the API and the UI agree to the character.
- **DEC-041 — `mypy --strict` also covers `tests/fixtures/make_data.py`, and generated synthetic CSVs are gitignored.** *Context:* DEC-013 kept `tests/` out of `[tool.mypy].files` on the grounds that tests are not source. The synthetic generator is different in kind: it is test infrastructure that every M2, M3 and M4 test depends on for its inputs, so a silent type regression there would surface as confusing failures far from the cause. It was written strict-clean with no `Any`, and that is worth keeping rather than rediscovering. Separately, the generator defaults its output to a temporary directory outside the checkout, but a developer passing `--out-dir .` could stage large CSVs by accident. *Decision:* add `tests/fixtures/make_data.py` (the module only, not its tests) to `[tool.mypy].files`, keeping `tests/unit/test_pyproject_pins.py` in step since it asserts that list; and add `*_synthetic_*.csv` to `.gitignore`, the filename shape the generator always produces. *Consequences:* `make lint` now type-checks 35 files instead of 34; the rest of `tests/` stays untyped as DEC-013 intended; generated data cannot be committed by accident.
- **DEC-042 — `DatasetFingerprint`, `RunManifest` and `Recipe`: a run records what it did, on what data, at what cost.** *Context:* the artefacts of plan §7 are each shaped for a screen, and the champion rule compared a new test score against a number stored from an older run. Neither supports asking, later and mechanically, "which choices, on which data, produced which numbers?" A stored score is not comparable to a new one unless the data behind both is known to be the same, and nothing in the design recorded that. *Decision:* three additions. `DatasetFingerprint` (`hash`, `algorithm`, `n_rows`, `columns`) is computed at ingest, carried on `DatasetProfile`, and identifies the exact dataset a run consumed; the digest is sha256 rather than Python's `hash()`, which is salted per process and would not survive a restart. `RunManifest` (`run_manifest.json`) is one flat record written for EVERY run, train and score alike, and written even when a run fails, carrying whatever is known, because a failed attempt is evidence too; it holds `run_id`, `recipe`, `dataset_fingerprint`, `seed`, `metrics`, `leaderboard_path`, `duration_s`, `cost_estimate` and `created_at`. `Recipe` holds every training choice and nothing else, so that the same recipe on the same fingerprint yields the same model; `train(recipe)` is the only entry point to training. `CostEstimate.estimated_usd` is null for a local run rather than zero, since nothing was billed and a fabricated zero would be indistinguishable from a real measurement of free compute (plan §13.3). *Consequences:* three artefacts beyond plan §7, listed in `BEYOND_PLAN_SECTION_7` so a future addition has to be made consciously rather than absorbed silently; `DatasetProfile` gains a required field, which only `ingest` constructs; evaluation, actions, monitoring and governance settings are deliberately absent from `Recipe`, because they shape what happens to predictions rather than how a model is fitted.
- **DEC-043 — The evaluate stage takes only the model, the test data and the evaluation config.** *Context:* an evaluate stage that also reads prepare or model-search settings can only measure the model that the current run just built. *Decision:* evaluate consumes a scorer that carries its own decision threshold and its own calibration, both fitted at train time on the validation split; it fits nothing and selects nothing. The baseline is trained in the train stage and measured through the same call, with a pure composition function building the comparison from two evaluation reports. *Consequences:* any stored model can be re-scored on demand, which is what DEC-044 needs; evaluate becomes a pure function of its three arguments and is testable without a training run; a threshold can no longer be chosen on the test split, which was never legitimate anyway.
- **DEC-044 — Promotion re-scores the champion and the challenger on the same held-out data.** *Context:* the previous rule compared a challenger's fresh test score against the champion's stored score. Those two numbers came from different test splits, possibly different preprocessing and possibly a different population, so a challenger could win or lose for reasons unrelated to model quality. *Decision:* both models are scored on one frame, on the same metric, and only then compared; a stored score is never an input to the decision. The arithmetic in `should_promote` is unchanged, but its precondition is now that both scores come from the same evaluation frame. *Consequences:* promotion costs one extra scoring pass over the test split; the champion's predictor must be loadable, and the cases where it is not, or where its feature schema no longer fits the new data, are decided explicitly rather than by accident.
- **DEC-045 — The test split is final-decision-only.** *Context:* three-way splits are easy to erode: a threshold chosen here, a model picked there, and the hold-out quietly becomes a second validation set that flatters every number built on it. *Decision:* validation is where every selection happens: threshold, calibration, model choice, hyperparameters, features. The test split is measured once, for the promotion decision, and code that touches it carries a comment saying so. *Consequences:* the auto threshold is chosen on validation even though test is present in the same stage; reported test numbers keep their meaning as an estimate of unseen performance.
- **DEC-046 — Prepare is two phases with the split between them, and every statistic is fitted on the training rows.** *Context:* plan §6.1 orders the train flow `ingest → validate → prepare → split → train`, so the prepare stage never sees the split, and M3 read plan §6.3's "fit-on-train-only for anything statistical" as "fitted on the training file, never recomputed on the scoring file". That reading is too weak: a median or a 99th percentile measured over the whole uploaded file carries the validation and test rows into the values used for training, which is the leakage a three-way split exists to prevent, and it inflates the hold-out numbers the promotion decision of DEC-044 rests on. DEC-045 makes the test split final-decision-only, which the weaker reading quietly contradicts, and the user's instruction is explicit: fit all transforms on train only. *Decision:* prepare becomes two functions with a seam. `prepare_rows` applies everything that needs no fitted statistic and changes which rows exist — column exclusions, PII handling, the time-column cast, the consent filter, the missing-target drop, deduplication and the `missing_values: drop_rows` rule — and must run before the split, or a duplicate lands in one partition and its twin in another. `fit_transforms(..., fit_index=...)` fits the fill values and clip bounds **only on the rows `fit_index` names** (the training partition) and applies them to every partition; those are the transforms recorded in `prepare.json`, and `replay` still reproduces them from the recorded parameters alone. The stage list of plan §6.1 is not renumbered: the PREPARE stage is executed in two parts around SPLIT — `prepare_rows` → `split_dataset` → `fit_transforms(fit_index=parts["train"].index)` — and the partitions are re-sliced from the fitted frame by index. `prepare` keeps its signature as the single-frame convenience (every row a fit row), which is correct only for a frame that is entirely training data; the train pipeline may not call it. *Consequences:* no fill value or clip bound can be measured on a hold-out row, and every fitted transform records `fit_rows`, so `prepare.json` says what each parameter was fitted on; the split's fractions now apply to the rows that survive the row phase, and a row that is both an outlier and missing a feature is counted as a missing-value drop rather than an outlier, because `drop_rows` moved ahead of the split; a column whose values appear only outside the training rows is recorded as not applied instead of being filled from the hold-out; `outliers: remove_rows` still removes from every partition, using training bounds, so all three parts keep coming from one population; the Running screen is unchanged, because plan §6.1's prepare and split stages already share one group label; and `engine/pipeline.py` must adopt the three-call sequence when `run_train` lands, which is the only remaining caller-side work.
- **DEC-047 — Approval may only sign off the head-to-head it was actually taken on: `approve` refuses when the champion has changed.** *Context:* `LocalModelRegistry.approve` checked only that a version was `pending_approval`. `ModelVersion` recorded `previous_champion_id` and `improvement_pct` but nothing saying **which** champion the comparison that produced them was made against, so two versions could each beat champion C, one be approved and become champion, and the other then be crowned over it on the strength of a comparison with a model that no longer held the title. That is a promotion decided on a stored score from an older comparison, which plan §6.3's "beats the champion" and DEC-044 both forbid. *Decision:* the register stage records the champion a pending decision was measured against in `ModelVersion.measured_against_champion_id` — that champion's model id, the sentinel `NO_CHAMPION_AT_DECISION` (`"__none__"`) when there was no champion at the time, and null only for rows written before the field existed; `approve` compares it against the use case's current champion and refuses with `RegistryError("CHAMPION_CHANGED")` when they differ, naming both and saying to retrain, re-score or promote deliberately instead. A null is approved without the check, because such a row does not say what its decision was measured against. `api.routes.models` maps the new code to `409`, since the request is well formed and the version exists; an unmapped code would have been answered as a `500`. *Consequences:* a stale approval is a business refusal with a next step rather than a silent champion swap; `registry.db` gains a column, and Phase 1 has no migration tool, so a registry file written before this entry has to be recreated (plan §1.3 makes that a local development file, not client data); `promote` is unchanged and remains the recorded manual override for the cases where a human really does want to crown a version anyway.
- **DEC-048 — `predict` resolves its own model version and returns a record, not a series.** *Context:* the M1 stub was `predict(predictor_key, frame, config, *, storage) -> pd.Series`: the caller had already decided which model to load, and the stage's whole output was the scores. Every M4 finding about the score flow starts there. A caller that picks the model version picks it by its own rule — which is exactly how `POST /runs` came to accept a version belonging to another use case — and a stage that returns only scores forces its caller to re-derive everything else the run has to write: which version scored the file, how the rows were prepared, and how far they have moved from the training data. *Decision:* `predict(frame, config, *, run_id, storage, registry, model_version_id=None) -> PredictResult`. The stage takes the registry and answers the "which model" question itself through :func:`resolve_model_version`; `run_id` is the scoring run, so the drift report can name it; `model_version_id` is the user's explicit choice and defaults to the champion. `PredictResult` carries the resolved `model_version`, the loaded `scorer` (so `explain_rows` does not load the predictor a second time), the calibrated `scores` on the input frame's own index, the replayed `prepared` frame, the `prepare_report`, the `drift` report and the Running-screen `detail` line. *Consequences:* the stage is one call with one answer and no caller-side policy; `predictor_key` is no longer an input, so nothing can score with a predictor that no registry row points at; the pipeline assigns `frame[config.actions.score_field] = result.scores` and writes `result.drift` and `result.prepare_report` under the scoring run's key; the signature is now fixed for M4's `run_score`, and the stage still takes no `CancelToken`, which stays an open question for M7.
- **DEC-049 — A scoring run's `prepare.json` is the training run's, replayed and returned; there is no override.** *Context:* plan §6.3 says the score flow replays `prepare.json`, and plan §7 lists `prepare.json` as an artefact of a run directory. Those two readings pull apart: if the score flow ran its own prepare stage, a small scoring batch would re-derive column drops and re-fit fill values and clip bounds from the file being scored, and every customer's score would move relative to the run that chose the bands. But if it writes nothing, the Data page of a scoring run has nothing to render. *Decision:* the model chooses the preparation. The transforms come from the `prepare.json` of the run named by `ModelVersion.run_id`, read through `_prepare_report` and applied by `prepare.replay`, which measures nothing; a training run that kept no such record is `PREPARE_REPORT_NOT_SAVED` rather than a re-fit. That report is returned as `PredictResult.prepare_report` — it is already loaded, so returning it costs nothing — and the pipeline writes it unchanged under the scoring run's key. There is no run-level override of a model's preparation, by configuration or by request body. *Consequences:* a scoring run's `prepare.json` carries the *training* run's `run_id`, which is the truth about how those rows were prepared and lets a reader find the model's own run; the score flow's prepare stage does nothing that `predict` does not already do, so it must not re-fit; and a user who wants different preparation trains a new model, which is the only thing that can honestly change it.
- **DEC-050 — A model version named explicitly is scorable at any status; only the implicit choice has to be approved.** *Context:* `POST /runs` carries an optional `model_version_id`, and the registry has five statuses. Refusing everything but `champion` would make it impossible to re-score history with the model that produced it, or to try a candidate before approving it; accepting anything when *no* version was named would put unapproved numbers in front of a business user under the label of "the model". *Decision:* `resolve_model_version` honours a named version whatever its status — candidate, pending approval, champion or archived — and falls back to the use case's champion only when no version was named, refusing with `CHAMPION_NOT_FOUND` when there is none. A named version whose status is not `champion` is logged at INFO, and `run.json` records `model_version_id`, so a run scored with an unapproved model says so in both places. *Consequences:* re-scoring history and trying a candidate are ordinary operations rather than special cases; the only thing a status now controls is what happens when the user names nothing; and a version belonging to another use case is still refused, because a target that means something else is not a status question (`MODEL_USE_CASE_MISMATCH`).
- **DEC-051 — Drift is a reported signal, never a gate, and a comparison that cannot be made is reported as not measured.** *Context:* plan §6.3 asks for PSI per feature and a warning above the threshold, and says nothing about drift stopping a run. A stage that refused to score a drifted file would leave the user with no numbers at all precisely when the data has changed, which is when they most need to see them. Separately, PSI is a comparison between two distributions, and the arithmetic answers even when there is nothing to compare: a file with no rows leaves every baseline bin empty, which is the largest PSI the metric can produce, so a zero-row upload came back "drifted"; a baseline with no features sums over nothing, so it came back "PSI 0.00, stable". Both numbers describe the absence of data while reading as statements about the data. *Decision:* drift never blocks scoring — a run whose drift is high is scored, reported and logged at WARNING — and `compute_drift` returns `None`, "drift not measured", whenever no comparison happened: no stored baseline, no rows in the scored frame, or no features in the baseline. The reason is logged at WARNING with the model version, `PredictResult.drift` is `None`, and the Running-screen detail line ends "drift not measured" instead of a verdict. *Consequences:* `compute_drift` returns `DriftReport | None`, so a caller has to handle the not-measured case explicitly rather than reading a fabricated zero; `scoring_summary.json` already allows null drift fields, which is exactly this case; no verdict in the product is ever a statement about data that is not there; and a scoring file too small to be worth comparing is the user's decision to make, since the rows it does have are still scored.
- **DEC-052 — The score stage's failures are a code/message/suggestion table, and `POST /runs` maps those codes onto the envelope.** *Context:* plan §13.4 asks every user-facing error to carry a code, a message and a suggestion, and `engine/errors.py` does exactly that for the pipeline's own failures in `ENGINE_ERRORS`. `ScoreError` had seven codes that existed only as string literals at their raise sites: nothing could enumerate them, the API could not map them onto HTTP statuses without copying literals, and the generated documentation had no way to know they existed. Its docstring also still promised that the codes would collapse into `EngineError` "when `engine/errors.py` lands", which it has. *Decision:* `SCORE_ERRORS` maps each code to its message template and its suggestion, in the shape `ENGINE_ERRORS` already uses; every code is a module constant; `score_error(code, **values)` is the only way this module raises, so an unregistered code cannot reach a user; and `ScoreError.suggestion` is filled from the table the way `EngineError.suggestion` is. `api.routes.runs.SCORE_ERROR_STATUS` maps the codes the run endpoint can meet onto HTTP statuses, and an unmapped code is a `500` rather than a guessed 4xx, exactly as `api.routes.models.REGISTRY_STATUS` already does. The three coded exceptions stay separate classes: `engine.errors.run_error` already turns any of them into the `RunError` that reaches `status.json` by reading `code` and `message`, so collapsing them would buy nothing and would cost the reader the name of the stage to go to. *Consequences:* the codes are enumerable, testable and documentable; a new failure mode has to be written down before it can be raised; `RunError` still has no field for a suggestion, so it reaches the log rather than the screen, which is where DEC-072 already leaves `EngineError.suggestion`.
- **DEC-053 — `approve` and `promote` stay two operations, not one endpoint with a flag.** *Context:* both end with the same champion swap, and plan §8 lists them separately without saying why. Merging them would have been less code. *Decision:* they mean different things and are kept apart. `approve` finishes a decision the engine already took — the register stage marked the version `pending_approval` because it *did* beat the re-scored champion and `governance.approval_required` held it back — so it applies only to that status, takes no reason, and is refused when the comparison behind it has gone stale (DEC-047). `promote` overrides the champion rule by hand from any state the registry deems eligible, so it requires a `reason`, which is stored as `promotion_note` and is the only record of why the rule was set aside. A version that is promoted records `promoted_by`/`promoted_at` and no approver; a version that is approved records `approved_by`/`approved_at` and no note. *Consequences:* the audit trail distinguishes "a human said yes to the engine's decision" from "a human overruled it", which is the distinction a governance review actually asks about; `approve` can be made stricter (as DEC-047 did) without taking away the deliberate escape hatch; and the UI has one button per meaning rather than one button with a mode.
- **DEC-054 — One resolver answers "which model scores this file", and one code says "there is no champion".** *Context:* the question was answered twice. `engine.stages.score` resolved the champion or the named version with the full rule, while `api.routes.runs.score_schema` re-derived it from the registry with a laxer one of its own: it accepted any `model_version_id` the registry knew, including a version belonging to **another use case**. Such a run was accepted, validated against a foreign model's schema and then failed halfway through at the predict stage. The same split produced two machine codes for one condition — the endpoint's `NO_CHAMPION_MODEL` and the stage's `CHAMPION_NOT_FOUND` — so a caller switching on the code had to know both. *Decision:* `engine.stages.score.resolve_model_version` is the single source of truth, and `POST /runs` calls it before it accepts a scoring run, mapping its codes onto HTTP statuses (`CHAMPION_NOT_FOUND` → 409, `MODEL_USE_CASE_MISMATCH` → 409, `MODEL_NOT_FOUND` → 404) and reporting the stage's own message. `NO_CHAMPION_MODEL` is retired; `CHAMPION_NOT_FOUND` is the one code for "this use case has no champion", wherever it is met. *Consequences:* a version the endpoint accepts is one the stage will score, and a version it refuses is refused before a run directory exists, with the sentence the engine would have used; a `model_version_id` that names nothing is now a `404` about that id rather than a `409` about a champion; and the resolver's rules can only change in one place.
- **DEC-055 — "Who approved this" is a caller-supplied string, required and unverified.** *Context:* plan §1.3 and plan §14 leave Phase 1 without authentication, and `approve`/`promote` both write a name into the registry row that is the audit trail for a champion swap. There were three options: invent a name (`"system"`, `"local user"`), allow the field to be empty, or require the caller to supply one. *Decision:* `approved_by` and `promoted_by` are required, non-blank and stored verbatim; a request without one is a `422`, and the API neither verifies the value nor substitutes one of its own. Both the route docstrings and this entry say plainly that the value is a claim, not an identity. *Consequences:* the audit trail records what the caller claimed rather than something the API made up, which is the honest version of an unauthenticated Phase 1 (plan §13.3); it is not evidence of who really acted, and must not be presented as such in the UI; and when authentication lands in a later phase the field becomes verified in place, with no change to the registry schema or to the routes' shapes.

## Phase 4a — AWS implementations and deployment (DEC-300 … DEC-399)

Phase 1 put storage, jobs and the model registry behind protocols so that AWS would be a set of new
*implementations* rather than a rewrite (plan §12). Phase 4a writes those implementations. The
numbering is allocated by area so that entries written in parallel could not collide, and a block
with a gap in it has a gap because nobody had a tenth decision worth writing down, not because one
is missing:

| Block | Area |
|---|---|
| DEC-300 … 311 | Settings, secrets, and the protocol seams |
| DEC-312 … 323 | `S3Storage` and the shared storage conformance suite |
| DEC-324 … 337 | `JobSpec`, the SageMaker job runner, the container entrypoint and the price table |
| DEC-338 … 348 | Postgres metadata, Alembic, and the model registry over S3 |
| DEC-349 … 363 | The container, the local stack and the pipelines |
| DEC-364 … 379 | The CDK infrastructure |
| DEC-380 … 399 | Observability and the two documents |

Two rules run through every entry below. **Local behaviour does not change**: every default
reproduces Phase 1 exactly, and where that is not obvious the entry says how it is enforced rather
than merely intended. And **no number that was not measured** (plan §13.3): a constant that was
chosen says so in its own docstring, a cost that was not measured is absent rather than estimated,
and a published list price is labelled as a rate card and never as a bill.

---

- **DEC-300 — One `Settings` object describes a deployment, and its defaults reproduce Phase 1 exactly.** *Context:* Phase 1 answered "where do the artefacts live" with two environment variables read at the point of use — `MARKETING_AI_DATA_DIR` in `engine/storage.py`, `MARKETING_AI_CONFIG_DIR` in `engine/config.py`. That is enough for one machine and one backend; Phase 4a has three backends per concern, and an operator has to be able to supply the answer from Parameter Store. *Decision:* `engine/settings.py` holds one frozen pydantic model with the whole answer, built by explicit `from_env` / `from_aws` / `load` classmethods rather than by `pydantic-settings` (which `tests/unit/test_pyproject_pins.py` forbids as a dependency, and whose `settings_customise_sources` is a worse fit for a four-source merge than fifteen lines of explicit precedence). `Settings()` with nothing set selects the local filesystem, SQLite and a two-worker thread pool, in the same directory and with the same worker count Phase 1 used, and the two existing environment variables keep their spelling. *Consequences:* local behaviour is unchanged *by construction* rather than by anyone remembering to keep it that way, and `tests/unit/test_settings.py` asserts every one of those defaults so a later edit cannot drift them; nothing that set the old variables has to change; and there is one table to read rather than a scattering of `os.environ` calls to find.
- **DEC-301 — Precedence, lowest first: SSM parameters, the Secrets Manager document, the process environment, then explicit overrides.** *Context:* a deployment reads from up to four places and they will disagree. *Decision:* the order above, implemented once in `resolve_values` and unit-tested on its own. *Consequences:* the environment beating AWS is the deliberate part: it is what lets an operator override one value on a task without editing a parameter, and what lets a test point a deployed shape at a local directory. Explicit overrides beat everything so a caller that passes a value gets it.
- **DEC-302 — A backend that cannot work is refused where it is described, not at the first request that needs it.** *Context:* `storage_backend=s3` with no bucket is a deployment that will fail, and the only question is when. *Decision:* a model validator refuses an incomplete backend at construction: s3 without a bucket, postgres without a URL, sagemaker without a role, an image, both instance types and a region — and sagemaker without s3, because a remote job cannot read a local disk. *Consequences:* the failure arrives at startup with the field named, rather than at the first upload with a `KeyError`; `SettingsError` carries a code and the field, and `api/main.py` renders it as a 503 (the process is healthy, the configuration is not).
- **DEC-303 — A secret is invisible by default, and no construction path can put one in a message.** *Context:* `database_url` carries a password. Pydantic's `ValidationError` renders the whole input mapping as `input_value=...`, truncated in the middle — measured here: a long URL comes out mangled and a short one comes out whole. "Happens to be truncated" is not a guarantee. *Decision:* secret fields are `SecretStr`; `redacted()` replaces them; `summary()` renders an explicit *allow-list* of non-secret fields and `__repr__`/`__str__` are built from it; and `Settings.__init__` itself is wrapped so that `from_env`, `from_aws`, a test fixture and a bare `Settings(...)` all raise the same `SettingsError`, whose message names the field and never the value. *Consequences:* a secret field added in a later phase is hidden until somebody deliberately adds it to `SUMMARY_FIELDS`, which is the safe direction for the mistake to fall; and there is no remaining constructor that can leak one.
- **DEC-304 — An unrecognised `MARKETING_AI_*` variable is refused, with a written-down escape list.** *Context:* a misspelt parameter name is invisible: the setting simply has no effect, and the first sign is somebody wondering why. *Decision:* `resolve_values` raises `SETTINGS_UNKNOWN` for any `MARKETING_AI_*` variable that does not name a field, and `NON_FIELD_ENV_VARS` is the explicit list of the ones that deliberately are not settings — the job-spec key the container is handed, the failure file SageMaker reads, and the two variables the Postgres fixtures use. *Consequences:* a typo fails loudly at startup; adding a non-setting variable is a visible act rather than a silent exemption; and a task definition may set only names from the frozen table, which the infrastructure asserts.
- **DEC-305 — Parameter Store holds the settings, Secrets Manager holds the one credential, and a parameter may be named either way.** *Context:* two stores answer two different questions, and the IAM a task role needs differs for each. *Decision:* plain `String` parameters under a flat, non-recursive `/marketing-ai/<env>/`, and one JSON document at `marketing-ai/<env>/app` for the database URL. A parameter leaf is accepted as the bare field name (`s3_bucket`) or as its environment spelling (`MARKETING_AI_S3_BUCKET`), and a leaf matching neither is ignored. *Consequences:* the task role can be granted `ssm:GetParametersByPath` on one prefix and `secretsmanager:GetSecretValue` on exactly one secret, which is a boundary a reviewer can check at a glance; and Parameter Store stays a shared namespace that a later phase can put its own things in without this version refusing to start.
- **DEC-306 — Nothing under `engine/aws/` imports boto3 at module scope, and the AWS packages are an optional extra.** *Context:* a laptop checkout must keep importing `engine.settings`, `engine.storage` and `engine.registry` for free, and `make test` must keep working without the cloud dependencies. *Decision:* `boto3`, `botocore`, `psycopg[binary]` and `alembic` are the `aws` extra; the CDK packages are a separate `deploy` extra; every AWS import sits inside the function or constructor that needs it; and the factories in `engine/settings.py` import a backend's module only in that backend's branch. *Consequences:* the cost and the failure both land on the caller who actually asked for AWS; a local install stays exactly as heavy as it was; and `tests/integration/test_design_rules.py` asserts the rule rather than trusting it. Note that boto3 was *already* a transitive dependency through `autogluon-common` — the extra declares and pins what was there rather than adding weight.
- **DEC-307 — A production deployment may not inherit the laptop's wide-open CORS.** *Context:* DEC-024 left `allow_origins=["*"]` because the Phase 1 UI is opened as a local file. That is a statement about a laptop, not about an internet-facing load balancer, and a deployment that never mentions CORS would inherit the laptop's answer by omission. *Decision:* `cors_origins` defaults to `("*",)`, so nothing local changes, and `Settings` refuses `env=prod` while it is still `*`. `create_app` also refuses `data_dir=` combined with a non-local storage backend, because `data_dir` is how the whole test suite points the app at a `tmp_path` and a stray environment variable must not be able to redirect a test's artefacts into a bucket. *Consequences:* the narrowing has to be a deliberate act on the one deployment where it matters; `data_dir` keeps outranking everything, which is what makes the existing suite safe.
- **DEC-308 — `engine/settings.py` decides *what* to construct; `api/deps.py` remains the only place the API constructs it.** *Context:* the repository's standing rule is that `api/deps.py` is the single construction site. A SageMaker container has no `api/deps.py` at all and must build the same objects from the same description. *Decision:* `build_storage`, `build_registry` and `build_services` live in `engine/settings.py` and are called by both; `api/deps.py` keeps its `_LOCK`, its `app.state` caching and its rule that `create_app(data_dir=…)` wins. *Consequences:* the API and a job can never disagree about where the artefacts are; the rule is restated rather than broken. One correction was needed while writing it: `_LOCK` is not reentrant, so every provider now resolves its dependencies *before* taking it — constructing inside the critical section would have deadlocked the first request.
- **DEC-309 — The AWS wire loggers are capped at INFO wherever a client is first built.** *Context:* botocore at DEBUG prints request headers and query strings, and therefore pre-signed URLs, which are bearer credentials. Setting the engine's own level to DEBUG must not turn that on by accident. *Consequences:* `quiet_aws_wire_logs()` raises the level of `botocore`, `boto3`, `urllib3` and `s3transfer` to INFO if they are lower, and never lowers one that is already quieter.
- **DEC-310 — One layout for a published model prefix, and the unused second one is deleted.** *Context:* `engine/storage.py` defined `model_key(model_id, …)` → `models/<model_id>/…`, which had no call site anywhere and which the Phase 4 notes already flagged as unused. Phase 4a needs `models/<use_case_id>/<version>/…`. Two conventions for one prefix in one tree is an invitation to use the wrong one. *Decision:* `model_key` is deleted and `published_model_key(use_case_id, version, *parts)` replaces it. *Consequences:* the use case and the version are in the key in the order a human browses a bucket in, and it is the boundary an IAM prefix condition can be written against; the only cost is one test that changed with it.
- **DEC-311 — A capability that only some stores have gets its own protocol, never a member on `Storage`.** *Context:* `S3Storage` needs two things `LocalStorage` does not: an explicit publish for the write direction of `local_path()`, and a pre-signed download URL. Adding either to the `Storage` protocol would break `isinstance(x, Storage)` for `LocalStorage` and for every structural fake in the suite — which `tests/unit/test_storage.py` asserts — and would contradict the phase's own rule that AWS is implementations, not protocol changes. *Decision:* `SupportsLocalMirror` and `SupportsPresignedDownload` are declared *beside* `Storage`, and four free functions dispatch to them and no-op (or return `None`) on a store that lacks them. The same shape is used for `ReconcilingJobRunner` on the job side. *Consequences:* call sites such as `engine/stages/train.py` and `engine/pipeline.py` call the free function unconditionally and a local run is bit-for-bit unchanged; both protocols' member lists are now documented as frozen, with the reason; and a new capability later follows an established pattern instead of reopening the question.
- **DEC-312 — `local_path()` is a read-through mirror on a remote store, and the write direction is an explicit `publish_local_path(key)`.** *Context:* `local_path()` is the protocol's one escape hatch, for AutoGluon and pyarrow, which insist on a real directory. Over S3 that path cannot be the store. Reading can be made transparent - hydrate the tree out of the bucket on first use - but writing cannot be inferred: a `Path` has no close event, AutoGluon writes the predictor tree through the filesystem and the store is never called again, so nothing exists to trigger an upload. *Decision:* `S3Storage.local_path(key)` hydrates the object or the whole `key/` subtree into a per-instance mirror on first use and returns a path that, exactly as `LocalStorage` does, need not exist. The write direction is `publish_local_path(key)` from `SupportsLocalMirror`, dispatched by the free function in `engine/storage.py` that no-ops on a store without the capability. The engine has exactly one write-direction call site: `engine/stages/train.py`, immediately after `predictor.save()` and before the leaderboard, the scorer fit or anything else that can raise. *Consequences:* A local run is bit-for-bit unchanged - the dispatcher returns `()`. A remote run publishes the predictor at the first moment it is complete, so a later failure in the same stage cannot lose it. AutoGluon 1.6.3 was measured not to write into the predictor directory after `save()`, so nothing is missed by publishing there. The cost is that a new call site which writes through `local_path` and forgets to publish loses its bytes on S3 and not on disk; the conformance suite tests the round trip through a second independent store so the pattern is at least demonstrated once.
- **DEC-313 — a publish is content-diffed against a SHA-256 this module writes as user metadata, not against the ETag.** *Context:* `publish_local_path` has to be cheap to call twice: the train stage publishes a predictor tree that a later stage may already have mirrored. The obvious diff key is the ETag, but an ETag is the MD5 of the body only for an unencrypted single-part upload - it is neither stable across the multipart boundary nor meaningful at all under SSE-KMS, which is exactly the configuration a production bucket runs in. *Decision:* Every upload this module makes carries `x-amz-meta-content-sha256`. Single `PutObject` writes hash the buffered body at commit; a mirror publish hashes the file first, because multipart metadata can only be set at `CreateMultipartUpload`. `_publish_file` compares size first (free), then the digest, and skips the upload when they match. An object with no digest metadata is treated as different, re-uploaded once, and stable from then on. *Consequences:* A second publish of an unchanged tree costs one `HeadObject` per file and no bytes, under SSE-KMS as much as without it. A large multipart body written through plain `open_write` carries no digest and will be re-uploaded once if it is ever published from a mirror. Nothing depends on S3's ETag algorithm, so changing `PART_BYTES` later cannot silently invalidate every diff.
- **DEC-314 — reads are ranged GETs behind a seekable raw stream; writes are parts behind a buffered one.** *Context:* A parquet file does not fit in memory just because a disk would hold it, and `pyarrow.parquet.read_table` raises `io.UnsupportedOperation: seek` on a non-seekable stream - measured in this environment. A `StreamingBody` straight off `GetObject` is not seekable. *Decision:* `open_read` returns an `io.BufferedReader` over a raw stream that holds at most one `READ_CHUNK_BYTES` window and re-issues a ranged GET on a seek outside it; the object's length comes from the `HeadObject` that already has to happen, so `SEEK_END` costs no request. `open_write` returns an `io.BufferedWriter` over a raw writer that drains parts of exactly `PART_BYTES` as the buffer fills. Every buffer size, chunk size, timeout and retry count is a `Final` whose docstring says it is chosen and not measured, and names the documented S3 limit it sits under where one applies. *Consequences:* Peak memory is arithmetic on declared constants rather than a function of the object, and `tests/unit/test_s3_streaming.py` asserts it with `tracemalloc` against a bound derived from those same constants - no figure in the tree claims to be a benchmark. A seek-heavy reader pays one GET per window change; a sequential reader pays one per chunk.
- **DEC-315 — atomicity comes from S3's own commit point, and the `status.json` polling guarantee is tested on both backends.** *Context:* `LocalStorage` gets atomic writes from `os.replace`. A remote store has no rename, and the API's browser polls `status.json` while the run is still writing it - a reader that can see half a document sees a JSON parse error it can neither explain nor retry. *Decision:* Nothing is sent until the block exits normally: below the threshold one `PutObject` at commit, above it `CompleteMultipartUpload` as the commit point with `AbortMultipartUpload` on any exception (including a failure inside the commit itself). The two crash guarantees - a crash mid-write leaves no object, a crash mid-REWRITE leaves the previous document readable in full - are written once in the conformance suite and run against both backends. *Consequences:* A crashed run leaves neither a half-written object nor a dangling multipart upload waiting for a lifecycle rule. A failed abort is logged by exception class and swallowed, because replacing the caller's original exception with it would hide the failure that actually matters. A very large write is held entirely in parts until commit, so the abort path discards real uploaded bytes - that is the price of the guarantee.
- **DEC-316 — `exists()` raises on 403 and returns False only on 404.** *Context:* Without `s3:ListBucket` on the bucket, S3 answers `HeadObject` for a key that is not there with 403 rather than 404. So 'absent' and 'forbidden' arrive as different codes for the same question, and only one of them is an answer. *Decision:* `exists()` returns `False` for 404 (and the `NoSuchKey`/`NotFound` spellings) and raises `StorageError('READ_FAILED')` for 403 and everything else. `size_bytes` behaves the same way through the shared `_head` helper. *Consequences:* A permissions mistake surfaces as a loud failure on the first request instead of as an artefact that quietly does not exist - a run that re-does work, or an API that reports a completed run has no results, with nothing downstream able to tell the difference. The cost is that `exists()` is not total: a caller on a bucket where the role genuinely lacks `s3:ListBucket` gets an exception where it may have expected a boolean, which is the honest answer.
- **DEC-317 — the 512-character key gate and the 1024-byte S3 key limit are checked separately.** *Context:* `validate_key` limits a storage key to 512 *characters*; S3 limits an object key to 1024 *bytes*. One non-ASCII character is up to four bytes, and the bucket prefix is prepended before S3 ever sees the key, so a key this product considers valid can still be a key S3 will not accept. *Decision:* `_object_key` applies `validate_key` first, builds `<prefix>/<key>`, and then measures the UTF-8 length of the result against `MAX_S3_KEY_BYTES`, raising `KEY_INVALID` with both numbers in the message. *Consequences:* An over-long key fails with the product's own error code at the call site instead of as a signing or request error from the wire, and the failure names the prefix's contribution, which is the part the caller did not choose. Two limits have to be kept in mind rather than one.
- **DEC-318 — object tags are derived from the key, not passed in.** *Context:* Cost allocation and per-customer lifecycle rules want `run_id` and `client_id` on every object, but `Storage` has thirteen frozen methods and none of them takes a tag. Adding a parameter would change the protocol for every implementation, which is the thing Phase 4a promised not to do. *Decision:* `S3Storage` reads the run id back out of the key with the `runs/<id>/…` pattern that `engine.storage.run_key` owns, and adds `client_id` from its constructor when the deployment serves a named customer. A tag value outside S3's documented character set is dropped rather than sent. *Consequences:* Tagging is free at every call site and cannot be forgotten. It is also only as good as the key layout: a future artefact prefix that carries a run id in a different shape gets no `run_id` tag until the pattern is extended, and the test that asserts the tag set is where that would show up.
- **DEC-319 — the pre-signed URL lifetime comes from the caller; this module declares no default for it.** *Context:* `engine/settings.py` already owns `download_url_ttl_seconds`, bounded and defaulted to 900. A second default here would be a second place for the policy to live. *Decision:* `presigned_download_url(key, *, expires_in, filename=None)` takes the lifetime as a required keyword and declares no constant of its own; a non-positive lifetime is refused rather than signed. A `filename` becomes a `Content-Disposition` with quotes, backslashes and newlines stripped. *Consequences:* There is exactly one number to change, and no way for the two to drift apart. The URL is a bearer credential for as long as it lives, which is why `quiet_aws_wire_logs()` is called before any client is built and why nothing in this module logs one. The filename scrub prevents a response-header injection through an uploaded file's name.
- **DEC-320 — the AWS-to-StorageError mapping is exhaustive and ordered, and never quotes the AWS message.** *Context:* The interesting failures are the ones a lazy mapping makes invisible. `NoSuchBucket` arrives as a 404; a KMS grant failure arrives as a 400 with a `KMS.AccessDeniedException` code; `AccessDenied` on a read and on a write are not the same event for the caller. *Decision:* `_s3_error` checks `NoSuchBucket` first (a missing bucket is configuration, so `READ_FAILED`/`WRITE_FAILED`, never `KEY_NOT_FOUND`), then the denial codes including the KMS and credential spellings and a bare 403 (`READ_FAILED` on a read, `WRITE_FAILED` on a write), then the not-found codes and a bare 404 (`KEY_NOT_FOUND` on a read; on a write the same status means the bucket or the upload has gone, so `WRITE_FAILED`). The error is read structurally off `exc.response` rather than by catching `ClientError`, so botocore stays out of module scope. The message carries the exception class and the AWS error code and never the AWS message, which routinely contains the key and can contain a query string. *Consequences:* A permissions problem can never present as a missing artefact, and a misconfigured bucket never sends a reader looking for a run that was never written. The mapping is tested from constructed `ClientError`s rather than provoked ones, because moto 5.2.3 raises a bare `KeyError` for `complete_multipart_upload` with a bogus upload id - provoking failures would test moto's fidelity instead of this table.
- **DEC-321 — the backend-agnostic storage assertions live in one parametrised conformance suite.** *Context:* A frozen protocol is worth exactly the tests that check it. A contract tested once per implementation is really two contracts that share a name: the moment one suite tests `list_keys` ordering and the other does not, the backends are free to disagree and nothing fails. *Decision:* `tests/unit/test_storage_contract.py` holds a `storage` fixture parametrised over `['local', 's3']` (s3 via moto) and a `make_storage` factory beside it, and every assertion about the protocol - the invalid-key sweep across every method, the round trips, zero-byte values, overwrite, `KEY_NOT_FOUND`, idempotent delete, listing, awkward keys, the streams, the two crash guarantees and the `local_path` round trip through a second independent store - is written once and run twice. `tests/unit/test_storage.py` keeps the local store's own atomic-rename details and was not touched. *Consequences:* A third backend costs one fixture parameter and inherits 28 assertions. The suite runs in about 4.6s, so it stays in `make test`. The factory, rather than a bare store, is what makes materialise-on-read testable at all: a mirror that is already warm proves nothing about hydration.
- **DEC-322 — bounded memory is proved against a generated body and `tracemalloc`, not a large fixture.** *Context:* The claim is that a 40 GiB object costs the same memory as a 40 KiB one. A fixture large enough to test that for real is a fixture nobody runs, and a test nobody runs is not a guarantee. *Decision:* `tests/unit/test_s3_streaming.py` uses a fake client that invents the bytes of whatever range it is asked for from a 64 KiB tile and records only the shape of the traffic - how many ranged GETs, how many parts, what size each was. The assertions are the traffic shape plus a `tracemalloc` peak bounded both by a fraction of the object's size and by a ceiling computed from this module's own declared buffer constants. The default sizes are single-digit multiples of `PART_BYTES` so the file runs in well under a second; a 48-part variant carries `@pytest.mark.slow`. *Consequences:* The memory claim is checked on every `make test` rather than aspired to, and the ceiling is arithmetic on constants rather than a number measured on one laptop and frozen into the tree. What is not checked is real throughput against a real bucket - nothing in this repository claims it is.
- **DEC-323 — `list_keys` sorts in Python rather than trusting S3's ordering.** *Context:* `ListObjectsV2` returns keys in UTF-8 binary order. That is not Python's string order for every input, and `LocalStorage` sorts with Python's. *Decision:* `S3Storage.list_keys` collects every page, strips the store root, drops directory-marker keys ending in '/' and sorts the result itself, exactly as `LocalStorage` does. *Consequences:* The two backends return the same tuple for the same content, which is what lets the ordering assertion live in the shared conformance suite. The cost is that the full key list is materialised before it is sorted - acceptable for an artefact store, and the same thing `LocalStorage` already does with `rglob`.
- **DEC-338 — `SqlRegistryStore` is extracted from `LocalModelRegistry` with its method bodies unchanged, and `LocalModelRegistry` becomes a subclass that only chooses the engine.** *Context:* Phase 4a needs the same registry over Postgres. The two honest options were to write a second implementation of the registry against Postgres, or to separate what the registry *says* from what it says it *to*. The registry's hardest property is that a champion swap — demote the incumbent, crown the challenger — is one transaction, and that `approve` refuses a decision measured against a champion that has moved (DEC-047). A second implementation is a second copy of that, and the copy that drifts is the one nobody is looking at. *Decision:* `SqlRegistryStore(engine)` holds every statement the registry makes, with the method bodies moved verbatim — not rewritten, not re-indented into a new shape. `LocalModelRegistry(SqlRegistryStore)` keeps its exact `__init__(db_path)`, its `db_path` property and `check_same_thread=False`, and adds `create_registry_tables(self.engine)`. `engine/aws/postgres.py:postgres_store(settings)` hands the same class a Postgres engine. The champion rule `should_promote` is untouched and is still a pure function nobody in the store calls. *Consequences:* One copy of the transaction, exercised twice: `tests/unit/test_registry.py` now parametrises every store test over SQLite and a migrated Postgres schema, and the DEC-047 stale-approval sequence is proved on both. `api/deps.py` and `default_registry()` are unchanged. A caller that wants only the statements — `S3ModelRegistry` — composes the store instead of subclassing the file-based registry.
- **DEC-339 — Every datetime column is `DateTime(timezone=True)`, and `aware_utc`/`to_utc` convert rather than merely attach.** *Context:* SQLModel compiles a bare `datetime` field to `TIMESTAMP WITHOUT TIME ZONE` on the postgresql dialect. Measured on a server running `Asia/Kolkata`: an aware `2026-09-22T12:00:00+00:00` handed to such a column is stored as the session's wall clock, `17:30:00` naive, and Phase 1's `_aware` — which only attached UTC to a naive value — read it back as `17:30:00+00:00`. Every `ModelVersion.created_at` on a non-UTC server was five and a half hours into the future, silently, and only on that server. The read side had a second, quieter defect: a `timestamptz` comes back in the session's time zone, so leaving an aware value alone would publish the server's offset into a field the contract says is UTC. *Decision:* Every timestamp column on `ModelVersionRow` and on the new `RunRow` is declared through an explicit `sa_column=Column(name, DateTime(timezone=True), ...)`. `_aware` becomes the public `aware_utc`: naive means UTC, aware is `astimezone(UTC)`. `_utc` becomes the public `to_utc` and every write goes through it, including the run index's, because SQLite has no timestamp type and stores exactly what it is handed. `alembic/env.py` sets `compare_type=True`, so a later revision cannot quietly undo this. *Consequences:* `sa_column` is mutually exclusive with SQLField's `index=`/`primary_key=` and a `Column` object belongs to one table, so each column is declared separately and no timestamp is indexed except `run.created_at`, which gets its index on the `Column` itself. The fix is proved by a test that runs on both backends and was demonstrated to fail — by the server's exact UTC offset — when reverted.
- **DEC-340 — `create_all` is scoped to a named table list, never to the whole `SQLModel.metadata`.** *Context:* `SQLModel.metadata` is a process-wide namespace, and what is in it depends on what has been imported. Phase 1's `LocalModelRegistry.__init__` called `SQLModel.metadata.create_all(engine)` with no table list. Phase 4a adds a second `table=True` class, the run index. The moment anything imported `engine.aws.postgres` — `api/deps.py` on a settings path, a test module, a script — every `registry.db` in existence would gain a `run` table it never asked for, on a deployment that chose SQLite precisely to avoid all of this. *Decision:* `engine.registry.create_registry_tables(engine)` creates only `model_version`; `engine.aws.postgres.create_run_index_tables(engine)` creates only `run`. `METADATA_TABLES = ("model_version", "run")` is the definite list of what this product owns, and `alembic/env.py`'s `include_name` holds autogenerate to it so an unrelated table in the same database is neither dropped nor reported as drift. *Consequences:* Three tests assert the file contents directly: a `registry.db` holds `{model_version}`, a run-index database holds `{run}`, and the two creators together produce exactly the set `0001` migrates to. A future table has to be added to `METADATA_TABLES` deliberately, which is also the moment somebody has to write its migration.
- **DEC-341 — Alembic owns the Postgres schema from `0001`; `create_all` is for SQLite only.** *Context:* `create_all` adds a missing table and never a missing column. On a laptop that is a fair trade — the answer to a stale `registry.db` is to delete the file. On a deployment the same behaviour means the first column added after go-live is missing in production, silently, until a query fails, and there is no file anyone is willing to delete. *Decision:* `alembic/versions/0001_initial.py` creates `model_version` and `run` as they stand — a description of the destination, not a replay of how the SQLite file got there, because there was no Postgres before this revision. Nothing on the Postgres path calls `create_all`. The test fixtures create each test's schema with the real `alembic upgrade head`, so what the tests exercise is what a deployment gets. The migration is reversible, and its docstring says plainly that dropping `run` costs a rebuildable index while dropping `model_version` destroys the registry. *Consequences:* One linear history, asserted by a test. A schema change is now two edits — the model and a revision — and the drift test fails if only one of them happens.
- **DEC-342 — A `run` table that indexes `run.json`; the row is written after the document, a failed row never fails a run, and the table is rebuildable.** *Context:* `GET /runs` lists every key under `runs/` and reads each `run.json` back. On S3 that pages over every object of every run — artefacts included — and its cost grows with the number of artefacts in the bucket, forever. An index fixes it, and the obvious next step, making the table the record, is the one that loses data. *Decision:* `run.json` stays the artefact of record. The table holds a projection good enough to filter and order a list page and nothing more — no `overrides`, no `artefacts`, nothing computed. `mirror_run(index, record, manifest=None) -> bool` is called **after** the document is written, returns `False` rather than raising for any failure including `index=None` (the local deployment), and logs with `log_failure` so no exception message reaches the log. `RunIndex.list_run_ids` returns ids, not entries, so `GET /runs` still reads each `run.json` from storage. `scripts/reconcile_runs.py` rebuilds every row from `runs/*/run.json`, upserting first and dropping orphans second, counting unreadable documents rather than deleting their rows. `engine/aws/run_index.py` holds the protocol, the projection and the two functions and is table-free and driver-free, so `engine/pipeline.py` can import it on a laptop; the table and the SQL live in `engine/aws/postgres.py`. *Consequences:* A database outage costs a list page its completeness and never a customer their run, and even that is recoverable with one command. A rebuild deliberately does not read `run_manifest.json` — that would double an already expensive scan — so rebuilt rows have `duration_s`, `compute_backend` and `estimated_usd` back at null, which is the honest value for "rebuilt from the record alone". `--dry-run` reports what a rebuild would do while writing nothing.
- **DEC-343 — `PostgresConfig.from_settings` is the only translation from a deployment to a DSN; this product reads the environment exactly once.** *Context:* The temptation on every backend module is a `from_env` of its own. Two readers of the environment is two answers to "which database", and the one that is wrong is whichever one the reader was not looking at. *Decision:* `engine/aws/postgres.py` contains no `os.environ`, no `getenv` and no `from_env` — a test asserts all three on the module source. `PostgresConfig` is a frozen dataclass built by `from_settings(settings)`. It normalises a bare `postgresql://` DSN to `postgresql+psycopg://`, because the URL RDS shows an operator names no driver and SQLAlchemy reads that as psycopg 2, which this product does not install. `postgres_schema` is validated against a plain-identifier pattern before being interpolated into `-csearch_path=<schema>,public`, which is set as a libpq connect option so a pooled connection is already pointed at the right schema before any statement runs. The engine sets `pool_pre_ping=True` and `hide_parameters=True` and nothing else: a pool size or a recycle interval is a number, and none has been measured. *Consequences:* A migration and the application connect the same way, through the same function. The password never appears in `repr(engine)` (asserted) and a failing INSERT does not quote the row. A schema name containing `;DROP SCHEMA` is refused by field name with the value withheld from the message.
- **DEC-344 — A Postgres test that does not run says why, and `MARKETING_AI_REQUIRE_POSTGRES=1` turns the skip into a failure.** *Context:* A skipped test proved nothing, and the dangerous kind is the one nobody notices. CI that is supposed to have a database and does not should go red, not green with a note nobody reads. *Decision:* `tests/fixtures/postgres.py::postgres_unavailable_reason()` returns a sentence naming the URL (password masked) and the driver exception class, probed once per session. `skip_without_postgres()` raises that as the skip reason, or as a `pytest.fail` when `MARKETING_AI_REQUIRE_POSTGRES=1`. `pyproject.toml`'s `addopts` already carries `-rs`, so every skipped test prints its reason. Each test gets its own schema, migrated by the real `alembic upgrade head` and dropped afterwards. *Consequences:* Both branches were exercised for real against a dead port: the skip prints the sentence, and `REQUIRE=1` fails with it. The fixtures are imported by name into the modules that need them rather than living in a conftest, because `tests/conftest.py` holds the two path fixtures and nothing else.
- **DEC-345 — `alembic.ini` carries no DSN; `env.py` resolves the URL as `-x url=`, then the ini, then `Settings`.** *Context:* A DSN in a committed file is a credential in a committed file even when today's value is a localhost password, because the next person who needs a staging run edits it and the one after that forgets to put it back. *Decision:* `sqlalchemy.url` is empty in `alembic.ini` and a test asserts that no non-comment line in the file contains `://`. `env.py` resolves in that order, with `-x schema=` following `-x url=` and `postgres_schema` following the settings, so the URL and its schema can never come from different deployments. A Postgres URL is opened through `postgres_engine`, so a migration connects exactly the way the application does; anything else (SQLite, in the drift test) gets a plain engine. `env.py` deliberately does not call `fileConfig`, so Alembic installs no handler of its own — this product's formatter is the one that withholds exception messages, and a migration failing against a real database is exactly where a driver would otherwise print a row. *Consequences:* All three resolution paths are tested. `alembic upgrade head` with no arguments migrates the database the product is actually configured to use, and cannot be pointed at a different one by a stale file.
- **DEC-346 — `S3ModelRegistry` publishes a version's files to `published_model_key(use_case_id, version, ...)` at register time, and owns nothing else.** *Context:* Phase 1 stores a model version as a row of keys pointing into the run directory that produced it. That is right while the model and the run are the same thing on one disk, and wrong the moment a run directory has a lifecycle: one bucket expiry rule and the champion of a use case loses its predictor while the registry goes on claiming to have one. *Decision:* `register` copies the files to `models/<use case>/<version>/…` — via `engine.storage.published_model_key`, called and never re-spelled — and stores those keys; the run directory is left exactly as it was, so `run.json` still points at its own artefacts. Publishing happens *before* the row is written: a missing `schema_key`, `run_config_key` or predictor directory is `RegistryError('MODEL_ARTEFACT_MISSING')` and the version is not registered at all, because a row for a model whose predictor is absent would be crowned by the champion rule and the first scoring run would be what discovered the truth. An optional key that names nothing — `drift_baseline_key`, which the register stage sets whether or not a baseline was written — keeps the key it had and is logged. A key that already is its published target is left alone, so re-registering a version read back out of the registry copies nothing. Copies are streamed with `shutil.copyfileobj` over `open_read`/`open_write`; a predictor directory is detected by whether anything is stored beneath it, because `exists()` is always False for a prefix. Everything else — `get`, `list_versions`, `get_champion`, `next_version`, `approve`, `promote`, `archive` — is delegated to `SqlRegistryStore` verbatim. *Consequences:* `models/<use case>/<version>/` is a prefix a lifecycle rule and an IAM condition can both be written against. Archiving does not delete files: ending their life is a lifecycle rule's job and is not something a mistake should be able to do. Idempotence is proved by deleting the run directory first, so any attempted copy would raise instead of quietly succeeding.
- **DEC-348 — The SageMaker Model Registry mirror is off by default, one way, and can never fail a registry write.** *Context:* An AWS-native team expects to find a model in the SageMaker Model Registry. This product's registry is not that and must not become it: the champion rule, the stale-approval refusal and the `pending_approval` state are this product's meaning of "approved", and letting a SageMaker approval change a champion would be two registries racing to own one decision. *Decision:* `SageMakerModelRegistryMirror.mirror(version)` writes and never reads; nothing here can change a champion. `SageMakerRegistryConfig.enabled` defaults to `False` and there is no `Settings` field for it, so a deployment that wants the mirror has to construct it deliberately — the right amount of friction for a write into a shared account. Every failure is caught and returned as `None`, logged with the exception's class name only, and `S3ModelRegistry._mirror` guards the call a second time so the promise holds even if this module is one day given a bug. The mirror is passed as an optional keyword to `S3ModelRegistry`, whose `(store, storage)` signature is unchanged, and the `ModelMirror` protocol is declared at the consumer so `s3_registry` never imports `sagemaker_registry`. Four lifecycle states map onto SageMaker's three words: `candidate` and `pending_approval` both become `PendingManualApproval`, because the difference between them is this registry's business and SageMaker has no word for it; `archived` becomes `Rejected` so a console reader never sees a retired model still marked approved. No `InferenceSpecification` is invented — it needs a `ModelDataUrl` pointing at a single `model.tar.gz` and this product publishes a predictor *directory* — so one is sent only when a deployment supplies both an image and a URL. *Consequences:* A disabled mirror makes no AWS call at all, asserted rather than assumed. A failing mirror leaves the registry write intact, and the failure log line is asserted to carry the exception class and not its message. The honesty limit is stated in the module docstring: the two calls were exercised against moto, never against real SageMaker.
- **DEC-380 — the log format is a Settings field, not a logging configuration of its own.** *Context:* A JSON rendering had to be selectable per deployment. The obvious alternatives are a logging.config dictConfig file, or a separate MARKETING_AI_LOG_CONFIG path. *Decision:* `configure_logging(level, *, log_format=...)` takes `Settings.log_format`, which is already in the frozen environment-variable table and already printed by `Settings.summary()`. No new environment variable, no configuration file. *Consequences:* One table still describes the whole deployment, and the format a process is writing in is visible in its own startup line. The cost is that an operator cannot reshape logging without a code change - which is the intended trade, because the shape is what the redaction guarantee is built on.
- **DEC-381 — the redaction guarantee is a class, not a convention - RedactingJsonFormatter must not override formatException.** *Context:* Plan 13.7 says an exception message is customer data because a library builds one out of the value that upset it. A second rendering is a second chance to leak it. *Decision:* `RedactingJsonFormatter` subclasses `RedactingFormatter` and deliberately does not define `formatException`. The inherited one is the only code in this repository that turns an exception into text, and it withholds every message. `tests/unit/test_logging_audit.py` asserts `"formatException" not in vars(RedactingJsonFormatter)` and that the attribute is identically `RedactingFormatter.formatException`. *Consequences:* A third rendering added later inherits the guarantee for free. Anybody who adds a `formatException` "just to put the traceback in a field of its own" fails a test that names the reason.
- **DEC-382 — the JSON payload is built from a closed allow-list, never from record.__dict__.** *Context:* The usual JSON formatter serialises `record.__dict__` minus a deny-list of the attributes `logging` itself sets. That fails in the worst direction: an attribute nobody here has heard of is serialised, and the unknown attribute is the one most likely to hold a value. *Decision:* `JSON_FIELDS` is the closed list of keys the formatter may write (time, level, logger, message, run_id, stage, client_id, exception). The payload is assembled key by key; there is no code path that reads the record's dictionary. *Consequences:* A LoggerAdapter payload, an `extra=` mapping, uvicorn's `client_addr` - none can be serialised by accident. A new field has to be added by hand, which is the point. A test logs with `extra={"offending_cell": SENTINEL, ...}`, asserts the value really is on the record, and asserts it is absent from the JSON.
- **DEC-383 — run identity reaches the record through a ContextVar and a handler-level logging.Filter.** *Context:* The alternatives were threading a bound logger through every stage signature, or a LoggerAdapter per run. *Decision:* `run_id`/`stage`/`client_id` live on a `ContextVar`; `ContextFilter` (installed on the handler by `configure_logging`, idempotently via `install_context_filter`) stamps all three onto every record, or None. It overwrites an attribute a caller attached, so the ContextVar is the single source. *Consequences:* No stage signature changes, and records pandas and botocore write on their own loggers are stamped too, because the filter sits at the sink rather than on one logger. A record cannot carry a forged run_id from a second, unaudited mechanism. The three fields are named identifiers rather than a free-form mapping, so there is nowhere a cell value could be smuggled in.
- **DEC-384 — the binding happens inside the job body, never around the submit.** *Context:* `ThreadPoolExecutor` starts its workers with a fresh context rather than a copy of the submitter's, so a ContextVar bound around `runner.submit(...)` is gone by the time the job runs. *Decision:* `bind_log_context` is documented as the job callable's first statement, and three tests drive a real `ThreadJobRunner` to prove it: a binding made inside the body reaches the log; a binding wrapped around the submit leaves `record.run_id is None`; and two jobs meeting at a `threading.Barrier` produce exactly two records whose run_ids are the two distinct ones. *Consequences:* The failure mode - a run whose lines are silently anonymous - is a test failure rather than something discovered in CloudWatch. The second test is written so that if CPython ever starts copying contextvars into workers, it fails and tells the reader the constraint has lifted.
- **DEC-385 — metrics are CloudWatch EMF log lines, not PutMetricData.** *Context:* Both would work. The difference is in permissions, in what runs on the run's thread, and in whether the API and a job need different code. *Decision:* `EmfMetricSink` writes one EMF JSON document per datapoint to stdout; the log driver already carrying the process's output to CloudWatch Logs carries it, and CloudWatch extracts the metrics. *Consequences:* It needs no new IAM permission - a SageMaker job role and an ECS task role already have the `logs:PutLogEvents` their driver uses, whereas `PutMetricData` would need a wildcard-resource `cloudwatch:PutMetricData` on both. It adds no synchronous signed HTTPS call to the thread that is in the middle of a stage (nothing to block, throttle or time out). And it is the same code from the API and from inside a job: no client, no region, no credentials. A laptop simply prints a line nothing consumes. Nothing in engine/aws/metrics.py imports boto3, which a test asserts by parsing the module.
- **DEC-386 — the EMF sink owns its stream and does not go through logging.** *Context:* Routing EMF through the application logger would be tidy, but `RedactingJsonFormatter` would wrap the document in another JSON object and destroy it. *Decision:* `EmfMetricSink` writes to a stream it holds (defaulting to `sys.stdout`, resolved on every write so `redirect_stdout` and pytest capture work), serialised by a lock held across one write plus one flush. *Consequences:* A metric line is a document CloudWatch parses, not a message a formatter may reshape. The lock is there because a partial line is not a metric - CloudWatch drops the whole document; a test runs four threads writing 25 datapoints each and asserts all 100 lines parse.
- **DEC-387 — one guard, in one place - a metric may never fail a run.** *Context:* A try/except at each call site is the version where the fifth call site eventually gets written without one. *Decision:* The public API is the `record_*` functions, and every one of them goes through a single `_emit` helper that catches `Exception` and logs it with `log_failure` (class name only). `MetricSink.emit` is the raw call and is allowed to raise. *Consequences:* A broken stream, a full disk or a badly written sink costs a datapoint, not a run. A parametrised test drives all five recording functions against a sink that raises `OSError("no space left on device")` and asserts the message never reaches the log, only `error=OSError`.
- **DEC-388 — JobCostUsd is emitted only where a real figure exists, and never as a zero.** *Context:* Plan 13.3. `CostEstimate.estimated_usd` is already null for a local run, for no billable time reported, and for no published rate. *Decision:* `record_job_cost` emits nothing when the estimate is None, when `estimated_usd` is None, or when it is <= 0. A genuine zero is dropped too: it can only come from zero billable seconds, and the rule "this graph never shows a zero" is worth more than that datapoint. *Consequences:* A point on a cost graph always means money was estimated to have been spent. "We do not know" is a gap, which is what it looks like. Parametrised tests cover no_estimate / unstateable / zero.
- **DEC-389 — LlmCostUsd is a hook that is off by default and reads nothing.** *Context:* The generative phase is absent from this repository: there is no Bedrock client, no model price table and no file to consult. *Decision:* `record_llm_cost(sink, *, model_id, usd, enabled=False)` exists so the call site can be written once, and returns immediately unless a caller passes both `enabled=True` and a figure it computed itself. `LlmCostUsd` is marked `alarmable=False`, so it gets a dashboard widget (labelled "reserved; no data yet") and no alarm. *Consequences:* Nothing is invented and no missing file is read - asserted by parsing the module for `open`/`read_text`/`load` calls and for boto3 imports, rather than by a substring search that could not tell the module's prose about boto3 from actual code. When the generative phase arrives it passes `enabled=settings.bedrock_enabled`.
- **DEC-390 — every datapoint is published under two dimension sets, coarse and detail.** *Context:* CloudWatch does not aggregate across dimensions: a datapoint stored under {Env, ClientId, Stage} is not readable as {Env, ClientId}. A metric emitted only with its detail could not be put on a dashboard without naming every stage, use case and backend by hand. *Decision:* EMF's `Dimensions` is a list of sets, so each document declares `[[Env, ClientId], [Env, ClientId, <Detail>]]`. Detail dimensions: UseCaseId for the run counters, Stage for durations, Backend for job cost, ModelId for the reserved LLM cost. A blank detail drops that set rather than sending an empty dimension value, which CloudWatch rejects. *Consequences:* Dashboards and alarms address the coarse set and need no substitution per use case; drill-down is free. A test asserts every dimension name a document declares has a value in its body - the mistake that produces a metric CloudWatch accepts and then silently drops.
- **DEC-391 — dashboard.json and alarms.json are generated from the metric registry and committed.** *Context:* Same argument as DEC-014 for the upload templates: a generated artefact that is not committed is one nobody reviews, and one that is committed but not checked drifts. *Decision:* `scripts/gen_dashboard.py` follows `scripts/gen_templates.py` exactly - a `write_*` returning an exit code, a `--out`, a `--check` that writes nothing and prints a unified diff. It reads `NAMESPACE`, `METRICS` and `COARSE_DIMENSIONS` from `engine.aws.metrics`; there is no second list of metric names anywhere. *Consequences:* A metric cannot be renamed in one place and left behind in the other. `render_alarms` additionally refuses an alarm naming a metric that is not in the registry. Tests assert widget-per-metric, no widget overlap within the 24-column grid, that the dashboard body has no key beyond `widgets` (PutDashboard validates the document), and that generating into an empty directory reproduces the committed bytes.
- **DEC-392 — a threshold nobody has measured stays a substitution, not a number.** *Context:* Plan 13.3. Two of the three alarm thresholds are things this repository has no basis for: how long a stage should take is a measurement never taken here, and how much a day should cost is a business decision nobody has stated. *Decision:* Those two thresholds are emitted as `${StageDurationSecondsAlarmThresholdSeconds}` and `${JobCostUsdDailyBudgetUsd}` - `Fn.sub`-compatible tokens a deployment must supply. Only `RunsFailed >= 1` is a literal, because a failed run is an event and is countable. Every alarm carries `threshold_source: literal|substitution`, and `alarms.json` carries an exhaustive `placeholders` table (also covering `${Env}` and `${ClientId}`). *Consequences:* No invented number is committed anywhere, and `Fn.sub` fails loudly on a token a stack did not supply. A test asserts the two unmeasured thresholds still match the placeholder pattern, and that the set of placeholders used across both files equals the set declared.
- **DEC-393 — every alarm carries a written rationale beside it.** *Context:* Statistic, period, evaluation count and datapoints-to-alarm are all choices made before this product has served a request. *Decision:* Each alarm in `alarms.json` has a `rationale` field that says in words that it is policy chosen before any traffic exists, and why that particular shape. A test asserts each rationale exists, exceeds 120 characters, and contains "POLICY" or "measurement". *Consequences:* Whoever tunes these later reads what the original reasoning was rather than guessing. The rationale is in the generated artefact, so it reaches the reviewer of the deployed alarm and not only the reader of the generator.
- **DEC-394 — CloudWatch limits are cited from the botocore model in this checkout.** *Context:* docs.aws.amazon.com is blocked by the egress proxy in this environment, so a documentation URL would be a number nobody here could check. *Decision:* `MAX_DIMENSIONS_PER_METRIC=30`, `MAX_METRIC_NAME_LENGTH=255` and `MAX_DIMENSION_VALUE_LENGTH=1024` each carry a docstring saying they are SERVICE LIMITS and naming the exact source: botocore 1.43.99, `botocore/data/cloudwatch/2010-08-01/service-2.json.gz`, shapes `Dimensions`/`MetricName`/`DimensionValue`. The docstring on the value-length constant separately says that *truncating* rather than dropping is this module's POLICY, not a limit. *Consequences:* Every number is version-pinned, offline and re-checkable by the next reader with one command. The service-limit/policy distinction the plan asks for is explicit on each constant.
- **DEC-395 — ClientId is always present, using a documented 'unset' placeholder.** *Context:* A deployment may not set `Settings.client_id`, and a metric whose dimension set changes shape depending on configuration is one no dashboard or alarm can address - the widget on {Env, ClientId} would simply show nothing, with no error anywhere. *Decision:* `UNSET_CLIENT_ID = "unset"` fills the dimension when `client_id` is None, documented as a policy placeholder and explicitly not a guess at who the client is. *Consequences:* The coarse dimension set has one constant shape, so the generated dashboard and alarms address it unconditionally. Nothing about a customer is fabricated - the label says only that the deployment did not name one.
- **DEC-396 — configure_logging keeps one handler and re-dresses it.** *Context:* It had to stay idempotent (an existing test counts root handlers) while gaining the ability to change format on a later call - the API configures a placeholder logger at import and re-configures from Settings once they are loaded. *Decision:* The module holds a reference to the one handler it owns. The handler is created on the first call only; the formatter and the context filter are (re)set on every call, and only on that handler - never on handlers the module did not create. *Consequences:* A process that configures text and then JSON writes each line once, not twice. pytest's and uvicorn's own root handlers are left alone. Tests assert the handler count is unchanged across a format switch and that repeated calls leave exactly one ContextFilter.
- **DEC-349 — The image runs the application from a source layout, not from an installed wheel.** *Context:* the obvious image `pip install`s the project into the virtualenv. `api/main.py` computes `UI_DIR = Path(__file__).resolve().parent.parent / "ui"` and `engine/config.py` resolves the configuration root the same way, and the wheel target in `pyproject.toml` packages only `engine`, `api` and `scripts` — it carries neither `ui/` nor `configs/` nor `templates/`. An installed-package image therefore resolves both into `site-packages/` and serves a 404 for `/ui`, silently. *Decision:* third-party wheels go into `/opt/venv`; the application is `COPY`ed to `/app` and reached through `PYTHONPATH=/app`. *Consequences:* the image serves the UI and finds its configs; `tests/unit/test_container_files.py` asserts the `COPY` lines and the absence of a `pip install .`, so the mistake cannot come back quietly. Anybody who later wants a wheel-based image has to change that line in `api/main.py` first, and say so.
- **DEC-350 — Image versions come from `requirements-freeze.txt` as a pip constraints file.** *Context:* letting the image resolve `[project].dependencies` on its own produces a second, independent resolution that can differ from the one the tests ran against. *Decision:* the builder generates the requirement list from `pyproject.toml` with `scripts/requirements_from_pyproject.py` and installs it with `-c requirements-freeze.txt --only-binary=:all:`. *Consequences:* the image's pins are the repository's pins; the generator is a real module rather than a `python -c` string inside a `RUN`, so it can be read, reviewed and tested; and an unknown extra name is an error rather than a silently empty group.
- **DEC-351 — `libgomp1` is installed, and both the base image and the package list are build arguments.** *Context:* measured inside a built image: `import lightgbm` dies with `OSError: libgomp.so.1: cannot open shared object file`. The copies that scikit-learn and xgboost bundle have mangled SONAMEs (`libgomp-e985bcbb.so.1.0.0`) and do not satisfy the lookup, so there is no in-wheel fallback. *Decision:* the layer installs `${RUNTIME_APT_PACKAGES}`, defaulting to `libgomp1`, on `${PYTHON_BASE}`, defaulting to `python:3.11-slim`. *Consequences:* the normal build is the normal build; an environment whose egress policy refuses the Debian archive can still build and test the image by naming a base that already carries the library. That is not hypothetical — it is the environment this was written in, where `deb.debian.org` answers 403 and the layer could not be built at all.
- **DEC-352 — One entrypoint script, which understands SageMaker's two different launch conventions.** *Context:* a Training job launches the container as `<image> train`, appending that literal word; a Processing job replaces the entrypoint outright with its `ContainerEntrypoint`. Getting this wrong is the classic SageMaker packaging mistake. *Decision:* `scripts/entrypoint.sh` dispatches on the first argument — `serve` for uvicorn, `train`/`job` for the job entrypoint, `migrate` for Alembic — and `exec "$@"` for anything else, so `docker run <image> bash` still works. *Consequences:* one image serves the API and runs both job types; an operator can run an ad-hoc command without a second image or an `--entrypoint` override.
- **DEC-353 — The health check uses the interpreter that is already there, not curl.** *Context:* a slim image has no curl, and installing one to serve a health check buys a dependency for nothing. *Decision:* `HEALTHCHECK` runs `python -c` against `/healthz`. The 120-second start period is a **chosen** default, because AutoGluon's import is heavy; it is not a measurement of this image's startup, and the first real deployment should replace it with one it timed. *Consequences:* no extra package, and the number is labelled so nobody mistakes it for evidence.
- **DEC-354 — Two Postgres services in the compose file, one of them deliberately not UTC.** *Context:* on a UTC server a naive datetime and an aware one are indistinguishable, so a timezone bug passes every test. *Decision:* `postgres` on 55432 and `postgres-tz` on 55433 running `postgres -c timezone=Asia/Kolkata`, both on tmpfs. *Consequences:* the fix in DEC-339 is proved rather than assumed — and it was: writing `12:00:00+00:00` into the old naive column read back `17:30:00` on the Kolkata server. A test database that survived a restart would be a test of the developer's machine, which is why both are disposable.
- **DEC-355 — A deployment names an image digest, never a tag.** *Context:* a tag can be moved after it has been tested — by a later build, by a person, by a retry — so a deployment that names one cannot say what it is running. *Decision:* `scripts/build_push_image.sh` pushes and then asks the registry what digest it stored (rather than trusting a local one, because a manifest list and a single-platform manifest have different digests), writes `<repo>@sha256:…` to `.image-digest`, and `make aws-deploy` passes that to `cdk deploy`. *Consequences:* what the smoke test passed is what the service runs, and a rollback is naming a previous digest.
- **DEC-356 — Deploying is manual and credential-free; CI is automatic and deploys nothing.** *Context:* Phase 4a's deployment model is one deployment per customer account. A push to a branch has no business changing somebody's infrastructure. *Decision:* `ci.yml` runs on every push — lint, the fast suite against a real Postgres service, `cdk synth`, cdk-nag, and the fast suite *inside the image* — and deploys nothing. `deploy-dev.yml` is `workflow_dispatch` only and assumes a role by OIDC, with no access key anywhere. *Consequences:* the expensive, irreversible action requires a human; `tests/unit/test_container_files.py` asserts both properties, including that no long-lived credential name appears in the workflow.
- **DEC-357 — `scripts/aws_bootstrap.py` probes each permission with one real call and reports the IAM action that would fix it.** *Context:* `cdk deploy` creates the resources but cannot show that the task role can use them: an IAM policy is a document, not a demonstration. *Decision:* one read-only-or-self-cleaning probe per concern — configuration loads, an object written/read/deleted under `_bootstrap/`, the database connects and migrates, a SageMaker `Describe` of a job name that does not exist (a role allowed to look gets `ValidationException`, one that is not gets `AccessDenied`) — each reported as a line, all of them run rather than stopping at the first failure. *Consequences:* an operator gets the whole list of what to grant, not one item at a time; the probe reports the exception's class and never its message, because an AWS error routinely quotes the resource and the principal (plan §13.7).
