# Decisions

The architecture decision log. `plan.md` is normative and the reference prototype fills its silences;
**every other choice is an entry here**, in the order it was made. Each entry states its **Context**
(what the plan and the prototype do and do not say), the **Decision** taken, and its **Consequences**.

Milestone 1 opens the log with DEC-001 … DEC-030 from the design, DEC-031 … DEC-035 from its integration and
DEC-036 … DEC-040 from its review. Later milestones append; entries are never rewritten
in place — a decision that is reversed gets a new entry that names the one it supersedes (plan §13.2).

Phase 3a, the generative and hybrid features, numbers its entries from **DEC-200** so that Phase 2's
work can land in the same log without either phase renumbering the other.

---

- **DEC-001 — `engine.yaml` has a non-merged `catalog` and a merged `defaults` block.** *Context:* plan §5 wants every default in `engine.yaml`, but engine constants (AutoGluon key map, presets, labels, markers) are not per-use-case settings. *Decision:* two top-level blocks; only `defaults` is merged into use cases; `catalog` is read-only engine data whose dict keys are enums. *Consequences:* one file to read; a use-case YAML cannot invent or remap a model family, a metric or a label.
- **DEC-002 — Merge semantics: deep for mappings, replace for lists, `null` clears; `extra="forbid"` everywhere.** *Context:* plan §5 says "merges" without defining list behaviour. *Decision:* §4.5 rules 1–5; unknown keys fail after the merge with the offending path. *Consequences:* `candidates: [LightGBM]` means exactly one candidate; no "unset" syntax is needed; documented in `docs/API.md`.
- **DEC-003 — Seven use cases, six files: industry entries carry `status: available | planned` plus `name`/`description` for planned ones.** *Context:* plan §1.2 lists seven, §3 lists six YAMLs; the overview must show the Onboarding stage and its card. *Decision:* §3.7 loader rules; planned entries have no config and expose `problem_type`/`entity`/`target` as `null`; `GET /use-cases/{planned}` is `404 USE_CASE_PLANNED`. *Consequences:* the overview matches the prototype without a fabricated config; promoting a use case is one word plus one file.
- **DEC-004 — Per-use-case defaults equal `defaultAdv()`; the only value change is `min_positive` 200.** *Context:* prototype `minpos: 500`, plan §4.1 says 200; other prototype pages hint at per-use-case values (consent filter for win-back, focal loss / "watch" drift for fault prediction) that `defaultAdv()` does not set. *Decision:* the plan wins for `min_positive`; every other advanced-setting default is `defaultAdv()`'s for all six use cases (no per-use-case `recently_contacted_days`, `control_group_fraction`, `retraining`, `imbalance`, `consent_column`, `reasons_per_row`). Allowed per-use-case differences are listed in §3's preamble. *Consequences:* `test_prototype_parity.py` pins 36 values for all six configs; win-back's "marketing opt-in only" outcome comes from the default `suppress_opted_out`.
- **DEC-005 — Fractions in config, `scale: 100` in the schema, config units on the wire.** *Context:* prototype stores 15/15/10; plan §5 stores 0.15/0.15/0.10. *Decision:* config and overrides are fractions; the schema field carries `scale: 100` and min/max/step in config units; the UI multiplies for display and divides on submit; the server never guesses units (a submitted `15` fails the range check). *Consequences:* one representation in every artefact; no ambiguous `0.5 = 50 % or 0.5 %` coercion.
- **DEC-006 — `evaluation.threshold` is `{mode, value}`; `fixed` is enforced by rejection, not mutation.** *Context:* the prototype's "Manual (below)" has no number. *Decision:* §2.2; `THRESHOLD_FIXED_NOT_HALF`; `value` always present (default 0.50); revealed by `visible_when`. *Consequences:* one extra stage-5 field; frozen models stay frozen.
- **DEC-007 — KPI formulas are a three-form mini-grammar, parsed at load, never evaluated in M1.** *Context:* plan §5 shows one formula and no grammar. *Decision:* `count_rows()`, `count_where_band_in([...])`, `sum_where_band_in("col", [...])`; band/column names validated against the config. *Consequences:* no `eval`; a new KPI shape is a deliberate engine change.
- **DEC-008 — `actions.bands` is canonical; `hi`/`md` are generated views; three bands everywhere.** *Context:* prototype keeps two numbers and, on two Output pages, shows illustrative four-band pill sets (`Critical` for fault prediction, `Very low` for payment propensity) that `defaultAdv()` never configures. *Decision:* §2.1; every shipped use case has `High 0.80 / Medium 0.50 / Low 0.00`; the schema emits one field per non-floor band, so a client restores the prototype's fourth band with one YAML line (e.g. `{name: Critical, min_score: 0.90, action: "Schedule visit"}` above `High`) and gets a third field with no UI change. *Consequences:* settings match the prototype's advanced settings exactly; Output-page pills read High/Medium/Low for those two use cases.
- **DEC-009 — Model families and metrics are restricted to the engine's six families and seven metrics; per-use-case lists are the prototype's lists intersected with them, in prototype order.** *Context:* prototype offers `Linear Learner`, `LSTM (sequence)`, `Isolation Forest (anomaly)`, `Uplift forest`, `Uplift (Qini)` and "Focal loss"; plan §6.3 fixes six families, §5 seven metrics, §1.3 defers uplift. *Decision:* `Linear Learner` is covered by `LogisticRegression`; LSTM, Isolation Forest, Uplift forest and Qini are dropped; fault prediction's intersection would be two families, so `LightGBM` is added (the engine's default gradient-boosting family; CatBoost is not added, keeping the deviation minimal) → `[XGBoost, LightGBM, RandomForest]`; win-back → `[LightGBM, XGBoost, LogisticRegression]` and metrics `[roc_auc, recall, f1]`; fault prediction keeps `imbalance: auto` (AutoGluon Tabular has no focal loss). *Consequences:* two use cases show fewer options than the prototype mock; sequence/anomaly/uplift models are a Phase 3 conversation.
- **DEC-010 — Family and metric labels live in the catalog; config stores ids.** *Context:* the prototype shows `Random Forest`, `Logistic Regression`, `ROC-AUC`; the plan stores `RandomForest`, `roc_auc`. *Decision:* `catalog.model_families[*].label`, `catalog.metrics[*].label`, `CHOICE_LABELS` for every UI enum; `AutoML (recommended)` is `catalog.automl_choice` with sentinel value `__automl__`. *Consequences:* no display string is ever a wire value or a config value.
- **DEC-011 — `NeuralNet` is the optional `nn` extra (torch), absent from every default list, greyed in the schema, rejected at config validation when torch is missing.** *Context:* ENV_FACTS — torch is not installed and pulls multiple GB. *Decision:* `nn = ["torch>=2.10,<2.14"]`; `catalog.model_families.NeuralNet.requires: [torch]`; `check_dependencies()` raises `MODEL_FAMILY_UNAVAILABLE` ("The Neural network model needs the optional 'nn' extra. Run `make setup EXTRAS=nn`, or deselect it.") for YAML and override selections alike; the schema shows the choice `enabled: false` with that help. *Consequences:* `make setup` stays fast; nobody discovers the missing dependency mid-training.
- **DEC-012 — Hybrid use cases are predictive in Phase 1 and carry no generative keys.** *Context:* `rca` and `win-back-campaign` are hybrid; plan §1.3 defers LLM work. *Decision:* `ai_type: hybrid` loads, validates, trains the tabular model and shows the eight stages; no `generative:` block exists in M1; `rca` keeps `complaint_text` in its template with `features.text_columns: ignore`. *Consequences:* Phase 3 adds an optional block, never changes an existing one.
- **DEC-013 — `mypy --strict` covers `engine/`, `api/` and `scripts/` globally; the only override is `ignore_missing_imports` for autogluon/shap/sklearn/imblearn.** *Context:* plan §13.6 requires strict on `engine/`; ENV_FACTS shows the rest passes; `strict` is not a valid per-module option. *Consequences:* one flag, no per-module strictness games; tests are outside `files`.
- **DEC-014 — Generated files (`templates/*.csv`, `templates/*_README.md`, `docs/API.md`) are committed and drift-checked.** *Context:* the plan says generate, not whether to commit. *Decision:* commit; `make lint` and `test_generated_files.py` run `--check`. *Consequences:* reviewable diffs; regeneration is mandatory before commit.
- **DEC-015 — `run_config.json` is `ResolvedConfig` with `overrides_applied`, per-leaf `sources` and `warnings`.** *Context:* plan §5 requires the merged result; the Model page shows the training setup. *Consequences:* the UI can mark user-changed values; a run is reproducible from one file.
- **DEC-016 — Storage keys are opaque posix strings validated by one gate; writes are atomic; `local_path()` is the only escape hatch.** *Context:* plan §2.1 principle 3 and the Phase 4 S3 swap. *Consequences:* `S3Storage` later materialises into a temp dir and nothing else changes.
- **DEC-017 — Job cancellation is cooperative.** *Context:* plan §8 has `POST /runs/{id}/cancel`; Python threads cannot be killed. *Decision:* a `CancelToken` per job; stages poll between steps; a pending job is cancelled outright. *Consequences:* cancel is near-instant between stages and bounded by AutoGluon's `time_limit` during training.
- **DEC-018 — `hatchling` is unpinned; `requirements-freeze.txt` is committed for the pin test.** *Context:* pins must come from the resolver, whose output has no build backend and lives outside the repo. *Consequences:* no invented pin; the pin test has input on a clean checkout.
- **DEC-019 — Per-use-case `metric_choices` and `candidate_pool` preserve the prototype's per-use-case order; `candidates` is the ticked subset.** *Context:* prototype `SETUP` orders metrics and models differently per use case; the plan is silent on ordering. *Decision:* both lists are validated as subsets of the catalog (metrics filtered by problem type) and `candidates ⊆ candidate_pool`. *Consequences:* the "Optimise for" select and the algorithm grid match the prototype; the engine default lists cover targeted-advertisement, payment-propensity and rca's pool without restating.
- **DEC-020 — `status.json` keeps the plan's 8/7 engine stages; each carries the prototype's Running-screen `group_label`.** *Context:* plan §6/§9 render every stage; the prototype shows five/four rows. *Decision:* `GROUP_LABELS` in `engine/pipeline.py`; the UI renders one row per distinct `group_label`; engine `title`s never reach the screen; the API's `running_rows` is derived from the same constants. *Consequences:* engine honesty and UI fidelity coexist; one source of truth.
- **DEC-021 — Two stage modules beyond plan §3's tree: `engine/stages/register.py` and `engine/stages/export.py`.** *Context:* plan §6.1/§6.2 list `register` and `export` stages but §3's tree has no module for them; `split` fits in `prepare.py` as the tree says. *Consequences:* every stage id has a home (`STAGE_MODULE_MAP`); no logic in M1.
- **DEC-022 — Setup copy lives in a mergeable `ui` block; page titles are per use case.** *Context:* mode labels/help, target label, dataset/columns hints, run-button text and the Data/Model/Output H1s are per-use-case (or per-ai-type) prototype copy. *Decision:* `defaults.ui` with `{entity}` substitution; use cases override `ui.pages`; the generative case overrides labels in its own file later. *Consequences:* copy changes are config changes; `ui` is immutable per run.
- **DEC-023 — Column-name references are not config-load errors.** *Context:* `split.time_column`, `consent_column`, `fairness_column`, `opt_out_column` name columns of a file the engine has not seen; plan §4.2 lets the user pick the time column and §6.3 makes `TIME_COLUMN_MISSING`/`CONSENT_COLUMN_MISSING` validate-stage errors. *Decision:* `time_based` with `time_column: null` loads and adds a `ResolvedConfig.warnings` entry; template cross-checks apply only when the template is non-empty and the name is set. *Consequences:* the UI can switch split type before picking a column and gets the plan's 409 later, not a 422 now.
- **DEC-024 — `GET /healthz`, `GET /use-cases/{id}/template_README.md`, and open CORS in Phase 1.** *Context:* plan §8 lists neither route; the UI is opened as a local file with no auth. *Consequences:* two extra routes in `docs/API.md`; CORS must be tightened before Phase 4 (noted in `docs/AWS_DEPLOYMENT.md`).
- **DEC-025 — Template columns carry a `role`.** *Context:* the README's "Required" section and the target/time/consent cross-checks need to know what each column is. *Decision:* `primary_key | time | feature | target | consent | contact` with the validators of §3. *Consequences:* templates and configs cannot disagree about the key or target.
- **DEC-026 — `""` means "not selected" only in the UI; optional column paths coerce `""` → `null` in overrides.** *Context:* prototype uses `""`; config uses `null`. *Consequences:* `str | None` semantics stay honest; the UI needs no change.
- **DEC-027 — One state vocabulary `pending | running | done | failed | cancelled (| skipped)` for runs, stages and jobs.** *Context:* plan §6 defines it for stages. *Consequences:* `RunState` in `engine.contracts` is the only state enum; `skipped` is stage-only.
- **DEC-028 — Registry semantics: `approve` promotes `pending_approval → champion`; `promote` is the manual override; demotion happens in the same transaction; `should_promote` is a pure function in `engine/registry.py`, not a Protocol method.** *Context:* plan §6.3/§8. *Consequences:* Phase 4 registries store facts only; the policy is tested without a database in M1.
- **DEC-029 — Override shapes and paths: nested or dotted, `OVERRIDABLE_PATHS` = schema paths + `EXTRA_OVERRIDABLE_PATHS`, `IMMUTABLE_PATHS`, index patches as the one exception to "lists replace".** *Context:* plan §8 shows nested overrides; the UI holds dotted schema paths; the bands need element addressing. *Consequences:* "advanced settings are exactly the fields of this schema" is enforced in both directions.
- **DEC-030 — New validation code `SUPPRESSION_COLUMN_MISSING` (warning).** *Context:* plan §13.4 requires every user-facing message to be in the validation table; suppression columns may be absent from a scoring file. *Consequences:* the table gains one row, documented in `docs/DATA_CONTRACT.md` when M2 writes it.
- **DEC-031 — `VALIDATION_CODES` has 19 entries: plan §6.3's 18 codes plus `SUPPRESSION_COLUMN_MISSING`.** *Context:* the M1 design counts "19 plan codes plus one"; plan §6.3's table has exactly 18 rows (`PK_MISSING` … `CONSENT_COLUMN_MISSING`) and no other code appears anywhere in the plan. *Decision:* the plan wins; `engine.contracts.VALIDATION_CODES` holds the 18 transcribed codes plus DEC-030's, and `tests/unit/test_contracts.py` pins the literal table and the count. *Consequences:* a nineteenth plan code, should M2 find one, is added to the contract, the test and the plan's table together; `ValidationCheck` rejects any code outside the set.
- **DEC-032 — `404 TEMPLATE_EMPTY` is raised as a FastAPI `HTTPException` carrying the same `{"detail": {"code", "message", "path"}}` body, not as a `ConfigError`.** *Context:* the design fixes the `ConfigError` codes that map to 404 to exactly `USE_CASE_NOT_FOUND | USE_CASE_PLANNED | INDUSTRY_NOT_FOUND` (every other code is 422) and, in the same section, requires `404 TEMPLATE_EMPTY` for a use case that declares no template columns; such a use case is not an invalid document, so 422 would be wrong. *Decision:* `api/routes/use_cases.py` raises `HTTPException(404, detail={code, message, path})`; the app's 404 code set stays verbatim. *Consequences:* clients see one error shape for every 4xx; the code is API-only and never enters `engine/`.
- **DEC-033 — The template download routes answer `HEAD`, registered explicitly and kept out of the OpenAPI schema.** *Context:* FastAPI's `APIRoute` does not add `HEAD` to a `GET` route (Starlette's plain `Route` does); the M1 verification checklist probes `template.csv` with `curl -I`, and download clients probe the headers before fetching the body. *Decision:* a stacked `@router.head(..., include_in_schema=False)` on the same handler for `template.csv` and `template_README.md`, so the headers are the `GET` headers by construction and the server drops the body; the endpoint table in `docs/API.md` documents resources only (`HEAD`/`OPTIONS` rows are never rendered). *Consequences:* `curl -I` returns `200` with `content-type`, `content-disposition`, `cache-control` and the exact `content-length`; the other routes stay `GET`-only until a client needs more.
- **DEC-034 — In `engine/contracts.py` a bare `X | None` field is required-but-nullable; only a field written `= None` is optional.** *Context:* the design's code blocks write `= None` where a default is intended and a bare `X | None` elsewhere (41 fields such as `SplitReport.time_column`, `EvaluationReport.calibration` and `RunError.stage`); the prototype shows "—" for a value that does not exist and plan §2.1 forbids fabricated values. *Decision:* producing stages state every nullable value explicitly (`stage=None` when a failure is not tied to a stage) instead of relying on a silent default; `RunRecord`, which the design gives as a prose table, keeps sensible defaults. *Consequences:* a stage that forgets a value fails at validation time, not on the screen; the Required column of `docs/API.md` shows the convention; M2+ stage code constructs artefacts with explicit nulls.
- **DEC-035 — Registry edge cases the plan and the design leave open.** *Context:* plan §6.3 fixes the champion rule and DEC-028 the transitions; neither says what a `0.0` champion score, a repeated `archive`, or SQLite's dropped timezone should do. *Decision:* `should_promote` treats a champion `test_score` of exactly `0.0` as beaten by any strictly better candidate (and by an equal one only when the rule is `0 %`) instead of dividing by zero; `archive` is idempotent and accepts a version in any status; rows are stored in UTC and `tzinfo` is re-attached on read so `ModelVersion`'s aware datetimes round-trip; a `UNIQUE(use_case_id, version)` clash surfaces as the driver's `IntegrityError` because stages call `next_version()`. *Consequences:* no policy hides in a database; a friendly code for a version clash is added only when an API needs one.
- **DEC-036 — `model_search.time_limit_minutes` accepts 1 … 240 in steps of 1.** *Context:* the prototype's widget is `num("limit","Time limit (min)",5,5,240)` (minimum 5, step 5) and the design's §2 table copied it; plan §10 requires the integration train flow to run "with `time_limit_minutes: 1` and `strategy: fast`", and a schema that rejects 1 cannot run the plan's own test. The plan wins over the prototype. *Decision:* `ge=1` on the field; `min: 1` and `step: 1` on the schema field (a step of 5 from a minimum of 1 would make the default 30 an off-step value in a browser number input). The default stays 30 and the ceiling 240. *Consequences:* `tests/unit/test_advanced_settings_schema.py` pins `(1, 240, 1)`; the UI spinner is finer than the mock's; a one-minute limit is only useful for smoke runs, which is exactly what the plan uses it for.
- **DEC-037 — The `LEAKAGE_SUSPECTED` name patterns are the plan's four, split into two catalog keys.** *Context:* plan §6.3 lists `*_date` after target, `churn*`, `converted*`, `outcome*`; the M1 design shipped `^(churn|converted|outcome|label|target)|_after$`, which adds `label`, `target` and `_after`, drops `*_date`, and still claimed to be the plan's list. *Decision:* `catalog.column_name_patterns.leakage` is exactly `^(churn|converted|outcome)`, checked on every column. The fourth pattern needs a column's position as well as its name, so it has its own key, `leakage_after_target: "_date$"`, read as "a `*_date` column placed after the target column in the header": features describe the entity as of the snapshot (plan §4.2), so a date recorded after the outcome is the answer in disguise. M2's validate stage applies the first pattern to every column and the second only to the columns that follow the target. `label`, `target` and `_after` are not added; a deployment that wants them edits the catalog regex. *Consequences:* the catalog says what the plan says and nothing more; this reading of "after target" is recorded here, and a data-driven refinement (date values later than the snapshot) would be a new entry.
- **DEC-038 — A `UseCaseConfig` carries the catalog it was validated against, exposed as `config.catalog`.** *Context:* `load_use_case(id, root)`, `load_industry(root)`, `resolve_config(root=…)` and `create_app(config_root=…)` all take a configuration root, but the cross-file rule `METRIC_NOT_FOR_PROBLEM`, `check_dependencies`, the `trainable_in_phase_1`/`marker` properties, the advanced-settings labels and the time-like column pattern read `get_catalog()` with no root, so an explicit root was validated and labelled against the default (or `$MARKETING_AI_CONFIG_DIR`) `engine.yaml`, and a missing default root broke loading from a valid explicit one; the design (§4.4) only foresaw the environment variable. *Decision:* the loaders validate with `context={"catalog": get_catalog(root)}`; `UseCaseConfig` keeps that catalog in a private attribute and every catalog-dependent helper reads `config.catalog`. A document validated without a root (a `UseCaseConfig(...)` literal, or `run_config.json` read back) gets the default root's catalog, as before. *Consequences:* `_validate_use_case(document, catalog=…)` is keyword-only and nothing outside `engine/config.py` changes its calls; two configs are equal only when their fields and their catalog agree; `tests/unit/test_config_loading.py` and `tests/integration/test_api_config.py` point the loaders and the app at a fixture root whose catalog differs from the checkout's and assert that it governs.
- **DEC-039 — A `problem_type` override re-derives `model_search.metric_choices` and `metric` from the catalog; `ResolvedConfig.sources` gains `"derived"`.** *Context:* plan §6.3 (`TARGET_NOT_BINARY`: "Offer switch to regression if numeric") and §9 (detected problem type with override) need the switch to work, and the prototype promises "Metrics and models will switch to regression defaults"; but a use case's `metric_choices` are written for its own problem type and are not overridable, so `{"problem_type": "regression"}` was rejected for every shipped use case whatever else the run sent. *Decision:* in `resolve_config`, when the merged document's `problem_type` has catalog metrics and the use case's `metric_choices` do not all fit it, `metric_choices` becomes `catalog.metrics_for(problem_type)` in catalog order and `metric` its first entry unless the run set `model_search.metric` itself (an explicit metric that does not fit is still `METRIC_NOT_IN_CHOICES`); the touched leaves are `"derived"` in `sources`, `overrides_applied` stays what the run sent, and a warning states the switch. Model families are untouched: every supported family handles both problem types. A YAML that pairs a problem type with the wrong metrics is still a `METRIC_NOT_FOR_PROBLEM` load error; only runs switch. *Consequences:* `run_config.json` records what the engine chose and why; the UI can show derived values apart from user-changed ones; `forecasting` and `clustering` have no catalog metrics and are left alone.
- **DEC-040 — `humanise_count` and `humanise_bytes` round like the prototype's JavaScript and extend it one unit upwards.** *Context:* the prototype's `fmtSize` shows KB with one decimal (`toFixed(1)`) and `fmtN` uses `Math.round`; JavaScript rounds a half up on the exact binary value where Python's `round` and `format` round it to even; M1 rendered whole kilobytes and `2500 → "2K"`. Neither prototype helper has a branch above MB/M, so a 2 GB upload (plan §4.1's ceiling) would read `2048.0 MB`. *Decision:* KB, MB and M use `Decimal(value).quantize(0.1, ROUND_HALF_UP)` on the exact float and K rounds the same way to an integer, so `1536 → "1.5 KB"`, an exact `1.25 MB → "1.3 MB"` and `2500 → "3K"`, as in the browser; the GB and B branches stay as the one deliberate extension; a negative value is formatted by magnitude and signed. *Consequences:* `tests/unit/test_utils.py` pins the JavaScript results, exact-half cases included; the API and the UI agree to the character.
- **DEC-041 — `mypy --strict` also covers `tests/fixtures/make_data.py`, and generated synthetic CSVs are gitignored.** *Context:* DEC-013 kept `tests/` out of `[tool.mypy].files` on the grounds that tests are not source. The synthetic generator is different in kind: it is test infrastructure that every M2, M3 and M4 test depends on for its inputs, so a silent type regression there would surface as confusing failures far from the cause. It was written strict-clean with no `Any`, and that is worth keeping rather than rediscovering. Separately, the generator defaults its output to a temporary directory outside the checkout, but a developer passing `--out-dir .` could stage large CSVs by accident. *Decision:* add `tests/fixtures/make_data.py` (the module only, not its tests) to `[tool.mypy].files`, keeping `tests/unit/test_pyproject_pins.py` in step since it asserts that list; and add `*_synthetic_*.csv` to `.gitignore`, the filename shape the generator always produces. *Consequences:* `make lint` now type-checks 35 files instead of 34; the rest of `tests/` stays untyped as DEC-013 intended; generated data cannot be committed by accident.
- **DEC-042 — `DatasetFingerprint`, `RunManifest` and `Recipe`: a run records what it did, on what data, at what cost.** *Context:* the artefacts of plan §7 are each shaped for a screen, and the champion rule compared a new test score against a number stored from an older run. Neither supports asking, later and mechanically, "which choices, on which data, produced which numbers?" A stored score is not comparable to a new one unless the data behind both is known to be the same, and nothing in the design recorded that. *Decision:* three additions. `DatasetFingerprint` (`hash`, `algorithm`, `n_rows`, `columns`) is computed at ingest, carried on `DatasetProfile`, and identifies the exact dataset a run consumed; the digest is sha256 rather than Python's `hash()`, which is salted per process and would not survive a restart. `RunManifest` (`run_manifest.json`) is one flat record written for EVERY run, train and score alike, and written even when a run fails, carrying whatever is known, because a failed attempt is evidence too; it holds `run_id`, `recipe`, `dataset_fingerprint`, `seed`, `metrics`, `leaderboard_path`, `duration_s`, `cost_estimate` and `created_at`. `Recipe` holds every training choice and nothing else, so that the same recipe on the same fingerprint yields the same model; `train(recipe)` is the only entry point to training. `CostEstimate.estimated_usd` is null for a local run rather than zero, since nothing was billed and a fabricated zero would be indistinguishable from a real measurement of free compute (plan §13.3). *Consequences:* three artefacts beyond plan §7, listed in `BEYOND_PLAN_SECTION_7` so a future addition has to be made consciously rather than absorbed silently; `DatasetProfile` gains a required field, which only `ingest` constructs; evaluation, actions, monitoring and governance settings are deliberately absent from `Recipe`, because they shape what happens to predictions rather than how a model is fitted.
- **DEC-043 — The evaluate stage takes only the model, the test data and the evaluation config.** *Context:* an evaluate stage that also reads prepare or model-search settings can only measure the model that the current run just built. *Decision:* evaluate consumes a scorer that carries its own decision threshold and its own calibration, both fitted at train time on the validation split; it fits nothing and selects nothing. The baseline is trained in the train stage and measured through the same call, with a pure composition function building the comparison from two evaluation reports. *Consequences:* any stored model can be re-scored on demand, which is what DEC-044 needs; evaluate becomes a pure function of its three arguments and is testable without a training run; a threshold can no longer be chosen on the test split, which was never legitimate anyway.
- **DEC-044 — Promotion re-scores the champion and the challenger on the same held-out data.** *Context:* the previous rule compared a challenger's fresh test score against the champion's stored score. Those two numbers came from different test splits, possibly different preprocessing and possibly a different population, so a challenger could win or lose for reasons unrelated to model quality. *Decision:* both models are scored on one frame, on the same metric, and only then compared; a stored score is never an input to the decision. The arithmetic in `should_promote` is unchanged, but its precondition is now that both scores come from the same evaluation frame. *Consequences:* promotion costs one extra scoring pass over the test split; the champion's predictor must be loadable, and the cases where it is not, or where its feature schema no longer fits the new data, are decided explicitly rather than by accident.
- **DEC-045 — The test split is final-decision-only.** *Context:* three-way splits are easy to erode: a threshold chosen here, a model picked there, and the hold-out quietly becomes a second validation set that flatters every number built on it. *Decision:* validation is where every selection happens: threshold, calibration, model choice, hyperparameters, features. The test split is measured once, for the promotion decision, and code that touches it carries a comment saying so. *Consequences:* the auto threshold is chosen on validation even though test is present in the same stage; reported test numbers keep their meaning as an estimate of unseen performance.
- **DEC-046 — Prepare is two phases with the split between them, and every statistic is fitted on the training rows.** *Context:* plan §6.1 orders the train flow `ingest → validate → prepare → split → train`, so the prepare stage never sees the split, and M3 read plan §6.3's "fit-on-train-only for anything statistical" as "fitted on the training file, never recomputed on the scoring file". That reading is too weak: a median or a 99th percentile measured over the whole uploaded file carries the validation and test rows into the values used for training, which is the leakage a three-way split exists to prevent, and it inflates the hold-out numbers the promotion decision of DEC-044 rests on. DEC-045 makes the test split final-decision-only, which the weaker reading quietly contradicts, and the user's instruction is explicit: fit all transforms on train only. *Decision:* prepare becomes two functions with a seam. `prepare_rows` applies everything that needs no fitted statistic and changes which rows exist — column exclusions, PII handling, the time-column cast, the consent filter, the missing-target drop, deduplication and the `missing_values: drop_rows` rule — and must run before the split, or a duplicate lands in one partition and its twin in another. `fit_transforms(..., fit_index=...)` fits the fill values and clip bounds **only on the rows `fit_index` names** (the training partition) and applies them to every partition; those are the transforms recorded in `prepare.json`, and `replay` still reproduces them from the recorded parameters alone. The stage list of plan §6.1 is not renumbered: the PREPARE stage is executed in two parts around SPLIT — `prepare_rows` → `split_dataset` → `fit_transforms(fit_index=parts["train"].index)` — and the partitions are re-sliced from the fitted frame by index. `prepare` keeps its signature as the single-frame convenience (every row a fit row), which is correct only for a frame that is entirely training data; the train pipeline may not call it. *Consequences:* no fill value or clip bound can be measured on a hold-out row, and every fitted transform records `fit_rows`, so `prepare.json` says what each parameter was fitted on; the split's fractions now apply to the rows that survive the row phase, and a row that is both an outlier and missing a feature is counted as a missing-value drop rather than an outlier, because `drop_rows` moved ahead of the split; a column whose values appear only outside the training rows is recorded as not applied instead of being filled from the hold-out; `outliers: remove_rows` still removes from every partition, using training bounds, so all three parts keep coming from one population; the Running screen is unchanged, because plan §6.1's prepare and split stages already share one group label; and `engine/pipeline.py` must adopt the three-call sequence when `run_train` lands, which is the only remaining caller-side work.
- **DEC-047 — Approval may only sign off the head-to-head it was actually taken on: `approve` refuses when the champion has changed.** *Context:* `LocalModelRegistry.approve` checked only that a version was `pending_approval`. `ModelVersion` recorded `previous_champion_id` and `improvement_pct` but nothing saying **which** champion the comparison that produced them was made against, so two versions could each beat champion C, one be approved and become champion, and the other then be crowned over it on the strength of a comparison with a model that no longer held the title. That is a promotion decided on a stored score from an older comparison, which plan §6.3's "beats the champion" and DEC-044 both forbid. *Decision:* the register stage records the champion a pending decision was measured against in `ModelVersion.measured_against_champion_id` — that champion's model id, the sentinel `NO_CHAMPION_AT_DECISION` (`"__none__"`) when there was no champion at the time, and null only for rows written before the field existed; `approve` compares it against the use case's current champion and refuses with `RegistryError("CHAMPION_CHANGED")` when they differ, naming both and saying to retrain, re-score or promote deliberately instead. A null is approved without the check, because such a row does not say what its decision was measured against. `api.routes.models` maps the new code to `409`, since the request is well formed and the version exists; an unmapped code would have been answered as a `500`. *Consequences:* a stale approval is a business refusal with a next step rather than a silent champion swap; `registry.db` gains a column, and Phase 1 has no migration tool, so a registry file written before this entry has to be recreated (plan §1.3 makes that a local development file, not client data); `promote` is unchanged and remains the recorded manual override for the cases where a human really does want to crown a version anyway.
- **DEC-048 — `predict` resolves its own model version and returns a record, not a series.** *Context:* the M1 stub was `predict(predictor_key, frame, config, *, storage) -> pd.Series`: the caller had already decided which model to load, and the stage's whole output was the scores. Every M4 finding about the score flow starts there. A caller that picks the model version picks it by its own rule — which is exactly how `POST /runs` came to accept a version belonging to another use case — and a stage that returns only scores forces its caller to re-derive everything else the run has to write: which version scored the file, how the rows were prepared, and how far they have moved from the training data. *Decision:* `predict(frame, config, *, run_id, storage, registry, model_version_id=None) -> PredictResult`. The stage takes the registry and answers the "which model" question itself through :func:`resolve_model_version`; `run_id` is the scoring run, so the drift report can name it; `model_version_id` is the user's explicit choice and defaults to the champion. `PredictResult` carries the resolved `model_version`, the loaded `scorer` (so `explain_rows` does not load the predictor a second time), the calibrated `scores` on the input frame's own index, the replayed `prepared` frame, the `prepare_report`, the `drift` report and the Running-screen `detail` line. *Consequences:* the stage is one call with one answer and no caller-side policy; `predictor_key` is no longer an input, so nothing can score with a predictor that no registry row points at; the pipeline assigns `frame[config.actions.score_field] = result.scores` and writes `result.drift` and `result.prepare_report` under the scoring run's key; the signature is now fixed for M4's `run_score`, and the stage still takes no `CancelToken`, which stays an open question for M7.
- **DEC-049 — A scoring run's `prepare.json` is the training run's, replayed and returned; there is no override.** *Context:* plan §6.3 says the score flow replays `prepare.json`, and plan §7 lists `prepare.json` as an artefact of a run directory. Those two readings pull apart: if the score flow ran its own prepare stage, a small scoring batch would re-derive column drops and re-fit fill values and clip bounds from the file being scored, and every customer's score would move relative to the run that chose the bands. But if it writes nothing, the Data page of a scoring run has nothing to render. *Decision:* the model chooses the preparation. The transforms come from the `prepare.json` of the run named by `ModelVersion.run_id`, read through `_prepare_report` and applied by `prepare.replay`, which measures nothing; a training run that kept no such record is `PREPARE_REPORT_NOT_SAVED` rather than a re-fit. That report is returned as `PredictResult.prepare_report` — it is already loaded, so returning it costs nothing — and the pipeline writes it unchanged under the scoring run's key. There is no run-level override of a model's preparation, by configuration or by request body. *Consequences:* a scoring run's `prepare.json` carries the *training* run's `run_id`, which is the truth about how those rows were prepared and lets a reader find the model's own run; the score flow's prepare stage does nothing that `predict` does not already do, so it must not re-fit; and a user who wants different preparation trains a new model, which is the only thing that can honestly change it.
- **DEC-050 — A model version named explicitly is scorable at any status; only the implicit choice has to be approved.** *Context:* `POST /runs` carries an optional `model_version_id`, and the registry has five statuses. Refusing everything but `champion` would make it impossible to re-score history with the model that produced it, or to try a candidate before approving it; accepting anything when *no* version was named would put unapproved numbers in front of a business user under the label of "the model". *Decision:* `resolve_model_version` honours a named version whatever its status — candidate, pending approval, champion or archived — and falls back to the use case's champion only when no version was named, refusing with `CHAMPION_NOT_FOUND` when there is none. A named version whose status is not `champion` is logged at INFO, and `run.json` records `model_version_id`, so a run scored with an unapproved model says so in both places. *Consequences:* re-scoring history and trying a candidate are ordinary operations rather than special cases; the only thing a status now controls is what happens when the user names nothing; and a version belonging to another use case is still refused, because a target that means something else is not a status question (`MODEL_USE_CASE_MISMATCH`).
- **DEC-051 — Drift is a reported signal, never a gate, and a comparison that cannot be made is reported as not measured.** *Context:* plan §6.3 asks for PSI per feature and a warning above the threshold, and says nothing about drift stopping a run. A stage that refused to score a drifted file would leave the user with no numbers at all precisely when the data has changed, which is when they most need to see them. Separately, PSI is a comparison between two distributions, and the arithmetic answers even when there is nothing to compare: a file with no rows leaves every baseline bin empty, which is the largest PSI the metric can produce, so a zero-row upload came back "drifted"; a baseline with no features sums over nothing, so it came back "PSI 0.00, stable". Both numbers describe the absence of data while reading as statements about the data. *Decision:* drift never blocks scoring — a run whose drift is high is scored, reported and logged at WARNING — and `compute_drift` returns `None`, "drift not measured", whenever no comparison happened: no stored baseline, no rows in the scored frame, or no features in the baseline. The reason is logged at WARNING with the model version, `PredictResult.drift` is `None`, and the Running-screen detail line ends "drift not measured" instead of a verdict. *Consequences:* `compute_drift` returns `DriftReport | None`, so a caller has to handle the not-measured case explicitly rather than reading a fabricated zero; `scoring_summary.json` already allows null drift fields, which is exactly this case; no verdict in the product is ever a statement about data that is not there; and a scoring file too small to be worth comparing is the user's decision to make, since the rows it does have are still scored.
- **DEC-052 — The score stage's failures are a code/message/suggestion table, and `POST /runs` maps those codes onto the envelope.** *Context:* plan §13.4 asks every user-facing error to carry a code, a message and a suggestion, and `engine/errors.py` does exactly that for the pipeline's own failures in `ENGINE_ERRORS`. `ScoreError` had seven codes that existed only as string literals at their raise sites: nothing could enumerate them, the API could not map them onto HTTP statuses without copying literals, and the generated documentation had no way to know they existed. Its docstring also still promised that the codes would collapse into `EngineError` "when `engine/errors.py` lands", which it has. *Decision:* `SCORE_ERRORS` maps each code to its message template and its suggestion, in the shape `ENGINE_ERRORS` already uses; every code is a module constant; `score_error(code, **values)` is the only way this module raises, so an unregistered code cannot reach a user; and `ScoreError.suggestion` is filled from the table the way `EngineError.suggestion` is. `api.routes.runs.SCORE_ERROR_STATUS` maps the codes the run endpoint can meet onto HTTP statuses, and an unmapped code is a `500` rather than a guessed 4xx, exactly as `api.routes.models.REGISTRY_STATUS` already does. The three coded exceptions stay separate classes: `engine.errors.run_error` already turns any of them into the `RunError` that reaches `status.json` by reading `code` and `message`, so collapsing them would buy nothing and would cost the reader the name of the stage to go to. *Consequences:* the codes are enumerable, testable and documentable; a new failure mode has to be written down before it can be raised; `RunError` still has no field for a suggestion, so a `ScoreError`'s suggestion goes no further than the exception object it is attached to - it reaches neither `status.json` nor the screen, which is exactly where DEC-072 leaves `EngineError.suggestion`.
- **DEC-053 — `approve` and `promote` stay two operations, not one endpoint with a flag.** *Context:* both end with the same champion swap, and plan §8 lists them separately without saying why. Merging them would have been less code. *Decision:* they mean different things and are kept apart. `approve` finishes a decision the engine already took — the register stage marked the version `pending_approval` because it *did* beat the re-scored champion and `governance.approval_required` held it back — so it applies only to that status, takes no reason, and is refused when the comparison behind it has gone stale (DEC-047). `promote` overrides the champion rule by hand from any state the registry deems eligible, so it requires a `reason`, which is stored as `promotion_note` and is the only record of why the rule was set aside. A version that is promoted records `promoted_by`/`promoted_at` and no approver; a version that is approved records `approved_by`/`approved_at` and no note. *Consequences:* the audit trail distinguishes "a human said yes to the engine's decision" from "a human overruled it", which is the distinction a governance review actually asks about; `approve` can be made stricter (as DEC-047 did) without taking away the deliberate escape hatch; and the UI has one button per meaning rather than one button with a mode.
- **DEC-054 — One resolver answers "which model scores this file", and one code says "there is no champion".** *Context:* the question was answered twice. `engine.stages.score` resolved the champion or the named version with the full rule, while `api.routes.runs.score_schema` re-derived it from the registry with a laxer one of its own: it accepted any `model_version_id` the registry knew, including a version belonging to **another use case**. Such a run was accepted, validated against a foreign model's schema and then failed halfway through at the predict stage. The same split produced two machine codes for one condition — the endpoint's `NO_CHAMPION_MODEL` and the stage's `CHAMPION_NOT_FOUND` — so a caller switching on the code had to know both. *Decision:* `engine.stages.score.resolve_model_version` is the single source of truth, and `POST /runs` calls it before it accepts a scoring run, mapping its codes onto HTTP statuses (`CHAMPION_NOT_FOUND` → 409, `MODEL_USE_CASE_MISMATCH` → 409, `MODEL_NOT_FOUND` → 404) and reporting the stage's own message. `NO_CHAMPION_MODEL` is retired; `CHAMPION_NOT_FOUND` is the one code for "this use case has no champion", wherever it is met. *Consequences:* a version the endpoint accepts is one the stage will score, and a version it refuses is refused before a run directory exists, with the sentence the engine would have used; a `model_version_id` that names nothing is now a `404` about that id rather than a `409` about a champion; and the resolver's rules can only change in one place.
- **DEC-055 — "Who approved this" is a caller-supplied string, required and unverified.** *Context:* plan §1.3 and plan §14 leave Phase 1 without authentication, and `approve`/`promote` both write a name into the registry row that is the audit trail for a champion swap. There were three options: invent a name (`"system"`, `"local user"`), allow the field to be empty, or require the caller to supply one. *Decision:* `approved_by` and `promoted_by` are required, non-blank and stored verbatim; a request without one is a `422`, and the API neither verifies the value nor substitutes one of its own. Both the route docstrings and this entry say plainly that the value is a claim, not an identity. *Consequences:* the audit trail records what the caller claimed rather than something the API made up, which is the honest version of an unauthenticated Phase 1 (plan §13.3); it is not evidence of who really acted, and must not be presented as such in the UI; and when authentication lands in a later phase the field becomes verified in place, with no change to the registry schema or to the routes' shapes.
- **DEC-056 — No row leaves the explain stage without a reason: the tiers retry per row, and general reasons are the floor.** *Context:* `reasons_for_row` refuses to build a reason out of a zero contribution, which is right - a feature that did not move the score did not explain it - but `reasons_for` then let the resulting empty tuple through, and a row whose every contribution measured zero reached `scores.csv` with blank reason cells. Plan §6.2 and plan §10 both require a reason on every scored row, and `tests/integration/test_score_flow.py` asserted it; the module's own docstring meanwhile said an unexplained row "is the prototype's -". Two parts of the repository disagreed and the tests were red. A saturated prediction is the usual cause: when the model answers 0.0 whatever one feature does, every single-feature contribution really is zero, so the measurement is correct and it is the *handling* that was wrong. *Decision:* three things, in order. (1) The tiers of plan §6.3 now run per row as well as per run: a row a tier explained and could not move is handed to the next tier, on its own, rather than the whole frame falling to the next tier or none of it. (2) A row no tier can move keeps **general** reasons - the run's most important features, carrying that row's own values, `Direction.NONE`, a contribution of `0.0` and `(general)` in the sentence - ranked by the training run's `feature_importance.json`, else by the mean absolute contribution over the rows this run did measure, else by feature order. Nothing there is claimed to be measured on the row, because nothing was. (3) A row a tier never *covered* is not retried: the KernelSHAP sample is a coverage decision the caller's `max_rows` budget already made, and the train flow's sampled chart keeps exactly the rows it kept before. The count is reported rather than hidden: `RowReasons.fallback_rows`, `RowExplanation.method`, `ScoringSummary.rows_with_fallback_reasons`, the Running detail line and a "Reasons" row on the Output page. `Direction.NONE` and `ReasonMethod` are new in `engine/contracts.py`; `row_explanations.parquet` gains a `method` column. *Consequences:* the guarantee plan §6.2 states is now structural rather than probabilistic, and `make test-all` is green; a general reason is visibly weaker than a measured one, so the Output page does not read as though a saturated row was understood; `rows_with_fallback_reasons` is the signal that a model has saturated over part of its input, which is worth seeing rather than smoothing away; and the score flow now reads the training run's importance chart, which also improves the permutation tier's feature choice and its tie-breaks.
- **DEC-057 — `SCHEMA_MISMATCH` compares a scoring file against the champion's saved schema: a missing or retyped column is an error, an extra column only a warning, and the target is never reported missing.** *Context:* plan §4.4 says scoring "validates the new file against it and reports every missing, extra or type-mismatched column by name", and plan §6.3's table gives `SCHEMA_MISMATCH` one severity, `error`. Three things that happen on ordinary uploads are left undecided by both. A file to be scored has no outcome, so the target column is always absent against the training schema and a literal reading would refuse every correct file. An extra column the model was never fitted on is harmless, because scoring ignores it, but the single severity would refuse that file too. And a column read as `int64` when the model was trained and as `float64` in the file being scored is the same column, while a naive equality test calls it a type change. *Decision:* `check_schema_mismatch` runs in score mode only and skips with `"no schema given"` when `params.schema is None`. `missing` lists the required schema columns absent from the frame and explicitly excludes `schema.target`; `extra` lists frame columns the schema does not name, excluding the primary key; `type_changed` is decided by `types_compatible`, which is true for equal types and for two types sitting in one widening group (`_NUMERIC_TYPES`, `_TEMPORAL_TYPES`, `_TEXTUAL_TYPES`), so `int → float` is not a mismatch. Missing or retyped columns produce one `Severity.ERROR` finding that names every offending column in its message and is not acknowledgeable; extra columns alone produce one acknowledgeable `Severity.WARNING` saying they will be ignored while scoring; `details` carries `missing`, `extra`, `type_changed`, `model_version_id` and `expected_columns` whichever branch fired. *Consequences:* scoring a file that still carries the outcome column, or one with columns the model never saw, is an ordinary operation rather than a refusal, while a genuinely absent feature is a single `409` listing every problem column at once instead of one finding per column; `details.expected_columns` hands the Setup screen the full training column list without a second request, which is what lets the suggestion point at the template; a dtype that merely widened between two uploads of the same data cannot fail a run; and the cost is that a scoring file may differ from its training file in ways this check calls compatible, so the scored population is only as close to the trained one as drift reporting (DEC-051) says it is. The number was briefly reused in the working tree for today's AutoGluon HPO work; that second decision was renumbered before it was committed (`f921f46`) and is DEC-073, so DEC-057 means the schema comparison and nothing else.
- **DEC-058 — The `409` from `POST /runs` is M1's error envelope plus the whole `ValidationReport` under a sibling `validation` key.** *Context:* plan §8 says only "409 + validation.json on errors" and plan §9.2 says "On `409`, render the validation list inline with the confirmation controls"; neither fixes the body. M1 had already fixed one shape for every error response — `ErrorResponse`, "one `detail` object, never a bare string" — and the Setup screen needs the sentence *and* every finding, with its acknowledge token and its suggested override, out of a single response. Nesting the report inside `detail` would have made this one 4xx a different kind of body from every other; replacing the envelope with the report would have broken the client's one error path. *Decision:* `api.schemas.ValidationErrorResponse` has exactly two fields, `detail: ErrorBody` and `validation: ValidationReport`, and `api.routes.runs.validation_conflict` is the only thing that builds it: code `VALIDATION_FAILED`, a message pluralised off `report.error_count` ("{n} problem(s) must be fixed before this data can be used."), `path` null, and the report verbatim beside it, returned as a `JSONResponse` with status 409. Validation is synchronous on the request thread (plan §8), so the report is already in hand when the response is written. *Consequences:* a client that knows only `detail` still reads a coded, business-language sentence out of this 409, and one that knows `validation` renders the list, the acknowledgements and the override suggestions with no second request; the envelope stays the single documented shape for every other error, so nothing else in the app has to special-case it; and the body carries the same model `validation.json` holds, so the screen and the artefact cannot describe one run differently. This number was also briefly reused in the working tree for today's advisory-settings work, which was renumbered before it was committed (`f921f46`) and is DEC-074.
- **DEC-060 — The M2 training job replays ingest and validate onto `status.json` for real, then stops at `prepare` with a coded error.** *Context:* M2 owned `ingest` and `validate`; `prepare` and everything after it did not exist yet. Both obvious options were wrong. Letting the job raise `NotImplementedError` puts an untyped crash and a traceback where the Running screen reads a failure, which plan §13.4 forbids of anything user-facing. Leaving the later stages `pending` for ever, or marking them `running`, shows a pipeline state nobody measured, which is plan §13.3 applied to a half-built engine. *Decision:* `build_m2_job` in `api/routes/runs.py` returns a job that sets the run `RUNNING`, marks `INGEST` running and then `DONE` with `ingest.ingest_detail(profile)`, marks `VALIDATE` — or `VALIDATE_AGAINST_SCHEMA`, chosen by mode — running and then `DONE` with `validate.validation_detail(report)`, and then writes one `RunError`, code `STAGE_NOT_IMPLEMENTED` and message "Preparing features is not built yet.", onto both the `PREPARE` stage and the run, each `FAILED`. Both detail lines are computed from the profile and the report that the synchronous request already produced, so no number on the screen was invented for the job; `cancel.raise_if_cancelled()` runs between every step, and `JobCancelledError` cancels the run before re-raising. *Consequences:* an M2 training run shows two stages with real row counts and real finding counts and then a named, coded stop in a sentence a business user can read; the stop is one function M3 replaces wholesale rather than a set of stubs spread through the stage modules; a cancel issued during the replay still ends the run as `cancelled` rather than `failed`; and the cost is that the two detail lines are a replay rather than a live measurement, which is honest only because the work really was done moments earlier on the request thread.
- **DEC-061 — `ARTEFACT_REGISTRY` documents run-directory artefacts only, so `upload.json` deliberately stays out of it.** *Context:* `UploadRecord` is a frozen, extra-forbidding `Artefact` subclass like every other document the engine writes, so adding it to `engine.contracts.ARTEFACT_REGISTRY` looked like the obvious way to give it a model lookup. That map has a second job, though: `GET /runs/{id}/artefacts/{name}` whitelists the requested name against it — "a whitelist, not a path join" — and the generated artefact documentation is built from it. An upload is not a run: plan §7 opens "Every run directory `data/runs/<run_id>/` contains, at most:" and lists twenty filenames, none of them `upload.json`. *Decision:* the registry holds exactly those twenty run-directory filenames and nothing else; `UploadRecord` keeps its `Artefact` base and stays out of the map, with the reason written at its definition. *Consequences:* an upload record cannot be fetched through a run's artefact route, where it does not belong, and that route's whitelist keeps meaning "a file this run directory may contain"; the generated documentation stays a description of a run directory rather than of every JSON document in the system; and the cost is that `upload.json` has no entry in the one map pairing a filename with its model, so the two routers that read it name `UploadRecord` directly.
- **DEC-062 — Columns the engine governs rather than learns from are exempt from every leakage branch.** *Context:* plan §6.3's `LEAKAGE_SUSPECTED` row describes the detection — a single column above 0.98 AUC, or a name matching `churn*`, `converted*`, `outcome*`, or `*_date` after the target — and says nothing about which columns may be accused. Taken literally it accuses the target, which predicts itself perfectly, and it accuses shipped targets by name: `converted_30d`, `churn_next_60d` and the Telco file's own `Churn` all match the configured pattern, so a perfectly clean upload for those use cases would be refused with a `409`. *Decision:* `leakage_exempt_names` returns the target and every one of its aliases, the primary key, the six columns the engine governs rather than learns from — time, group, consent, opt-out, recently-contacted and fairness — and anything the user has already excluded; `candidate_columns` subtracts that set once, and all three branches (name pattern, per-column AUC and the whole-frame baseline) read exactly its result, so no branch can flag an exempt column. Every exempt column has a check of its own, so the rule redirects a column to the right message rather than silencing it. *Consequences:* the shipped use cases validate clean, which `test_clean_never_flags_the_target` pins with a companion test asserting that at least one shipped target really does trip the pattern, so the regression test cannot pass for the wrong reason; a duplicate identifier still surfaces as `PK_NOT_UNIQUE` and an absent consent column still surfaces as `CONSENT_COLUMN_MISSING`, so nothing is hidden; excluding a column in response to a finding also stops it being accused, which makes acting on the suggestion idempotent; and the cost is that a genuinely leaky column named like a consent or time column is never examined, which is accepted because those names are the engine's own vocabulary rather than the user's.
- **DEC-063 — `LEAKAGE_SUSPECTED`'s severity comes from the branch that fired: a measured AUC is an error, a name match only a warning, and an AUC hit supersedes a name hit on the same column.** *Context:* plan §6.3 gives the code one blended severity — "warning, becomes error unless user confirms" — for branches of very different strength. A column measured above the AUC threshold is evidence about the data in front of the engine. A column matching `^(churn|converted|outcome)`, or sitting to the right of the target with a `_date` suffix, is evidence about a name and a position only: `win-back-campaign` ships `churn_reason`, a legitimate pre-outcome feature, and header order is the only signal a file carries about the after-target case. Blocking a run on either of those refuses legitimate data. *Decision:* the finding loop in `check_leakage_suspected` is an `if/elif` over one candidate set — a column in `scored` is reported `reason="auc"` at `Severity.ERROR` carrying the measured number, and a column only in `named` is reported `reason="name_pattern"` or `"after_target"` at `Severity.WARNING` with `auc` null and the pattern that matched. The `elif` is the supersession rule: a column that both matches a pattern and measures above the threshold is reported once, as the error, with the number. All three are acknowledgeable, and every finding carries `override_path: "prepare.exclude_columns"`, the exact `override_value` to send back and an `acknowledge` token, so the user is offered the same next step whichever branch fired. *Consequences:* a name-based hit informs the Data page without blocking the run and `report.passed` stays true, while a measured hit blocks until the user confirms, which is the distinction plan §6.3's single row could not express; the name branch still fires on an upload too small for the AUC branch to run, so plan §8's `409` path holds even on a file that was never fully read; the cost is that two findings of one code can carry two severities, so a caller must read `details.reason` rather than assume the code's declared severity. The citation is a test section header rather than a docstring at the implementation, so this entry states the rule from `engine/stages/validate.py` and its reasoning from the tests that pin each branch.
- **DEC-065 — A check knows about data, not about a request: every check is a pure function of a frame and a flat, fully-defaulted `CheckParams`.** *Context:* plan §6.3 specifies eighteen checks as rules about a file, but every one of them needs settings that live in a `UseCaseConfig` — patterns, thresholds, column names, the problem type. The obvious implementation passes the config in, and with it the storage, the profile, the upload and the run, so that a check cannot be exercised without building a whole request and cannot be used anywhere but at the moment a file is uploaded. *Decision:* every check takes a `pandas.DataFrame` and a frozen `CheckParams` whose every field has a default, and returns a `CheckResult`. It never sees a `UseCaseConfig`, a `Storage`, a `DatasetProfile`, a run, an upload or the clock, so `check(df, CheckParams())` is always legal. Three layers compose them: `run_checks` derives the frame facts once, runs the checks of a mode in plan §6.3's table order, swallows any exception a check raises and sorts the findings errors-first; `validate_frame` adds acknowledgements and the counted report; `validate_for_training` and `validate_against_schema` are the run-level conveniences the API calls. `params_from_config` is the only place a `UseCaseConfig` is read, and the catalog defaults are restated as module constants so `CheckParams()` needs neither a config nor a catalog read. *Consequences:* every check is unit-testable from a literal frame, which is how the whole check table is covered; a check that raises costs its own finding rather than the upload; the same checks can later be re-run over engineered features, because nothing in them knows what an upload is; nothing here raises on bad data (plan §6.3) and nothing here logs a data value (plan §13.7); and the one concession is written in place — `_ingest_helpers` imports `detect_pii` from the ingest stage inside a function body, so PII detection has exactly one definition in the engine without adding a module-level edge that the import-graph test forbids.
- **DEC-066 — A third leakage branch: an out-of-fold logistic regression over every candidate column at once, reported as a warning that names no column.** *Context:* plan §6.3's `LEAKAGE_SUSPECTED` is entirely single-column — "a single column predicts the target with AUC > 0.98" — and leakage is frequently not single-column. Two columns whose sum reproduces the outcome each pass the per-column test and give the answer away together, which is the shape a joined table usually leaks in. *Decision:* when the per-column branch found nothing and `leakage_baseline` is on, `baseline_auc` fits an L2 logistic regression over the candidate columns and returns its out-of-fold ROC-AUC together with every feature's mean absolute standardised coefficient. Above the same threshold the check emits one `Severity.WARNING` finding with **no** `column` — "The data predicts '{target}' almost perfectly ({auc:.1%} AUC) with a simple model, even though no single column does." — carrying `reason: "baseline"`, the model, the fold count, the number of features used and the top three by weight, acknowledged by the bare code rather than by `CODE:column`, because no single column is being accused. Out-of-fold is the correctness condition rather than an optimisation: an in-sample L2 fit with 200 standardised features can exceed 0.98 on clean data by overfitting alone and would fire on every wide upload. The branch guards itself — no target, fewer than 100 sampled rows, no resolvable positive label, or fewer than 30 rows in either class, all return "not measured" — caps the design matrix at 200 features, skips high-cardinality text columns, and seeds `StratifiedKFold` from `params.seed`, which comes from the upload id, so one file gives the same verdict in every process. *Consequences:* distributed leakage is caught, and is never an error, because the evidence names no column the user could exclude; the branch is suppressed whenever a per-column hit already fired, so one file never produces both accusations; `leakage_baseline` switches off this branch alone while `leakage_check` still switches off the whole check; the cost is a `scikit-learn` fit over the sampled frame during validation, which is why `sklearn` is imported inside the function so `import engine` stays fast. The citation is a test section header rather than a docstring at the implementation, so the reasoning here is taken from `baseline_auc`'s own docstring and from the tests that pin each property.
- **DEC-067 — The product never names an artefact, a method or a number that did not actually happen; this number was reused for two separate applications of that rule, in two milestones.** *Context:* the number is cited from two unrelated places and both citations are real, so this entry covers both rather than documenting one and leaving the other a dead link; renumbering was rejected because the citations in the code are the fixed points. Facet (a), M2, `api/routes/runs.py`: `run_manifest.json` had to be named in the API before M3 wrote it, because the artefact route needs a constant for it, and a freshly created run that advertised a manifest it had not written would be claiming an artefact that does not exist. Facet (b), M3, `engine/stages/explain.py`: the global chart is AutoGluon permutation importance on the test split (plan §6.3) while the per-row tiers use TreeSHAP or KernelSHAP, so a caption reading "SHAP importance" would name a method that chart never ran. *Decision:* for (a), `RUN_MANIFEST_FILENAME` is defined and documented as reserved but is pointedly left out of `CREATED_ARTEFACTS`, the tuple `RunRecord.artefacts` is built from at creation; the file becomes fetchable on its own the moment it exists, because `read_artefact` whitelists against `engine.contracts.ARTEFACT_REGISTRY`, which has carried `run_manifest.json` since DEC-042. For (b), `IMPORTANCE_CAPTION` is "Permutation importance on the test split (%)" and `global_importance` attaches it to the chart that method produced, with `IMPORTANCE_UNAVAILABLE_CAPTION` — "Feature importance could not be computed for this model." — on the empty chart, so absence is stated rather than filled in. Both are plan §13.3 applied to a name rather than to a number. *Consequences:* a run created under M2 listed exactly the five files it had written and M3 only added to that map, so no client ever saw a 404 for an artefact a run had advertised; the caption under the importance chart is a claim about the method that actually ran, which is what makes `FeatureImportance.caption` worth being a contractual field; and the cost of the reuse is this entry — one number answers two citations, and a reader following either lands on both facets rather than on the wrong one.
- **DEC-068 — A failure in the explain stage is never fatal: the chart comes back empty with a caption that says so.** *Context:* `explain` is the seventh of plan §6.1's eight training stages, so the fitted model, the leaderboard and the evaluation are all on disk by the time it runs, and its inputs are the ones most likely to fail for reasons that have nothing to do with the model — permutation importance re-scores a shuffled hold-out under a time limit, the predictor has to be loaded back off storage, and the frame has to carry the label column for AutoGluon to shuffle anything at all. Failing the run there throws away a real model for the sake of a chart. *Decision:* `global_importance` wraps the whole computation in `try`/`except Exception`, logs at WARNING with `exc_info=True` and returns `unavailable_importance(run_id)` — no items, `top_n` zero, and the caption "Feature importance could not be computed for this model." It takes the same exit, with its own log line, when the hold-out frame carries no target column, and `build_feature_importance` returns the same empty chart for an importance frame with no rows. The per-row tiers follow the same rule: a tier that raises is logged at WARNING and the next one runs, and `RowReasons` carries the tier that actually produced the numbers. *Consequences:* a model that trained successfully is always registered and always scorable, whatever the explanation did; the Output page renders an honest statement of absence rather than a blank panel or a fabricated bar chart, which is plan §13.3 applied to the empty case; the traceback goes to the log, where plan §13.7 wants it, and never into an artefact a user reads; and the cost is that a broken explanation is quiet — it shows up in a caption and a WARNING rather than in the run's state — so a chart that is empty on every run is a log line somebody has to go and read.
- **DEC-069 — The TreeSHAP tier reaches into private AutoGluon API, so the whole tier is guarded by a bare `except Exception` and falls through to the next one.** *Context:* plan §6.3's first explanation tier is exact TreeSHAP on the best single tree model, and AutoGluon exposes no public way to reach that model: `_tree_shap` walks `predictor._trainer`, unwraps the bagged wrapper, calls `predictor.transform_features` and `model.preprocess`, and hands `model.model` to `shap.TreeExplainer`. Every one of those is an AutoGluon or `shap` internal that no test in this repository can pin across versions, and plan §13.8 says to follow the installed version rather than to assume the plan's API names. A bare `except Exception` is normally a smell, which is exactly why the choice has to be recorded rather than left to look like carelessness. *Decision:* the whole tier body sits in one `try`, and any exception at all is logged at WARNING with `exc_info=True` and returns `None` — the same answer the tier gives when there is no tree model to explain — so the caller runs KernelSHAP, and failing that the permutation tier, which needs no `shap` at all and therefore always works. `TREE_FAMILIES` bounds the tier up front to `XGBoost`, `LightGBM`, `RandomForest` and `CatBoost`, so the guard exists for version drift rather than for the ordinary case of a model TreeSHAP cannot explain. *Consequences:* an AutoGluon upgrade that moves a private attribute costs a run its exact explanation and buys it a slower approximate one, never a failed run, and `RowReasons.method` names on the Running screen which tier actually answered, so the degradation is visible rather than silent; the traceback reaches the log and not the user; and the price of the broad `except` is that a genuine bug inside the tier is swallowed too, which is why the log line carries the full traceback and why each fallback tier is tested on its own.
- **DEC-070 — `Reason.text` is built from the feature, its value and the measured direction, and from nothing else; the plan's `"12 visits"` unit is not rendered.** *Context:* plan §6.3 gives the reason sentence as `"visits_last_7d ↑ (12 visits)"`. The unit `"visits"` is in no config, in no column and in no template, so to print it the engine would have to guess a noun from a column name — exactly what plan §13.3 forbids in a code path that reaches the UI, and a departure plan §13.9 asks be written down rather than silently made. *Decision:* `reason_text(feature, value, direction, *, numeric, missing)` is the one renderer and `_reason` its only caller, so every sentence in `scores.csv` comes through it. A numeric contribution renders `"visits_last_7d ↑ (12)"`, with `↑` or `↓` by measured direction; a categorical one renders `"plan_tier = basic"`; an absent value renders `"last_contacted_at missing"`, and `missing` is a separate argument precisely so that a categorical level literally spelled `"missing"` does not render identically to an absent one; a general reason (`Direction.NONE`, DEC-056) carries no arrow, because no direction was measured on that row, and ends in `(general)`. `format_value` is the value half of the same rule, normalising a cell to `"true"`, `"12"`, `"3.5"`, `"basic"` or `"missing"` with no unit, symbol or label attached. *Consequences:* the sentence a business user reads is exactly what was measured, at the cost of reading a little less naturally than the plan's example; a unit can be added later as configuration without touching the renderer, because the decision is against inventing one rather than against ever having one; and a reader can tell a measured reason from a general one, and an absent value from the string `"missing"`, at a glance in the exported file.
- **DEC-072 — `run_error` turns any exception into the `RunError` the run documents carry: a coded exception keeps its own code and message, anything else becomes `STAGE_FAILED` naming only the stage.** *Context:* every stage module already raises a coded exception of its own — `IngestError`, `TrainError`, `EvaluationError`, `RegistryError`, `StorageError`, `ConfigError` — each carrying a machine-readable code and a business-language message (plan §13.4). The pipeline nevertheless has to write *something* into `status.json` and `run.json` for every failure, including the ones nobody anticipated, and both easy answers are wrong: restating each stage's message texts in a second table lets the two copies drift apart, and writing the exception's `str()` into the artefact puts a traceback in front of a business user. *Decision:* `engine/errors.py` adds exactly two things and copies nothing. `EngineError` covers the failures the pipeline itself decides on rather than a stage — a run blocked by validation, and a stage asked to run before the one that feeds it — with `ENGINE_ERRORS` as the whole of its code/message/suggestion table, so the API documentation can be generated from one place. `run_error(exc, stage=..., title=...)` reads `code` and `message` off any exception and, when both are non-empty strings, builds the `RunError` from them whoever raised it; anything else is a bug rather than a handled condition and becomes `STAGE_FAILED` with the message "{stage} failed unexpectedly." and nothing more, while the pipeline logs that case with `_LOGGER.exception` and a coded failure at WARNING as its code and message. *Consequences:* a user reads the words the stage that understood the failure chose, and a bug reaches the screen as a named stage rather than as a stack trace, with the traceback in the log where plan §13.7 wants it; a stage that adds a coded exception needs to register nothing here to be reported correctly. The cost is stated plainly rather than implied: `RunError` carries a code, a message and a stage but **no suggestion**, so `EngineError.suggestion` goes no further than the exception object — nothing in the engine or the API reads it, it is written into neither run document, and neither log line prints it. It exists because plan §13.4 asks every engine error to carry one, and it becomes useful the moment a failed run grows a help line on the screen or in the API.
- **DEC-073 — `model_search.tuning_trials` is AutoGluon HPO, with the installed version's own search spaces.** *Context:* the setting was validated, merged, shown in the Model-search group of the advanced settings and written into `run_config.json`, and no stage read it. A user could move a control labelled "Tuning trials" from 5 to 500 and nothing whatsoever would change about the model, which is the kind of promise plan §2.1.5 exists to forbid. *Decision:* `autogluon_fit_kwargs` now passes `hyperparameter_tune_kwargs={"num_trials": tuning_trials, "scheduler": "local", "searcher": "auto"}`, which is the dict shape AutoGluon 1.6.3 documents; `searcher: "auto"` is bayesian optimisation on the neural family and random search on the tree families. The families are still passed as `{key: {}}` rather than with search spaces written here: an empty dict means "that family's default space", and for most families the installed version carries a real one — a tuned run fits `LightGBM/T1..Tn` with genuinely different `learning_rate`, `num_leaves` and `feature_fraction`, and `LinearModel` and `CatBoost` likewise, all verified by fitting them rather than assumed. **`RandomForest` is the exception and it ships in the default candidate list:** AutoGluon 1.6.3 has no default search space for it, so the same call fits one bare `RandomForest` with its defaults and `tuning_trials` does nothing for that family. Authoring a space for the one family that lacks one was rejected — it would freeze this engine's idea of a sensible range into exactly the place plan §13.8 says to follow the installed version — so the engine says so instead: `FAMILIES_WITHOUT_SEARCH_SPACE` names it, `available_families` warns when a run selects it, and a test checks the set against the installed package so the claim cannot rot silently. Authoring spaces in the engine would freeze one version's idea of a sensible range into it, and plan §13.8 says to follow the installed version instead. Two consequences had to be handled rather than discovered later. (1) HPO decorates every fitted model with a trial suffix *outside* the bagging decorations — `LightGBM_BAG_L1/T3` — so `family_for_model_name` strips `/T\d+` first; without that it returns `None` for every model of a tuned run, which would silently cost the leaderboard its family column and cost the explain stage its TreeSHAP tier, since that tier picks the best model *by family*. (2) A trial is a real fit, so 50 trials across four families is 200 fits: the slow tests that run on plan §10's one-minute budget now override `tuning_trials: 5` (the schema floor) alongside the `ensemble`/`folds` overrides they already carried, for the same reason those exist. *Consequences:* the control does what it says; a default run now searches hyperparameters rather than taking the preset's defaults, which costs time within the configured `time_limit` and is what the setting was always meant to buy; `tuning_trials` is part of the recipe hash, because it genuinely changes the model.
- **DEC-074 — A setting no stage reads is marked `advisory`, rendered disabled, and left out of the recipe hash.** *Context:* after DEC-073 wired `tuning_trials`, nine settings remained that the schema carries and no stage reads: the whole `features` block (`auto_feature_engineering`, `categorical_encoding`, `numeric_scaling`, `text_columns`, `selection`, `max_features`), `monitoring.retraining`, `monitoring.performance_alert_drop_pct` and `governance.retention_days`. - **DEC-075 — One `Settings`, built from the environment on every read, is the only place a variable is named.** *Context:* three modules read `os.environ` directly - `engine/config.py` for `MARKETING_AI_CONFIG_DIR`, `engine/storage.py` and `engine/registry.py` for `MARKETING_AI_DATA_DIR` - and Phase 4a adds a second implementation of the store, the job runner and the metadata database, each with connection details of its own. - **DEC-076 — `LLMClient` is three methods, its fake is a hash, and no fake output may reach a screen.** *Context:* Phase 3a needs a language model behind a protocol with a local implementation (protocol rule 6), and the fast suite has to run entirely against that implementation. *Decision:* `engine/llm.py` defines `LLMClient` with `complete`, `embed` and `count_tokens` and nothing else - streaming, tool use and provider-shaped options are a provider leaking into the engine, and the two implementations this has to cover (a hash and Bedrock) agree on nothing beyond the three. `FakeLLMClient` derives every answer from a SHA-256 of the exact request, so the same call returns the same bytes on any machine, and records an `LLMCall` per request so a test can assert that a prompt was built once rather than per row. All 13 cases share one module-scoped journey fixture, so a stop anywhere in the walk reports as 13 errors rather than one — the cost of paying for the journey once instead of thirteen times. And plan §11's criterion now has exactly one place that answers it, so whether Phase 1 is finished stops being an argument about what the rest of the suite covers.
- **DEC-081 — `POST /runs` chooses its job by the run's mode, and the train flow is the one a training run gets.** *Context:* plan §11's acceptance test had never been run, and driving it in a browser stopped on the product's own words: "Run failed · Preparing features is not built yet." The route chose between two job builders on `if version is None`, and `version` is only ever assigned on the score path (`score_version(...)`, inside `if body.mode is RunMode.TRAIN: ... else:`). So the test was true for *every* training run, and every training run got DEC-060's `build_m2_job` — the milestone-2 placeholder that replays ingest and validate and then stops at `prepare` with `STAGE_NOT_IMPLEMENTED`. `Pipeline.run_train` had worked since M3 and was simply never reached from the product: run in process on the same configuration and data it takes 42 s and returns ROC-AUC 0.897. The suite did not catch it because `test_m2_job_runs_two_stages_then_fails_honestly_at_prepare` asserted the failure, so 2,699 fast tests and 94 slow tests were green over a product that could not train. A second defect sat behind it: `ui/api.js` never sent `mode` with an upload, `POST /uploads` defaults it to `train` and `POST /runs` refuses a mismatch, so "Score new data" failed on the Run click with `UPLOAD_MODE_MISMATCH` — advice the screen could not act on, since uploading again is what had just failed. *Decision:* the route dispatches on `body.mode`, which is the thing that actually decides the flow; `build_train_job` is the mirror of `build_score_job` and submits `Pipeline.run_train`; `postUpload` takes the mode and `usecase.js` passes the one it already holds. `build_m2_job` is kept but unreachable from the route, because a stage that genuinely cannot run should stop with a code and a sentence rather than raising, and that behaviour is worth keeping tested for the next stage that needs it. The test that asserted the bug is replaced by `test_a_training_run_submits_the_train_flow`, which asserts the builder the route submits — the assertion whose absence let this ship — and the API module now stands in for the train flow the way it already stands in for ingest and validate, so the fast suite does not fit a model per test. *Consequences:* the product can train; plan §11's acceptance test passes end to end in a browser (DEC-080); and the lesson is recorded where it happened — a test that asserts a placeholder's behaviour keeps the placeholder alive long after the real thing lands, so the assertion has to be about what the caller *chooses*, not about what the callee currently does.
- **DEC-082 — Integrating Phase 2 with the trunk: one run lifecycle, and a dataset is an `UploadInfo`.** *Context:* Phase 4a moved run creation, job specs and job bodies into `engine/runs.py` (DEC-327) while Phase 2 extended the old copies in `api/routes/runs.py` to accept a `dataset_id` (DEC-107); merging both kept two lifecycles, and the second never got a job spec, so a dataset run could not run in a container. Three further places assumed every run has an upload: the win-back and root-cause modules re-read `upload_key(record.upload_id, ...)`, and the Phase 4a run index requires `upload_id`. *Decision:* the copies in `api/routes/runs.py` are deleted. `_DatasetSource` satisfies `UploadInfo` (its `upload_id` is the dataset id, its `source_key` the dataset frame), and the provenance a dataset adds travels as a `DatasetLineage` argument to `create_run`, which sets `dataset_id`, `client_id` and `dataset_fingerprint` and leaves `upload_id` null. Reading a run's rows back goes through `engine.onboarding.datasets.run_source_key`, which answers the upload's source file or the dataset frame and refuses a record naming neither. The run index projects the dataset id into its `upload_id` column rather than making the column nullable, which would need a migration for no reader that tells the two apart. DEC-078's guard is gone, as its consequences said it would be; DEC-107's four refusals stay. *Consequences:* one code path creates and submits every run; a dataset run gets a `job_spec.json` and can run on SageMaker like an upload; the generative stages work on a dataset run; and composite keys are still refused with 501 until `StageContext.primary_key` is ruled on.

## Phase 2 — Data onboarding (DEC-100 … DEC-199)

- **DEC-100 — The onboarding *vocabulary* lives in `engine/config.py`'s PHASE-2 block; `engine/onboarding/specs.py` holds the *artefacts* and re-exports both.** *Context:* the Phase 2 plan §3 says "all pydantic models in `engine/onboarding/specs.py`", but four of them — the standard schema, the feature definition, the label and the snapshot definition — are blocks of a use-case YAML and of `engine.yaml:defaults`, so `UseCaseConfig` has fields of their types. `engine/config.py` imports nothing of ours by design and `engine/contracts.py` imports it one-way; defining the vocabulary in `specs.py` would mean `config → specs → contracts → config`, a cycle. *Decision:* the vocabulary a YAML file can contain (`StandardSchemaConfig`, `FeatureDef`, `SubAggregation`, `WhereClause`, `LabelDefinition`, `SnapshotDefinition`, `OnboardingConfig`, `RoleCatalogue` and their enums) is defined inside this branch's `PARALLEL_WORK_PROTOCOL.md` §4 block at the foot of `engine/config.py`, which is what it is — configuration vocabulary; the saved, hashed, per-client documents (`SourceProfile`, `MappingSpec`, `FeatureSpec`, `OnboardingSpec`, `DatasetManifest`, `BuildReport`, `BuildStatus`) are defined in `engine/onboarding/specs.py`; and `specs.py` re-exports the vocabulary, so the plan's promise holds at the import site. `LabelSpec` and `SnapshotSpec` are aliases of the config models rather than copies, so the configured default and the saved spec can never drift apart. *Consequences:* the dependency graph stays one-way and acyclic; the block is append-only and rebases cleanly; nobody has to know which half a model lives in to import it.
- **DEC-101 — The build report carries `OnboardingCheck`, a twin of `ValidationCheck`, rather than widening the Phase 1 model.** *Context:* plan §7 gives the onboarding checks the same contract as the Phase 1 ones and then re-runs the full Phase 1 validation on the assembled dataset, appending its findings to the same list — so one type has to accept both code tables. The obvious change is to `ValidationCheck._known_code` in `engine/contracts.py`, which sits above this branch's block, and `PARALLEL_WORK_PROTOCOL.md` §4 forbids editing above the block. *Decision:* `OnboardingCheck` is defined in `engine/onboarding/specs.py` with the same five fields plus `source_id`, its own code table (`ONBOARDING_VALIDATION_CODES`, the 26 codes of plan §7, which never overlap the Phase 1 19), and `from_validation_check()` to carry a Phase 1 finding across unchanged. It also refuses `acknowledgeable=True` on `FUTURE_EVENTS_LEAKED`, because plan §7 says that code is a bug and must never be user-acknowledgeable, and a model is a better place to enforce that than a convention. `docs/CROSS_BRANCH_REQUESTS.md` asks for the two models to be unified in a later reviewed change on `main`. *Consequences:* the Phase 1 contracts file is untouched by this branch, so `test_contracts.py`'s 19-code assertion and `test_shared_file_markers.py` both hold; the cost is one duplicated field list, recorded here so it is closed deliberately rather than forgotten.
- **DEC-102 — A dataset directory has its own artefact registry, separate from the run one.** *Context:* `engine.contracts.ARTEFACT_REGISTRY` is pinned name-for-name against Phase 1 plan §7's run-directory list by `tests/unit/test_artefact_registry.py`, whose whole point is that a new artefact is added deliberately rather than absorbed silently. `dataset_manifest.json`, `build_report.json` and `build_status.json` are not run artefacts: they live in `data/datasets/<dataset_id>/`, they outlive any single run, and several runs can reference one of them. *Decision:* `DATASET_ARTEFACT_REGISTRY` and `DATASET_ARTEFACTS` live in `engine/onboarding/specs.py` and cover the dataset directory; `ARTEFACT_REGISTRY` stays exactly the run contract it has always been, and a test asserts the two never overlap. *Consequences:* the Phase 1 registry test passes unedited and keeps its meaning; "what does a run write?" and "what does a build write?" stay two answerable questions rather than one list of everything.
- **DEC-103 — `configs/roles.yaml` is engine data, like `engine.yaml:catalog`.** *Context:* plan §4.1 gives the role catalogue as a config file, and principle 7 says the engine executes specs and never contains client-specific logic. A role is not a per-use-case setting: `bills` means the same thing for every client, and a use case that could rename or remap a role would be a use case that could branch the engine by YAML. *Decision:* `roles.yaml` is loaded by `load_role_catalogue()`, cached per root like `engine.yaml`, never merged into a use case and never overridable. Exactly one role has `kind: entity` and every event role requires the same two standard columns, `entity_key` and `event_time`; both are validated on load, and a missing file is an error rather than an empty catalogue, because "this client has no roles" and "the engine lost its role table" are different problems and only one is the user's. *Consequences:* adding a role is a YAML block; `RoleCatalogue.require()` answers an unknown role by listing the ones that exist.
- **DEC-104 — The onboarding cross-field checks live in `engine/onboarding/roles.py`, not in `UseCaseConfig._cross_field`.** *Context:* `engine/config.py` validates each Phase 2 block on its own, but the checks that read two blocks at once — a suggested feature must not be named after a standard column, a forward-looking label must name an *event* role — need `UseCaseConfig._cross_field`, which is above this branch's §4 block. *Decision:* those checks are `validate_onboarding_config(config, roles)` in `engine/onboarding/roles.py`, a file this branch owns outright, and `tests/unit/onboarding/test_roles.py` runs them over every shipped use case so CI catches in seconds what the config loader would otherwise have caught on load. The cost is the moment of failure: a use case naming a role that does not exist fails when onboarding reads it rather than when the loader does. *Consequences:* `engine/config.py` never imports a role catalogue it has no other use for, and this branch rebases that shared file without conflicts; the parametrised test is the thing that keeps the trade honest, so it must never be skipped.
- **DEC-105 — Specs are hashed by one function: sorted keys, no timestamps, no ids.** *Context:* plan §13 rule 15 requires two identical specs to hash identically, or the dataset lineage and the future Phase 5 archive are worthless. A naive `model_dump_json()` hash includes `created_at` and `spec_id`, so the same recipe saved twice would be two recipes. *Decision:* `spec_hash()` in `engine/onboarding/specs.py` is the only hasher; it dumps in JSON mode with sorted keys and separators, excludes `VOLATILE_FIELDS` (`created_at`, `built_at`, `hash`, `spec_id`, `mapping_id`, `dataset_id`, `fingerprint`), and prefixes a domain separator so a spec hash can never collide with a file or dataset hash. `MappingSpec.with_hash()` and `OnboardingSpec.with_hash()` are the only writers of a `hash` field. *Consequences:* a recipe re-saved a day later is recognisably the same recipe; a changed window is recognisably a different one; the property is pinned by a test that saves the same recipe under two ids and two timestamps.
- **DEC-106 — `UseCaseConfig` gains four optional fields above this branch's block, announced rather than worked around.** *Context:* `PARALLEL_WORK_PROTOCOL.md` §3 assigns the `standard_schema`, `suggested_features` and `label` sections of `configs/use_cases/*.yaml` to Phase 2, and §4 forbids this branch from editing `engine/config.py` above its block. Those two rules contradict each other: `_Base` sets `extra="forbid"`, so a use-case YAML cannot carry a section the model has no field for, and the contracts-first task could not add the fields because the Phase 2 plan was not in the repository when it ran (`docs/CROSS_BRANCH_REQUESTS.md`, 2026-09-22). *Decision:* the four field declarations are added, and they are the *only* edit this branch makes above its block in that file. All four are optional with defaults, so every existing config validates unchanged and neither Phase 3a nor Phase 4a is affected; their annotations are forward references to types defined in the PHASE-2 block, resolved by a `model_rebuild()` at the foot of that block; and every cross-field rule that would have needed more room above the block went to `engine/onboarding/roles.py` instead (DEC-104). The change is announced in `docs/CROSS_BRANCH_REQUESTS.md` the day it lands, as §3 requires. *Consequences:* the other two branches rebase over four defaulted fields, which cannot change their behaviour; had this been done the other way — a separate `configs/onboarding/*.yaml` — the plan's own §5.1 and §5.2 examples would have been wrong and the protocol's ownership table would have pointed at sections that do not exist.

- **DEC-107 — A built dataset is resolved into the shape the upload path already consumes; a periodic one is refused by name.** *Context:* plan §6.5 change 4 has `POST /runs` take an `upload_id` or a `dataset_id`. The two differ in provenance, not in what a run needs from them: a storage key holding one row per entity, a profile of it, and a row count. *Decision:* `_DatasetSource` reduces a dataset to exactly those three, so the whole validate-create-submit path below is the one Phase 1 already had — the difference between Phase 2 reaching the engine and Phase 2 forking it. `run.json` gains `dataset_id`, `client_id` and `dataset_fingerprint` (four optional fields above this branch's §4 block in `engine/contracts.py`, and `upload_id` widened to nullable, announced in `docs/CROSS_BRANCH_REQUESTS.md` as DEC-106 was), because without them the lineage the build recorded stops at the dataset and never reaches the model trained on it. Four refusals, because these are four different problems with four different answers: `DATASET_NOT_FOUND` (404), `DATASET_USE_CASE_MISMATCH`, `DATASET_CLIENT_MISMATCH` and `DATASET_NOT_BUILT` (409), and `DATASET_COMPOSITE_KEY_NOT_WIRED` (501). `client_id` without a `dataset_id` is refused too: it was accepted and ignored, which is how a caller comes to believe they scoped a run to a client when they scoped it to nothing. *Consequences:* the periodic path is the honest stop — plan §6.5 change 1 widened the key on the contracts, and teaching `prepare`, `split`, `explain`, `actions` and `export` to carry both columns is the half still outstanding; a run that took the first column would join on the customer, lose the snapshot date, train one row per customer out of twelve and report success.
- **DEC-108 — A build reads every row; the profiling row cap is lifted explicitly.** *Context:* `engine.stages.ingest.read_upload` defaults `row_cap` to `DEFAULT_PROFILE_ROW_CAP` (2,000,000), and `FileSourceReader.read` went through `read_table`, which does not pass one. For a *profile* that default is right and deliberate — a profile of two million rows describes a file as well as a profile of ten million, and `DatasetProfile.row_count` stays exact either way (DEC-046). For a *build* it is silently wrong: the rows are aggregated, so a capped read produces feature values computed from part of the history, for a subset of the entities, with nothing anywhere saying so. Measured at the plan's target size: every event table came back exactly 2,000,000 rows long and the build failed seven checks it should have passed. *Decision:* `FileSourceReader.read` calls `read_upload` with an explicit `row_cap=UNBOUNDED_ROWS`, and a test asserts it does. The cap is lifted deliberately rather than inherited by accident, and the reason is written where the call is. *Consequences:* a build of a very large source is bounded by memory rather than by a silent cap, which is the correct trade — a build that cannot fit should fail loudly, not quietly produce a wrong dataset. Nothing below two million rows changes, which is why no test caught this.
- **DEC-109 — The leak probe compares floats to a tolerance and everything else exactly.** *Context:* `_leak_probe` re-runs the feature spec against tables carrying rows dated after the last snapshot and reports any feature whose value moved. It compared with `Series.equals`, which is exact. DuckDB aggregates in parallel, so the order it sums a column in is not fixed between runs: building the same features twice over *identical, untouched* tables returns floats that differ in their last bits. Measured at 240,000 rows over 3,000,000 events, the largest such difference was 5.5e-12 on a sum of order 500 — about 1e-15 relative, which is arithmetic noise. So every float feature was reported as moved as soon as a build was large enough for DuckDB to use a second thread, and the finding it raised was `FUTURE_EVENTS_LEAKED` — the one a user may never acknowledge (`OnboardingCheck` refuses to mark it acknowledgeable, by design). Large builds were impossible, and the engine's own correctness check was what made them so. *Decision:* counts, dates and categories are still compared exactly, because a count that changes at all has counted something it should not have; a value that appears or disappears is a change whatever its type, so null positions are compared exactly in both branches; floats are compared at `rtol=1e-9`, a thousand times the measured noise and many orders of magnitude below any real leak, since an event that should not have been counted moves a count by a whole 1 and a mean by a real amount, never by a part in a billion. *Consequences:* the probe still fails the build when the time bound is deliberately broken, which the flow test asserts; a test pins the non-determinism itself, so the tolerance can be removed if DuckDB ever becomes order-stable — but only with a measurement showing it.
- **DEC-110 — `complaints.text` is documented as unredacted rather than the detector changed.** *Context:* `configs/roles.yaml` promised that PII in the free-text complaint column "is redacted at profiling time". It is not. `engine.stages.ingest.detect_pii` and `engine.stages.prepare._detect_pii` both match a whole cell (`pattern.fullmatch`), so a phone number that *is* the cell is caught and one buried in a sentence is not — measured on a synthetic complaints table at 363 of 1,105 rows carrying an email the shipped pattern finds by `search`, with `detect_pii` returning nothing for the column. That is defensible for the columns Phase 1 sees, where a `phone` column holds phone numbers, and exactly wrong for the free-text column Phase 2 introduces, which is where a customer types "call me back on 0400 123 456" and which Phase 3 will read to write summaries. *Decision:* correct the claim, not the code. Switching to a substring match would start redacting columns that are not redacted today in *every existing use case*, changing what Phase 1 trains on; `min_value_match_rate` and `min_distinct_ratio` are calibrated for whole-cell matching and would need recalibrating with them. That is a decision for the human reviewer, and it is filed in `docs/CROSS_BRANCH_REQUESTS.md`. The role description now says the detectors match whole cells and the column should be treated as unredacted free text, and `tests/fixtures/raw/make_raw.py` plants contacts in the exact shapes the shipped patterns recognise so whoever takes the decision has something to test against. *Consequences:* a documented gap rather than an undocumented one; the promise the config made is the kind of claim that is worse than silence, because a reader plans around it.

### Foundation (DEC-700 … DEC-706)

- **DEC-700 — `PHASE_APP_HOOKS` in `create_app`.** *Context:* access control and the audit trail must apply to every route, including Phase 1's and the other phases' routers that Phase 4b may not edit; neither can be expressed as a router, and a dependency added after a router is included does not reach that router's routes. *Decision:* `api/main.py` gains `PHASE_APP_HOOKS: list[Callable[[FastAPI], None]]`, called with the new app **before** any router is included; it is the one edit above a block in that file. Phase 4b registers `install_access` (a global dependency plus the audit middleware) and `install_scheduling` (startup and shutdown handlers) in its block. *Consequences:* every route, `/healthz` included, inherits the enforcement dependency without its router knowing; the list is empty on a checkout without Phase 4b, so nothing changes there.
- **DEC-701 — `Settings` gains a Phase 4b section whose defaults change nothing.** *Context:* sign-in, audit export, the scheduler and alerts each need configuration, and the protocol forbids changing an existing field. *Decision:* added fields only — `auth_mode`, `auth_session_ttl_seconds`, `audit_export_bucket`, `audit_export_prefix`, `audit_retention_days`, `scheduler_backend`, `scheduler_tick_seconds`, `scheduler_group_name`, `scheduler_target_arn`, `scheduler_role_arn`, `alert_backend`, `alert_sns_topic_arn` — each with a `MARKETING_AI_*` variable in `ENV_VARS`, and `eventbridge`/`sns` added to `_REQUIRED_FOR`. Every default reproduces the behaviour before Phase 4b: nobody signs in, nothing fires on its own, an alert is a log line, an audit export goes to local disk. *Consequences:* a Phase 1–4a deployment that upgrades behaves exactly as before until it opts in.
- **DEC-702 — `auth_mode` is `off` or `local`; `off` acts as a named principal; prod fails closed.** *Context:* a laptop needs no sign-in, a deployment must have one, and the identity provider (decision P5) is not chosen. *Decision:* `off` makes every request act as `LOCAL_OPERATOR` (all four roles), so the audit trail still names an actor; `local` uses the built-in user store. `Settings` does **not** refuse `env=prod` with `auth_mode=off` — Phase 4a's prod contexts and tests predate the field — instead `api/access.py` answers every non-public route with 503 `AUTH_NOT_CONFIGURED` (naming `MARKETING_AI_AUTH_MODE`) while `/healthz` keeps answering, and logs an ERROR at startup; on dev or staging with sign-in off it logs a WARNING. OIDC/Cognito is deferred to M50 pending P5. *Consequences:* a misconfigured prod deployment stays up and says why, rather than failing to boot or serving unauthenticated. *Amended by DEC-725 (Part 1 review).*
- **DEC-703 — Roles are a set, not a ladder.** *Context:* the plan names Viewer, Analyst, Approver and Admin; a ladder would make an Admin an Approver. *Decision:* `Principal.roles` is a set; Viewer is implied by any role; Admin does **not** imply Approver or Analyst (separation of duties: the person who manages users cannot also approve the champion unless separately granted it). `SYSTEM_SCHEDULER` holds Analyst only. *Consequences:* scheduled work can score, check drift and train a challenger but can structurally never approve or promote; an Admin sees approve buttons refused with the reason. *Amended by DEC-723 (Part 1 review).*
- **DEC-704 — One policy table keyed by (method, path template); fail closed.** *Context:* "every route declares its required role", but the legacy routers belong to other workstreams. *Decision:* `api/access_policy.py` holds `RoutePolicy(role, action, object_type, object_param, audit_reads, purpose)` keyed by method and route template. Legacy routes are declared centrally (`LEGACY_POLICIES`); each Phase 4b router registers its own next to its routes at import. A route with no policy answers 403 `ROUTE_HAS_NO_POLICY`, and a test fails if any mounted route lacks one. Reads are audited only when they export row-level data (`audit_reads=True`). *Consequences:* a new route is refused until someone decides who may call it.
- **DEC-705 — No data values in the audit log.** *Context:* the audit trail must itself not become a copy of customer data (plan M47, the Phase 1 logging-audit approach). *Decision:* `AuditEvent.details` accepts only keys in the closed `DETAIL_KEYS` set, holding identifiers, codes and counts; a data principal appears only as `principal_hash(id, salt)`; before/after are hashes, never bodies. *Consequences:* adding a detail is a reviewed edit of `DETAIL_KEYS`; tests byte-search the audit table for planted values.
- **DEC-706 — `platform.db` beside `registry.db`; Alembic owns the Postgres schema.** *Context:* users, sessions, audit, consent, erasure and schedules need tables. *Decision:* locally a SQLite `platform.db` beside the artefacts (and `registry.db`); on a deployment the registry's Postgres. `create_tables(engine, names)` creates only the named tables and only on SQLite (DEC-340's scoped creation); the Postgres schema is Alembic's, in revisions `0002` → `0003` → `0004` after `0001`. *Consequences:* a Phase 1 data directory gains `platform.db` only when a Phase 4b feature is used.

### M46–M47 — Access control and audit (DEC-710 … DEC-722)

- **DEC-710 — Password hashing.** *Context:* the local user store needs passwords without adding a dependency. *Decision:* PBKDF2-HMAC-SHA256 from `hashlib`, a 16-byte random salt per user, `hmac.compare_digest`, stored as `pbkdf2_sha256$<iter>$<salt>$<hash>` with 600,000 iterations (OWASP 2023). Unknown usernames are checked against a decoy hash so response time does not reveal which accounts exist. *Consequences:* the stored iteration count lets the default be raised later without breaking old hashes; tests pass a low iteration count through the constructor.
- **DEC-711 — Bearer sessions stored as a hash.** *Context:* a copied database must not let anyone sign in. *Decision:* the token is `secrets.token_urlsafe(32)`; only its unsalted SHA-256 is stored, which is safe because the token has 256 bits of entropy. Expiry comes from `auth_session_ttl_seconds`. Logout revokes one session; disabling a user, changing their roles or changing their password revokes all of their sessions. *Consequences:* removing a role takes effect immediately; a password change signs the user out everywhere.
- **DEC-712 — The last Admin cannot be removed.** *Context:* a deployment with no Admin cannot be managed through the API. *Decision:* disabling or demoting the last enabled Admin is refused with 409 `LAST_ADMIN`, checked under a process lock inside one transaction; `scripts/create_user.py` is the recovery path. *Consequences:* two API processes on one Postgres could still race this rule; accepted, because it guards against a mistake, not an attack.
- **DEC-713 — Identity seam for M50.** *Context:* the identity provider (P5) is undecided. *Decision:* an `IdentityProvider` protocol with `DisabledIdentity` and `LocalIdentity`; the future OIDC/Cognito provider is a third class selected by a new `auth_mode` value. *Consequences:* the policy table, audit and UI read only the `Principal`, so nothing else changes when M50 lands; JWT validation and claim-to-role mapping are left to P5.
- **DEC-714 — Append-only below the application.** *Context:* the `AuditLog` protocol has no update or delete, but that only stops careless code. *Decision:* database triggers reject UPDATE and DELETE on `audit_events` (a plpgsql trigger that also rejects TRUNCATE on Postgres, via `0002`; `RAISE(ABORT)` triggers on SQLite, created by both the migration and `SqlAuditLog`). *Consequences:* changing history needs someone to drop a trigger first; the Object Lock export (DEC-715) covers the database owner. The Postgres trigger, TRUNCATE included, is pinned by a `postgres`-marked test run against a local PostgreSQL 16 at integration.
- **DEC-715 — Audit exports use S3 Object Lock in COMPLIANCE mode.** *Context:* governance mode can be bypassed by anyone holding `s3:BypassGovernanceRetention`. *Decision:* S3 exports are written in COMPLIANCE mode with RetainUntilDate = now + `audit_retention_days` and `ContentMD5`, behind the `AuditExportSink` protocol; local mode writes JSON lines to `<data_dir>/audit/exports`, never overwriting. The export's own audit event carries the file's SHA-256 as `after_hash` and its key as `export_key`. *Consequences:* a bucket without Object Lock fails the export loudly (502 `AUDIT_EXPORT_FAILED`); exports are copies, and the table remains the record. *Amended by DEC-726, DEC-727 (Part 1 review).*
- **DEC-716 — Legacy policy mapping.** *Context:* every route that existed before Phase 4b needs a role. *Decision:* GETs are Viewer; creating or changing work, and generative actions that spend tokens, are Analyst; approving or promoting a champion and approving copy are Approver only; AWS connection writes and test are Admin; row-level downloads (`runs.scores_download`, `runs.artefact_download`, `copy.messages_download`, `datasets.sample`) are `audit_reads`; each policy has a `purpose` phrase from which the refusal sentence is built ("Only an Approver can approve a champion."). *Consequences:* an Admin cannot approve (DEC-703); a test fails if any legacy write is open to a Viewer or has no purpose.
- **DEC-717 — Enforcement is a fail-closed global dependency.** *Context:* the policy is keyed by route template, which is only known after routing. *Decision:* a global dependency on `app.router.dependencies` (DEC-700); a missing policy is 403; `auth_mode=off` on prod is 503 per request (DEC-702); HEAD uses the GET policy. *Consequences:* FastAPI parses the body before dependencies run, so a malformed JSON body gets its 422 before the sign-in check (nothing runs). The OpenAPI, docs and static `/ui` routes are not APIRoutes and stay public.
- **DEC-718 — A pure-ASGI audit middleware writes one event per request.** *Context:* exactly one event per mutating or `audit_reads` request, with no buffering of downloads. *Decision:* the outcome comes from the status (401/403 `denied`; other 4xx/5xx and exceptions `failed`). `after_hash` is the SHA-256 of the exact 2xx JSON response bytes, hashed chunk by chunk as they pass. The request id is a uuid4, or an incoming `X-Request-ID` matching `[A-Za-z0-9._-]{8,64}`. A path parameter becomes `object_id` only if it matches `[A-Za-z0-9._:-]{1,128}`, so an email typed into a URL is withheld. Unmatched routes are recorded as `request.unmatched` with no path. *Consequences:* streaming is unaffected; routes enrich the event through `set_audit_context` (which may also override the action, outcome and actor) and never write a second one. *Amended by DEC-724 (Part 1 review).*
- **DEC-719 — A failed audit write does not fail the request.** *Context:* the audit database must not become a single point of failure, and the response has already been sent when the event is written. *Decision:* log at ERROR with the action and the exception class only, and increment `app.state.audit_write_failures`. *Consequences:* a deployment should alarm on that ERROR line; the gap is visible rather than silent.
- **DEC-720 — Login privacy.** *Context:* a sign-in form should not confirm which accounts exist or are disabled. *Decision:* wrong password, unknown user and disabled user all get the same 401 and message; the audit event is `failed` with `reason_code`, and `object_id` is set only when the user is known. The username and password are never recorded; a successful login's `after_hash` is the principal view, not the body that contains the token. *Consequences:* there is no rate limiting or lockout yet; only the PBKDF2 cost slows guessing.
- **DEC-721 — One list of Phase 4b tables.** *Context:* several migration tests need a definite table set, and they asserted "exactly one migration". *Decision:* `engine.platform_db.PLATFORM_TABLES` lists every table a Phase 4b migration creates; the migration tests assert one linear Alembic chain from `0001` and `METADATA_TABLES ∪ PLATFORM_TABLES`. *Consequences:* each Phase 4b migration appends its tables there; drift for Phase 4b tables is checked by Phase 4b's own migration tests, because `alembic/env.py` limits autogenerate to `METADATA_TABLES` (DEC-797).
- **DEC-722 — No password on the command line.** *Context:* argv is visible in `ps`, shell history and some supervisors. *Decision:* `scripts/create_user.py` reads the password from two hidden prompts or from the first line of stdin with `--password-stdin`, and records the creation as `system:bootstrap`. *Consequences:* automation pipes the password in; even the first Admin has an audit entry.

### M48 — DPDP controls, engine (DEC-730 … DEC-745)

- **DEC-730 — Privacy policy lives in `configs/privacy.yaml`.** *Context:* purposes, the use-case-to-purpose mapping, which artefacts are row-level and the erasure mode are policy, and engine code may not name a use case. *Decision:* one engine-data YAML loaded through a frozen pydantic model; the loader rejects an undeclared purpose or a use case that does not exist, and the result is cached per config root. *Consequences:* legal can review and change policy without touching code. An unmapped use case is never gated. A missing file means no controls; a file that is present but wrong raises.
- **DEC-731 — Latest consent record wins.** *Context:* consent changes over time. *Decision:* the ledger is append-only. For a client, principal and purpose, the latest record with `recorded_at <= at` decides, ties to the higher `seq`; consent is valid only if that record is an unexpired grant; no record means no consent. *Consequences:* history is preserved, and validity can be answered as of any past time.
- **DEC-732 — The scoring seam.** *Context:* stages cannot be edited. *Decision:* inside the PHASE-4B block of `engine/pipeline.py`, `_ScoreFlow._actions` is rebound. If a ledger exists for the run's client and purpose (client = `RunRecord.client_id`, falling back to `Settings.client_id`), the ledger's verdict is written into the configured consent column, or into a synthetic column that is never exported; the existing `consent_false` rule suppresses those rows and its counts report them, and `consent_report.json` is written and listed in `run.json`. With no ledger, the Phase 1 method runs. *Consequences:* a test proves the output is byte-identical to Phase 1 and that no `platform.db` is created. Training is not gated. If the ledger database is unreachable, the stage fails closed. *Amended by DEC-738, DEC-739 (Part 1 review).*
- **DEC-733 — Principal ids are hashed everywhere in the database.** *Context:* the ledger and the erasure register would otherwise be a copy of the customer list. *Decision:* `consent_record`, `erasure_request` and the audit log store only `principal_hash(id, salt=privacy_salt(settings))` (the salt is `client_id`, else `"local"`); lookups hash their input. *Consequences:* erasure never needs to touch the database, and the sentinel test can byte-search `platform.db`. Limitation: the salt is not secret, so ids with little entropy can be brute-forced; a secret salt in Settings is recommended.
- **DEC-734 — Consent CSV import is all or nothing.** *Context:* a consent file is personal data. *Decision:* every row is validated first; errors report row number and column and never the value; nothing is written if any row fails unless `partial=True`. Unknown columns are ignored and listed; timestamps more than 5 minutes in the future are refused. *Consequences:* the ledger never ends up half-loaded, and error messages are safe to show or log.
- **DEC-735 — One store map.** *Context:* retention, erasure and export all need to know where personal data lives. *Decision:* `engine/privacy/layout.py` maps each key prefix to a store and holds a `StoreIndex` that reads `run.json`, `upload.json` and dataset manifests as raw JSON for dates and primary keys. *Consequences:* the three features stay consistent, and documents from older schemas do not break a pass.
- **DEC-736 — Retention.** *Context:* `governance.retention_days` becomes enforced. *Decision:* the plan is the dry run and apply executes exactly the plan. Items are dated from their own records, never file times; anything undatable is skipped as `UNDATED`. A run uses the value in its `run_config.json`; an input (upload or dataset) uses the maximum of its use case's value and every reading run's; a source uses the maximum over the datasets built from it. `0` means "once a finished run has read it"; inputs of unfinished runs are skipped as `IN_USE`. Row-level files are deleted; samples in kept reports (`profile.json` columns and preview rows, `scoring_summary.json` sample rows) are emptied. *Consequences:* a test proves the dry run equals the real run and that models, manifests and aggregate reports survive. *Amended by DEC-744 (Part 1 review).*
- **DEC-740 — S3 lifecycle rules are only a backstop.** *Context:* a lifecycle rule knows prefix and age, nothing else. *Decision:* rules cover `uploads/`, `datasets/` and `clients/<id>/sources/` under `s3_prefix`; expiry is the longest `retention_days` plus `grace_days`, and noncurrent versions expire after `grace_days`. Only rules whose ID starts with the configured prefix are replaced; others are read back and kept; if the current configuration cannot be read, nothing is written. *Consequences:* row-level run artefacts are enforced only by the retention job; nothing applies the rules yet (an ops step). *Amended by DEC-708 (Part 1 review).*
- **DEC-741 — Erasure scans the whole store and rewrites in place.** *Context:* a fixed list of "known files" goes stale. *Decision:* read every artefact key. Tabular files (csv via the csv module, parquet via pyarrow) match on the primary key recorded for the file, or on any cell when none is recorded; JSON matches string values only; text matches exact tokens (`C-104` never matches inside `C-1042`). Each file is rewritten in its own format, LLM cache hits are deleted, binary files are reported rather than rewritten, and every rewritten file is scanned again (`ERASURE_INCOMPLETE` if the id remains). *Consequences:* a sentinel test proves no byte of the id is left anywhere and that the product still reads every rewritten file. *Amended by DEC-707, DEC-737 (Part 1 review).*
- **DEC-742 — Delete or tombstone.** *Context:* some clients need counts to reconcile after an erasure. *Decision:* `delete` is the default; `tombstone` keeps the rows, replaces the id with `[erased]`, empties other text cells and keeps numbers. Stray mentions are masked in both modes. The consent history is kept by default under the hash (`consent_history: keep|delete`). *Consequences:* the mode is a policy line in `privacy.yaml`, not code. *Amended by DEC-737 (Part 1 review).*
- **DEC-743 — Models are flagged, not retrained.** *Context:* plan M48 says retraining happens at the next scheduled cycle, not immediately. *Decision:* `model_retrain_flag` holds model versions whose training run read an upload, dataset or source (by lineage) that contained the person, or whose own run directory did. The scheduler reads `models_flagged_for_retraining`, retrains into a challenger (champion rule and approval still apply), then calls `clear_flag` (DEC-768). *Consequences:* no model fit inside an HTTP request, and no model crowned without approval. *Amended by DEC-709 (Part 1 review).*
- **DEC-745 — Access export.** *Context:* plan M48 item 4. *Decision:* `find_principal` is reused, and the export is one zip of CSV rows (each file's own header), JSON fragments with their JSONPath and text lines, plus consent and erasure history and a README. The zip is returned, never stored. *Consequences:* its completeness test mirrors the erasure test, and the export creates no new copy that a later erasure would have to find.

### M48 — DPDP controls, API (DEC-746 … DEC-754)

- **DEC-746 — A principal id goes only in a request body.** *Context:* an id in a path or query string reaches the uvicorn access log, load-balancer logs and browser history, none of which can be erased, and the audit middleware would turn a path parameter into `object_id`. *Decision:* every route that takes a principal id is a POST with a JSON body, including the two that only read (consent lookup, access request). The event's `object_id` is the request's own id (lookup id, `ar_…`, `er_…`) and the person appears only as `principal_hash`, salted with `privacy_salt(settings)`; no response echoes the id. *Consequences:* those two reads are audited as mutations (`audit_reads` is GET-only); a unit test fails if any privacy route declares a path or query parameter named like a principal.
- **DEC-747 — Privacy roles.** *Context:* the plan gives retention, users and settings to Admin. *Decision:* every M48 route is Admin — consent evidence, erasure and access exports are decisions made for the client organisation — except the per-run consent report, which is Viewer like every other report of a run (counts only). *Consequences:* an Analyst cannot erase or export a person; tests check both refusal and a Viewer reading the report.
- **DEC-748 — Retention apply re-plans and checks the hash.** *Context:* the dry run must equal the real run, and the server should not keep plans between requests. *Decision:* the dry run returns `plan_hash` over `planned_at` (normalised to UTC) and the items. Apply plans again as of the same `planned_at` and deletes only if the hash matches; otherwise 409 `RETENTION_PLAN_CHANGED` and nothing is touched. `as_of` may be in the past, never the future. *Consequences:* a run started meanwhile, a new file, or a second apply of the same plan are all refused; any process can apply a plan another planned.
- **DEC-749 — One store rewrite at a time.** *Context:* erasure and retention both rewrite artefacts. *Decision:* a process-wide `_STORE_REWRITE_LOCK` serialises them. *Consequences:* it does not coordinate with a running pipeline job or with other API processes. *Amended by DEC-728 (Part 1 review).*
- **DEC-750 — Where the consent report is served.** *Context:* `/runs/{run_id}/artefacts/{name}` is Phase 1's route, and `PRIVACY_RUN_ARTEFACTS` is kept apart from `ARTEFACT_REGISTRY`. *Decision:* `GET /privacy/runs/{run_id}/consent-report`; a run that was not gated answers 404 `CONSENT_REPORT_NOT_FOUND`, which the UI reads as "not gated". *Consequences:* `api/routes/runs.py` is not edited, and the generic artefact route still does not serve `consent_report.json`.
- **DEC-751 — Consent import and client resolution.** *Context:* a consent file is personal data and loads all or nothing (DEC-734). *Decision:* 201 with the report when rows were written; 422 with the same report when refused, so every problem shows at once. At most 64 MB, UTF-8, parsed off the event loop. The client is the request's `client_id`, else `Settings.client_id`, else 422 `CLIENT_ID_REQUIRED`, and must match `[A-Za-z0-9._:-]{1,128}`. *Consequences:* an empty file is also 422 with no rows imported.
- **DEC-752 — Erasure errors and one audit event.** *Context:* a failed erasure still needs an id, and the audit rule allows one event per request. *Decision:* the route mints the `er_…` id before calling the engine with `audit_log=None`, then enriches the middleware's event with `erasure_audit_details`. On failure it returns 500 with the engine's code, the message names the id, and the register row reads `failed`. *Consequences:* `GET /privacy/erasure/{id}` shows failures; a test counts exactly one `privacy.erasure` event.
- **DEC-753 — Access export audit.** *Context:* the trail must prove what was handed over. *Decision:* the zip is returned and never stored; the event records `after_hash` = SHA-256 of the zip, `object_id` = the export's `ar_…` id, and a count of files and stores. *Consequences:* a test shows no new file in the data directory holds the id afterwards.
- **DEC-754 — Retention uses the client store only if it already exists.** *Context:* using `ClientStoreDep` created an empty `clients.db` as a side effect of a dry run. *Decision:* use the store only when `app.state.client_store` is set or `<data_dir>/clients.db` exists, as `scripts/run_retention.py` does. *Consequences:* the dry run leaves the data directory byte for byte unchanged.

### M48–M49 — Privacy and monitoring screens (DEC-755 … DEC-759)

- **DEC-755 — Controls on the production module's own screens are refused as they are drawn.** *Context:* `gate.js`'s `ACTION_CONTROLS` table (DEC-792) exists for other workstreams' screens. *Decision:* the privacy and monitoring screens call `controls.actionButton(method, path)`, which asks `reasonFor` from `/auth/me` while painting; a refused route draws the control disabled, with the server's sentence beside it and as its title, and with the same `data-pb-gate` marker so the capture listener swallows clicks on it. *Consequences:* controls stay visible and explained, never hidden; when `/auth/me` is unknown nothing is refused; a static test fails if an `actionButton` names a route with no policy or a listed M48/M49 action loses its control.
- **DEC-756 — A data principal's id never leaves the request body (the UI side of DEC-746).** *Context:* URLs, the hash and browser history cannot be erased. *Decision:* the id is read from its input on submit and sent only in a POST JSON body; it is never kept in screen state, put in the hash or drawn again; answers show `principal_hash` only. The access-export zip is fetched through the wrapped fetch and saved under the server's file name. Each change shows its audit action and object id, with "Open in the audit log" for an Admin. *Consequences:* after a repaint the input is empty; a jsdom test fails if the id appears in any URL, the hash or the page.
- **DEC-757 — Destructive privacy actions need confirmation; retention applies only the plan on screen.** *Context:* erasure and retention cannot be undone. *Decision:* nothing is sent until the "I understand" or "I have reviewed" box is ticked. Apply sends back exactly the `plan_id`, `planned_at` and `plan_hash` of the dry run shown; afterwards (success or 409) the plan is marked applied or out of date and only "Plan again" leads to another apply. A refused consent file is shown as its report; `PRIVACY_NOT_CONFIGURED` is shown once in place of the forms. *Consequences:* a plan can never be applied twice from one screen; a Viewer's privacy screens make no privacy API calls.
- **DEC-758 — The monitoring screen family, and where a run's outcomes live.** *Context:* M49 reads are Viewer and changes are Analyst (DEC-780); Phase 1's Output page may not be edited. *Decision:* `#/monitoring/...` with tabs Schedules, Alerts, Missed runs and Outcomes; outcomes live at `#/monitoring/runs/<run_id>` (upload, performance against the alert level, incrementality input, consent report). Reports that do not exist yet are read as "not yet", not as errors. *Consequences:* an Admin without Analyst sees schedule changes refused (DEC-703); a slow answer never paints over a newer screen.
- **DEC-759 — What the schedule form sends.** *Context:* the payload must be exactly what the API validates. *Decision:* cadence Daily, Weekly, Monthly (02:00) or Custom, with the cron line sent only for Custom; timezone defaults to Asia/Kolkata; the client is omitted unless typed (the recipe's client is used, DEC-786), never `settings.client_id`; only typed parameter ids are sent; delete asks twice in the row; "Run now" shows the firing's own status; managed schedules show an explanation instead of the edit form. *Consequences:* jsdom tests assert the payloads byte for byte.

### M49 — Scheduling, monitoring and outcomes, engine (DEC-760 … DEC-774)

- **DEC-760 — Scheduling package and actor.** *Context:* M49 needs schedules, firing, monitoring and outcomes, and scheduled work must never be able to approve anything. *Decision:* everything lives in `engine/scheduling/` (engine-only, never imports `api`), and every firing acts as `SYSTEM_SCHEDULER` (Analyst only). *Consequences:* a firing can score, check drift and train a challenger, and structurally cannot approve or promote; the API routes are thin wrappers over `service.py`, `firing.py` and `outcomes.py`.
- **DEC-761 — Own five-field cron parser; portability checked when the schedule is written.** *Context:* EventBridge uses a six-field dialect with Sunday numbered 1 and rejects restricting both day-of-month and day-of-week. *Decision:* a small tested parser (numbers, `*`, lists, ranges, steps, 0/7 both Sunday, Vixie's day rule) with `next_after` computed in the schedule's timezone (default Asia/Kolkata), plus `to_eventbridge()`. Names, `L`, `W`, `#` and `?` are refused by name, and `CRON_NOT_PORTABLE` is raised everywhere. *Consequences:* a schedule that works on a laptop also works on EventBridge; no new dependency; presets are stored as their cron line.
- **DEC-762 — The local scheduler is a daemon thread and the table is its only state.** *Context:* development needs schedules to fire without AWS, and tests must be deterministic. *Decision:* `LocalScheduler` ticks every `scheduler_tick_seconds`, settles finished firings, then runs `run_due` for each enabled schedule; the clock is injectable, `tick()` is public, and one broken schedule never stops the others. *Consequences:* a restart loses nothing; `sync`/`remove` are no-ops.
- **DEC-763 — A due slot fires at most once.** *Context:* EventBridge retries, multiple replicas and sweeps can all reach the same slot. *Decision:* a unique index on `(schedule_id, scheduled_for)`; a firing inserts its row before doing any work, and the loser of the insert does nothing. Manual firings have a null slot, so "fire now" is always allowed. `next_due_at` moves on before the work starts. *Consequences:* at most one firing per slot even across processes.
- **DEC-764 — Missed runs and catch-up.** *Context:* slots can pass while nothing is running. *Decision:* a slot is on time if it is the only due slot and within the grace (2 ticks + 60 s locally, 30 minutes for the EventBridge sweep). Otherwise every due slot is recorded as a `missed` firing (at most 100), one `schedule_missed` alert is raised, and **one** catch-up firing runs, because every kind of work reads the latest data. The EventBridge sweep never claims a slot still inside the grace. Disabled periods produce no backlog. *Consequences:* missed slots stay visible in the history without repeating the same work. *Amended by DEC-775, DEC-779 (Part 1 review).*
- **DEC-765 — The EventBridge target is an ECS RunTask of this image running `scripts/fire_schedule.py`.** *Context:* the plan says "EventBridge Scheduler calling the API", but EventBridge Scheduler cannot call an arbitrary HTTPS endpoint without an API destination, which means a stored credential and an endpoint to defend. *Decision:* the target is the cluster (`scheduler_target_arn`); the task-definition family is the cluster name + `-job`; the network reuses `sagemaker_subnet_ids`/`sagemaker_security_group_ids`; the input overrides the container command with `--schedule-id <id> --scheduled-time <aws.scheduler.scheduled-time>`; retry is 2 attempts within 1 hour; `sync` uses Get then Create/Update (IAM grants no List). Create writes the table then pushes, rolling back the row if the push fails; delete removes the EventBridge schedule first. *Consequences:* no extra credential and the same `fire()` path everywhere; it matches `infra/operations.py`. The input substitution needs checking on the M50 dev deployment (moto cannot fire schedules).
- **DEC-766 — A firing uses the engine's own run path on the client's latest tables.** *Context:* a scheduled run must behave exactly like the API's. *Decision:* `start_dataset_run` repeats the dataset branch of `create_run_endpoint` call for call, with the same codes; scoring resolves the champion via `resolve_model_version`; datasets are built with `build_dataset` then `register_dataset`; `latest_recipe_inputs` swaps each recipe table for the newest source with the same confirmed role that contains every mapped column, reusing the saved mapping. *Consequences:* a scheduled run and a clicked run are indistinguishable; the route logic is duplicated in engine code and can drift (a follow-up can make the route call `start_dataset_run`).
- **DEC-767 — `monitoring.retraining` is live through managed schedules.** *Context:* the setting existed but nothing read it. *Decision:* `manual` → no managed schedule; `weekly`/`monthly` → one managed `retrain` schedule with that preset; `on_drift` → one managed weekly `drift_check` that retrains on drift. Managed ids are deterministic per client × use case × kind with `managed_by="monitoring.retraining"`; people's own schedules are never touched; managed schedules can be paused but not edited or deleted (`SCHEDULE_MANAGED`). The value is read from the use case's configuration, not from a run (DEC-795). *Consequences:* sync is idempotent and safe across replicas.
- **DEC-768 — Erasure flags are answered by the next retraining cycle; cleared only after a successful retrain.** *Context:* DEC-743. *Decision:* a `retrain` firing, or an `on_drift` drift check (which retrains when a model of its use case is flagged even without drift, result `RETRAIN_FOR_ERASURE`), records the flagged model ids in `flagged_models`; `settle` clears them only when the training run is `done` and registered a version. *Consequences:* the flagged champion stays champion until an Approver approves the challenger; under `manual` retraining flags stay open until a retrain schedule is fired by hand. *Amended by DEC-777 (Part 1 review).*
- **DEC-769 — One audit event per firing, ids only.** *Context:* M47 requires an audit trail without data values. *Decision:* every firing writes `schedules.fire` and every batch of missed slots writes `schedules.missed` (object type `schedule`, actor `system:scheduler`), with `firing_id`, `schedule_kind`, `dataset_id` (new `DETAIL_KEYS`), `run_id`, `trigger`, `outcome`, `reason_code`, `models_flagged` and `count`. A firing started through the API passes `audit_log=None`, so the middleware's event is the only one. *Consequences:* the audit trail joins to the firing history with no free text.
- **DEC-770 — Alerts are persisted first and written in business language.** *Context:* email is the least controlled output channel. *Decision:* every alert writes an `alert` row and one log line (kind and ids only); the SNS sink then publishes (subject ≤ 100 characters, ids in the body); a publish failure is logged by class name and never fails the job. Messages carry counts and ids, never values. Acknowledgement is recorded once and is idempotent. *Consequences:* alert history exists even with SNS down; there is no deduplication yet.
- **DEC-771 — Outcome window; the uploaded file is never stored.** *Context:* outcomes are incomplete until the label horizon has passed. *Decision:* the horizon is the recipe label's `horizon_days`, else the use case's `label.horizon_days`, else `OUTCOME_WINDOW_UNKNOWN`; the window starts at the dataset's last snapshot date when recorded, else at the run's `finished_at`; before `anchor + horizon` the request is refused with `OUTCOME_WINDOW_NOT_MATURED`, naming the date. The file is parsed in memory and never written. *Consequences:* retention and erasure gain no new row-level store; the artefacts hold aggregates only.
- **DEC-772 — Real-world metric: the model's own metric, on the control group when possible.** *Context:* treated rows were acted on, so a successful campaign would read as a model failure. *Decision:* use the version's metric at the threshold in `evaluation.json` (0.5 if missing), measured on control rows when there are ≥ 50 matched control rows (both classes for a classifier), otherwise on all matched rows; `metric_basis` says which. `relative_drop_pct` is signed by metric direction, and an alert is raised when it exceeds the run's `monitoring.performance_alert_drop_pct`. *Consequences:* honest performance alerts, with a documented basis.
- **DEC-773 — `IncrementalityInput` v1 is the interface Plan B consumes.** *Context:* Plan B is not in this repository. *Decision:* `runs/<id>/incrementality_input.json` is written only when the run held out a control group: treated vs control rows, suppressed rows excluded and counted, per group and band the rows, positives and outcome rate or mean, a descriptive `observed_difference` (no interval), the window, `control_group_fraction` and the unmatched count. `schema_version` changes only on a breaking change. *Consequences:* Plan B computes intervals and lift from aggregates alone.
- **DEC-774 — Migration `0004` and `OutcomeReport` v1.** *Context:* Postgres schemas belong to Alembic; Phase 5's Monitor will read outcome reports. *Decision:* `0004` creates exactly `schedule`, `schedule_firing` and `alert`, including the unique slot index; it is reversible, and a drift test compares it to the models. `OutcomeReport` fields are only ever added to. *Consequences:* `PLATFORM_TABLES` includes the three tables.

### M49 — Scheduling, monitoring and outcomes, API (DEC-780 … DEC-786)

- **DEC-780 — Who may use the M49 routes.** *Context:* the routes need roles consistent with DEC-716. *Decision:* every read (schedules, firing history, outcome reports, incrementality input, alerts, missed firings) is Viewer; creating, changing, pausing, deleting, firing and syncing schedules, uploading outcomes and acknowledging alerts are Analyst; nothing needs Approver or Admin. Starting scoring or training by hand is Analyst, and firings act as `SYSTEM_SCHEDULER`. *Consequences:* scheduling a retrain grants no right the Analyst did not already have; a test pins it.
- **DEC-781 — "Fire now" runs inside the request and is audited once.** *Context:* M47 allows one audit event per request, and the engine firer writes its own. *Decision:* `POST /schedules/{id}/fire` calls `ScheduleFirer.fire(trigger=manual)` in the worker thread with the services copied and `audit_log=None`, and passes `firing_audit_details` to `set_audit_context`. It answers 201 with the firing as recorded, which may be `failed` with an `error_code`. *Consequences:* the dataset build runs inside the request; the training or scoring run itself goes to the job runner; paused schedules can still be fired by hand.
- **DEC-782 — The scheduler starts and stops with the app.** *Context:* a thread must never start by default. *Decision:* `install_scheduling` adds startup and shutdown handlers. For `none` the startup does nothing at all; for `local` it syncs the managed schedules, then starts `LocalScheduler`; for `eventbridge` it only syncs. Create, update and delete push to the same cached `Scheduler`. *Consequences:* a startup failure is logged at ERROR and the API keeps serving; because nothing else settles API-started firings when the backend is not `local`, `GET /schedules/{id}/firings` settles running firings first.

### M46–M47 — Sign-in and admin screens (DEC-790 … DEC-794)

Calls, tokens and latency are still metered exactly; `cost_estimate_usd` is `null`, a `PRICE_UNKNOWN` warning names the model that was missing, and the screen shows the em dash it already shows for any figure it does not have (plan §2.1, principle 5). `budget.max_calls_per_run` still bounds such a run; `max_cost_usd_per_run` cannot, and the run records that it could not. *Consequences:* an operator gets a true "we did not price this" instead of a plausible fiction, and filling the table in is a documented one-file change that turns the cost line on.
- **DEC-209 — The advanced-settings sweeps are narrowed to the use cases that train something, and the planned-entry rules move to a fixture.** *Context:* two shipped test sweeps assumed things that adding the first generative use case made false. `advanced_settings_schema` already returned no stages for `ai_type: generative` — correctly, since none of its eight stages is a choice a RAG assistant has — so seven sweeps over every use case failed on the eighth by it being exactly what it is. And `tests/unit/test_industry_config.py` proved the planned-entry rules against the one planned entry the shipped telecom file had, which Phase 3a turns into an available one. *Decision:* the settings sweep is computed off the configs (`ai_type is not GENERATIVE`), never listed by hand, and is paired with a test that a narrowed sweep still covers something and one that a generative use case really does get an empty table; the planned-entry rules are proved against a new valid fixture, `industry_with_a_planned_use_case.yaml`, so they outlive whichever use cases happen to be unbuilt. *Consequences:* the rules both tests existed to protect are still enforced, neither test needs editing when a use case is added by YAML alone (plan §2.1, principle 1), and neither passes vacuously.
- **DEC-210 — Generative artefacts get their own registry map, parallel to `ARTEFACT_REGISTRY` rather than inside it.** *Context:* `tests/unit/test_artefact_registry.py` pins `ARTEFACT_REGISTRY` name-for-name and asserts that every addition beyond plan §7 is a deliberate, commented entry in a second list; `TRAIN_ARTEFACTS` and `SCORE_ARTEFACTS` have their intersection pinned too, and the flow tests assert that every member of each was really written. A generative artefact belongs to none of those sets: `root_cause_summary.json` is not written by a run, it is written *over* one, and a scoring run that nobody asked for copy on is complete without `copy_batch.json`. *Decision:* `engine.generative.contracts.GENERATIVE_ARTEFACTS` and `GENERATIVE_TABULAR_SCHEMAS` are parallel maps, proved disjoint from the predictive ones by a test, and the artefact route serves the union. `ARTEFACT_REGISTRY` is untouched. *Consequences:* the predictive registry goes on meaning "what a run writes", which is what its tests are about; a generative artefact is served by the same URL with no special case; and the two can be told apart by which map a filename is in, which is what the `GET /runs/{id}` body needs in order to show a generative block only when there is one.
- **DEC-211 — A generative job keeps its own status document rather than appending to the run's.** *Context:* a root-cause or copy job runs over a run that has already finished. `status.json` is that run's record of how it went, with every stage `done` and a final state. *Decision:* `root_cause_status.json`, `copy_status.json` and `index_status.json` are separate documents sharing one `GenerativeStatus` model, whose stage keys are plain strings rather than `StageKey` members — a root-cause job has one step per segment and their names are data (`generate:High`), where the predictive stage vocabulary is closed and pinned by `engine.pipeline`. The state vocabulary is `RunState`, unchanged, so one screen renders either. *Consequences:* a finished run's documents are never rewritten, which is what makes them evidence; `StageKey`, `TRAIN_STAGES` and `SCORE_STAGES` do not move; and a generative job that fails leaves a status a person can read without any doubt about which run state it describes.
- **DEC-212 — The generative package has its own coded error table, and `generative_error` is the only way it raises.** *Context:* plan §13.4 wants every user-facing failure to carry a code, a message and a suggestion, and `ENGINE_ERRORS` and `SCORE_ERRORS` already do exactly that. *Decision:* `GENERATIVE_ERRORS` is a third table in the same shape; every code is a module constant; `generative_error(code, **values)` fills the template, so a code nobody wrote down raises `KeyError` at the raise site rather than reaching a user. *Consequences:* the codes are enumerable, mappable onto HTTP statuses and assertable; a new failure mode has to be described before it can happen; and `engine.errors.run_error` turns one of these into a `RunError` with no edit to that module, because it reads `code` and `message` structurally.
- **DEC-213 — The `name` PII detector is not run over free text.** *Context:* `engine.stages.ingest.PII_DETECTORS` is reused verbatim for the in-text redaction the generative engine needs, because two copies of a pattern drift. One detector does not survive the change of venue: `name` matches "one to four capitalised words", which over a column with an open vocabulary distinguishes a roster of people from a category, and inside a sentence matches the first word of every sentence, every product and every place. *Decision:* the other four run; `name` is left out, and the omission is written down where the scanner is built rather than inferred from its absence. *Consequences:* a complaint keeps its meaning after redaction instead of becoming a row of markers; a personal name genuinely written in a complaint can survive redaction, which is a real gap and is the reason complaint text reaches a prompt as a sample rather than in bulk; and nobody adds `name` back without reading the paragraph that says why it went.
- **DEC-214 — Phase 3a adds a second fake beside `FakeLLMClient` rather than changing it.** *Context:* DEC-076 built the shared fake around a digest, deliberately: visibly machine-made, reaching nothing, assertable byte for byte. That is right for a seam and wrong for retrieval — a hash embedding has no semantics, so the chunk that answers a question sits no closer to it than any other, and `[fake completion 3f2a…]` quotes no extract and cites no chunk. A RAG test against it would assert that one random number beat another, and every grounding test would pass for the wrong reason. *Decision:* `FakeLLMClient` is untouched and its tests still pin it. `GroundedFakeLLMClient` implements the same protocol, hashes words into buckets so shared vocabulary means proximity, and builds its reply out of the extracts, the evidence pack or the allowed placeholder list it was handed; `GroundedFakeMode` then breaks exactly one rule at a time. `build_client` hands the grounded one to a generative flow. *Consequences:* two fakes, which is one more than ideal and is the price of not weakening the shared one; the whole retrieval path is genuinely exercised offline; and plan §13.3 applies to both — with a fake backend, no path that renders generated text may be reachable.
- **DEC-215 — An embedding batch's tokens are estimated, and the artefact says so.** *Context:* the `LLMClient` protocol's `embed` returns vectors and nothing else, because no provider reports usage through it, and DEC-076 chose three methods and no more on purpose. The meter still has to charge a budget for the call. *Decision:* the tokens are worked out from the text with the same `APPROX_CHARS_PER_TOKEN` ratio the chunker sizes a chunk with and both fakes answer `count_tokens` with — one definition, so three parts of the system that have to agree cannot drift — and `LlmUsageReport.warnings` carries `TOKENS_ESTIMATED:embedding`. *Consequences:* an embedding's cost is good enough to budget with and is not presented as a measurement; the alternative, a `count_tokens` round trip per text, would have cost a real API call per chunk to improve a number nobody bills from.
- **DEC-216 — PII found in a knowledge document is a warning; PII found in complaint text is redacted.** *Context:* the same detectors run over both, and the obvious consistency — redact everywhere — is wrong in one of the two places. A knowledge document is the client's own published material, and the support address, escalation number or sample account format printed in it is frequently the very thing a question is about; redacting it damages the answer and leaves the assistant citing `[REDACTED:email]` as the address to write to. Complaint text is a customer's own words, was never published, and reaches a prompt only as evidence. *Decision:* `build_index` records `PII_IN_DOCS:<kinds>` on the manifest, names the kinds and never a value, and indexes the text exactly as written; `redaction.redact` is applied to every complaint before it is put in an evidence pack. *Consequences:* an operator uploading a document that genuinely should not have been published is told, in the artefact, which kinds were seen and in which document, and can withdraw it — the engine does not decide that for them; a customer's words never reach a model unredacted; and the asymmetry is written down here rather than read as an oversight in whichever module is looked at second.
- **DEC-217 — A chunk is embedded with its document and heading in front of it, not bare.** *Context:* heading-aware chunking already guarantees `Chunk.section` is a fact rather than a guess, and that fact was being thrown away at the one moment it is worth most. The words a question uses are very often in the heading and nowhere in the prose beneath it: "Late payment and reconnection" is the entire vocabulary of "what is the late payment fee?", while the paragraph under it says "a fee of ₹100 or 2% of the outstanding amount, whichever is higher" and never repeats the heading at all. *Decision:* `chunking.embedding_text` renders a chunk as `"<doc id> <section>\n\n<text>"` and `build_index` embeds that; `Chunk.text` is untouched, so a citation still quotes the document's words and the prompt still receives the passage. The question is embedded bare — the prefix is context the passage lacks, not a format both sides must share. `doc_id` is used rather than `document` because a filename carries an extension, and "pdf" is a word in every chunk of every PDF. *Consequences:* measured over the 45 answerable questions of the reference set, the right document is retrieved 40 times where the bare passage managed 28, and the margin between a real question and an off-topic one *widens* rather than narrowing, because a heading is specific where a body paragraph is discursive; an index built before this change embeds differently from one built after, so the change is a rebuild and `ChunkConfig` records the settings that produced each index.
- **DEC-218 — The similarity floor is calibrated per embedding model, and the shipped default is calibrated for a real one.** *Context:* `min_similarity: 0.25` decides whether the assistant refuses without calling a model, so it is the single most consequential number in the RAG config — and it is not portable. A real embedding model places all its vectors in a narrow cone, where a relevant pair scores 0.3 to 0.9; `GroundedFakeLLMClient` hashes words into buckets, where vectors really are near-orthogonal and a relevant pair scores 0.2 to 0.4. The same threshold means different things to the two. *Decision:* the shipped `0.25` is calibrated for the Bedrock embedding model and is not moved to suit the fake. A generative test that needs a particular retrieval outcome sets its own floor, and the reference-set score produced under the fake is a smoke number that proves the evaluation runs, never a quality gate — the quality claim is a Bedrock claim, made under `-m bedrock`. *Consequences:* the floor cannot be asserted as a constant across backends, and the `ChunkConfig` on every index records which embedding model produced it so the question "is this floor right for this index?" is answerable; changing embedding model is a re-calibration, not a swap.
- **DEC-219 — A lexical fake cannot exercise the floor's refusal on an off-topic question that shares the domain's vocabulary.** *Context:* the two refusal paths are different mechanisms and only one is reachable offline. "Can you recommend a competitor with a cheaper plan?" shares almost no vocabulary with the corpus, scores 0.154 against every chunk and is refused by the floor with no model call at all. "How many employees does Northwind Telecom have?" scores 0.289 — above several genuine questions — because the brand name and the question words appear in every document; a bag of words has no way to tell it apart, where a real model separates the two on meaning. *Decision:* the floor path is tested with a question whose vocabulary is genuinely disjoint, which proves what the test claims — nothing survived, no model was called. The prompt-level refusal is tested with `GroundedFakeMode.REFUSING`, which exercises the parse and the artefact without pretending the floor caught it. The same-domain off-topic case is a Bedrock assertion. *Consequences:* no test asserts a refusal the fake produced for the wrong reason, which is the failure mode this whole grounded fake exists to avoid; and the gap is written down, so a later reader does not add the "obvious" missing test and quietly pin noise.
- **DEC-220 — An incremental rebuild decides what to re-embed from the document's fingerprint, never from the chunk id.** *Context:* `chunk_id` is `(doc_id, ordinal)` and nothing else, which is what makes a rebuild of an unchanged document produce byte-identical chunks. It also means an *edited* document produces chunks with exactly the same ids as the ones it replaced. Carrying vectors over from the previous index by matching on chunk id therefore hands a rewritten passage the vector of the passage it replaced, and the index goes silently stale — the text updated, the vectors not. In a retrieval system that is the worst available failure: a question matches on wording that is no longer in the document and is answered from text nobody searched for, with a citation that looks perfectly ordinary. It was written that way first, and measured: after rewriting a document end to end, its stored vector was still cosine 1.0000 with the *old* text and 0.19 with its own. *Decision:* `_index_one` already works out whether a document's fingerprint moved, and `_embed` takes that answer as `fresh` and excludes those chunk ids from what may be carried over. A fingerprint is the only evidence that a re-embed is needed. *Consequences:* the saving survives intact — rebuilding three documents unchanged embeds nothing at all, and editing one of them embeds exactly that document's chunks — while a stale vector is now unreachable rather than merely unlikely; and the test that pins it edits a document's bytes rather than only adding one, because adding a document exercises none of this.

## Public dataset library (DEC-400 … DEC-449)

The `library/` branch reserves DEC-400 … DEC-449. Its entries are about **configuration and data**,
never about engine behaviour: where a dataset needed the engine to change, the branch filed a
[cross-branch request](CROSS_BRANCH_REQUESTS.md) instead and the entry below says which one.

- **DEC-400 — The library's industries and use cases live in `library/configs/`, a second config root, not in `configs/`.** *Context:* the library adds four industries (banking, insurance, e-commerce, ad-tech) and four use cases to prove the "one engine, many industries" claim by configuration alone, and `configs/industries/*.yaml` and `configs/use_cases/*.yaml` are the branch's to add new files to. Two assertions in `tests/unit/test_config_loading.py` forbid it: `list_industries() == ("telecom",)` pins the industry directory to exactly one file, and `sorted(available) == sorted(list_use_case_ids())` pins the telecom industry to listing *every* shipped use case. A third, `test_templates_are_up_to_date`, then requires a generated pair in `templates/`, which is not this branch's either. Adding the files as granted would leave `make test` red on a shared branch. *Decision:* the four industry files, the four use-case files and their generated templates go in `library/configs/`, which the engine already supports as a config root (`MARKETING_AI_CONFIG_DIR`, or `root=` on every loader, DEC-038); `library/configs/engine.yaml` is a **symlink** to `configs/engine.yaml`, so there is exactly one copy of the defaults and nothing to drift. `library/run_engine.py` takes `--config-root`. The two test assertions are filed in `docs/CROSS_BRANCH_REQUESTS.md` as *two assertions forbid a second industry*. *Consequences:* `git status` on this branch shows `library/` and two appended documents and nothing else — no existing file is touched and no test breaks; the library's industries do **not** appear in the running product until that request is resolved, at which point moving them is `git mv library/configs/industries/*.yaml configs/industries/` plus `make generate`; the `telco-churn` dataset, which reuses a shipped use case, runs against the repository's own `configs/` and proves the same point inside the product.
- **DEC-401 — UCI Online Retail (2010–2011) stands in for Online Retail II.** *Context:* the brief names "Kaggle Online Retail II / any e-commerce transactions set". Online Retail II is published only as an `.xlsx` on `archive.ics.uci.edu`, which the environment's egress policy blocks; the 2010–2011 Online Retail CSV is reachable through a mirror. *Decision:* use Online Retail (541,909 invoice lines) and say which file it is, in `library/online-retail/README.md` and in `LICENSE.txt`. *Consequences:* the schema, the retailer and the aggregation story are identical and only the date range differs; swapping in Online Retail II later is a change to `SOURCE_URL` and three date constants in `fetch.py`.
- **DEC-402 — The win-back label is a 90/90 window around a 2011-09-10 snapshot, and the audience is the lapsed cohort only.** *Context:* a transaction log has no target; one has to be defined, and the definition decides whether the file is honest. *Decision:* the snapshot is the last date in the log minus 90 days, so every shopper's outcome window is complete and nobody is labelled "did not return" because the data ran out; a shopper is in the audience when their last purchase is at least 90 days before the snapshot (1,463 of the 4,338 customers with at least one non-cancelled purchase; the log names 4,372 in all); `reactivated_90d` is 1 when a non-cancelled purchase falls in the 90 days after it. Every feature aggregates invoice lines dated on or before the snapshot, and `fetch.py` asserts `recency_days >= 90` on every row, which cannot hold if a post-snapshot purchase leaked into a feature. *Consequences:* 1,463 rows and 41.3 % positives, both above the engine's floors; the positive rate is high because the audience is pre-filtered to lapsed shoppers, which is the population a win-back budget is actually spent on; the "41 % come back with no intervention" figure is the bar any campaign has to beat, and is stated in the run report.
- **DEC-403 — `duration` stays in the bank file, and the leakage argument is made in the run report instead.** *Context:* UCI's notes say `duration` (call length, known only after the call) should be discarded for a realistic model. Dropping it in `fetch.py` would have been safe and would have hidden the more interesting question: does the engine notice? *Decision:* keep it, run the defaults, and report what the engine said — which is nothing, correctly, because none of `LEAKAGE_SUSPECTED`'s three branches describes a column that does not *contain* the answer but merely does not exist yet. Then run a second time with `prepare.exclude_columns: ["duration"]`, one configuration override and no code, and report both. *Consequences:* the library carries the clearest statement it can make about the limits of automated leakage detection: ROC-AUC 0.9509 with the column, 0.7906 without, and no check able to tell the two apart; the second run is the model anyone should use, and the demo script shows them in that order.
- **DEC-404 — Dotted column names are renamed in `fetch.py`, not worked around by emptying the template.** *Context:* `TemplateColumn.name` must match `^[A-Za-z_][A-Za-z0-9_]*$`, and two datasets publish dotted names — `emp.var.rate` and three siblings in the bank file, and the *target* `default.payment.next.month` in the credit-card file. The alternative was to leave `template.columns` empty, which costs the use case its generated template and its `TARGET_MISSING` hint. *Decision:* rename to the underscored form in preparation and record every rename in `mapping.yaml`, which is exactly what a mapping layer is for; file the restriction in `docs/CROSS_BRANCH_REQUESTS.md` (*a template column name cannot contain a dot*) so it is either widened or written down in the data contract. *Consequences:* both use cases carry full templates; the source names survive in `mapping.yaml` so nothing is lost; when Phase 2's column-mapping UI lands, these renames are rows in it rather than a script.
- **DEC-405 — A derived primary key is the 1-based row number in the published order.** *Context:* the bank file and the Criteo file ship no key, and the data contract requires one. *Decision:* add `client_id` / `impression_id` as the 1-based row number in the file's own published order, which is documented as meaningful (the bank rows are in campaign-call order) and is stable for a given download. *Consequences:* the key identifies a row rather than a person, which is the honest reading and is said in both READMEs; the engine never uses a key as a feature, so nothing can learn from it; re-downloading a file that has been re-ordered upstream would re-number the rows, which is why `mapping.yaml` records the derivation.
- **DEC-406 — Criteo Uplift is mapped and drafted but not installed, not fetched and not trained.** *Context:* two independent reasons. The question the dataset exists to answer is uplift, which plan §12 puts in Phase 3; a propensity model on `conversion` would train happily and rank users by how likely they are to convert *anyway*, which is the mistake uplift modelling exists to prevent. Separately, `go.criteo.net`, `huggingface.co` and every mirror tried are blocked by the environment's egress policy, so no byte of the file was ever obtained. *Decision:* `library/configs/industries/ad_tech.yaml` lists `criteo-uplift` as **planned**; the use-case file is drafted at `library/criteo-uplift/use_case.yaml` rather than installed, so the engine cannot offer a model it cannot make honest; `fetch.py` is written against the published URL and carries a `verify()` step, and is labelled as never having been run; there is no `sample.csv`, no committed data and no metric anywhere for this dataset, and `run_report.md` says so in its first line. *Consequences:* the library has five runs and six mappings, which is what the brief asked for; the three things Phase 3b needs (a `treatment` column role, an uplift metric, uplift model families — the last two already recorded as cut in DEC-009) are written down where the next person will find them.
- **DEC-407 — The library's use cases set both suppression columns to `null`.** *Context:* the engine defaults to `suppress_opted_out: true` with `opt_out_column: marketing_opt_in` and `suppress_recently_contacted: true` with `last_contacted_at`. No public dataset carries either column, so every run would raise two `SUPPRESSION_COLUMN_MISSING` warnings. *Decision:* set both to `null`, following `telco_churn.yaml`'s own precedent and its comment ("the public file carries no consent or contact history"), so the configuration says what is actually true rather than warning about it on every run. *Consequences:* the validation reports are about the data rather than about a setting that was never going to apply; a customer file that *does* carry consent columns turns the switches back on with two YAML lines; `docs/LIBRARY.md` notes that no dataset in the library can demonstrate suppression, which is a gap in the demo rather than in the engine.
- **DEC-408 — Raw and prepared data are git-ignored; a seeded 5,000-row `sample.csv` is committed.** *Context:* the brief caps committed raw data at 20 MB and asks for a sample of at most 5,000 rows; the downloads run from 0.9 MB to 45 MB. *Decision:* `library/.gitignore` excludes `*/data/` and `.runs/`; each `fetch.py` writes `sample.csv` as a `random_state=20260922` sample of at most 5,000 rows, sorted back into file order. *Consequences:* a clean checkout can run every library test without a network; rebuilding a dataset is one command; the online-retail sample is all 1,463 prepared rows, because the whole file is already under the limit.
- **DEC-409 — The library's tests live in `library/tests/` and are not in pytest's default `testpaths`.** *Context:* `pyproject.toml` sets `testpaths = ["tests"]`, and each library test trains a real model for about a minute. *Decision:* leave `testpaths` alone — it is not this branch's file — and put the tests in `library/tests/`, run on purpose with `python -m pytest library/tests`. They are marked `slow` and `integration`, the markers `pyproject.toml` already declares. *Consequences:* `make test` and `make test-all` are unchanged; the library's tests are opt-in and documented in `library/README.md` and `docs/LIBRARY.md`.
- **DEC-410 — The library tests assert "not materially worse than the baseline" plus a per-dataset ROC-AUC floor; they assert strictly beating the baseline only where it is reproducible, and on one dataset they assert no score at all.** *Context:* the brief asks each library test to assert that test AUC beats the baseline, on a `fast`, one-minute train over the committed sample. Measured over repeated runs of exactly that budget — thirty-three in all, fifteen of them re-measured after the merge turned hyperparameter tuning on (DEC-073) — the comparison is a coin flip for three of the five datasets. On the current engine: `uci-credit-default` beat its baseline 3 times of 3 by +0.0522 at worst, `uci-bank-marketing` 3 of 3 but by as little as +0.0091, `telco-customer-churn` 2 of 3 with a worst margin of −0.0025, `health-insurance-cross-sell` 2 of 3 at −0.0035, and `online-retail` 2 of 3 at −0.0484. The model and the baseline are fitted on the same rows and the winner is often a logistic regression either way, so on a few thousand rows with a sixty-second budget they are separated by noise. `online-retail` is worse than noisy: 1,463 rows give a 219-row test split, and nine runs across the two engines produced ROC-AUC from 0.5307 to 0.6907. Asserting the strict comparison everywhere would make the suite flaky, and the usual repair — a floor or a tolerance lowered until the test stops failing — is a number chosen to make a test pass, which hides real regressions. *Decision:* three tiers. Every library test asserts what does not flip: the run finishes, validation passes with no errors, and (where a floor is meaningful) test ROC-AUC clears one recorded from observed runs with 0.05 to 0.09 of headroom. It then asserts `test_roc_auc >= baseline_roc_auc - 0.02`, stated for what it is — a one-minute search must never be *materially* worse than a logistic regression — where 0.02 is about four times the largest shortfall measured on the four datasets that use it (0.0054). `uci-credit-default`, whose margin is an order of magnitude clear of that noise and which has now won 6 of 6 across both engines, additionally asserts the strict comparison the brief asks for. `online-retail` asserts **no score at all**: its worst run lands 0.0627 below its baseline, more than three times the tolerance, so even the weaker statement would fail. Instead it checks that the aggregation produced 1,463 rows and 13 features, that the derived target carries both outcomes, that the validator reports exactly the one `CONSTANT_COLUMN` finding, and that a baseline comparison was computed and is readable. Each test's docstring lists the runs its numbers came from, on both engines where both were measured. *Consequences:* the suite fails when something is broken rather than when a sixty-second search lands on the other side of a coin flip — it survived the engine gaining hyperparameter tuning underneath it without a single floor moving, which is the property being bought; the brief's assertion is kept where it is reproducible and replaced by weaker true statements where it is not, rather than by a tolerance dressed up as the original; and the win-back negative result stays visible in `docs/LIBRARY.md` and in its run report instead of being absorbed by a test that passes anyway.
- **DEC-411 — `retail-win-back` optimises PR-AUC; every other library use case keeps the engine's `roc_auc`.** *Context:* the win-back audience is 41 % positive and the business question is "who is worth spending an offer on", which is a question about the positives. *Decision:* `model_search.metric: pr_auc` in `retail_win_back.yaml`; `pr_auc` is already in the engine's default `metric_choices`, so this is one line and no code. *Consequences:* the leaderboard in that dataset's run report is ranked on PR-AUC and says so; the `roc_auc` numbers are still reported, because `evaluation.json` carries every metric valid for the problem type.
- **DEC-221 — A document's identity across a rebuild is its fingerprint *and* its id, never either alone.** *Context:* the incremental rebuild reused a document's chunks whenever its fingerprint appeared in the previous manifest. The fingerprint answers "are these the same bytes?" and nothing more, and on its own it breaks two ways that look unrelated and are not. A file renamed between builds keeps its bytes, matches on fingerprint, and is handed the previous manifest's entry — which carries the *old* filename, so every citation goes on naming a file that no longer exists. And two different files with identical bytes, a policy attached twice under two names or a duplicated upload, both match that one entry, so one document's chunks are written into the index twice and two rows carry the same `chunk_id`. *Decision:* `_reusable_chunks` is keyed on `(fingerprint, doc_id)`, and a rebuild may reuse chunks only when both halves match. *Consequences:* a file that was only renamed is re-embedded, which is the right trade — `chunk_id` is built from `doc_id`, so its chunks really are different chunks and reusing them would put the wrong id on every one of them; and a duplicated upload now contributes its own entry and its own ids instead of corrupting its twin's.
- **DEC-222 — An unreadable reply is dropped, not relabelled.** *Context:* `assistant._parse` documented that "showing a customer an unparsed blob would be worse than saying the documents do not cover it", and then returned the blob itself as the answer text with `refused=True`. The flag was honest and the screen was not: `AssistantAnswer.answer` is what a caller renders, so the unparsed reply reached the customer anyway. *Decision:* when the reply is not a JSON object it is discarded and the operator's configured refusal sentence is returned in its place, with a `MODEL_OUTPUT_MALFORMED` guardrail check recording that the parse is what failed. The reply is not lost — it is what the model was metered for. *Consequences:* every path out of `answer` now renders either a grounded answer or a sentence the operator wrote, which is what "grounded or nothing" has to mean at the boundary where text becomes a screen; and a malformed reply is visible as a guardrail outcome rather than as a strange-looking answer.
- **DEC-223 — Every guardrail check on one answer is targeted at the same thing.** *Context:* `answer.guardrails` is one tuple assembled from two places. `Guardrails.check` targets the question; `_parse` targeted its `UNKNOWN_CITATION` check at the answer's first 60 characters. A reader of that tuple could not tell which rows meant which, so the column was unreadable rather than merely inconsistent. *Decision:* `_parse` takes the question and targets it, matching what is appended beside it. *Consequences:* `target` means one thing in the artefact, so a screen can show it as a column and a test can assert on it.
- **DEC-224 — A search refuses an index whose two files disagree, rather than pairing a passage with another passage's vector.** *Context:* an index is two Parquet files, written separately and each atomically. That makes either file whole on its own and says nothing about the pair: a crash between the two writes, or an overwrite of an id something is reading, leaves one new file beside one old one. `exists()` is then true, and `search` zips `chunks[i]` with `matrix[i]` — so every similarity is measured against a different passage than the one returned, and the answer comes back with an ordinary-looking citation attached. Where the counts differ it was an `IndexError` from deep inside NumPy; where they happen to match it was silent. *Decision:* `search` compares the two lengths and raises `INDEX_CORRUPT`, naming both counts and telling the operator to rebuild. *Consequences:* one comparison per search, against a failure that is otherwise invisible and produces confidently wrong citations; and the docstring's "an index is written whole or not at all" is now true of the pair rather than of each file separately, which is what a reader took it to mean.
- **DEC-225 — `mmr` sorts its candidates rather than trusting that they arrived sorted.** *Context:* the docstring promises that the first pick is always the best raw match, which is what makes a reader who checks the top citation find the passage they expected. The implementation took `remaining.pop(0)`, so the promise held only because every caller in the tree happens to hand over a similarity-ordered list. It is a precondition the signature does not state and the type does not carry, and a direct caller passing an unordered list would get whichever candidate happened to be first as the top citation - no error, and a plausible answer. *Decision:* `mmr` sorts by similarity itself. It is a no-op for both existing callers. *Consequences:* the docstring is now true of the function rather than of its current callers, and `mmr` can be reused without a comment explaining what has to be done before calling it.
- **DEC-226 — A citation's quote is checked against the chunk it names, and dropped when the chunk does not contain it.** *Context:* `Citation.quote` is documented as "at most 25 words copied from the chunk", and `docs/GENERATIVE.md` said the same. Neither was true: `assistant._parse` built the quote as `" ".join(str(entry.get("quote", "")).split()[:QUOTE_WORDS])` from the model's own citation object, so the engine enforced the length and nothing else. Every other field on a `Citation` — the chunk id, the document, the heading, the similarity — is copied from the match the engine retrieved, which makes an unchecked quote the single invented thing in a row of otherwise real provenance, shown to the reader who is checking the claim precisely because they did not want to take it on trust. The extract *number* was already checked; the words attributed to it were not. *Decision:* `_verified_quote` looks for the trimmed quote in the cited chunk's own text, with case and runs of whitespace flattened on both sides — a passage crosses a template and comes back inside a JSON string, so a faithful copy can arrive re-wrapped, and refusing those would throw away quotes exactly as checkable as the ones that survive. A quote that is not found is replaced by an empty string and an `UNSUPPORTED_QUOTE` guardrail check, targeted at the question like every other check on an answer (DEC-223). The citation itself stands: what the model got wrong was the quote, and the chunk id, document, heading and similarity remain the engine's own facts. A reply that quoted nothing — an absent, blank or `null` quote — claimed no words and so invents none, and records no check. *Consequences:* a fabricated quote can no longer be rendered under a real document and a real heading; the artefact's own field description becomes true rather than aspirational; a screen must render an empty quote as no quote rather than as an empty box; and a cooperative model loses nothing, which the grounded fake's end-to-end answer proves rather than assumes.
- **DEC-227 — `budget_usd` is null whenever any call went unpriced, and the cost ceiling promises "not one call more" rather than "not a cent more".** *Context:* two claims about `Meter` were stronger than the code. `budget_usd` returned `None` only when the price table was *entirely* empty, so a half-filled table — a deployment that priced its generating model and not its judge — reported a real ceiling into `llm_usage.json` while `_all_priced` was false and `_check_budget` silently skipped the cost test: a ceiling on a screen that nothing was being checked against, which is exactly the pretence DEC-208 and this module's own docstring say cannot happen. And `_check_budget` compares what has *already been spent* against the ceiling, so the call that reaches the ceiling has already been paid for and the job ends at or above `max_cost_usd_per_run`, where the module docstring and `docs/GENERATIVE.md` both said "not a cent more". *Decision:* `budget_usd` returns `None` when the table is empty **or** any call so far could not be priced, which is the same condition `cost_so_far` already reports null under — the ceiling in the artefact is now the ceiling being tested, or nothing. `_check_budget` then needs no separate `_all_priced` test, because asking `budget_usd` is that test. The before-the-call comparison stays as it is and the documentation is corrected instead: what a call will cost is known only once it comes back, since the output tokens are the model's to choose, so the honest promise is that a run stops at the first call after its spending reached the ceiling. *Consequences:* a partly priced deployment has no cost ceiling at all and says so, and `max_calls_per_run` — which needs no prices — is what still stops it; the alternative, projecting a call's cost from `max_output_tokens` and refusing on the projection, would bound the total with a number nobody measured, which plan §13.3 forbids as squarely for cost as for an accuracy score; and the tests now assert the weaker true statement (spending at the stop is at or above the ceiling, and not one further call is made) instead of the stronger false one.

## Phase 4a — AWS implementations and deployment (DEC-300 … DEC-399)

Phase 1 put storage, jobs and the model registry behind protocols so that AWS would be a set of new
*implementations* rather than a rewrite (plan §12). Phase 4a writes those implementations. The
numbering is allocated by area so that entries written in parallel could not collide, and a block
with a gap in it has a gap because nobody had a tenth decision worth writing down, not because one
is missing:

| Block | Area |
|---|---|
| DEC-300 … 311 | Settings, secrets, and the protocol seams |
| DEC-312 … 323 | `S3Storage` and the shared storage conformance suite |
| DEC-324 … 337 | `JobSpec`, the SageMaker job runner, the container entrypoint and the price table |
| DEC-338 … 348 | Postgres metadata, Alembic, and the model registry over S3 |
| DEC-349 … 360 | The container, the local stack and the pipelines |
| DEC-361 … 379 | The CDK infrastructure |
| DEC-380 … 399 | Observability and the two documents |

Two rules run through every entry below. **Local behaviour does not change**: every default
reproduces Phase 1 exactly, and where that is not obvious the entry says how it is enforced rather
than merely intended. And **no number that was not measured** (plan §13.3): a constant that was
chosen says so in its own docstring, a cost that was not measured is absent rather than estimated,
and a published list price is labelled as a rate card and never as a bill.

---

- **DEC-300 — One `Settings` object describes a deployment, and its defaults reproduce Phase 1 exactly.** *Context:* Phase 1 answered "where do the artefacts live" with two environment variables read at the point of use — `MARKETING_AI_DATA_DIR` in `engine/storage.py`, `MARKETING_AI_CONFIG_DIR` in `engine/config.py`. That is enough for one machine and one backend; Phase 4a has three backends per concern, and an operator has to be able to supply the answer from Parameter Store. *Decision:* `engine/settings.py` holds one frozen pydantic model with the whole answer, built by explicit loaders — `Settings.from_env`, `settings_from_aws` and `load_settings`, which picks between them — rather than by `pydantic-settings` (which `tests/unit/test_pyproject_pins.py` forbids as a dependency, and whose `settings_customise_sources` is a worse fit for a four-source merge than fifteen lines of explicit precedence). `Settings()` with nothing set selects the local filesystem, SQLite and a two-worker thread pool, in the same directory and with the same worker count Phase 1 used, and the two existing environment variables keep their spelling. *Consequences:* local behaviour is unchanged *by construction* rather than by anyone remembering to keep it that way, and `tests/unit/test_settings.py` asserts every one of those defaults so a later edit cannot drift them; nothing that set the old variables has to change; and there is one table to read rather than a scattering of `os.environ` calls to find.
- **DEC-301 — Precedence, lowest first: SSM parameters, the Secrets Manager document, then the process environment.** *Context:* a deployment reads from three places and they will disagree. *Decision:* the order above, implemented once in `settings_from_aws` and unit-tested on its own. *Consequences:* the environment beating AWS is the deliberate part: it is what lets an operator override one value on a task without editing a parameter, and what lets a test point a deployed shape at a local directory. A caller that wants to force a value passes an `environ` mapping rather than keyword overrides, so there is one precedence rule to read and not two.
- **DEC-302 — A backend that cannot work is refused where it is described, not at the first request that needs it.** *Context:* `storage_backend=s3` with no bucket is a deployment that will fail, and the only question is when. *Decision:* a model validator refuses an incomplete backend at construction: s3 without a bucket, postgres without a URL, sagemaker without a role, an image, both instance types and a region — and sagemaker without s3, because a remote job cannot read a local disk. *Consequences:* the failure arrives at startup with the field named, rather than at the first upload with a `KeyError`; `SettingsError` carries a code and the name of the variable to export, and `api/main.py` renders it as a 503 (the process is healthy, the configuration is not).
- **DEC-303 — A secret is invisible by default, and no construction path can put one in a message.** *Context:* `postgres_dsn` carries a password. Pydantic's `ValidationError` renders the whole input mapping as `input_value=...`, truncated in the middle — measured here: a long URL comes out mangled and a short one comes out whole. "Happens to be truncated" is not a guarantee. *Decision:* secret fields are `SecretStr`; `redacted()` replaces them; `summary()` renders an explicit *allow-list* of non-secret fields and `__repr__`/`__str__` are built from it; and every loader converts pydantic's report into a `SettingsError` through one `_invalid` helper, whose message names the variable to export and never the value. *Consequences:* a secret field added in a later phase is hidden until somebody deliberately adds it to `SUMMARY_FIELDS`, which is the safe direction for the mistake to fall; and there is no remaining constructor that can leak one.
- **DEC-304 — An unrecognised `MARKETING_AI_*` variable is refused, with a written-down escape list.** *Context:* a misspelt parameter name is invisible: the setting simply has no effect, and the first sign is somebody wondering why. *Decision:* the check is made where it can actually be acted on — at the deployment. `ENV_VARS` is the frozen field-to-variable table, `NON_FIELD_ENV_VARS` is the explicit list of `MARKETING_AI_*` names that deliberately are not settings (the job-spec key the container is handed, the failure file SageMaker reads, and the two variables the Postgres fixtures use), and `tests/infra/test_task_definition.py` fails the build when a synthesised task definition sets a `MARKETING_AI_*` variable that is in neither. *Consequences:* a typo in a CDK file is a red test rather than a setting that silently had no effect; adding a non-setting variable is a visible act rather than a silent exemption. This is narrower than refusing an unknown variable inside `from_env`, which would make the application refuse to start over a `MARKETING_AI_*` name some *other* tool on the host happened to export — a failure mode the deployment check does not have.
- **DEC-305 — Parameter Store holds the settings, Secrets Manager holds the one credential, and a parameter may be named either way.** *Context:* two stores answer two different questions, and the IAM a task role needs differs for each. *Decision:* plain `String` parameters under a flat, non-recursive `/marketing-ai/<env>/`, and one JSON document at `marketing-ai/<env>/app` for the database URL. A parameter leaf is accepted as the bare field name (`s3_bucket`) or as its environment spelling (`MARKETING_AI_S3_BUCKET`), and a leaf matching neither is ignored. *Consequences:* the task role can be granted `ssm:GetParametersByPath` on one prefix and `secretsmanager:GetSecretValue` on exactly one secret, which is a boundary a reviewer can check at a glance; and Parameter Store stays a shared namespace that a later phase can put its own things in without this version refusing to start.
- **DEC-306 — Nothing under `engine/aws/` imports boto3 at module scope, and the AWS packages are an optional extra.** *Context:* a laptop checkout must keep importing `engine.settings`, `engine.storage` and `engine.registry` for free, and `make test` must keep working without the cloud dependencies. *Decision:* `boto3`, `botocore`, `psycopg[binary]` and `alembic` are the `aws` extra; the CDK packages are a separate `deploy` extra; every AWS import sits inside the function or constructor that needs it; and the factories in `engine/settings.py` import a backend's module only in that backend's branch. *Consequences:* the cost and the failure both land on the caller who actually asked for AWS; a local install stays exactly as heavy as it was; and `tests/integration/test_design_rules.py` asserts the rule rather than trusting it. Note that boto3 was *already* a transitive dependency through `autogluon-common` — the extra declares and pins what was there rather than adding weight.
- **DEC-307 — A production deployment may not inherit the laptop's wide-open CORS.** *Context:* DEC-024 left `allow_origins=["*"]` because the Phase 1 UI is opened as a local file. That is a statement about a laptop, not about an internet-facing load balancer, and a deployment that never mentions CORS would inherit the laptop's answer by omission. *Decision:* `cors_origins` defaults to `("*",)`, so nothing local changes, and `Settings` refuses `env=prod` while it is still `*`. `create_app` also refuses `data_dir=` combined with a non-local storage backend, because `data_dir` is how the whole test suite points the app at a `tmp_path` and a stray environment variable must not be able to redirect a test's artefacts into a bucket. *Consequences:* the narrowing has to be a deliberate act on the one deployment where it matters; `data_dir` keeps outranking everything, which is what makes the existing suite safe.
- **DEC-308 — `engine/settings.py` decides *what* to construct; `api/deps.py` remains the only place the API constructs it.** *Context:* the repository's standing rule is that `api/deps.py` is the single construction site. A SageMaker container has no `api/deps.py` at all and must build the same objects from the same description. *Decision:* `build_storage`, `build_registry` and `build_services` live in `engine/settings.py` and are called by both; `api/deps.py` keeps its `_LOCK`, its `app.state` caching and its rule that `create_app(data_dir=…)` wins. *Consequences:* the API and a job can never disagree about where the artefacts are; the rule is restated rather than broken. One correction was needed while writing it: `_LOCK` is not reentrant, so every provider now resolves its dependencies *before* taking it — constructing inside the critical section would have deadlocked the first request.
- **DEC-309 — The AWS wire loggers are capped at INFO wherever a client is first built.** *Context:* botocore at DEBUG prints request headers and query strings, and therefore pre-signed URLs, which are bearer credentials. Setting the engine's own level to DEBUG must not turn that on by accident. *Consequences:* `quiet_aws_wire_logs()` raises the level of `botocore`, `boto3`, `urllib3` and `s3transfer` to INFO if they are lower, and never lowers one that is already quieter.
- **DEC-310 — One layout for a published model prefix, and the unused second one is deleted.** *Context:* `engine/storage.py` defined `model_key(model_id, …)` → `models/<model_id>/…`, which had no call site anywhere and which the Phase 4 notes already flagged as unused. Phase 4a needs `models/<use_case_id>/<version>/…`. Two conventions for one prefix in one tree is an invitation to use the wrong one. *Decision:* `model_key` is deleted and `published_model_key(use_case_id, version, *parts)` replaces it. *Consequences:* the use case and the version are in the key in the order a human browses a bucket in, and it is the boundary an IAM prefix condition can be written against; the only cost is one test that changed with it.
- **DEC-311 — A capability that only some stores have gets its own protocol, never a member on `Storage`.** *Context:* `S3Storage` needs two things `LocalStorage` does not: an explicit publish for the write direction of `local_path()`, and a pre-signed download URL. Adding either to the `Storage` protocol would break `isinstance(x, Storage)` for `LocalStorage` and for every structural fake in the suite — which `tests/unit/test_storage.py` asserts — and would contradict the phase's own rule that AWS is implementations, not protocol changes. *Decision:* `SupportsLocalMirror` and `SupportsPresignedDownload` are declared *beside* `Storage`, and four free functions dispatch to them and no-op (or return `None`) on a store that lacks them. The same shape is used for `ReconcilingJobRunner` on the job side. *Consequences:* call sites such as `engine/stages/train.py` and `engine/pipeline.py` call the free function unconditionally and a local run is bit-for-bit unchanged; both protocols' member lists are now documented as frozen, with the reason; and a new capability later follows an established pattern instead of reopening the question.
- **DEC-312 — `local_path()` is a read-through mirror on a remote store, and the write direction is an explicit `publish_local_path(key)`.** *Context:* `local_path()` is the protocol's one escape hatch, for AutoGluon and pyarrow, which insist on a real directory. Over S3 that path cannot be the store. Reading can be made transparent - hydrate the tree out of the bucket on first use - but writing cannot be inferred: a `Path` has no close event, AutoGluon writes the predictor tree through the filesystem and the store is never called again, so nothing exists to trigger an upload. *Decision:* `S3Storage.local_path(key)` hydrates the object or the whole `key/` subtree into a per-instance mirror on first use and returns a path that, exactly as `LocalStorage` does, need not exist. The write direction is `publish_local_path(key)` from `SupportsLocalMirror`, dispatched by the free function in `engine/storage.py` that no-ops on a store without the capability. The engine has exactly one write-direction call site: `engine/stages/train.py`, immediately after `predictor.save()` and before the leaderboard, the scorer fit or anything else that can raise. *Consequences:* A local run is bit-for-bit unchanged - the dispatcher returns `()`. A remote run publishes the predictor at the first moment it is complete, so a later failure in the same stage cannot lose it. AutoGluon 1.6.3 was measured not to write into the predictor directory after `save()`, so nothing is missed by publishing there. The cost is that a new call site which writes through `local_path` and forgets to publish loses its bytes on S3 and not on disk; the conformance suite tests the round trip through a second independent store so the pattern is at least demonstrated once.
- **DEC-313 — a publish is content-diffed against a SHA-256 this module writes as user metadata, not against the ETag.** *Context:* `publish_local_path` has to be cheap to call twice: the train stage publishes a predictor tree that a later stage may already have mirrored. The obvious diff key is the ETag, but an ETag is the MD5 of the body only for an unencrypted single-part upload - it is neither stable across the multipart boundary nor meaningful at all under SSE-KMS, which is exactly the configuration a production bucket runs in. *Decision:* Every upload this module makes carries `x-amz-meta-content-sha256`. Single `PutObject` writes hash the buffered body at commit; a mirror publish hashes the file first, because multipart metadata can only be set at `CreateMultipartUpload`. `_publish_file` compares size first (free), then the digest, and skips the upload when they match. An object with no digest metadata is treated as different, re-uploaded once, and stable from then on. *Consequences:* A second publish of an unchanged tree costs one `HeadObject` per file and no bytes, under SSE-KMS as much as without it. A large multipart body written through plain `open_write` carries no digest and will be re-uploaded once if it is ever published from a mirror. Nothing depends on S3's ETag algorithm, so changing `PART_BYTES` later cannot silently invalidate every diff.
- **DEC-314 — reads are ranged GETs behind a seekable raw stream; writes are parts behind a buffered one.** *Context:* A parquet file does not fit in memory just because a disk would hold it, and `pyarrow.parquet.read_table` raises `io.UnsupportedOperation: seek` on a non-seekable stream - measured in this environment. A `StreamingBody` straight off `GetObject` is not seekable. *Decision:* `open_read` returns an `io.BufferedReader` over a raw stream that holds at most one `READ_CHUNK_BYTES` window and re-issues a ranged GET on a seek outside it; the object's length comes from the `HeadObject` that already has to happen, so `SEEK_END` costs no request. `open_write` returns an `io.BufferedWriter` over a raw writer that drains parts of exactly `PART_BYTES` as the buffer fills. Every buffer size, chunk size, timeout and retry count is a `Final` whose docstring says it is chosen and not measured, and names the documented S3 limit it sits under where one applies. *Consequences:* Peak memory is arithmetic on declared constants rather than a function of the object, and `tests/unit/test_s3_streaming.py` asserts it with `tracemalloc` against a bound derived from those same constants - no figure in the tree claims to be a benchmark. A seek-heavy reader pays one GET per window change; a sequential reader pays one per chunk.
- **DEC-315 — atomicity comes from S3's own commit point, and the `status.json` polling guarantee is tested on both backends.** *Context:* `LocalStorage` gets atomic writes from `os.replace`. A remote store has no rename, and the API's browser polls `status.json` while the run is still writing it - a reader that can see half a document sees a JSON parse error it can neither explain nor retry. *Decision:* Nothing is sent until the block exits normally: below the threshold one `PutObject` at commit, above it `CompleteMultipartUpload` as the commit point with `AbortMultipartUpload` on any exception (including a failure inside the commit itself). The two crash guarantees - a crash mid-write leaves no object, a crash mid-REWRITE leaves the previous document readable in full - are written once in the conformance suite and run against both backends. *Consequences:* A crashed run leaves neither a half-written object nor a dangling multipart upload waiting for a lifecycle rule. A failed abort is logged by exception class and swallowed, because replacing the caller's original exception with it would hide the failure that actually matters. A very large write is held entirely in parts until commit, so the abort path discards real uploaded bytes - that is the price of the guarantee.
- **DEC-316 — `exists()` raises on 403 and returns False only on 404.** *Context:* Without `s3:ListBucket` on the bucket, S3 answers `HeadObject` for a key that is not there with 403 rather than 404. So 'absent' and 'forbidden' arrive as different codes for the same question, and only one of them is an answer. *Decision:* `exists()` returns `False` for 404 (and the `NoSuchKey`/`NotFound` spellings) and raises `StorageError('READ_FAILED')` for 403 and everything else. `size_bytes` behaves the same way through the shared `_head` helper. *Consequences:* A permissions mistake surfaces as a loud failure on the first request instead of as an artefact that quietly does not exist - a run that re-does work, or an API that reports a completed run has no results, with nothing downstream able to tell the difference. The cost is that `exists()` is not total: a caller on a bucket where the role genuinely lacks `s3:ListBucket` gets an exception where it may have expected a boolean, which is the honest answer.
- **DEC-317 — the 512-character key gate and the 1024-byte S3 key limit are checked separately.** *Context:* `validate_key` limits a storage key to 512 *characters*; S3 limits an object key to 1024 *bytes*. One non-ASCII character is up to four bytes, and the bucket prefix is prepended before S3 ever sees the key, so a key this product considers valid can still be a key S3 will not accept. *Decision:* `_object_key` applies `validate_key` first, builds `<prefix>/<key>`, and then measures the UTF-8 length of the result against `MAX_S3_KEY_BYTES`, raising `KEY_INVALID` with both numbers in the message. *Consequences:* An over-long key fails with the product's own error code at the call site instead of as a signing or request error from the wire, and the failure names the prefix's contribution, which is the part the caller did not choose. Two limits have to be kept in mind rather than one.
- **DEC-318 — object tags are derived from the key, not passed in.** *Context:* Cost allocation and per-customer lifecycle rules want `run_id` and `client_id` on every object, but `Storage` has thirteen frozen methods and none of them takes a tag. Adding a parameter would change the protocol for every implementation, which is the thing Phase 4a promised not to do. *Decision:* `S3Storage` reads the run id back out of the key with the `runs/<id>/…` pattern that `engine.storage.run_key` owns, and adds `client_id` from its constructor when the deployment serves a named customer. A tag value outside S3's documented character set is dropped rather than sent. *Consequences:* Tagging is free at every call site and cannot be forgotten. It is also only as good as the key layout: a future artefact prefix that carries a run id in a different shape gets no `run_id` tag until the pattern is extended, and the test that asserts the tag set is where that would show up.
- **DEC-319 — the pre-signed URL lifetime comes from the caller; this module declares no default for it.** *Context:* `engine/settings.py` already owns `download_url_ttl_seconds`, bounded and defaulted to 900. A second default here would be a second place for the policy to live. *Decision:* `presigned_download_url(key, *, expires_in, filename=None)` takes the lifetime as a required keyword and declares no constant of its own; a non-positive lifetime is refused rather than signed. A `filename` becomes a `Content-Disposition` with quotes, backslashes and newlines stripped. *Consequences:* There is exactly one number to change, and no way for the two to drift apart. The URL is a bearer credential for as long as it lives, which is why `quiet_aws_wire_logs()` is called before any client is built and why nothing in this module logs one. The filename scrub prevents a response-header injection through an uploaded file's name.
- **DEC-320 — the AWS-to-StorageError mapping is exhaustive and ordered, and never quotes the AWS message.** *Context:* The interesting failures are the ones a lazy mapping makes invisible. `NoSuchBucket` arrives as a 404; a KMS grant failure arrives as a 400 with a `KMS.AccessDeniedException` code; `AccessDenied` on a read and on a write are not the same event for the caller. *Decision:* `_s3_error` checks `NoSuchBucket` first (a missing bucket is configuration, so `READ_FAILED`/`WRITE_FAILED`, never `KEY_NOT_FOUND`), then the denial codes including the KMS and credential spellings and a bare 403 (`READ_FAILED` on a read, `WRITE_FAILED` on a write), then the not-found codes and a bare 404 (`KEY_NOT_FOUND` on a read; on a write the same status means the bucket or the upload has gone, so `WRITE_FAILED`). The error is read structurally off `exc.response` rather than by catching `ClientError`, so botocore stays out of module scope. The message carries the exception class and the AWS error code and never the AWS message, which routinely contains the key and can contain a query string. *Consequences:* A permissions problem can never present as a missing artefact, and a misconfigured bucket never sends a reader looking for a run that was never written. The mapping is tested from constructed `ClientError`s rather than provoked ones, because moto 5.2.3 raises a bare `KeyError` for `complete_multipart_upload` with a bogus upload id - provoking failures would test moto's fidelity instead of this table.
- **DEC-321 — the backend-agnostic storage assertions live in one parametrised conformance suite.** *Context:* A frozen protocol is worth exactly the tests that check it. A contract tested once per implementation is really two contracts that share a name: the moment one suite tests `list_keys` ordering and the other does not, the backends are free to disagree and nothing fails. *Decision:* `tests/unit/test_storage_contract.py` holds a `storage` fixture parametrised over `['local', 's3']` (s3 via moto) and a `make_storage` factory beside it, and every assertion about the protocol - the invalid-key sweep across every method, the round trips, zero-byte values, overwrite, `KEY_NOT_FOUND`, idempotent delete, listing, awkward keys, the streams, the two crash guarantees and the `local_path` round trip through a second independent store - is written once and run twice. `tests/unit/test_storage.py` keeps the local store's own atomic-rename details and was not touched. *Consequences:* A third backend costs one fixture parameter and inherits 28 assertions. The suite runs in about 4.6s, so it stays in `make test`. The factory, rather than a bare store, is what makes materialise-on-read testable at all: a mirror that is already warm proves nothing about hydration.
- **DEC-322 — bounded memory is proved against a generated body and `tracemalloc`, not a large fixture.** *Context:* The claim is that a 40 GiB object costs the same memory as a 40 KiB one. A fixture large enough to test that for real is a fixture nobody runs, and a test nobody runs is not a guarantee. *Decision:* `tests/unit/test_s3_streaming.py` uses a fake client that invents the bytes of whatever range it is asked for from a 64 KiB tile and records only the shape of the traffic - how many ranged GETs, how many parts, what size each was. The assertions are the traffic shape plus a `tracemalloc` peak bounded both by a fraction of the object's size and by a ceiling computed from this module's own declared buffer constants. The default sizes are single-digit multiples of `PART_BYTES` so the file runs in well under a second; a 48-part variant carries `@pytest.mark.slow`. *Consequences:* The memory claim is checked on every `make test` rather than aspired to, and the ceiling is arithmetic on constants rather than a number measured on one laptop and frozen into the tree. What is not checked is real throughput against a real bucket - nothing in this repository claims it is.
- **DEC-323 — `list_keys` sorts in Python rather than trusting S3's ordering.** *Context:* `ListObjectsV2` returns keys in UTF-8 binary order. That is not Python's string order for every input, and `LocalStorage` sorts with Python's. *Decision:* `S3Storage.list_keys` collects every page, strips the store root, drops directory-marker keys ending in '/' and sorts the result itself, exactly as `LocalStorage` does. *Consequences:* The two backends return the same tuple for the same content, which is what lets the ordering assertion live in the shared conformance suite. The cost is that the full key list is materialised before it is sorted - acceptable for an artefact store, and the same thing `LocalStorage` already does with `rglob`.
- **DEC-324 — `JobSpec` becomes the description of the work, and the closure is derived from it.** *Context:* `JobRunner.submit(job_id, fn)` takes a Python callable. That is exactly right for a thread pool and impossible for a container: a closure cannot cross a process boundary. The protocol has four members, four test fakes implement it, and `tests/unit/test_jobs.py` asserts `isinstance(runner, JobRunner)` — changing the signature would break all of them, and plan §12 forbids it anyway. *Decision:* invert which of the two is primary. `engine.contracts.JobSpec` is the declarative description of a run's work; `engine.runs.build_job_fn` turns a spec into the closure `ThreadJobRunner` runs in this process; `engine.runs.run_job_spec` is what that closure calls, and is also what `scripts/run_job_entrypoint.py` calls inside the container after reading the same document back out of the same store. `SageMakerJobRunner.submit` ships the spec's storage key and explicitly `del fn`. *Consequences:* the protocol is untouched and the four fakes still satisfy it; a local run and a remote run are two renderings of one description, so there is no second definition of the work to drift; and `del fn` is a line a reader will stop at, which is why it carries the decision number rather than being silently dropped.
- **DEC-325 — A job can end without this process hearing about it, so reconciliation is an additive capability.** *Context:* the container can be killed, the instance can fail to start, the job can be stopped from the console. In every one of those cases nothing in this process was there to write the ending, and `status.json` says "running" for ever. *Decision:* `ReconcilingJobRunner` is a separate `Protocol` with one method, and a free-function dispatcher that **no-ops** for a runner that does not implement it; `GET /runs/{id}` calls the dispatcher. `ThreadJobRunner` does not implement it, because a thread that vanished took the process with it. Reconciliation writes `JOB_FAILED_REMOTELY` onto the stage the run had reached, with the detail line that stage had earned. *Consequences:* `JobRunner` keeps four members (DEC-324's constraint holds); a local deployment calls a function that returns immediately and nothing about it changes; a stuck remote run resolves itself the next time anybody looks at it, rather than needing an operator. The grace period before a still-starting job is treated as gone is a margin and its docstring says so, not a measurement.
- **DEC-326 — `build_train_job` runs the real training pipeline, and `build_m2_job` stays as a test double.** *Context:* since M2, `POST /runs` has submitted `build_m2_job` for every training run — the stub that runs ingest and validate and then stops at `prepare` with a named error — while `Pipeline.run_train` has been complete and tested for just as long. The training half of this product could not succeed through its own API. *Decision:* `ENTRYPOINTS` routes a training job to `build_train_job`, which is `build_score_job` with `run_train` in it. `build_m2_job` stays exported and tested. *Consequences:* training works end to end through the API for the first time. `build_m2_job` is kept rather than deleted because it is still the only honest way to stand a job body in for a test that does not want to train a model; its docstring now says no route submits it.
- **DEC-327 — `engine/runs.py` imports no `api`, and the two fields a job body needs arrive through a protocol.** *Context:* design §5.3 always gave run creation its own module, and `api/routes/runs.py` said in its own docstring that the job bodies "move unchanged when it lands". Phase 4a forces the move: the container runs the job body and has no FastAPI in its image. *Decision:* `create_run`, `update_run`, `update_stage`, `cancel_run` and the job bodies move to `engine/runs.py` unchanged; the two pieces of `upload.json` a body reads arrive through a small `UploadInfo` protocol, which `api.schemas.UploadRecord` satisfies on the request thread and `SpecUpload` satisfies in the container. *Consequences:* the image does not need the web framework; `api/routes/runs.py` becomes routing and validation only; and neither side knows about the other, so the protocol is the whole coupling.
- **DEC-328 — One environment variable is the entire contract between the runner and the container.** *Context:* a container needs to be told what to do. Every extra variable is a second thing that can be set wrong and a second thing to keep in step. *Decision:* `MARKETING_AI_JOB_SPEC_KEY` carries the storage key of `job_spec.json` and nothing else; everything about the work is in the document. `JOB_SPEC_UNREADABLE` is a coded engine error for the one case the container cannot recover from, so a job that ran nothing says why. *Consequences:* the contract fits in a sentence and is asserted in one test; a spec written by a newer submitter and read by an older image fails on the document's schema, which is a versioned artefact, rather than on a variable nobody thought about.
- **DEC-329 — Compute is recorded onto an existing manifest, never onto an invented one.** *Context:* `_record_compute` wants to put where the run ran and what it cost onto `run_manifest.json`. A job that never reached the container has no manifest. *Decision:* write only onto a manifest the pipeline already wrote; a job that failed before the container started gets none. *Consequences:* the alternative was writing one here, which would mean inventing a dataset fingerprint and a seed for a run that never read any data — a fabricated record, which plan §13.3 forbids as firmly as a fabricated number. The absence is the honest record. The write also runs at most once per job, so a poll after a restart reads rather than rewrites.
- **DEC-330 — A list price is published as a list price, in words, on every estimate.** *Context:* `RunManifest.cost_estimate` has carried `estimated_usd=None` since Phase 1 because a laptop is not billed. A SageMaker job is billed, so the number becomes writable — and the same rule has to decide how. *Decision:* what is measurable is **billable time**, which AWS itself reports in `DescribeTrainingJob.BillableTimeInSeconds` and which is the only source `ComputeInfo.billable_seconds` is ever filled from. What is not measurable here is a **bill**. So the arithmetic is `billable seconds × instances × list rate`, and `CostEstimate.basis` says in a sentence that that is what it is, naming the instance type, the region, the rate, the offer version and the publication date of the rate card. *Consequences:* a reader of the manifest cannot mistake the figure for an invoice line; savings plans, spot, free tier, tax and negotiated discounts are all excluded and the basis is what says so; and the run index column carries the number while the basis carries the caveat, so a list query stays cheap without the caveat being lost.
- **DEC-331 — An AWS `FailureReason` never reaches a user-facing message.** *Context:* `FailureReason` is the container's last words. A container that died inside a pandas operation can put a column name, or a value out of the customer's file, into that string. *Decision:* `SageMakerError` carries an engine error code and a message written in this product's own words; the AWS text is logged through the redacting formatter and never rendered into a run's error. `JOB_SUBMIT_FAILED` covers the service refusing a job outright, so a run that never had a stage still says why. *Consequences:* plan §13.7 holds across the remote boundary too; an operator reads the account's logs for the AWS text, which is where the access control for it already is.
- **DEC-332 — Train is a Training job, score is a Processing job, and the distinction survives into the manifest.** *Context:* the two are billed under different rate-card components, and only one of them reports a billable time. *Decision:* `BACKEND_FOR_ENTRYPOINT` maps the two entrypoints to the two job types; `ComputeInfo.backend` says `sagemaker` and `ComputeInfo.entrypoint` says which of the two it was; `engine/aws/prices.py` looks the rate up by entrypoint. A processing job's start and end times are wall clock, so they fill `duration_s` and `billable_seconds` stays `None`. *Consequences:* a scoring run gets `NO_BILLABLE_TIME` and no price, which is true — wall clock is not what SageMaker bills — rather than a number derived from the wrong quantity. Training is also the one SageMaker resource that carries a model artefact, which is the other half of why the two are not one job type.
- **DEC-333 — The rate card is generated, reviewed in the diff, and never checked by CI.** *Context:* `configs/aws_prices.yaml` comes from a third party's price list. A price change at AWS must not turn a green build red. *Decision:* `scripts/fetch_aws_prices.py` writes the file with the offer version, the publication date and the URL it read; `make prices` runs it by hand; unlike `gen_templates` and `gen_api_docs` it is **not** wired into `make generate` or `make check-generated`. A malformed or missing card returns `None` and is logged, never raised: the cost is an annotation on the manifest and the run is the thing that matters. *Consequences:* the provenance travels into every `basis` sentence, so a reader can check the rate rather than trust it; a checkout with no card still runs, and says "no rate card is installed" instead of guessing; and an instance type the card does not price produces `None` and names itself.
- **DEC-334 — No `List*` API call, anywhere in this module.** *Context:* the natural way to find a job again is to list jobs and filter. *Decision:* every question is asked about a *named* job with `Describe*`, and the name is derived deterministically from the run id and the configured prefix. The module makes six calls in total — three `Describe`, two `Create`, one `Stop` — and a fake that raises on anything else is what proves it. *Consequences:* the execution role can be scoped to `…:training-job/<prefix>-*` and nothing else, which is a boundary a reviewer can check at a glance. `ListTrainingJobs` would need read permission over the whole account's job history to answer a question about one run, in an account this product is a guest in.
- **DEC-335 — A queue is not a state: a run waiting for compute is `pending`.** *Context:* `max_concurrent_jobs` holds runs back, and the obvious move is a `queued` member on `RunState`. DEC-027 says there is one state vocabulary for runs, stages and jobs. *Decision:* a held run stays `pending`, which is exactly what it is, and its first stage carries the detail line "Waiting for compute". The queue drains on the status polls the UI already makes, so nothing new has to run. *Consequences:* the Running screen says the true thing without the enum growing a member that only one backend would ever set, and every existing consumer of `RunState` keeps working unchanged. A local deployment never sees the queue at all.
- **DEC-336 — An unset billed quantity is left out of the request, not filled with a number.** *Context:* `CreateTrainingJob` wants a volume size; `StoppingCondition` wants a maximum runtime. Both are billed, and both have a service default. *Decision:* `volume_size_gb` and `max_runtime_seconds` default to `None` and are *omitted from the request* when unset, so the service's own default applies. Where the API has no default and the value is genuinely required, the module refuses with a message naming the setting to export. *Consequences:* the service's default is a better number than one this repository would have to invent, and it is AWS's to change. Plan §13.3 again: refusing is honest, a made-up 30 GB is not.
- **DEC-337 — The container's environment is an allow-list, and no secret is in it.** *Context:* a job's environment is visible to anybody who can call `DescribeTrainingJob` on the account. *Decision:* `SHIPPED_SETTINGS_FIELDS` is an explicit allow-list of the settings the container is handed, rendered through `engine.settings.ENV_VARS` so there is no second spelling to keep in step. Nothing in `SECRET_FIELDS` may appear in it and a unit test asserts that it does not: the database URL reaches the container from Secrets Manager, read by the container's own role. *Consequences:* the failure mode of forgetting a field is a container that says "this setting is not configured"; the failure mode of an accidental inclusion would have been a credential in an API response, and the allow-list is what makes the first possible and the second not. The `sagemaker_*` fields are absent because the container submits nothing, and `local_cache_dir` is absent because it names a directory on the host that submitted the job.
- **DEC-338 — `SqlRegistryStore` is extracted from `LocalModelRegistry` with its method bodies unchanged, and `LocalModelRegistry` becomes a subclass that only chooses the engine.** *Context:* Phase 4a needs the same registry over Postgres. The two honest options were to write a second implementation of the registry against Postgres, or to separate what the registry *says* from what it says it *to*. The registry's hardest property is that a champion swap — demote the incumbent, crown the challenger — is one transaction, and that `approve` refuses a decision measured against a champion that has moved (DEC-047). A second implementation is a second copy of that, and the copy that drifts is the one nobody is looking at. *Decision:* `SqlRegistryStore(engine)` holds every statement the registry makes, with the method bodies moved verbatim — not rewritten, not re-indented into a new shape. `LocalModelRegistry(SqlRegistryStore)` keeps its exact `__init__(db_path)`, its `db_path` property and `check_same_thread=False`, and adds `create_registry_tables(self.engine)`. `engine/aws/postgres.py:postgres_store(settings)` hands the same class a Postgres engine. The champion rule `should_promote` is untouched and is still a pure function nobody in the store calls. *Consequences:* One copy of the transaction, exercised twice: `tests/unit/test_registry.py` now parametrises every store test over SQLite and a migrated Postgres schema, and the DEC-047 stale-approval sequence is proved on both. `api/deps.py` and `default_registry()` are unchanged. A caller that wants only the statements — `S3ModelRegistry` — composes the store instead of subclassing the file-based registry.
- **DEC-339 — Every datetime column is `DateTime(timezone=True)`, and `aware_utc`/`to_utc` convert rather than merely attach.** *Context:* SQLModel compiles a bare `datetime` field to `TIMESTAMP WITHOUT TIME ZONE` on the postgresql dialect. Measured on a server running `Asia/Kolkata`: an aware `2026-09-22T12:00:00+00:00` handed to such a column is stored as the session's wall clock, `17:30:00` naive, and Phase 1's `_aware` — which only attached UTC to a naive value — read it back as `17:30:00+00:00`. Every `ModelVersion.created_at` on a non-UTC server was five and a half hours into the future, silently, and only on that server. The read side had a second, quieter defect: a `timestamptz` comes back in the session's time zone, so leaving an aware value alone would publish the server's offset into a field the contract says is UTC. *Decision:* Every timestamp column on `ModelVersionRow` and on the new `RunRow` is declared through an explicit `sa_column=Column(name, DateTime(timezone=True), ...)`. `_aware` becomes the public `aware_utc`: naive means UTC, aware is `astimezone(UTC)`. `_utc` becomes the public `to_utc` and every write goes through it, including the run index's, because SQLite has no timestamp type and stores exactly what it is handed. `alembic/env.py` sets `compare_type=True`, so a later revision cannot quietly undo this. *Consequences:* `sa_column` is mutually exclusive with SQLField's `index=`/`primary_key=` and a `Column` object belongs to one table, so each column is declared separately and no timestamp is indexed except `run.created_at`, which gets its index on the `Column` itself. The fix is proved by a test that runs on both backends and was demonstrated to fail — by the server's exact UTC offset — when reverted.
- **DEC-340 — `create_all` is scoped to a named table list, never to the whole `SQLModel.metadata`.** *Context:* `SQLModel.metadata` is a process-wide namespace, and what is in it depends on what has been imported. Phase 1's `LocalModelRegistry.__init__` called `SQLModel.metadata.create_all(engine)` with no table list. Phase 4a adds a second `table=True` class, the run index. The moment anything imported `engine.aws.postgres` — `api/deps.py` on a settings path, a test module, a script — every `registry.db` in existence would gain a `run` table it never asked for, on a deployment that chose SQLite precisely to avoid all of this. *Decision:* `engine.registry.create_registry_tables(engine)` creates only `model_version`; `engine.aws.postgres.create_run_index_tables(engine)` creates only `run`. `METADATA_TABLES = ("model_version", "run")` is the definite list of what this product owns, and `alembic/env.py`'s `include_name` holds autogenerate to it so an unrelated table in the same database is neither dropped nor reported as drift. *Consequences:* Three tests assert the file contents directly: a `registry.db` holds `{model_version}`, a run-index database holds `{run}`, and the two creators together produce exactly the set `0001` migrates to. A future table has to be added to `METADATA_TABLES` deliberately, which is also the moment somebody has to write its migration.
- **DEC-341 — Alembic owns the Postgres schema from `0001`; `create_all` is for SQLite only.** *Context:* `create_all` adds a missing table and never a missing column. On a laptop that is a fair trade — the answer to a stale `registry.db` is to delete the file. On a deployment the same behaviour means the first column added after go-live is missing in production, silently, until a query fails, and there is no file anyone is willing to delete. *Decision:* `alembic/versions/0001_initial.py` creates `model_version` and `run` as they stand — a description of the destination, not a replay of how the SQLite file got there, because there was no Postgres before this revision. Nothing on the Postgres path calls `create_all`. The test fixtures create each test's schema with the real `alembic upgrade head`, so what the tests exercise is what a deployment gets. The migration is reversible, and its docstring says plainly that dropping `run` costs a rebuildable index while dropping `model_version` destroys the registry. *Consequences:* One linear history, asserted by a test. A schema change is now two edits — the model and a revision — and the drift test fails if only one of them happens.
- **DEC-342 — A `run` table that indexes `run.json`; the row is written after the document, a failed row never fails a run, and the table is rebuildable.** *Context:* `GET /runs` lists every key under `runs/` and reads each `run.json` back. On S3 that pages over every object of every run — artefacts included — and its cost grows with the number of artefacts in the bucket, forever. An index fixes it, and the obvious next step, making the table the record, is the one that loses data. *Decision:* `run.json` stays the artefact of record. The table holds a projection good enough to filter and order a list page and nothing more — no `overrides`, no `artefacts`, nothing computed. `mirror_run(index, record, manifest=None) -> bool` is called **after** the document is written, returns `False` rather than raising for any failure including `index=None` (the local deployment), and logs with `log_failure` so no exception message reaches the log. `RunIndex.list_run_ids` returns ids, not entries, so `GET /runs` still reads each `run.json` from storage. `scripts/reconcile_runs.py` rebuilds every row from `runs/*/run.json`, upserting first and dropping orphans second, counting unreadable documents rather than deleting their rows. `engine/aws/run_index.py` holds the protocol, the projection and the two functions and is table-free and driver-free, so `engine/pipeline.py` can import it on a laptop; the table and the SQL live in `engine/aws/postgres.py`. *Consequences:* A database outage costs a list page its completeness and never a customer their run, and even that is recoverable with one command. A rebuild deliberately does not read `run_manifest.json` — that would double an already expensive scan — so rebuilt rows have `duration_s`, `compute_backend` and `estimated_usd` back at null, which is the honest value for "rebuilt from the record alone". `--dry-run` reports what a rebuild would do while writing nothing.
- **DEC-343 — `PostgresConfig.from_settings` is the only translation from a deployment to a DSN; this product reads the environment exactly once.** *Context:* The temptation on every backend module is a `from_env` of its own. Two readers of the environment is two answers to "which database", and the one that is wrong is whichever one the reader was not looking at. *Decision:* `engine/aws/postgres.py` contains no `os.environ`, no `getenv` and no `from_env` — a test asserts all three on the module source. `PostgresConfig` is a frozen dataclass built by `from_settings(settings)`. It normalises a bare `postgresql://` DSN to `postgresql+psycopg://`, because the URL RDS shows an operator names no driver and SQLAlchemy reads that as psycopg 2, which this product does not install. `postgres_schema` is validated against a plain-identifier pattern before being interpolated into `-csearch_path=<schema>,public`, which is set as a libpq connect option so a pooled connection is already pointed at the right schema before any statement runs. The engine sets `pool_pre_ping=True` and `hide_parameters=True` and nothing else: a pool size or a recycle interval is a number, and none has been measured. *Consequences:* A migration and the application connect the same way, through the same function. The password never appears in `repr(engine)` (asserted) and a failing INSERT does not quote the row. A schema name containing `;DROP SCHEMA` is refused by field name with the value withheld from the message.
- **DEC-344 — A Postgres test that does not run says why, and `MARKETING_AI_REQUIRE_POSTGRES=1` turns the skip into a failure.** *Context:* A skipped test proved nothing, and the dangerous kind is the one nobody notices. CI that is supposed to have a database and does not should go red, not green with a note nobody reads. *Decision:* `tests/fixtures/postgres.py::postgres_unavailable_reason()` returns a sentence naming the URL (password masked) and the driver exception class, probed once per session. `skip_without_postgres()` raises that as the skip reason, or as a `pytest.fail` when `MARKETING_AI_REQUIRE_POSTGRES=1`. `pyproject.toml`'s `addopts` already carries `-rs`, so every skipped test prints its reason. Each test gets its own schema, migrated by the real `alembic upgrade head` and dropped afterwards. *Consequences:* Both branches were exercised for real against a dead port: the skip prints the sentence, and `REQUIRE=1` fails with it. The fixtures are imported by name into the modules that need them rather than living in a conftest, because `tests/conftest.py` holds the two path fixtures and nothing else.
- **DEC-345 — `alembic.ini` carries no DSN; `env.py` resolves the URL as `-x url=`, then the ini, then `Settings`.** *Context:* A DSN in a committed file is a credential in a committed file even when today's value is a localhost password, because the next person who needs a staging run edits it and the one after that forgets to put it back. *Decision:* `sqlalchemy.url` is empty in `alembic.ini` and a test asserts that no non-comment line in the file contains `://`. `env.py` resolves in that order, with `-x schema=` following `-x url=` and `postgres_schema` following the settings, so the URL and its schema can never come from different deployments. A Postgres URL is opened through `postgres_engine`, so a migration connects exactly the way the application does; anything else (SQLite, in the drift test) gets a plain engine. `env.py` deliberately does not call `fileConfig`, so Alembic installs no handler of its own — this product's formatter is the one that withholds exception messages, and a migration failing against a real database is exactly where a driver would otherwise print a row. *Consequences:* All three resolution paths are tested. `alembic upgrade head` with no arguments migrates the database the product is actually configured to use, and cannot be pointed at a different one by a stale file.
- **DEC-346 — `S3ModelRegistry` publishes a version's files to `published_model_key(use_case_id, version, ...)` at register time, and owns nothing else.** *Context:* Phase 1 stores a model version as a row of keys pointing into the run directory that produced it. That is right while the model and the run are the same thing on one disk, and wrong the moment a run directory has a lifecycle: one bucket expiry rule and the champion of a use case loses its predictor while the registry goes on claiming to have one. *Decision:* `register` copies the files to `models/<use case>/<version>/…` — via `engine.storage.published_model_key`, called and never re-spelled — and stores those keys; the run directory is left exactly as it was, so `run.json` still points at its own artefacts. Publishing happens *before* the row is written: a missing `schema_key`, `run_config_key` or predictor directory is `RegistryError('MODEL_ARTEFACT_MISSING')` and the version is not registered at all, because a row for a model whose predictor is absent would be crowned by the champion rule and the first scoring run would be what discovered the truth. An optional key that names nothing — `drift_baseline_key`, which the register stage sets whether or not a baseline was written — keeps the key it had and is logged. A key that already is its published target is left alone, so re-registering a version read back out of the registry copies nothing. Copies are streamed with `shutil.copyfileobj` over `open_read`/`open_write`; a predictor directory is detected by whether anything is stored beneath it, because `exists()` is always False for a prefix. Everything else — `get`, `list_versions`, `get_champion`, `next_version`, `approve`, `promote`, `archive` — is delegated to `SqlRegistryStore` verbatim. *Consequences:* `models/<use case>/<version>/` is a prefix a lifecycle rule and an IAM condition can both be written against. Archiving does not delete files: ending their life is a lifecycle rule's job and is not something a mistake should be able to do. Idempotence is proved by deleting the run directory first, so any attempted copy would raise instead of quietly succeeding.
- **DEC-348 — The SageMaker Model Registry mirror is off by default, one way, and can never fail a registry write.** *Context:* An AWS-native team expects to find a model in the SageMaker Model Registry. This product's registry is not that and must not become it: the champion rule, the stale-approval refusal and the `pending_approval` state are this product's meaning of "approved", and letting a SageMaker approval change a champion would be two registries racing to own one decision. *Decision:* `SageMakerModelRegistryMirror.mirror(version)` writes and never reads; nothing here can change a champion. `SageMakerRegistryConfig.enabled` defaults to `False` and there is no `Settings` field for it, so a deployment that wants the mirror has to construct it deliberately — the right amount of friction for a write into a shared account. Every failure is caught and returned as `None`, logged with the exception's class name only, and `S3ModelRegistry._mirror` guards the call a second time so the promise holds even if this module is one day given a bug. The mirror is passed as an optional keyword to `S3ModelRegistry`, whose `(store, storage)` signature is unchanged, and the `ModelMirror` protocol is declared at the consumer so `s3_registry` never imports `sagemaker_registry`. Four lifecycle states map onto SageMaker's three words: `candidate` and `pending_approval` both become `PendingManualApproval`, because the difference between them is this registry's business and SageMaker has no word for it; `archived` becomes `Rejected` so a console reader never sees a retired model still marked approved. No `InferenceSpecification` is invented — it needs a `ModelDataUrl` pointing at a single `model.tar.gz` and this product publishes a predictor *directory* — so one is sent only when a deployment supplies both an image and a URL. *Consequences:* A disabled mirror makes no AWS call at all, asserted rather than assumed. A failing mirror leaves the registry write intact, and the failure log line is asserted to carry the exception class and not its message. The honesty limit is stated in the module docstring: the two calls were exercised against moto, never against real SageMaker.
- **DEC-380 — the log format is a Settings field, not a logging configuration of its own.** *Context:* A JSON rendering had to be selectable per deployment. The obvious alternatives are a logging.config dictConfig file, or a separate MARKETING_AI_LOG_CONFIG path. *Decision:* `configure_logging(level, *, log_format=...)` takes `Settings.log_format`, which is already in the frozen environment-variable table and already printed by `Settings.summary()`. No new environment variable, no configuration file. *Consequences:* One table still describes the whole deployment, and the format a process is writing in is visible in its own startup line. The cost is that an operator cannot reshape logging without a code change - which is the intended trade, because the shape is what the redaction guarantee is built on.
- **DEC-381 — the redaction guarantee is a class, not a convention - RedactingJsonFormatter must not override formatException.** *Context:* Plan 13.7 says an exception message is customer data because a library builds one out of the value that upset it. A second rendering is a second chance to leak it. *Decision:* `RedactingJsonFormatter` subclasses `RedactingFormatter` and deliberately does not define `formatException`. The inherited one is the only code in this repository that turns an exception into text, and it withholds every message. `tests/unit/test_logging_audit.py` asserts `"formatException" not in vars(RedactingJsonFormatter)` and that the attribute is identically `RedactingFormatter.formatException`. *Consequences:* A third rendering added later inherits the guarantee for free. Anybody who adds a `formatException` "just to put the traceback in a field of its own" fails a test that names the reason.
- **DEC-382 — the JSON payload is built from a closed allow-list, never from record.__dict__.** *Context:* The usual JSON formatter serialises `record.__dict__` minus a deny-list of the attributes `logging` itself sets. That fails in the worst direction: an attribute nobody here has heard of is serialised, and the unknown attribute is the one most likely to hold a value. *Decision:* `JSON_FIELDS` is the closed list of keys the formatter may write (time, level, logger, message, run_id, stage, client_id, exception). The payload is assembled key by key; there is no code path that reads the record's dictionary. *Consequences:* A LoggerAdapter payload, an `extra=` mapping, uvicorn's `client_addr` - none can be serialised by accident. A new field has to be added by hand, which is the point. A test logs with `extra={"offending_cell": SENTINEL, ...}`, asserts the value really is on the record, and asserts it is absent from the JSON.
- **DEC-383 — run identity reaches the record through a ContextVar and a handler-level logging.Filter.** *Context:* The alternatives were threading a bound logger through every stage signature, or a LoggerAdapter per run. *Decision:* `run_id`/`stage`/`client_id` live on a `ContextVar`; `ContextFilter` (installed on the handler by `configure_logging`, idempotently via `install_context_filter`) stamps all three onto every record, or None. It overwrites an attribute a caller attached, so the ContextVar is the single source. *Consequences:* No stage signature changes, and records pandas and botocore write on their own loggers are stamped too, because the filter sits at the sink rather than on one logger. A record cannot carry a forged run_id from a second, unaudited mechanism. The three fields are named identifiers rather than a free-form mapping, so there is nowhere a cell value could be smuggled in.
- **DEC-384 — the binding happens inside the job body, never around the submit.** *Context:* `ThreadPoolExecutor` starts its workers with a fresh context rather than a copy of the submitter's, so a ContextVar bound around `runner.submit(...)` is gone by the time the job runs. *Decision:* `bind_log_context` is documented as the job callable's first statement, and three tests drive a real `ThreadJobRunner` to prove it: a binding made inside the body reaches the log; a binding wrapped around the submit leaves `record.run_id is None`; and two jobs meeting at a `threading.Barrier` produce exactly two records whose run_ids are the two distinct ones. *Consequences:* The failure mode - a run whose lines are silently anonymous - is a test failure rather than something discovered in CloudWatch. The second test is written so that if CPython ever starts copying contextvars into workers, it fails and tells the reader the constraint has lifted.
- **DEC-385 — metrics are CloudWatch EMF log lines, not PutMetricData.** *Context:* Both would work. The difference is in permissions, in what runs on the run's thread, and in whether the API and a job need different code. *Decision:* `EmfMetricSink` writes one EMF JSON document per datapoint to stdout; the log driver already carrying the process's output to CloudWatch Logs carries it, and CloudWatch extracts the metrics. *Consequences:* It needs no new IAM permission - a SageMaker job role and an ECS task role already have the `logs:PutLogEvents` their driver uses, whereas `PutMetricData` would need a wildcard-resource `cloudwatch:PutMetricData` on both. It adds no synchronous signed HTTPS call to the thread that is in the middle of a stage (nothing to block, throttle or time out). And it is the same code from the API and from inside a job: no client, no region, no credentials. A laptop simply prints a line nothing consumes. Nothing in engine/aws/metrics.py imports boto3, which a test asserts by parsing the module.
- **DEC-386 — the EMF sink owns its stream and does not go through logging.** *Context:* Routing EMF through the application logger would be tidy, but `RedactingJsonFormatter` would wrap the document in another JSON object and destroy it. *Decision:* `EmfMetricSink` writes to a stream it holds (defaulting to `sys.stdout`, resolved on every write so `redirect_stdout` and pytest capture work), serialised by a lock held across one write plus one flush. *Consequences:* A metric line is a document CloudWatch parses, not a message a formatter may reshape. The lock is there because a partial line is not a metric - CloudWatch drops the whole document; a test runs four threads writing 25 datapoints each and asserts all 100 lines parse.
- **DEC-387 — one guard, in one place - a metric may never fail a run.** *Context:* A try/except at each call site is the version where the fifth call site eventually gets written without one. *Decision:* The public API is the `record_*` functions, and every one of them goes through a single `_emit` helper that catches `Exception` and logs it with `log_failure` (class name only). `MetricSink.emit` is the raw call and is allowed to raise. *Consequences:* A broken stream, a full disk or a badly written sink costs a datapoint, not a run. A parametrised test drives all five recording functions against a sink that raises `OSError("no space left on device")` and asserts the message never reaches the log, only `error=OSError`.
- **DEC-388 — JobCostUsd is emitted only where a real figure exists, and never as a zero.** *Context:* Plan 13.3. `CostEstimate.estimated_usd` is already null for a local run, for no billable time reported, and for no published rate. *Decision:* `record_job_cost` emits nothing when the estimate is None, when `estimated_usd` is None, or when it is <= 0. A genuine zero is dropped too: it can only come from zero billable seconds, and the rule "this graph never shows a zero" is worth more than that datapoint. *Consequences:* A point on a cost graph always means money was estimated to have been spent. "We do not know" is a gap, which is what it looks like. Parametrised tests cover no_estimate / unstateable / zero.
- **DEC-389 — LlmCostUsd is a hook that is off by default and reads nothing.** *Context:* The generative phase is absent from this repository: there is no Bedrock client, no model price table and no file to consult. *Decision:* `record_llm_cost(sink, *, model_id, usd, enabled=False)` exists so the call site can be written once, and returns immediately unless a caller passes both `enabled=True` and a figure it computed itself. `LlmCostUsd` is marked `alarmable=False`, so it gets a dashboard widget (labelled "reserved; no data yet") and no alarm. *Consequences:* Nothing is invented and no missing file is read - asserted by parsing the module for `open`/`read_text`/`load` calls and for boto3 imports, rather than by a substring search that could not tell the module's prose about boto3 from actual code. When the generative phase arrives it passes `enabled=settings.bedrock_enabled`.
- **DEC-390 — every datapoint is published under two dimension sets, coarse and detail.** *Context:* CloudWatch does not aggregate across dimensions: a datapoint stored under {Env, ClientId, Stage} is not readable as {Env, ClientId}. A metric emitted only with its detail could not be put on a dashboard without naming every stage, use case and backend by hand. *Decision:* EMF's `Dimensions` is a list of sets, so each document declares `[[Env, ClientId], [Env, ClientId, <Detail>]]`. Detail dimensions: UseCaseId for the run counters, Stage for durations, Backend for job cost, ModelId for the reserved LLM cost. A blank detail drops that set rather than sending an empty dimension value, which CloudWatch rejects. *Consequences:* Dashboards and alarms address the coarse set and need no substitution per use case; drill-down is free. A test asserts every dimension name a document declares has a value in its body - the mistake that produces a metric CloudWatch accepts and then silently drops.
- **DEC-391 — dashboard.json and alarms.json are generated from the metric registry and committed.** *Context:* Same argument as DEC-014 for the upload templates: a generated artefact that is not committed is one nobody reviews, and one that is committed but not checked drifts. *Decision:* `scripts/gen_dashboard.py` follows `scripts/gen_templates.py` exactly - a `write_*` returning an exit code, a `--out`, a `--check` that writes nothing and prints a unified diff. It reads `NAMESPACE`, `METRICS` and `COARSE_DIMENSIONS` from `engine.aws.metrics`; there is no second list of metric names anywhere. *Consequences:* A metric cannot be renamed in one place and left behind in the other. `render_alarms` additionally refuses an alarm naming a metric that is not in the registry. Tests assert widget-per-metric, no widget overlap within the 24-column grid, that the dashboard body has no key beyond `widgets` (PutDashboard validates the document), and that generating into an empty directory reproduces the committed bytes.
- **DEC-392 — a threshold nobody has measured stays a substitution, not a number.** *Context:* Plan 13.3. Two of the three alarm thresholds are things this repository has no basis for: how long a stage should take is a measurement never taken here, and how much a day should cost is a business decision nobody has stated. *Decision:* Those two thresholds are emitted as `${StageDurationSecondsAlarmThresholdSeconds}` and `${JobCostUsdDailyBudgetUsd}` - `Fn.sub`-compatible tokens a deployment must supply. Only `RunsFailed >= 1` is a literal, because a failed run is an event and is countable. Every alarm carries `threshold_source: literal|substitution`, and `alarms.json` carries an exhaustive `placeholders` table (also covering `${Env}` and `${ClientId}`). *Consequences:* No invented number is committed anywhere, and `Fn.sub` fails loudly on a token a stack did not supply. A test asserts the two unmeasured thresholds still match the placeholder pattern, and that the set of placeholders used across both files equals the set declared.
- **DEC-393 — every alarm carries a written rationale beside it.** *Context:* Statistic, period, evaluation count and datapoints-to-alarm are all choices made before this product has served a request. *Decision:* Each alarm in `alarms.json` has a `rationale` field that says in words that it is policy chosen before any traffic exists, and why that particular shape. A test asserts each rationale exists, exceeds 120 characters, and contains "POLICY" or "measurement". *Consequences:* Whoever tunes these later reads what the original reasoning was rather than guessing. The rationale is in the generated artefact, so it reaches the reviewer of the deployed alarm and not only the reader of the generator.
- **DEC-394 — CloudWatch limits are cited from the botocore model in this checkout.** *Context:* docs.aws.amazon.com is blocked by the egress proxy in this environment, so a documentation URL would be a number nobody here could check. *Decision:* `MAX_DIMENSIONS_PER_METRIC=30`, `MAX_METRIC_NAME_LENGTH=255` and `MAX_DIMENSION_VALUE_LENGTH=1024` each carry a docstring saying they are SERVICE LIMITS and naming the exact source: botocore 1.43.99, `botocore/data/cloudwatch/2010-08-01/service-2.json.gz`, shapes `Dimensions`/`MetricName`/`DimensionValue`. The docstring on the value-length constant separately says that *truncating* rather than dropping is this module's POLICY, not a limit. *Consequences:* Every number is version-pinned, offline and re-checkable by the next reader with one command. The service-limit/policy distinction the plan asks for is explicit on each constant.
- **DEC-395 — ClientId is always present, using a documented 'unset' placeholder.** *Context:* A deployment may not set `Settings.client_id`, and a metric whose dimension set changes shape depending on configuration is one no dashboard or alarm can address - the widget on {Env, ClientId} would simply show nothing, with no error anywhere. *Decision:* `UNSET_CLIENT_ID = "unset"` fills the dimension when `client_id` is None, documented as a policy placeholder and explicitly not a guess at who the client is. *Consequences:* The coarse dimension set has one constant shape, so the generated dashboard and alarms address it unconditionally. Nothing about a customer is fabricated - the label says only that the deployment did not name one.
- **DEC-396 — configure_logging keeps one handler and re-dresses it.** *Context:* It had to stay idempotent (an existing test counts root handlers) while gaining the ability to change format on a later call - the API configures a placeholder logger at import and re-configures from Settings once they are loaded. *Decision:* The module holds a reference to the one handler it owns. The handler is created on the first call only; the formatter and the context filter are (re)set on every call, and only on that handler - never on handlers the module did not create. *Consequences:* A process that configures text and then JSON writes each line once, not twice. pytest's and uvicorn's own root handlers are left alone. Tests assert the handler count is unchanged across a format switch and that repeated calls leave exactly one ContextFilter.
- **DEC-397 — The Phase 4a cost tables ship unmeasured, with the commands that fill them.** *Context:* the Phase 4a plan asks for a measured idle-cost table and a per-run cost table, and no AWS account exists behind this repository. *Decision:* both tables ship with every cell holding the literal marker `NOT YET MEASURED`, beside the exact Cost Explorer, run-manifest and CloudWatch commands that fill them, and §6 says once, near its top, that nothing in it has been measured. *Consequences:* the document is honest about what is not known and still useful to the person who will find out; a half-filled table is caught by `tests/unit/test_docs_honesty.py`; §6.3 keeps list price and bill distinguishable in the reader's mind, the way `CostEstimate.basis` does in the product (plan section 13.3).
- **DEC-398 — `docs/RUNBOOK.md` is separate from `docs/AWS_DEPLOYMENT.md`.** *Context:* one document was carrying both "get this running for the first time" and "it is 2 a.m. and an alarm fired". *Decision:* this document is the deployment walk-through, read once per account; `docs/RUNBOOK.md` is day-two operations, read under time pressure, and is organised by symptom. *Consequences:* two shorter documents with one question each; §10 here stays the five failures of a *first* deployment, and everything that happens to a deployment already serving lives in the runbook.
- **DEC-399 — Documentation honesty is enforced by a test, not by review.** *Context:* the rule that no unmeasured number is written down holds only as long as every future editor remembers it. *Decision:* `tests/unit/test_docs_honesty.py` fails the build when a currency figure appears outside a command block without a source citation, when a cost table loses its marker, when either document tells the reader to run a `make` target the Makefile does not define, or names a `MARKETING_AI_*` variable the application would refuse to start with. *Consequences:* the cheapest mistakes are caught mechanically; the test gates the documents and not the product, so a real measurement is added by adding it with its source beside it.
- **DEC-349 — The image runs the application from a source layout, not from an installed wheel.** *Context:* the obvious image `pip install`s the project into the virtualenv. `api/main.py` computes `UI_DIR = Path(__file__).resolve().parent.parent / "ui"` and `engine/config.py` resolves the configuration root the same way, and the wheel target in `pyproject.toml` packages only `engine`, `api` and `scripts` — it carries neither `ui/` nor `configs/` nor `templates/`. An installed-package image therefore resolves both into `site-packages/` and serves a 404 for `/ui`, silently. *Decision:* third-party wheels go into `/opt/venv`; the application is `COPY`ed to `/app` and reached through `PYTHONPATH=/app`. *Consequences:* the image serves the UI and finds its configs; `tests/unit/test_container_files.py` asserts the `COPY` lines and the absence of a `pip install .`, so the mistake cannot come back quietly. Anybody who later wants a wheel-based image has to change that line in `api/main.py` first, and say so.
- **DEC-350 — Image versions come from `requirements-freeze.txt` as a pip constraints file.** *Context:* letting the image resolve `[project].dependencies` on its own produces a second, independent resolution that can differ from the one the tests ran against. *Decision:* the builder generates the requirement list from `pyproject.toml` with `scripts/requirements_from_pyproject.py` and installs it with `-c requirements-freeze.txt --only-binary=:all:`. *Consequences:* the image's pins are the repository's pins; the generator is a real module rather than a `python -c` string inside a `RUN`, so it can be read, reviewed and tested; and an unknown extra name is an error rather than a silently empty group.
- **DEC-351 — `libgomp1` is installed, and both the base image and the package list are build arguments.** *Context:* measured inside a built image: `import lightgbm` dies with `OSError: libgomp.so.1: cannot open shared object file`. The copies that scikit-learn and xgboost bundle have mangled SONAMEs (`libgomp-e985bcbb.so.1.0.0`) and do not satisfy the lookup, so there is no in-wheel fallback. *Decision:* the layer installs `${RUNTIME_APT_PACKAGES}`, defaulting to `libgomp1`, on `${PYTHON_BASE}`, defaulting to `python:3.11-slim`. *Consequences:* the normal build is the normal build; an environment whose egress policy refuses the Debian archive can still build and test the image by naming a base that already carries the library. That is not hypothetical — it is the environment this was written in, where `deb.debian.org` answers 403 and the layer could not be built at all.
- **DEC-352 — One entrypoint script, which understands SageMaker's two different launch conventions.** *Context:* a Training job launches the container as `<image> train`, appending that literal word; a Processing job replaces the entrypoint outright with its `ContainerEntrypoint`. Getting this wrong is the classic SageMaker packaging mistake. *Decision:* `scripts/entrypoint.sh` dispatches on the first argument — `serve` for uvicorn, `train`/`job` for the job entrypoint, `migrate` for Alembic — and `exec "$@"` for anything else, so `docker run <image> bash` still works. *Consequences:* one image serves the API and runs both job types; an operator can run an ad-hoc command without a second image or an `--entrypoint` override.
- **DEC-353 — The health check uses the interpreter that is already there, not curl.** *Context:* a slim image has no curl, and installing one to serve a health check buys a dependency for nothing. *Decision:* `HEALTHCHECK` runs `python -c` against `/healthz`. The 120-second start period is a **chosen** default, because AutoGluon's import is heavy; it is not a measurement of this image's startup, and the first real deployment should replace it with one it timed. *Consequences:* no extra package, and the number is labelled so nobody mistakes it for evidence.
- **DEC-354 — Two Postgres services in the compose file, one of them deliberately not UTC.** *Context:* on a UTC server a naive datetime and an aware one are indistinguishable, so a timezone bug passes every test. *Decision:* `postgres` on 55432 and `postgres-tz` on 55433 running `postgres -c timezone=Asia/Kolkata`, both on tmpfs. *Consequences:* the fix in DEC-339 is proved rather than assumed — and it was: writing `12:00:00+00:00` into the old naive column read back `17:30:00` on the Kolkata server. A test database that survived a restart would be a test of the developer's machine, which is why both are disposable.
- **DEC-355 — A deployment names an image digest, never a tag.** *Context:* a tag can be moved after it has been tested — by a later build, by a person, by a retry — so a deployment that names one cannot say what it is running. *Decision:* `scripts/build_push_image.sh` pushes and then asks the registry what digest it stored (rather than trusting a local one, because a manifest list and a single-platform manifest have different digests), writes `<repo>@sha256:…` to `.image-digest`, and `make aws-deploy` passes that to `cdk deploy`. *Consequences:* what the smoke test passed is what the service runs, and a rollback is naming a previous digest.
- **DEC-356 — Deploying is manual and credential-free; CI is automatic and deploys nothing.** *Context:* Phase 4a's deployment model is one deployment per customer account. A push to a branch has no business changing somebody's infrastructure. *Decision:* `ci.yml` runs on every push — lint, the fast suite against a real Postgres service, `cdk synth`, cdk-nag, and the fast suite *inside the image* — and deploys nothing. `deploy-dev.yml` is `workflow_dispatch` only and assumes a role by OIDC, with no access key anywhere. *Consequences:* the expensive, irreversible action requires a human; `tests/unit/test_container_files.py` asserts both properties, including that no long-lived credential name appears in the workflow.
- **DEC-357 — `scripts/aws_bootstrap.py` probes each permission with one real call and reports the IAM action that would fix it.** *Context:* `cdk deploy` creates the resources but cannot show that the task role can use them: an IAM policy is a document, not a demonstration. *Decision:* one read-only-or-self-cleaning probe per concern — configuration loads, an object written/read/deleted under `_bootstrap/`, the database connects and migrates, a SageMaker `Describe` of a job name that does not exist (a role allowed to look gets `ValidationException`, one that is not gets `AccessDenied`) — each reported as a line, all of them run rather than stopping at the first failure. *Consequences:* an operator gets the whole list of what to grant, not one item at a time; the probe reports the exception's class and never its message, because an AWS error routinely quotes the resource and the principal (plan §13.7).
- **DEC-358 — The markers that spend money are excluded by the Makefile's selection, not by `addopts` and not only by missing credentials.** *Context:* the `@bedrock` smoke tests call Amazon Bedrock for real. They self-skip without the `BEDROCK_SMOKE_*` variables and AWS credentials, but both gates are facts about a machine rather than a decision, and `make test-all` was bare `pytest` - so the first runner with a role would have started billing nightly, with the invoice as the first signal (reviewer finding E-1). The obvious fix, `-m "not bedrock"` in `pyproject.toml`'s `addopts`, does not work: pytest keeps only the last `-m`, and `make test` already passes `-m "not slow"`, which replaces it. Measured: all 7 paid tests are still collected. *Decision:* `PAID_MARKERS := not bedrock and not aws` in the Makefile, composed into both default targets; `@aws` joins `@bedrock` because `pyproject.toml` already declares it never selected by default. `pytest -m bedrock` still opts in. *Consequences:* spending money is something a person asks for, not something that starts when a credential appears; `tests/unit/test_container_files.py` evaluates each default target's expression against both markers, plus a check that the free suites are still selected, so the guard cannot be satisfied by selecting nothing. Any new target that runs pytest must compose `$(PAID_MARKERS)` too; the test covers the two default targets and says so.
- **DEC-359 — The image's test stage copies the whole build context, not just `tests/`.** *Context:* `make image-test` runs the fast suite inside the api image to catch what a runner cannot - a missing system library, the non-root user, the read-only tree. The stage copied only `tests/`, and about forty tests check the repository rather than the runtime (the docs name only real `make` targets, the workflows say what they should, the generated dashboard matches its registry), reading `docs/`, the Makefile, the Dockerfile and `.github/`. CI run #62 - the first run on this branch to finish in hours - failed exactly those forty and nothing else. *Decision:* the test stage does `COPY . /app/`, and `.dockerignore` stops excluding `docs`, `.github` and root `*.md`; it keeps `docs/prototype` (10 MB of screenshots no test reads) out. The production stages still copy named directories only, so nothing that ships changes. *Consequences:* a new repository-checking test cannot break the image job by existing, which a per-test exclusion list would have. The runtime under test is still the api image's - /opt/venv, the system libraries and user 10001 come from the stage above - and the engine and api files `COPY .` lays over it are the same bytes from the same context. The stage's CMD also carries DEC-358's paid-marker filter. Measured by rebuilding the stage's file layout from the tracked checkout: 4061 passed, 0 failed, where the old layout failed 40; the build itself and the read-only tree are CI's to prove.
- **DEC-361 — `infra/naming.py` holds a second copy of the settings table, and a test is what makes the copy safe.** *Context:* a deployment is two artefacts that never import each other — the CDK app and the application — that still have to agree about a dozen strings: the SSM path a parameter lives at, the environment variable that fills a setting, the S3 prefix a policy is written against, the log group a task writes to, the prefix every SageMaker job name starts with. `infra/` cannot import `engine`, because the infra virtualenv has aws-cdk-lib in it and not pydantic. *Decision:* the names are constants in `infra/naming.py`, and `tests/infra/test_settings_contract.py` — which runs in the infra venv, where the product *is* installed for exactly this reason — imports both and asserts them equal. *Consequences:* the two are not "kept in sync by remembering"; a field added to `Settings` without a thought for the deployment fails the infrastructure suite. The duplication is deliberate and its safety is mechanical.
- **DEC-364 — Nothing under `engine/`, `api/` or `scripts/` may import `infra/`.** *Context:* the deploy extra pulls aws-cdk-lib, constructs, jsii and a Node bridge. The product must keep installing, and keep its image small, without any of them. *Decision:* `infra/` is imported by `infra/app.py` and by `tests/infra/` and by nothing else; `infra/` has its own virtualenv (`make infra-setup`), its own lint and its own test target, and the image build never copies it. *Consequences:* a deployment tool cannot become a runtime dependency by accident. The reverse import — `tests/infra/` importing `engine` — is allowed and is what DEC-361 depends on.
- **DEC-365 — An unknown CDK context key is an error, not a silent default.** *Context:* CDK context is a bag of strings with no schema. `cdk deploy -c db_storage_gb=50` and `-c db_storage_bg=50` are equally acceptable to the toolkit: the second synthesises happily, quietly uses the default, and the only symptom is a database that is the wrong size three weeks later. *Decision:* `AppContext` is a typed frozen object with every default in one place, and a flat unprefixed key it does not know raises `ContextError`. CDK's own keys share the bag and are recognised structurally — a key starting with `@` or containing `:` is not ours — and ignored. Both the bare spelling (`-c env_name=dev`) and the namespaced one (`-c marketing-ai:env_name=dev`) are accepted; supplying both with *different* values is an error, because there is no defensible answer to which the operator meant. *Consequences:* the same failure `engine/settings.py` refuses for environment variables (DEC-304) is refused here, in the same shape. The toolkit gives the app no way to enumerate context through `Node.try_get_context`, so the merged mapping is read from `CDK_CONTEXT_JSON`; tests call `from_mapping` directly and never depend on that variable.
- **DEC-366 — `cdk-nag` is pinned, because the newest version does not run.** *Context:* cdk-nag is the reason the nag job exists, and an unpinned linter is a build that breaks on somebody else's release schedule. *Decision:* `pyproject.toml` pins `cdk-nag==2.38.2`, which synthesises and evaluates every rule in this app. *Consequences:* the pin is a fact about a measured incompatibility, recorded in `infra/nag_suppressions.py`, `infra/README.md` and the deployment guide's troubleshooting section, so the next person to try bumping it finds out why before they spend an afternoon on it rather than after.
- **DEC-367 — `env_name` is not a label: there is one complete list of what it changes, and a test asserts each line.** *Context:* an environment name that quietly means eleven different things is how a `dev` deployment ends up with prod's retention and prod ends up with dev's removal policy. *Decision:* `infra/context.py` carries a "what env_name changes" section naming every difference between `dev` and `prod`, and `tests/infra/test_env_name.py` asserts every entry of it against synthesised templates. *Consequences:* the document cannot drift from the app, because a line in it that is no longer true is a failing test; and a reviewer asking "what is different about prod" has one place to read rather than seven files to grep.
- **DEC-368 — A `Settings` field added without a thought for the deployment fails the infra suite.** *Context:* `SETTINGS_FIELDS` is the list of SSM parameters the deployment writes, and a new field that nobody added to it is a setting the deployment cannot supply. *Decision:* `tests/infra/test_settings_contract.py` compares `infra.naming.SETTINGS_ENV_VARS` with `engine.settings.ENV_VARS` key by key, in both directions. *Consequences:* the failure arrives in the pull request that adds the field, when the author still has the context to decide whether the deployment should set it — which is the only moment the decision is cheap.
- **DEC-369 — Every IAM statement is written out as a document, not generated by a `grant*` helper.** *Context:* CDK's helpers are convenient and slightly too generous — `bucket.grantReadWrite(role)` hands the role the whole bucket — and none of them leaves a reviewer anything to read except a synthesised blob. *Decision:* `infra/policies.py` writes each statement out, with its sid, its actions and its resources. Two properties are enforced by tests rather than by care: `RESOURCE_WILDCARD_ALLOW_LIST` names every action for which AWS offers no resource-level alternative with the reason beside it, and `tests/infra/test_iam.py` walks every identity policy in every synthesised stack and fails on an `Allow` with `"Resource": "*"` whose actions are not all on that list. *Consequences:* the policy is a document a reviewer can read in the diff; an ARN with a wildcard *path* (`…/uploads/*`, `…/training-job/marketing-ai-*`) is a different thing from `"*"` and is the point, because it names a prefix. `s3:ListBucket` is granted on the bucket itself and deliberately carries no `s3:prefix` condition: during a `GetObject` there is no `s3:prefix` in the request, so such a condition would fail closed, and without the action S3 answers `403` for a key that is simply absent — which would turn every missing-artefact path in the product into a permissions bug report.
- **DEC-370 — The SageMaker stack creates a role and no SageMaker resource.** *Context:* a job is created at run time by `SageMakerJobRunner` from a `JobSpec`, with a name derived from the run. There is nothing to create ahead of time except the identity the job runs as and the boundary that identity is scoped to. *Decision:* the stack creates the execution role; the boundary is a name prefix, `marketing-ai-*`, which `infra/policies.py` scopes the caller's statements to. No `List*` action is granted anywhere, because `sagemaker:ListTrainingJobs` cannot be scoped to a prefix and granting it would show this deployment every job in the account (the other half of DEC-334). The execution role carries the one EC2 statement AWS documents with no resource types, because a VPC-attached job makes SageMaker create ENIs in our subnets. *Consequences:* that statement is on the wildcard allow-list with its reason, which is what DEC-369's test requires of it; nothing else about the job is pre-created, so the runner and the role cannot drift apart.
- **DEC-371 — An empty model list is an explicit `Deny`, never an absent `Allow`.** *Context:* leaving the Bedrock permission out when no model is configured is indistinguishable from forgetting it. *Decision:* with generative disabled or no model named, the role carries an explicit `Deny` on `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream`. *Consequences:* the difference matters the day somebody attaches a broad managed policy to the task role for an unrelated reason: an explicit `Deny` survives that and an absent `Allow` does not. The rule reads the same from both sides — "empty means deny, never allow-all".
- **DEC-372 — Private subnets, and the endpoint-or-NAT choice is a parameter with a guard.** *Context:* everything runs in private subnets, which leaves one question — how a private subnet reaches the AWS APIs it cannot work without — with two answers that are priced differently and fail differently. A NAT gateway routes everything to the internet, including calls to services nobody thought about. Interface endpoints put a private ENI per named service per subnet, and the failure of a missing one is not "slower", it is a task that stops before it writes a log line. *Decision:* `nat_gateways` and `vpc_endpoints` are context, and `AppContext.validate` refuses the combination where a Fargate task could not pull its image, start its log driver or read its settings. The guard lives in the context object rather than in the stack so it fires before any construct is created and the operator gets a sentence instead of a stack trace. *Consequences:* neither price is written down here — endpoints are billed per endpoint, per AZ, per hour plus per GB, and a NAT gateway per hour plus per GB; the *shape* of the charge is the part worth knowing when choosing, and the rate is AWS's to publish and has not been measured (plan §13.3).
- **DEC-373 — The bucket policy denies the *wrong* encryption header, not the absent one.** *Context:* the snippet in every blog post denies any `PutObject` that does not carry `x-amz-server-side-encryption: aws:kms`. That would break this product: `S3Storage` sets the encryption headers only when `s3_kms_key_id` is configured, and with it unset — a perfectly valid deployment, and what a local-to-S3 migration looks like on its first day — every PUT is header-less and would be refused, as `AccessDenied` on a write, which reads like a broken role. *Decision:* a header-less PUT is not an unencrypted one: S3 applies the bucket's default encryption and the object lands encrypted exactly as intended. So the deny is `StringNotEquals` guarded by `Null: false`, which can only match a request that actually set the header, and the same shape is applied to the key id so a caller cannot name a different KMS key. *Consequences:* both configurations work and neither can write a plaintext or wrong-key object. `enforce_ssl` and `minimum_tls_version: 1.2` are the other two denies and neither substitutes for the other: one refuses plaintext HTTP, the other an obsolete cipher suite over HTTPS.
- **DEC-374 — The observability stack contains no threshold and no widget list of its own.** *Context:* a threshold typed into a CDK file is a number that looks measured because it is in code. *Decision:* `infra/observability/dashboard.json` and `infra/observability/alarms.json` are generated beside the stack, and the stack renders them if they are there. What is genuinely the stack's own is the log groups (they must exist with a retention *before* anything writes to them — a group created implicitly by ECS or RDS is created with "Never expire", which is why the RDS group is created here under the name RDS exports to and why this stack is ordered ahead of the database stack), the alarm topic (an alarm with nowhere to go is a colour in a console) and the metric filters (a filter's pattern is a statement about the log *schema*, which is a fact; a threshold is a judgement). *Consequences:* "where did 0.95 come from" stays answerable. With neither JSON file present the stack still deploys and an operator gets log groups, a topic and two custom metrics with no alarms — a smaller thing than intended but not a broken one, which is what makes the two sides independently deployable.
- **DEC-375 — Cost-allocation tags carry `product`, `env` and `client`, and never `use_case`.** *Context:* one deployment serves every use case, so at the stack level the use case is not known. *Decision:* `AppContext.tags()` returns `product`, `env` and, when one is named, `client`; every taggable resource in every stack carries them. The use case is carried on the things that *do* belong to one — `JobSpec.tags` puts it on a SageMaker job, and the object prefixes carry it in S3. *Consequences:* a per-use-case tag at deployment level would be a value that is wrong for every run but one. The budget's cost filter uses `product`, which means it only sees tagged spend once that tag is activated in Billing and Cost Management — an account-level action CloudFormation cannot perform, which takes up to 24 hours, and which the README says so next to the first-deployment checklist.
- **DEC-376 — Two secrets, and the composed URL is written down as a seam.** *Context:* `marketing-ai/<env>/db` is the credential RDS knows about and the AWS single-user rotation function rewrites. `marketing-ai/<env>/app` is the application document `engine/aws/secrets.py` fetches, whose keys are `Settings` field names, and it holds one key — `postgres_dsn` — composed at deploy time from the credential secret through a CloudFormation dynamic reference. *Decision:* keep the two, and record the consequence rather than hide it: the composed URL is a *snapshot*. The rotation function changes `password` in the credential secret and knows nothing about the application document, so after the first rotation the URL carries the previous password until someone redeploys the database stack. *Consequences:* the rotation schedule is set to the longest interval that is still a rotation, `infra/README.md` says plainly what has to happen when it fires, and the nag suppression that covers it cites this entry rather than claiming the arrangement is fine. The fix is not in the CDK: it is for `engine.settings` to accept the standard RDS credential document (`username`, `password`, `host`, `port`, `dbname`) and build the URL itself, at which point the stack keeps one secret and rotation is end to end.
- **DEC-377 — The task definition sets three environment variables, and that is the only shape that leaves SSM meaning anything.** *Context:* the process environment beats SSM (DEC-301). So a task definition that also sets `MARKETING_AI_S3_BUCKET` does not "agree with" the parameter of the same name — it overrides it, permanently and invisibly, and an operator who edits `/marketing-ai/<env>/s3_bucket` watches their change have no effect. *Decision:* everything the deployment knows goes into Parameter Store; the task definition carries only what has to be true before any of it can be read — which deployment this is, which region to read it from, and that it should read AWS at all. `tests/infra/test_task_definition.py` fails on a fourth. *Consequences:* Parameter Store is the place to change a setting, which is what an operator expects of it. The database password is not in the task definition in any form: the task reads the application secret itself with `secretsmanager:GetSecretValue` on exactly one ARN, so what the deployment hands the container is a name and what the container fetches is never rendered into something anyone with `ecs:DescribeTaskDefinition` can read.
- **DEC-378 — No `monthly_budget_usd`, no budget — there is no default amount.** *Context:* a budget is a statement about what a deployment is *allowed* to cost, and nobody in this repository knows that number: it depends on the customer, the account and what else is in it. *Decision:* the field has no default. With no amount there is no budget and a stack output that says so in words, rather than an empty stack that looks like a bug. With an amount, `AppContext.validate` refuses the combination of an amount and no `alert_email`, because a budget nobody is told about is a number in a console. The two notification thresholds are percentages of the operator's own number, so they carry no claim about what anything costs. *Consequences:* a plausible-looking default would be the same mistake as a fabricated metric — it would look like a decision somebody made (plan §13.3).
- **DEC-379 — An alarm whose threshold would be a guess is not created, and says which context value would create it.** *Context:* `infra/observability/alarms.json` commits a threshold only where the number is a definition rather than a measurement. For the others it leaves a `${Name}` substitution and says why. *Decision:* the operator supplies them with `-c alarm_thresholds=Name=value,…`, parsed by `AppContext.alarm_threshold_values`. An alarm whose substitution is not supplied is **not created**, and the observability stack reports which context value would have created it. *Consequences:* a threshold invented by this deployment would read as though somebody had measured it (plan §13.3). The deployment guide points the operator at their own history as the place the number comes from, which is the only place it can come from on day thirty and does not exist on day one.

- **DEC-228 — The browser chooses a credential source, never a credential.** *Context:* different people use this product with different AWS credentials, and the obvious way to let them is a form with an access key and a secret. *Decision:* there is no such form. The connection screen chooses between boto3's default chain and an AWS CLI profile *by name*; the server resolves the name from `~/.aws/`, the SSO token cache or the task role - the one place built to hold, refresh and rotate a secret. `AwsConnection` has exactly two fields, `source` and `profile`, and refuses any third. A person without a profile is told how to make one (`aws configure --profile NAME`, `aws configure sso`) on the machine running the server. *Consequences:* a secret is never in a request body, a browser, a proxy log or a HAR file attached to a bug report, and SSO users get short-lived credentials for free; the cost is that a person must be able to run the AWS CLI on the server's machine - true of every laptop install, and a deployment uses its role anyway.
- **DEC-229 — Only the page the product serves, on a local install, asked from loopback, may choose.** *Context:* the API is unauthenticated (AWS_DEPLOYMENT.md §9.2), so there is no person to scope a choice to. Loopback alone is not enough: a reverse proxy on the same host makes every request loopback, and - the finding that made this rule stricter - another website open in the same browser sends requests that genuinely come from 127.0.0.1. With CORS open to any origin, a `text/plain` POST needs no preflight; measured, such a page could read the full account id and ARN, list the profiles and save `prod-admin`, and a DNS-rebinding page could do the same without CORS at all. *Decision:* `editability` requires `env == local`, a loopback peer, a `Host` naming this machine, an `Origin` (when sent) that is a loopback page, and no forwarding header. Everyone else - another machine, another site, any deployment - gets a masked, read-only answer. *Consequences:* the choice belongs to the person at the keyboard of the machine whose identities they are; a plain TCP port-forward of localhost can still make a remote user local, and is recorded here rather than solved.
- **DEC-230 — A connection test proves the connection without spending anything.** *Context:* the tempting check is a one-token completion, which costs money, needs a Meter it has no job to belong to, and still does not say *who* the credentials are. *Decision:* `sts:GetCallerIdentity` (needs no IAM permission) says who; `bedrock:GetFoundationModelAvailability` says whether each configured model is enabled for that account and region, invoking nothing. A denied availability check is *unverified*, never *unavailable*, because a task role scoped to `InvokeModel` is refused the question and can still use the model. At most four checks run at once; the rest are refused with `429 CHECK_BUSY`, so an unauthenticated caller cannot tie up the worker threads the rest of the API needs. *Consequences:* testing is free and safe to press repeatedly; cross-region inference-profile ids cannot be checked this way and are reported as unverified.
- **DEC-231 — These routes read their own bodies, because FastAPI's default 422 repeats its input.** *Context:* measured, a request carrying `aws_secret_access_key` had the secret reflected in the validation error, and so did a bare JSON string. *Decision:* `/connection/aws` parses the raw body, capped at 4 KiB before it is read; an error names the fields that are *accepted* and never repeats what was sent. A body that looks like a credential - a field named like a secret, an access key id, a secret-key or session-token shape anywhere, including one hidden behind a duplicated key - gets `CREDENTIALS_NOT_ACCEPTED`, which says nothing was stored and that the key should be rotated. AWS's own error text never reaches a report either, because `SignatureDoesNotMatch` quotes the credential scope, which names the access key id. Every response, errors included, is `Cache-Control: no-store`. *Consequences:* a person who makes the mistake learns about it at once and is not handed their secret back; a rare 40-character profile name of mixed case and digits would be refused as a possible key.
- **DEC-232 — What is remembered is a profile name, on a laptop, readable by its owner - and a deployment never looks.** *Context:* the choice has to survive a restart, and anything persisted is something that can be planted or read. *Decision:* the only file is `<data_dir>/local/aws_connection.json`, holding `source` and `profile` and nothing else - never the resolved account or ARN (engine/settings.py, rule 1). It is written through a fresh random temporary file, 0600 in a 0700 directory, and read only if it is a regular file, not a symlink, owned by this user and writable by nobody else. A deployment neither writes it nor reads one that is there, and a file that no longer parses means the default chain, never a guessed profile. Generative jobs ask `profile_in_force()`, which decides from the deployment name alone, because building full settings from the environment fails validation on `prod` - an earlier version did exactly that and would have turned every generative job on `prod` into a 503. *Consequences:* nothing planted in a deployment's data directory can redirect whose account it bills, and nobody who never opens the screen sees any change, because no choice is `None` - boto3's own default chain.
