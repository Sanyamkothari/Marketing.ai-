## 1. Summary

Milestone M99 introduces an offer and channel catalogue, channel-aware consent, and data-driven regional
compliance rules (Plan J, milestone M99, DEC-1309).

Before M99, consent was all-or-nothing, actions were free-text labels with no channel or cost, and channel
costs lived in `configs/pilot/value.yaml`. Customers often opt out of one channel (SMS) and stay in for
another (email), and offers have their own channels, costs and regulatory requirements (a registered DLT
template for SMS in India).

M99 delivers:
1. **The action catalogue (`engine/decide/catalogue.py`)**:
   - `configs/decide/catalogue.yaml`, validated by a frozen pydantic model `ActionCatalogue` (the
     `configs/privacy.yaml` pattern): a unique `action_id`, a `label`, `channels`, `offer_cost`,
     `contact_cost`, `eligibility`, and regulatory metadata (`dlt_template_id`, `message_category`, `purpose`).
   - Every treat list summary carries `catalogue_sha256` (`TreatListSummary.catalogue_sha256`).
   - **Claude Code fix (second review):** it is the sha256 of the catalogue **the run ran under**, not of the
     file when the treat list is built. A run whose config root has a catalogue writes `catalogue_stamp.json`
     after the actions stage (the sha256 and the channels of each action the use case names); the treat list
     plans channels from it and, when the file has since changed, been added or been removed, logs a warning
     and says so in `catalogue_note`. A run with no catalogue has `catalogue_sha256: null`.
   - **Claude Code fix:** the repository ships **no** catalogue. `configs/decide/catalogue.example.yaml` is a
     labelled example, never read, whose DLT template id is the placeholder `<your DLT template id>` (a
     placeholder counts as missing). `channels` is a list (a single `channel:` is still accepted; a comma in
     it is refused). The cache is keyed by root and content, so an edited file is read again.
2. **One cost lookup (`engine/pilot/roi.py::lookup_value_costs`)**:
   - With a catalogue, its channels' contact costs replace `configs/pilot/value.yaml`'s for those channels.
   - **Claude Code fix:** an offer cost comes only from an action id (`action_id=`); a channel gives a contact
     cost only. An unknown id is `CATALOGUE_ACTION_UNKNOWN`. With no catalogue the answer is M97's exactly.
3. **Additive action references in use cases**:
   - `Band.action_id` (propensity) and `uplift.policy.treat_action_id` (uplift); `Band.action` stays the label.
   - An unknown action id fails config load with `CATALOGUE_ACTION_UNKNOWN`
     (`engine.decide.catalogue.validate_action_ids`, called in place by `load_use_case` and `resolve_config`).
   - **Claude Code fix:** both fields, `SuppressionConfig.channels` and `SuppressionCount.channel_counts` are
     left out of the serialised file while unset (`exclude_if`), so a default `run_config.json` and
     `scoring_summary.json` are byte for byte what they were.
4. **Channel-aware contactability**:
   - `actions.suppression.channels {channel: {consent_column, contactable_column}}`. The three suppression
     reasons and the DEC-A2 precedence are unchanged; a channel opt-out does not suppress the customer in
     `scores.csv`.
   - **Claude Code fix:** the partner's treat list read the consent columns from `scores.parquet`, which a real
     run never writes, so every customer was contactable on every channel. Contactability is now worked out
     **during the run**, right after the actions stage (`engine/decide/contactability.py`, installed in the
     Plan J block of `engine/pipeline.py`), from the columns as uploaded and, when the consent ledger gates the
     run, from the ledger's records for each channel. It is written as `channel_contactability.parquet`
     (row-level) and `channel_contactability.json` (counts). Default runs write nothing new.
   - **Claude Code fix:** `channel_counts` is, per channel, the rows eligible to be treated (neither suppressed
     nor held out as control) that are not contactable on it. It rides on the `opted_out` entry of
     `scoring_summary.json`, else the `consent_false` entry; no entry is ever invented for it.
5. **The treat list (`engine/decide/treat_list.py`)**:
   - Carries `channel` (the channel used) and `contactable_channels`. This is a reviewed change to an existing
     artefact: **every** treat list, default runs included, gains the `contactable_channels` column (empty for
     a run without channels) and every `treat_list_summary.json` gains `"catalogue_sha256": null` when the run
     had no catalogue, as the M99 spec asks; the four golden treat lists were updated for it.
   - A customer is treated only on a channel they are contactable on; one with no contactable planned
     channel is not treated (`treat = 0`) and is not suppressed.
   - **Claude Code fix:** it joins `channel_contactability.parquet` on every key column. A customer the file
     does not cover (and every customer of a run without channels) has a null `contactable_channels` and is
     treated as before. The summary adds `channel_counts` and `uncontactable_rows` (both absent when the run
     configured no channels).
   - **Claude Code fix (second review):** `contactable_channels` is labelled from the flag patterns present
     (`_channel_labels`, `np.unique` over rows), never a table of all 2^k channel combinations, so any number of
     configured channels costs time linear in rows.
6. **Channel-aware consent ledger (`engine/privacy/`)**:
   - Nullable `channel` on `ConsentRecordRow` and `ConsentRecord`, Alembic `0007_consent_channel.py` chained to
     `0006`. Null means every channel, so existing records keep applying to all channels.
   - **Claude Code fix:** a laptop's SQLite `platform.db` from before M99 gets the column in place
     (`add_missing_columns`), also when the scoring seam opens the ledger without creating tables; the channel
     is stored stripped and in lower case.
   - **Claude Code fix (second review):** the channel must be a channel name (`engine.decide.spec.CHANNEL_NAME`,
     the rule config and catalogue use). An imported row with `e-mail` or `text msg` is refused with
     `CONSENT_CHANNEL_INVALID`, as other bad cells are, and `ConsentLedger.record` raises `ValueError`, so an
     opt-out that no configured channel could ever match is never stored.
7. **Data-driven regional rules (`configs/regions/in.yaml`)**:
   - `sms_requires: [dlt_template_id, message_category]`, applied to the catalogue's `region` with no region
     named in Python. A missing DLT template id is `ACTION_DLT_TEMPLATE_MISSING`.

## 4. New Error Codes

1. **`CATALOGUE_ACTION_UNKNOWN`**: the use case (or a cost lookup) names an `action_id` that
   `configs/decide/catalogue.yaml` does not declare, or there is no catalogue.
2. **`ACTION_DLT_TEMPLATE_MISSING`**: the catalogue's region requires a DLT template id for a channel an action
   uses (`configs/regions/<region>.yaml`), and the action has none or still has the example's placeholder.
3. **`CATALOGUE_INVALID`**: `configs/decide/catalogue.yaml` failed validation (a missing or extra field, a
   duplicate action id, `channels` not a list of channel names, or a region's other required field missing).

The help text is returned with this review for `configs/pilot/help.yaml`.

## 7. Open Questions and Known Gaps

1. **Multi-offer arbitration (M100/M101).** One planned action per band (or per uplift run). Choosing among
   several offers by net value is M100's.
2. **Channel order.** The first contactable planned channel is used, in the catalogue action's order (or the
   configured order). Choosing the cheapest is for M100.
3. **Channel columns as features.** A channel consent column in a training file is not reserved by
   `engine/stages/prepare.py` the way `governance.consent_column` and `opt_out_column` are, so a model could
   learn from it. Reserving it means editing a Phase 1 stage outside DEC-1300 (c); raised, not done.
4. **The catalogue is read from the run-time config root.** A run reads `decide/catalogue.yaml` where it reads
   `privacy.yaml`: `MARKETING_AI_CONFIG_DIR`, else `configs/`. An API started with `create_app(config_root=...)`
   and no such variable validates action ids against its own root but stamps from the run-time root; in a
   deployment both are the same directory. (Resolved by the second review: the treat list no longer reads the
   catalogue as it is when the list is built; see §10.)
5. **The scoring gate's all-channel question** reads only all-channel ledger records: a customer whose only
   records are channel-specific has no all-channel consent and is suppressed as `consent_false`.

## 8. Self-Check (§4.7 Checklist)

1. **Public entry point, real run's configuration.** The acceptance tests run `Pipeline.run_train` and
   `Pipeline.run_score` and build the treat list from what those runs wrote (§3). No test writes a run
   artefact by hand.
2. **Compute once, pass everything down.** Contactability is computed once, in the run; the treat list reads it.
3. **Linear time at 1M rows.** Column-wise masks, a hash join on the key, one ledger query per channel, and
   `contactable_channels` labelled from the distinct flag patterns present (at most min(rows, 2^channels)); no
   loop over customers except building the principal keys, as the consent gate already does.
4. **Nothing fabricated, nothing mislabelled.** No catalogue ships; the example says it is one and its
   placeholders are refused. A customer the contactability file does not cover gets null, not a guess.
5. **Defaults unchanged, and the one reviewed change.** With no `actions.suppression.channels` and no catalogue
   nothing runs and nothing is written. Run artefacts (`scores.*`, `run_config.json`, `scoring_summary.json`)
   and config loads are byte-identical to `main` (the new config and summary fields are left out while unset),
   and costs are identical (§3). The on-demand treat list deliberately changes: it gains a
   `contactable_channels` column (empty for runs without channels) and a `catalogue_sha256: null` summary
   field, as the M99 spec requires; the four golden treat lists were updated as a reviewed edit.
6. **Stay in your lane.** `scripts/bench_1m.py` and `engine/stages/actions.py` are `main`'s. `engine/config.py`
   has in-place edits only (listed in §2), typed in `engine/decide/spec.py`, and its PLAN-J block holds the
   rest. Edits outside Plan J's paths are listed in §2 and announced in the cross-branch notes.
