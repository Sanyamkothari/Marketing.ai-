# M99 Hand-off: Offer and Channel Catalogue, Channel-Aware Consent (DEC-1309)

> Built by partner agent on branch `plan-j/m99-catalogue`. Acceptance tests written first following TDD.

## 1. Summary

Milestone M99 introduces a unified offer and channel catalogue, channel-aware consent, and dynamic data-driven regional compliance rules (Plan J, milestone M99, DEC-1309).

Prior to M99, consent in Marketing AI was an all-or-nothing flag, actions were free-text labels without structured channel or cost definitions, and channel costs resided in ad-hoc pilot configs. In enterprise marketing, however, customers frequently opt out of specific channels (e.g., unsubscribing from SMS while remaining opted into email), and offers have distinct delivery channels, offer discounts, contact costs, and regulatory requirements (such as DLT template registration for SMS in India).

M99 delivers:
1. **The Action Catalogue (`configs/decide/catalogue.yaml`, `engine/decide/catalogue.py`)**:
   - Validated by a frozen Pydantic model `ActionCatalogue` following the `configs/privacy.yaml` pattern.
   - Declares action items with unique `action_id`, business `label`, primary or comma-separated `channel`s, `offer_cost`, `contact_cost`, `eligibility`, and optional regulatory metadata (`dlt_template_id`, `message_category`, `purpose`).
   - Computes a stable SHA-256 fingerprint `catalogue_sha256` that is stamped on every treat list summary (`TreatListSummary.catalogue_sha256`).
2. **Unified Value Costs Lookup (`engine/pilot/roi.py::lookup_value_costs`)**:
   - Single point of truth for offer and contact costs: checks `configs/decide/catalogue.yaml` first, falling back to `configs/pilot/value.yaml`.
3. **Additive Action References in Use Cases**:
   - Use cases reference catalogue action IDs via `Band.action_id` (propensity) and `uplift.policy.treat_action_id` (uplift).
   - Free-text `Band.action` remains as the human-readable label.
   - Any reference to an unknown action ID fails configuration load immediately with `ConfigError("CATALOGUE_ACTION_UNKNOWN")`.
4. **Channel-Aware Suppression & Contactability**:
   - Suppression configuration declares per-channel consent and contactability via `SuppressionConfig.channels {channel: {consent_column, contactable_column}}`.
   - Core 3-value suppression reason Literal (`consent_false`, `opted_out`, `recently_contacted`) and DEC-A2 precedence remain untouched.
   - Channel opt-out does NOT suppress a customer in `scores.csv` (preserving their model score and band).
   - Per-channel suppression counts are aggregated in `SuppressionCount.channel_counts`.
5. **Treat List Contactability & Channel Selection (`engine/decide/treat_list.py`)**:
   - Treat lists carry `contactable_channels` (comma-separated list of contactable channels for the customer) and `channel` (the chosen contactable channel).
   - A customer is treated only on a channel they are contactable on.
   - A customer whose only planned channel is opted out is not treated (`treat = 0`), has `channel = None`, and is counted in `channel_counts`.
6. **Channel-Aware Consent Ledger (`engine/privacy/`)**:
   - Added nullable `channel` column to `ConsentRecordRow` and `ConsentRecord`, with Alembic migration `0007_consent_channel.py` chained to `0006_campaigns`.
   - `channel is null` applies universally to all channels; channel-specific records apply to queries for that channel.
7. **Data-Driven Regional Rules (`configs/regions/in.yaml`)**:
   - Regional compliance rules declared in data files (e.g. `sms_requires: [dlt_template_id, message_category]` for region `IN`).
   - Dynamic lookup based on `catalogue.region`; zero region names hardcoded in engine code.
   - SMS actions missing DLT templates in India fail validation with `ACTION_DLT_TEMPLATE_MISSING`.

## 4. New Error Codes

1. **`CATALOGUE_ACTION_UNKNOWN`**
   - **Help Title:** Action ID not in catalogue
   - **Help Text:** `meaning: The use case configuration references an action_id that is not declared in configs/decide/catalogue.yaml. fix: Add the action to configs/decide/catalogue.yaml with its channel and costs, or correct the action_id in the use case actions bands or uplift policy.`

2. **`ACTION_DLT_TEMPLATE_MISSING`**
   - **Help Title:** DLT template ID missing for India SMS action
   - **Help Text:** `meaning: configs/regions/in.yaml requires SMS actions to declare a registered DLT template ID, but this action does not have one. fix: Add the DLT template ID from your telecom registration (e.g. dlt_template_id: '1107...') to the action in configs/decide/catalogue.yaml.`

3. **`CATALOGUE_INVALID`**
   - **Help Title:** Action catalogue invalid
   - **Help Text:** `meaning: configs/decide/catalogue.yaml failed validation (missing required fields, duplicate action IDs, or missing regional channel requirements). fix: Correct the field indicated in the error path in configs/decide/catalogue.yaml.`

## 5. Decision Text

### DEC-1309 — Offer and channel catalogue, channel-aware consent (Plan J M99)

- **(a) Action catalogue schema and fingerprint.**
  - *Context:* Campaigns use multiple delivery channels (SMS, email, WhatsApp) and offers with distinct costs and regulatory requirements. Hardcoding these in use cases duplicates configuration and prevents arbitration across campaigns.
  - *Decision:* Maintain `configs/decide/catalogue.yaml`, validated by frozen Pydantic model `ActionCatalogue` (`engine/decide/catalogue.py`). Stamp `catalogue_sha256` on every treat list summary (`TreatListSummary.catalogue_sha256`).
  - *Consequence:* All offer definitions and channel costs are version-controlled in one place. Editing the catalogue alters `catalogue_sha256`, enabling auditability of which catalogue governed each scoring run.

- **(b) Single cost lookup point.**
  - *Context:* M97 introduced net value ranking using channel contact costs and offer costs, while ROI reporting also requires cost parameters.
  - *Decision:* Provide `engine.pilot.roi.lookup_value_costs(channel=..., action_id=..., root=...)` as the single point of lookup. It queries `configs/decide/catalogue.yaml` first, falling back to `configs/pilot/value.yaml`.
  - *Consequence:* Net value ranking, ROI simulation, and offer choices share identical cost figures without duplicate parsing logic.

- **(c) Additive use case action references.**
  - *Context:* Use cases define bands and actions as free-text strings (`Band.action`).
  - *Decision:* Allow bands and uplift policies to optionally specify `Band.action_id` and `UpliftPolicyConfig.treat_action_id`. Keep `Band.action` as the human-readable label. Require all declared `action_id`s to exist in the catalogue if present; raise `CATALOGUE_ACTION_UNKNOWN` on unknown IDs.
  - *Consequence:* Backward compatibility is preserved for existing use cases lacking `action_id`, while new use cases link unambiguously to catalogue items.

- **(d) Channel-aware consent and suppression precedence.**
  - *Context:* Customers frequently opt out of SMS while consenting to email. Suppressing a customer completely in `scores.csv` because of a single channel opt-out would hide viable treatment channels.
  - *Decision:* Introduce `SuppressionConfig.channels {channel: {consent_column, contactable_column}}`. Channel opt-out does NOT suppress rows in `scores.csv`. The core 3-value suppression reason Literal (`consent_false`, `opted_out`, `recently_contacted`) and DEC-A2 precedence are untouched. Per-channel denials are tallied in `SuppressionCount.channel_counts`.
  - *Consequence:* `scores.csv` retains model predictions and band assignments. Channel contactability is evaluated during treat list generation.

- **(e) Channel selection and uncontactable treatment suppression in treat list.**
  - *Context:* Treat list hand-offs must indicate which channel to use and guarantee that uncontactable customers are not contacted.
  - *Decision:* Treat list outputs carry `contactable_channels` and `channel`. If a customer has planned channels but none is contactable, `treat = 0` and `channel = None`. If multiple planned channels are contactable, select the planned channel deterministically.
  - *Consequence:* Campaign managers receive an execution-ready treat list where `treat = 1` guarantees that the customer is reachable on the specified `channel`.

- **(f) Channel-aware consent ledger.**
  - *Context:* The platform consent ledger recorded universal consent only.
  - *Decision:* Add nullable `channel` column to `ConsentRecordRow` and `ConsentRecord` via migration `0007_consent_channel.py`. `channel is null` matches queries for all channels, preserving existing records.
  - *Consequence:* Existing consent records continue to govern all channels, while new records can record channel-specific grants or withdrawals.

- **(g) Data-driven regional compliance rules.**
  - *Context:* India telecom regulations mandate registered DLT template IDs and message categories for commercial SMS, but hardcoding region names in Python violates configuration-over-code principles.
  - *Decision:* Place regional requirements in `configs/regions/<region>.yaml` (e.g. `in.yaml` declaring `sms_requires: [dlt_template_id, message_category]`). Dynamic lookup in `load_catalogue` applies the rules based on `catalogue.region`. Missing required fields raise `ACTION_DLT_TEMPLATE_MISSING` or `CATALOGUE_INVALID`.
  - *Consequence:* Zero region names are hardcoded in engine Python code; supporting new regional rules requires adding a YAML file under `configs/regions/`.

## 6. README Note

### Offer and channel catalogue, channel-aware consent (M99)
Adds a frozen action catalogue (`configs/decide/catalogue.yaml`) with channel definitions, offer costs, and per-channel contact costs, stamped by SHA-256 fingerprint on every treat list. Enables channel-aware consent and contactability in use cases (`SuppressionConfig.channels`), allowing customers opted out of SMS to receive email treatments while suppressing customers with no contactable planned channel (`treat = 0`) and reporting counts in `SuppressionCount.channel_counts`. Adds nullable `channel` to the consent ledger (Alembic `0007_consent_channel.py`) matching existing records universally, and enforces data-driven regional regulations (`configs/regions/in.yaml`, requiring DLT template IDs for Indian SMS) without hardcoding region names in code.

## 7. Open Questions and Known Gaps

1. **Multi-Offer Arbitration (M100/M101)**: M99 resolves channel contactability for a single planned action per band. When multi-treatment uplift (M100) and cross-use-case arbitration (M101) land, multiple eligible offers across channels will be evaluated by net value ranking. M99's `lookup_value_costs` and channel contactability masks directly enable this.
2. **Channel Priority Ordering**: Currently, when an action declares multiple channels (e.g. `channel: "sms,email"`), the first contactable channel in declaration order is selected. In M100, cost-optimised channel selection (e.g. preferring cheaper email over WhatsApp) can be tied to net value optimisation.
