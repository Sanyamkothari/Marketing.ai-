## 1. Summary

Milestone M101 makes sure a customer gets **at most one action** (or the configured contact cap) in a cycle across
the use cases, and that each use case can still measure its own effect.

1. **Arbitration engine (`engine/decide/arbitrate.py`).** `arbitrate_treat_lists` is a pure function over the
   treat lists (M98) of several scoring runs; the order of the lists is the request's use case order.
   - Hold-out members are never treated by any use case.
   - A row M92 treated at random (`explore = 1`, `treat = 1`) keeps its action, like hold-out protection. Two
     explore-treated rows of one customer are both kept only if the contact cap allows; otherwise the first by
     request order is kept and the other is recorded as dropped.
   - The rest are ranked by `priority x value` **only when every candidate of the customer carries the same kind of
     value** (all `net_value`, or all `expected_gross_value`). Otherwise they are ranked by priority alone. A tie is
     broken by the request's use case order. A candidate with no value is never given one: there is no
     `fillna(1.0)`, and incremental and gross values are never compared.
   - `contact_cap_per_customer` (default 1) and `channel_caps` (default none) hold.
   - Every row says why (`arbitration_reason`); the summary counts how the customers who lost an action were decided.
2. **No configuration ships.** `configs/decide/arbitration.example.yaml` is a labelled example that is never read.
   With no `decide/arbitration.yaml` in the config root: priority 1 per use case, cap 1 per customer, no channel caps.
3. **One campaign per use case from its winning rows** (`create_arbitrated_campaign`,
   `engine/measurement/campaign.py`): only the use case's winners are in the treated arm; others are `suppressed`.
4. **Row-level privacy and access:** the two files are row-level artefacts (`configs/privacy.yaml`,
   `engine/privacy/layout.py`, `api/access_policy.py`); downloads are Analyst-only and audited.
5. **Results UI:** the `Arbitration & Conflicts` card.
6. **Scale:** whole-array work; 200,000 customers take about 1 second across two use cases and 1.5 seconds across
   three with every path on (about 5 to 8 seconds for a million).

product writes (`tests/fixtures/decide/treat_runs.py`) and treat lists built by `build_treat_list`; none builds a

## 7. Open Questions and Known Gaps

1. **`scripts/bench_1m.py` unreachable warning on macOS** is pre-existing and left alone.
2. **A control group of one use case's own** (Phase 1's per-run control, not M92's persistent hold-out) is not in
   the treat list as a flag, so another use case may treat that customer. Only M92's hold-out is protected across
   use cases (DEC-1311 (c)). Raise it if a client runs Phase 1 control groups beside Plan J.
3. **A malformed `arbitration.yaml`** is logged and the defaults are used, as in the partner's code; it does not stop
   the request. A client who writes channel caps and mistypes the file would run without them.
4. **Channel capacity is allocated once, after the contact cap**: a customer whose action is capped out of a channel
   is not moved to another channel or to their next-best action.
5. **`POST /decide/arbitrate` selects the latest scoring run of each use case** unless `run_ids` are given.
