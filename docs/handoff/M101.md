# M101 Hand-off: One Action Per Customer Across Use Cases (DEC-1311)

> Built on branch `plan-j/m101-arbitration` (branched from `origin/main` at `6069627`).
> Implements cross-use-case arbitration and campaign measurement isolation (Plan J, milestone M101, DEC-1311).

## 1. Summary

Milestone M101 implements cross-use-case arbitration to ensure **at most one action per customer** (or within a configured contact cap) across overlapping campaigns, resolving conflicts deterministically by `priority weight * net value` (DEC-1311).

In multi-campaign enterprises, customers frequently qualify for multiple simultaneous treatments (e.g. win-back, retention, churn prevention). Without arbitration, customers receive competing messages within the same marketing cycle, inducing customer fatigue and confounding causal evaluation.

M101 introduces:
1. **Deterministic Arbitration Engine (`engine/decide/arbitrate.py`)**:
   - `arbitrate_treat_lists`: vectorised, pure multi-table arbitration algorithm.
   - Computes candidate priority score:
     $$\text{priority\_score} = \text{priority\_weight} \times \text{net\_value}$$
     (falling back to expected gross value, raw score, or deterministic order).
   - Enforces `contact_cap_per_customer` (default `1`, configurable via `configs/decide/arbitration.yaml`).
   - Enforces optional delivery `channel_caps` (e.g. limiting SMS volume).
   - Produces `arbitrated_treat_list.csv` and `arbitrated_treat_list.parquet`, with explicit `winning_use_case`, `losing_actions` (suppressed candidate offers), and `priority_score`.
   - Produces aggregate `ArbitrationSummary` tracking total evaluated customers, conflicts (>1 qualifying action), treated winners, dropped actions count, and use case breakdowns.
2. **Holdout & Explore Safety**:
   - Customers in the persistent universal holdout (`holdout = 1`) in any participating use case are strictly protected: they are **never treated** under any circumstances (`treat = 0`).
   - Explore slice rows (`explore = 1, treat = 1`) preserve randomisation and are retained.
3. **Clean Campaign Measurement Isolation (`engine/measurement/campaign.py`)**:
   - `create_arbitrated_campaign`: creates one measurement campaign per participating use case containing only that use case's winning rows (`arm = "treated"`).
   - Candidate rows that lost arbitration are marked `arm = "suppressed"`, preventing contamination while preserving unconfounded incrementality evaluation.
4. **Row-Level Privacy and Access Gating**:
   - Registered `arbitrated_treat_list.csv` and `arbitrated_treat_list.parquet` as row-level run artefacts in `configs/privacy.yaml`, `engine/privacy/layout.py` (`Store.SCORES`), and `ROW_LEVEL_ARTEFACTS` in `api/access_policy.py`.
   - Access restricted to Analyst role when authentication is enabled; audited on download (`decide.arbitrated_treat_list_download`). Viewers are refused with HTTP 403.
   - Aggregate conflicts endpoint `GET /decide/conflicts` and `GET /decide/arbitrate` accessible to Viewers.
5. **Results UI Conflicts Summary (`ui/modules/decide/`)**:
   - Registered `arbitration_conflicts` via `registerResultsList` in `ui/modules/decide/index.js`.
   - `conflictsCardHtml` in `views.js` renders evaluated customers, conflicts (>1 qualifying action), treated winners, dropped actions, channel cap suppressions, and breakdown table by use case.
6. **Linear Performance**:
   - Pure vectorised sorting and group operations in Pandas/PyArrow.
   - Scale test: 200,000 customers across multiple use cases processed in **0.28 seconds** (well within the 3.0s budget), projecting linear scaling under **1.45 seconds for 1,000,000 customers**.

## 4. New Error Codes

M101 introduces no new platform error codes. It answers with existing standard codes:
- `RUN_NOT_SCORED` (HTTP 404/409): No finished scoring run found for specified use case(s), or failed to load treat list for a run.
- `PRIMARY_KEY_MISMATCH` (HTTP 422): Candidate runs use different primary key definitions (e.g. single column vs composite key) and cannot be joined.
- `NO_RUNS_TO_ARBITRATE` (HTTP 400): No finished scoring runs available across specified use cases.
- `ARBITRATION_NOT_FOUND` (HTTP 404): No arbitration has been run yet when requesting `/decide/arbitrate`.
- `ROW_LEVEL_DOWNLOAD_REFUSED` / HTTP 403: Returned when a Viewer attempts to download row-level arbitrated treat lists.

## 5. Decision Text (DEC-1311)

### DEC-1311: One action per customer across use cases

**Context:**
Modern marketing organisations execute multiple parallel use cases (e.g., win-back campaigns, churn mitigation, cross-sell, loyalty promotions). Without cross-use-case arbitration, individual customers frequently qualify for multiple campaigns simultaneously, causing customer contact fatigue, brand friction, and confounded causal incrementality measurements.

**Decisions:**
- **(a) Deterministic Winner Selection:** Competing candidate actions are ranked and selected deterministically by `priority_score = priority_weight * net_value` (falling back to gross value, model score, and use case order). Default priority weights and customer contact caps are loaded from `configs/decide/arbitration.yaml`.
- **(b) Contact & Channel Caps:** At most one action per customer is chosen per cycle (`contact_cap_per_customer: 1`), with support for delivery channel caps (`channel_caps`). Suppressed losing actions record `suppression_reason = "ARBITRATION_LOST"`. Winning rows record `winning_use_case`, `priority_score`, and `losing_actions`.
- **(c) Holdout & Explore Integrity:** Universal holdout members (`holdout = 1`) across ANY participating use case remain strictly untouched (`treat = 0`). Explore slice rows (`explore = 1, treat = 1`) preserve randomisation.
- **(d) Campaign Measurement Isolation:** Measuring an arbitrated cycle creates one campaign per use case via `create_arbitrated_campaign` (`engine/measurement/campaign.py`), assigning only that use case's winning rows as `arm = "treated"` and marking losing candidate rows as `arm = "suppressed"`. This guarantees each use case's effect remains cleanly measurable without cross-contamination.
- **(e) Row-Level Privacy & Access Control:** `arbitrated_treat_list.csv` and `.parquet` are registered row-level artefacts in `configs/privacy.yaml`, `engine/privacy/layout.py` (`Store.SCORES`), and `ROW_LEVEL_ARTEFACTS` in `api/access_policy.py`. Access is restricted to Analyst and above and audited on download.
- **(f) Results UI Conflicts Summary:** Results displays the `Arbitration & Conflicts` summary card via `registerResultsList` in `ui/modules/decide/`, visualizing evaluated customers, qualifying actions, customer conflicts, treated winners, dropped actions, and per-use-case breakdown tables.
- **(g) Single Use Case Parity:** Running arbitration over a single usecase yields identical treat results to that usecase's original treat list (M98 parity).

**Consequences:**
Enterprises can safely run concurrent automated campaigns without customer fatigue, while preserving pristine causal incrementality measurements for each individual marketing initiative.
