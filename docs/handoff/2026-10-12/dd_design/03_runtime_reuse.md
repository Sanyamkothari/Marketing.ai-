# 03 — Agent runtime: what to reuse (Explore report, 12 Oct 2026; read-only survey)

BOTTOM LINE: Plan G (engine/agent/) already runs a working data agent (in-memory frame, gated egress, grounded numbers, questions, approvals checklist, recipe that replays at scoring). Plan K (engine/agentic/) is the stricter governance spine (typed registry, default-deny policy, signed ledger, claims verifier, pass^k evals) but touches no data. RECOMMENDATION: Plan G's session+loop is the runtime; adopt Plan K contracts underneath (typed registration, policy for every proposal kind, ledger for approvals when agentic.enabled, claims verifier, pass^k + mutation test); Plan K's state-machine-with-INTERRUPT shape becomes the outer "visit"; Plan G's JSON-action loop is one bounded state (CONVERSE).

## Overlaps / conflicts
1 duplicate type names (ToolKind, ToolResult, Proposal, ProposalKind) with different meanings; 2 evidence ids: counter (G) vs content hash (K, needed for pass^k); 3 row-level data: G tools return masked rows, K forbids row data + 16KB → G tools can't register in K as-is and must never be MCP-exposed; 4 context: G AgentContext has frame/profile/config, K ToolContext has storage/principal/ledger; K checks role per call, G only at route; 5 policy: G's safety rules hard-coded in several places (CHAT_STEP_KINDS, NEVER_SUGGESTED_BY_CHAT, setting_allowed, check_recipe, NEVER_TICKED_STEPS, PII refusal) vs K default-deny mutation-tested engine with no data rule sets; 6 model freedom: G free tool loop (12 steps/turn) vs K enumerated choices; 7 explanations: numbers_grounded (necessary not sufficient) vs claims verifier (no data claim types); 8 approval record: session JSON+audit vs signed ledger (BODY_KEYS can't record recipe/upload ids); 9 persistence patterns compatible; 10 G behaviour depends on K's agentic.enabled; ledger needs platform DB, G does not; 11 evals: G golden + canary; K pass^k + mutation; neither runs the G chat against a real model.

## Proposed architecture
VISIT planner (rules-first state machine, persisted per step, INTERRUPT = person): INTAKE (engine/intake) → DIAGNOSE (readiness, how_files_fit, enough_data) → RECALL (memory offer_for, match_renames) → TREAT ⇄ CONVERSE (advise, first_look, offer_outcome; chat_turn LLM optional) → PREVIEW (run_recipe on 1,000 rows) → INTERRUPT approve (decide/answer + apply) → PRESCRIBE (DataRecipe + memory.remember) → FOLLOW-UP (replay_for_scoring + match_renames).
ONE registry (Plan K contract, data-aware context): kinds READ (inspect) | PROPOSE (transform/setting/role/mapping/label) | ASK (question). APPLY is not a tool kind: executor bound to an approved proposal (keeps I1). Boundary for anything an LLM sees: Plan G egress (prepare → for_prompt → assert_clean), sent records. Every proposal: data policy rule set (default deny) → pending → person → ledger (when agentic.enabled). Every sentence: numbers_grounded + guardrails (chat) or claims verifier (narratives).
Registry: DataToolContext = AgentContext + principal + optional ledger + Egress. READ: wrap 18 G tools + diagnose_file, how_files_fit, first_look, enough_data, offer_for, match_renames, offer_outcome; row-level tools exposure="session-only" (never MCP). PROPOSE: promote propose_step/propose_setting into registry; add propose_role, propose_mapping, propose_label (returns OutcomeOffer, builds nothing; DEC-1579). ASK: make ToolKind.ASK real → Plan G Question with enumerated options each mapping to a checkable proposal or "leave as is"; model may ask only when the advisor cannot decide. APPLY: only apply_agent_session (agent.py:1147) and decide_proposal execute. Extensibility: new tool = registry entry + RoutePolicy + golden fixtures + canary entry + (PROPOSE) a policy rule set (default deny forces it).
Planner: copy planner.py pattern (Step literal, _advance, save per transition, idempotent, resume) with Plan L visit states (plan L §5.1 :150-178); LLM only in CONVERSE, second opinions, claims-rendered explanations; with no AI service every state completes (Plan G promise).
Questions/approvals: reuse Question/QuestionOption, ProposalState, ProposalSource (rules/ai/person), AgentConfidence (sure/check), NEVER_TICKED_STEPS, session.decide/answer, guided.js UI; exact-text consent pattern for meaning-bearing proposals (labels, mappings); add user id to G decisions; when agentic.enabled write ledger entries with recipe_hash, upload_id, session_id, payload_digest (new BODY_KEYS, kinds recipe.approved signed, recipe_step.decided) + receipt.
Recipe: DataRecipe is the one artefact; replay exists; NEW "prescription" envelope = intake decisions (sheet, intake on/off, memory) + multi-file build spec/LabelSpec (DEC-1578: Doctor does not drive the builder yet) + recipe, hashed and replayed together.
Memory: reuse engine/doctor/memory.py; NEW per-client scope (plan L §5.6 :245-250), remember answers and approved mappings/labels; RECALL pre-ticks, never auto-applies.
Egress: one boundary; ai_data_access, always_hide_columns; product AI slot; third-party detection; MCP never lists session-only tools; default summaries_only for third-party providers or free-text columns.
Explanations: chat keeps numbers_grounded + guardrails + evidence ids; narratives use claims renderer with NEW data claim types (count, share, rate-by-group, "changed N of M rows" from a StepReceipt); fallback rules_narrative.
Evals: keep agent_bench golden digests, egress canary, header benchmark, pass^k + mutation (extended with data scenarios/rules); NEW model-backed chat eval (make agent-eval): grounding failures, refusals, injection success (planted instructions must never change a proposal digest), cost per visit; pass^k on proposal digests with the real Product AI; Plan L M160 messy-file benchmark (time to first run).
NEW TO BUILD: 1 unified registry (merge/namespace the duplicate types) with READ/PROPOSE/ASK, data context, content-hash evidence ids, session-only exposure; 2 visit state machine with CONVERSE as one state; 3 data policy rule set (allowed step kinds, no outcome/ID columns, PII drop-only, levels, never-ticked kinds, setting allow-list) under the mutation test; 4 propose_role, propose_mapping, propose_label, explain + multi-file chat context; 5 ledger kinds/body keys for data approvals, user id on decisions, receipts; 6 data claim types; 7 prescription envelope and replay; 8 per-client memory incl. answers/mappings; 9 chat on the Doctor page; 10 model-backed eval harness and cost reporting.

## Risks
Hallucination: numbers in words and false directional claims not caught; mitigations exist (cite a look, sample-measured, AI never ticked, rules advisor baseline); remaining: plausible but wrong map_values merges → person review, receipt figures, cap share of rows an AI step may change. Privacy: masked_data lets names inside free text in unmarked columns through (canary asserts on purpose); float phone-like columns unmasked in stored evidence; stored evidence not the gated copy; multi-file enlarges surface (join keys often PII); session-only tools never to MCP; default summaries_only for third-party providers or free-text columns. Cost: 40 calls/session, 12 steps/turn defaults; dollar budget per request not per session; Bedrock cost None → need per-visit budget/Meter. Determinism: free loop not deterministic; counter ids block pass^k → keep LLM out of SELECT-like decisions, content-hash ids, digests exclude wording. Replayability: only stateless steps; new AI actions must produce frozen specs; renamed columns stop scoring and are proposed; derive not proposed; combine/future-date leak probe gaps. Operational: per-process session lock; ledger needs platform DB and agentic.enabled → keep ledger additive so "works with everything off" holds; injection contained but PROPOSE widens it → default-deny + injection canary mandatory.
