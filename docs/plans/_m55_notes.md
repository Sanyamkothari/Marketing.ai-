# M55 notes for the integrator (merge into docs/DECISIONS.md and README.md, then delete this file)

Plan D, milestone M55: ruling R1 on DEC-096, the narrowed future-data leak check.

## Decision entries (trunk range, DEC-870 to DEC-874)

- **DEC-870 — The full future-data leak check exists beside the narrowed one, as `full_leak_check`, and the build report says which ran.** *Context:* Ruling R1 accepted DEC-096's narrowed leak probe (only the snapshot rows of the entities given future-dated events, plus up to 500 entities given none) as the default, on three conditions: a `full_leak_check: true` option; the full check forced on for the first build of any new recipe (DEC-871); and the full check run nightly and in the golden tests (DEC-873). *Decision:* "Full check" means the probe as it was before DEC-096 in *which rows it rebuilds*: every snapshot row, compared against the build's features as a whole frame. It still stacks the future rows inside DuckDB (DEC-096's `UNION ALL` view), so it never copies an event table. `build._run_leak_probe(full=True)` does this; `_leak_probe` keeps its signature and verdict for its existing callers. `engine.onboarding.build.build_dataset` gains `full_leak_check` and `first_build_of_recipe` (both default false). `POST /datasets` gains `full_leak_check: bool = false` in `DatasetBuildRequest`. The option belongs to the build request, not to `OnboardingSpec`: it changes how hard a build is checked, not what the dataset is, and a field on the spec would have changed every stored `spec_hash`. `BuildReport` gains `leak_check: LeakCheckRecord | null` with `scope` (`full` or `narrow`), `reason` (`first_build_of_recipe`, `option` or `default`), `recipe_hash`, `rows_total` (snapshot rows built), `rows_probed` (snapshot rows the probe rebuilt) and `summary` (one engine-worded sentence). It is null only when the build stopped before the probe ran, or for a report written before M55. When a build is both a recipe's first and asked for the full check, the reason is `first_build_of_recipe`, the rule R1 is checked against. The build logs the scope, reason, row counts and probe seconds at INFO. The SQL guard (`features.point_in_time_join_clause` and `assert_point_in_time` on every compiled query) is unchanged. So are FUTURE_EVENTS_LEAKED's severity, its non-acknowledgeability, its row counts and DEC-109's float tolerance. *Consequences:* the full check costs one more feature aggregation over the whole spine at the validate stage. That was DEC-096's 10.7 profiled seconds at 20,000 customers before the copy was removed. The measured cost is in docs/PERFORMANCE.md §8. `scripts/bench_onboarding.py --full-leak-check` measures it at any size.
- **DEC-871 — "The same recipe" is `recipe_hash`: the logic that decides what a feature reads, without ids or times. The full check is forced when no earlier successful build of it is registered for the client.** *Context:* R1 forces the full check on "the first build of any new onboarding recipe". The repo records a recipe as an `OnboardingSpec` (with a `spec_hash`) plus its `MappingSpec`s, and each passed build as a `DatasetManifest` registered in the client store (`ClientStore.register_dataset`/`list_datasets`). `spec_hash` hashes the spec's source and mapping ids. A monthly replay (`engine.onboarding.replay`) and a scheduled rebuild (`engine.scheduling.firing.latest_recipe_inputs`) change those ids every month without changing any logic, so `spec_hash` would have made every month a "new recipe". *Decision:* `engine.onboarding.specs.recipe_hash(spec, mappings)` is a sha256, with its own domain separator, over: the use case; the feature spec; the label spec; the snapshot rule; and, for every mapping, its role and its column decisions (client column, standard column, transform). Mappings are sorted, so their order does not count. It leaves out every id (spec, mapping, source, client, dataset), every timestamp, a mapping column's `confidence` and `decided_by`, a mapping's `unmapped_source` and `missing_required`, and `value_maps`, which repeats what the transforms say. The label is included, so editing only the churn definition makes a new recipe. That is conservative: it costs one more full check. A replay that had to drop a column the old mapping read is a new recipe. `DatasetManifest` gains `recipe_hash: str | null`, which is null for datasets built before M55. `build.is_first_build_of_recipe(spec, mappings, earlier)` is true unless `earlier` holds a manifest of the **same client** with the **same `recipe_hash`**. The callers that register datasets pass `store.list_datasets(client_id, use_case)` and forward the answer: `POST /datasets`, where it is decided when the request is accepted; the preview; and `build_dataset_from_spec` in `engine/scheduling/firing.py`, a three-line change to a Phase 4b file. Only a build that passed is registered, so a failed build, a cancelled build, a preview (never registered) and a pre-M55 dataset (no `recipe_hash`) do not count. Another client's build of the same recipe does not count either: the rule is about this client's data. *Consequences:* a client's first build of a recipe, and the first build after any change to its logic, is full. Monthly replays and scheduled rebuilds of an unchanged recipe are narrow. The first build of an existing recipe after M55 runs the full check once. Two builds of a new recipe requested before either has registered both run full. `build_dataset` itself has no client store. A caller that does not pass `first_build_of_recipe` (the benchmark, tests, a future caller) gets the narrowed default, so a new production entry point must call `is_first_build_of_recipe`. The report's `default` sentence says only that the full check was not asked for and is required only on a recipe's first build, so it is true for those callers too.
- **DEC-872 — Why R1 keeps the full check: a join-key bug that moves one entity from another's events passes the SQL guard and the narrowed check, and only the full check reports it.** *Context:* DEC-096's consequences name its blind spot: a leak that moves only entities that received no future rows and are outside the 500 control entities. R1 asked for a test that builds such a leak through the real machinery. *Decision:* `tests/unit/onboarding/test_leak_check.py` and `tests/integration/test_onboarding_leak_check.py` use the smallest honest seam. They replace `features.point_in_time_join_clause`, the one function that writes the join, with an edit a person could plausibly make: "an account's own events, or its linked account's" (the next id), written `e.entity_key = s.entity_key AND e.event_time <= s.snapshot_date -- GUARD OR e.entity_key = s.entity_key + 1`. AND binds before OR, so the linked branch has no time bound. The guard line is still exactly what the real function writes, so the unchanged `assert_point_in_time` accepts every compiled query, and a test asserts that it does. No guard is disabled. The fixture puts all 500 of the probe's future rows on the last customer. Its "linked" reader is the customer before it: not injected, and outside the first 500 non-injected customers the narrowed probe takes as controls. The end-to-end build on real CSVs, real mappings and the whole `build_dataset` shows three things. The narrowed check reports nothing, the build **passes and writes a dataset** whose victim row counts another customer's whole history. The full check (`full_leak_check=True`) reports FUTURE_EVENTS_LEAKED as an unacknowledgeable error and writes nothing. So does a first build (`first_build_of_recipe=True`) without the option. *Consequences:* the narrowed check's blind spot is pinned by a test that fails if the premise changes. If a later change makes the narrowed check see this bug, the test says the DEC-096/R1 trade-off must be re-read. At real scale with date-sorted files, the probe's injected rows land on hundreds of entities, so a uniform off-by-one key bug would probably move some probed entity and be caught by the narrowed check by chance. A bug confined to a few linked pairs would not. That is the case the full check on first builds, and nightly, is for.
- **DEC-873 — The full check runs nightly on the M37 benchmark tables (one tenth of the M14 size) and in the golden tests.** *Context:* R1 wants the full check nightly and in the golden tests. The nightly workflow runs `make test-all`, which includes `@slow`. The full-size fixture is the M14 target: 200,000 customers, 5,000,000 usage rows, 12 snapshots, 60 features and 1.4 GB of CSVs. On this repository's 4-CPU, 15.7 GiB container it builds in about 276 s plus the full check, peaks at about 9.3 GB, and needs its tables generated first (docs/PERFORMANCE.md §6). That is too much for a standard GitHub-hosted runner inside the nightly job's 60-minute budget, which the slow training suite already uses a quarter of, and a build the runner kills for memory is not a check that runs. *Decision:* `tests/integration/test_onboarding_leak_check.py::test_the_full_check_passes_on_the_benchmark_tables` is `@slow`. It generates the benchmark tables at the M37 size (20,000 customers, 500,000 usage rows), builds the benchmark's own recipe with `full_leak_check=True` (detected roles, suggested mappings, the first 60 suggested features, 12 snapshots), and asserts four things: the build passed, `leak_check` is full, `rows_probed == rows_total`, and nothing leaked. Its docstring says why it is not the full size and how to run that by hand (`scripts.bench_onboarding --customers 200000 --usage-rows 5000000 --full-leak-check`). The golden tests run the full check too. `test_onboarding_flow.py` (M13's end-to-end build, which `test_onboarding_build_reads.py` reuses) now builds with `full_leak_check=True` by default and asserts that the report and manifest record it. `test_features.py`'s hand-computed golden fixture is put through the build's probe with every row rebuilt. The browser acceptance journey (`test_onboarding_acceptance.py`) asserts that its first build, a new client's new recipe, showed the full check and the first-build reason. *Consequences:* the nightly full check covers 240,000 snapshot rows, not 2,400,000. The full size stays a manual measurement, to be recorded in docs/PERFORMANCE.md §8 when it is run. At the M37 size under a load average of about 12, the full probe took 18.6 s against the narrow probe's 1.0 s, adding 11 s to a 102 s build, with no higher peak memory and the same dataset fingerprint. Running the benchmark generator for this test exposed a hang. `scripts/bench_onboarding.write_sources` runs in a spawned child. The fingerprint render pool (`engine.stages.ingest`) is shut down only by `atexit`, which a multiprocessing child never runs, and the child's exit joins the idle pool workers, which wait indefinitely. So the child never exited once a table exceeded one 100,000-row chunk. The generator now joins the pool (`shutdown(wait=True)`; `wait=False` was tried and was not enough). The same hazard applies to any other code that fingerprints in a multiprocessing child. That is an engine-level follow-up (for example a `multiprocessing.util.Finalize` on the pool), not made here.
- **DEC-874 — The build review shows which leak check ran.** *Context:* R1 wants the build report to record whether the full or the narrow check ran. *Decision:* the Build step's review (`ui/modules/onboarding/steps.js`) adds one card, "Future-data check", showing `leak_check.summary`, the engine's own sentence with the measured row counts, for example "Full future-data check: all 240,000 snapshot rows were rebuilt with events dated after the last snapshot added, because this is the first build of this recipe for this client." The card carries `data-leak-check="full|narrow"`. A report without `leak_check` shows no card. `tests/unit/test_onboarding_ui.py` pins `BuildReport.leak_check` and `LeakCheckRecord.scope`/`summary` as fields the panel reads. No control to ask for the full check was added to the screen. The first build of a recipe already gets it, and the option is on the API (`POST /datasets`), which keeps the UI change small. *Consequences:* a reviewer can see, per dataset, whether it was built under the full check and why. `GET /datasets/{id}/report` returns the same record.

## README "what works" lines (Plan D, M55)

- Leak checking follows ruling R1. A dataset build runs the narrowed future-data leak check by default (DEC-096). The **full** check rebuilds every snapshot row. It runs when `POST /datasets` is sent `full_leak_check: true`, and always on a client's first build of a recipe. "The same recipe" is `recipe_hash`: the recipe's logic without ids or times, so monthly replays and scheduled rebuilds of an unchanged recipe count as the same one (DEC-870, DEC-871).
- The build report (`GET /datasets/{id}/report`, and a "Future-data check" card on the Build step) records which check ran, why, and how many snapshot rows it rebuilt. The manifest records the `recipe_hash` (DEC-874).
- A test builds a join-key leak that the SQL guard and the narrowed check both miss: the build passes and writes the dataset. The full check catches it with FUTURE_EVENTS_LEAKED (DEC-872). The full check runs nightly (`make test-all`) on the 20,000-customer benchmark tables and in the golden end-to-end tests (DEC-873). `python -m scripts.bench_onboarding --full-leak-check` measures it at any size.
