## Entries for `docs/DECISIONS.md`

- **DEC-853 — Uplift reads its key through `engine.keys`; the entity is the key's first column.** *Context:* Plan B §3 allows one row per customer per snapshot, and Plan A M34 made two-column keys a trunk feature (DEC-083), but the uplift flows refused them (`COMPOSITE_KEY_NOT_SUPPORTED`, DEC-800), `UpliftRunRequest.primary_key` was one string and campaign results narrowed the run key with `sole_key`. *Decision:* uplift reads keys exactly as Phase 1's stages do. Every key column (and the joined `_row_key`) is reserved from the features (`reserved_feature_exclusions`); rows are *identified* by `StageContext.row_key` (hold-out keys, `holdout_fingerprint`, row explanations, the reason join, the scoring summary); treatment, the hold-out, the control group and suppression are decided per **entity**, which is `engine.keys.entity_column` — the key's first column, the same entity Phase 1's grouped split, `apply_actions(entity_key=...)` and the consent ledger use. `scores.csv` writes each key column separately as text (`keys.key_text`), as Phase 1's does; a one-column key is written exactly as before. `POST /uplift/runs` accepts `primary_key` as a list and applies `split_config_for_key` so `run_config.json` records the derived group column; `measure_incrementality` joins the outcomes file on every key column (each part through `key_text`, so a Parquet timestamp matches a CSV date), and `POST /runs/{id}/campaign-results` passes the run's whole key. `_customer_key` and the flow's `COMPOSITE_KEY_NOT_SUPPORTED` are removed. *Consequences:* a periodic uplift file trains, scores and is measured keyed by both columns; a single-key uplift run is unchanged (every existing uplift test passes untouched). Phase 1's `POST /runs` still takes a composite key only with a built dataset (DEC-083, pinned by `test_a_composite_primary_key_is_refused_by_name`), so a scoring file with several snapshots per customer is scored through a dataset; `POST /uplift/runs` still takes an upload, not a `dataset_id`.

- **DEC-854 — `TREATMENT_VARIES_WITHIN_ENTITY`: a customer is in one arm per campaign.** *Context:* with snapshots, the same customer appears several times; if they are treated at one snapshot and held out at another, the uplift estimate compares a customer with itself and the per-customer control group of scoring has no meaning. *Decision:* a seventh uplift check, `TREATMENT_VARIES_WITHIN_ENTITY` (error, blocking, **not** acknowledgeable), added to `UPLIFT_VALIDATION_CODES` and to `CHECK_ORDER` right after `TREATMENT_NOT_BINARY`. It runs only for a two-column key: it groups the 0/1 treatment by the entity column — and by `uplift.campaign_id_column` when that is configured and present, so a customer may be re-drawn between campaigns but not within one — and names how many customers are in both arms. When it fires, `TREATMENT_ARM_TOO_SMALL` and the randomness check are skipped ("skipped, not failed twice"): there are no per-customer arms to count or to predict. For a two-column key the arms are counted in **customers** (distinct entities, and distinct converting entities for the positives), which keeps the existing message ("the treated group has N customers") true; the randomness classifier is cross-validated with `StratifiedGroupKFold` on the entity, since a customer's snapshots in two folds would let it recognise the customer rather than the targeting; and the snapshot date joins the `FEATURE_AFTER_TREATMENT` candidates, because a snapshot taken after the treatment date already contains the campaign's effect. `uplift_validation.json` gains optional `treated_rows`, `control_rows`, `entity_column`, `treated_entities`, `control_entities` (null in older reports), which the Data page shows. *Consequences:* the code is documented in `docs/UPLIFT.md` §3 and `docs/DATA_CONTRACT.md` §11, and `tests/unit/uplift/test_uplift_two_column_keys.py` fails if either document misses a code of `UPLIFT_VALIDATION_CODES`.

- **DEC-855 — The uplift hold-out is grouped by entity.** *Context:* `split_holdout` drew rows stratified on `(t, y)`; with snapshots, a customer's March row could be trained on and their April row graded, so the hold-out would measure memory. *Decision:* `split_holdout(..., groups=)` draws whole entities, stratified on the entity's arm (constant, by DEC-854) and whether the entity converted at any snapshot, with the same seed and the same half-up rounding per cell. The train flow passes the entity column for a composite key, whatever `split.type` the use case configures (an uplift split is always random-by-customer), and `split.json` records `group_column`. Without `groups` the function is byte-for-byte what it was. *Consequences:* no customer is on both sides (tested at unit and end-to-end level); there is still no validation part — an uplift learner is fitted without one — so "train / validation / holdout grouped by entity" reduces to train / hold-out.

- **DEC-856 — Uplift models store Phase 1's drift baseline; feature drift is Phase 1's PSI.** *Context:* uplift runs stored no drift baseline and scoring runs wrote no drift, a documented limit (UPLIFT.md §15). *Decision:* the uplift train flow's register stage writes `drift_baseline.json` through `engine.stages.register.drift_baseline`, over the **raw** training columns the feature spec kept (the same frame `schema.json` is written from), and sets `ModelVersion.drift_baseline_key`. A scoring run passes the raw uploaded frame and that baseline to `engine.stages.score.compute_drift` — no PSI code is duplicated. Raw on both sides is the right pairing for uplift, because the feature spec is replayed on raw scoring columns rather than through Phase 1's prepare. A model trained before M53 has no baseline: feature drift is then `null` with the reason, never an invented zero (DEC-051). Phase 4b's scheduled drift check replays `prepare.json`, which an uplift model does not have, and already reports "not measured" for it; that is unchanged. *Consequences:* `scoring_summary.json` of an uplift run now carries `drift_status`/`drift_max_psi`/`drift_summary` like a Phase 1 run's, and the manifest records `drift_max_psi`.

- **DEC-857 — The treated-share check: an absolute tolerance, `uplift.drift_treated_share_tolerance: 0.05`.** *Context:* an uplift model's segments and expected conversions were measured on a campaign with a particular treated share; new data from the same experiment with a very different share is a different design. *Decision:* when a scoring file carries the model's treatment column with 0/1 values, `uplift_drift.json` compares its treated share with the model card's `propensity`: `within_tolerance` when `|current − training| ≤ uplift.drift_treated_share_tolerance` (default 0.05, range 0–0.5, not agent-editable, overridable per run — it cannot make data look causal), else `outside_tolerance` (logged at WARNING). An absolute difference rather than a two-proportion z-test, because a test's verdict scales with the file: on a million rows it calls a 0.2-point move significant, on two hundred it misses a 10-point one. The pooled two-proportion p-value (`engine.uplift.incrementality.two_proportion_p_value`, reused) is recorded beside it for information. A file without the column, with a non-0/1 value or with no rows is `not_applicable` with the reason — the usual scoring file carries no treatment, because its campaign has not happened yet. *Consequences:* a new artefact `uplift_drift.json` (`UpliftDriftReport`, in `UPLIFT_ARTEFACTS`) is written by every uplift scoring run: Phase 1's `DriftReport` for the features (or null and why), the `TreatmentShareDrift`, and a one-line summary shown on the Running screen and the Data/Output pages.

- **DEC-858 — Phase 1's pages render uplift runs; `GET /runs/{id}/artefacts/{name}` whitelists `UPLIFT_ARTEFACTS`.** *Context:* a scoring run of an uplift model is a Phase 1 run (DEC-651) and opened in Phase 1's Data, Model and Output pages, which requested `prepare.json`, `drift.json` and `decile_lift.json` (404s in the console) and printed propensity wording on uplift numbers; the artefact route answered `ARTEFACT_UNKNOWN` for every uplift artefact. *Decision:* `read_artefact` adds `or name in UPLIFT_ARTEFACTS` — still a whitelist, never a path join; `GET /runs/{id}/uplift/{name}` stays as an alias. `ui/pages.js` keeps `PAGE_ARTEFACTS` for Phase 1 and adds `UPLIFT_PAGE_ARTEFACTS` and `pageArtefacts(kind, run)`, chosen by `run.problem_type === "uplift"`; `app.js` requests that list. For an uplift run: **Data** shows rows, treated and control (in customers and rows for a two-column key), the treated share, the randomness check against its limit (and whether a failure was acknowledged), causal yes/no, rows set aside, the train/test split with its group column, every uplift finding, and on a scoring run the drift card; **Model** shows AUUC and the Qini coefficient with their intervals, the ATE and uplift at 10/20/30%, the hold-out arms, and the Qini curve — drawn by the uplift module's own `qiniChart`, which `app.js` loads with a dynamic `import()` only for an uplift Model page (so `pages.js` keeps its static import graph inside Phase 1's modules and the two screens draw one picture; without the module the page lists the curve's points); **Output** shows the KPI the engine wrote, the four segments, the targeting recommendation, drift and the treat list under the run's key label. The Previous runs list labels every run's problem type (`train · Uplift`), and the Results strip uses the run's own problem type rather than the use case's. *Consequences:* no Phase 1 page requests an artefact an uplift run never writes (pinned by `tests/unit/uplift/test_phase1_pages_uplift.py` and its node suite); a Phase 1 run renders exactly as before.

- **DEC-859 — `POST /runs` refuses an uplift training run with `422 UPLIFT_REQUIRES_UPLIFT_ROUTE`.** *Context:* the catalog hides uplift from Phase 1's Setup (DEC-608), but a direct API caller could train uplift through `POST /runs`, where the uplift checks run only inside the job and fail late as `RUN_BLOCKED_BY_VALIDATION`. *Decision:* one synchronous check after the configuration is resolved: a **training** run whose resolved problem type is uplift — by override (`path: overrides.problem_type`) or by the use case's own configuration (`path: null`) — is refused, pointing to `POST /uplift/runs`. Scoring an uplift model stays on `POST /runs`: a scoring file needs no treatment column and is checked against the model's schema. The route's policy row is unchanged (Analyst), and a denied-role test covers it. *Consequences:* the refusal arrives before a run exists, in words that say where to go.
